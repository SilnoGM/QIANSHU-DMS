# 采购应付款

## 业务边界

- 审核采购订单时，在同一事务中生成定金、尾款两条应付。零金额阶段仍保留，展示为“无需付款”。
- 销售关联采购在审核时固定销售出单人 `issuerUserId`；备货采购固定为公司账户。付款操作者不改变资金归属。
- 首版按阶段一次付清剩余金额，客户端只能提交版本、付款方式、备注与幂等键，不能指定付款金额、账户或资金比例。
- 本次迁移不回填历史已审核订单，不补扣历史实际付款。没有应付的旧单不能继续通过旧付款接口绕过新流程。

## 事务与资金

先锁采购单，再读取阶段应付和实际付款。付款、应付版本、采购状态、资金批次与审计共用一个事务。

| 操作 | 来源 | consumer | 资金类型 |
| --- | --- | --- | --- |
| 销售关联采购付款 | `PURCHASE_PAYMENT` | `PURCHASE_PAYMENT.PAY` | `PURCHASE_PAYMENT` |
| 备货付款 | `PURCHASE_PAYMENT` | `PURCHASE_PAYMENT.STOCK_PAY` | `PURCHASE_PAYMENT` |
| 作废实际付款 | `PURCHASE_PAYMENT` | `PURCHASE_PAYMENT.VOID` | 原批次类型 |

备货沿用当前已发布的分摊规则，以有效用户比例 0%、公司比例 100% 计算，只产生公司分录；不修改业务配置或任何用户账户比例。配置不兼容时拒绝付款。

实际付款使用独立 UUID 作为资金业务身份。请求幂等键按操作者隔离，并保存请求指纹；相同请求重放不重复记账。作废按原批次全额反向入账，恢复应付余额；再次付款必须使用新的请求键和版本。普通资金冲账入口不能绕过采购作废流程。

数据库延迟约束核对阶段金额、归属、实际付款与资金批次，以及作废前后的分录。不可变字段不能事后补写。历史无资金批次的付款作废仅恢复历史采购付款统计，不创建资金流水。

## 查询与金额

- `GET /purchase-order-payables` 只查询仍有待付款项的有效采购订单，在筛选后分页；`total` 是待处理采购单组数，每组始终返回完整定金与尾款。已付清、全部无需付款及已取消订单不展示；付款作废产生待付金额后重新展示。付款成功响应仍返回完整采购单；返回列表或重新聚焦列表时刷新，移除已完成分组并重新核对分页。
- `GET /purchase-order-payables/:id` 按具体应付 ID 返回所在采购单分组，使用同一付款权限并禁止缓存。已付清、无需付款及已取消的旧链接仍可查看状态，不能继续付款；不存在的应付返回 `404`。
- `GET /purchase-order-payables/orders/:id` 按采购单 ID 精确返回应付分组，与款项详情使用相同权限、缓存和终态规则。
- `POST /purchase-order-payables/:id/pay` 使用 `Idempotency-Key` 和 `expectedVersion`；成功返回所在采购单分组。
- 实际采购金额、计算和接口返回统一两位。产品档案及旧参考成本、修订记录、归档图片快照保留原精度。
- 精度迁移遇到非零第三、四位时整体回滚，需先核对来源，不能静默改写历史金额。

变更入口的权限为 `purchase-orders:payment`。付款方式写入前核对 `payment.method` 的有效字典值。

## 批量付款

- `GET /purchase-order-payables/batch/suppliers` 从未付目录采购中返回供应商稳定 `value` 与历史标签，包含停用但仍有待付款项的供应商；自定义供应商仍按单付款。
- `GET /purchase-order-payables/batch/orders?supplierValue=...` 返回该供应商全部待付采购单，每单保留完整定金、尾款及各自状态。
- `POST /purchase-order-payables/batch/pay` 使用 `Idempotency-Key`，提交供应商、共同收款账户及资料版本、方式，以及全部选中订单的待付阶段 ID、阶段版本与凭证。禁止客户端传金额或资金归属。
- 前端一次选择付款截图，再通过现有阶段上传接口分别准备凭证。每笔凭证仍绑定自身应付款并归档到对应采购单，满足现有数据库不可变约束，不共享或重绑媒体身份。
- 服务端先验证操作者权限，再按批次根 key 获取事务锁；整批指纹包含完整排序后的阶段集合、版本、账户与凭证。同 key 增删订单或改变内容返回冲突，原样重试返回原批次结果，不重复扣款。
- 全部采购父单按 ID 锁定，重新计算每单完整待付阶段集合，遗漏尾款、跨供应商、已付款、取消或旧版本均整批拒绝。共同收款资料、付款方式和全部凭证锁定后，由资金模块按账户 ID 统一锁定全部相关账户，再逐阶段执行原有 `PURCHASE_PAYMENT` 分摊规则。
- 付款记录、采购状态、每笔归档凭证、媒体激活、资金和审计共用单个事务；任何一笔失败整体回滚。锁等待、死锁或事务冲突返回可重试的 `PURCHASE_PAYABLE_STATE_CHANGED`。

## 独立付款页

财务“采购付款”列表中的“付款”直接进入对应定金或尾款的独立付款页。运营“待办采购”中的“付款”仅复制 `【采购单号付款】网址`，链接绑定采购单 ID，打开后可在该单的定金、尾款间切换，默认选中待付款项。

两类链接均不携带金额、账户或授权凭据。打开链接后从服务端重新读取；未登录先登录并返回原链接，无 `purchase-orders:payment` 权限时禁止访问。

页面沿用固定金额、版本校验和幂等付款。请求结果未知时锁定输入并保留原请求键，可原样重试；版本冲突时重新核对服务端数据。打开链接或加载页面不会触发付款。

## 付款记录与审核后金额修订

- `GET /purchase-order-payments` 是财务“采购付款记录”的只读列表，按实际付款记录平铺分页，默认 `paidAt DESC, id DESC`；`status` 支持 `ALL/ACTIVE/VOIDED`，关键词匹配采购单号、自定义供应商、销售单号和付款备注。权限复用 `purchase-orders:payment`；`SELF` 数据范围按应付款 `ownerUserId` 过滤，历史无应付款的付款按采购单销售来源归属兜底。
- `POST /purchase-orders/:purchaseOrderId/amount-revisions` 由审核人员（`purchase-orders:review`）在采购审核已通过视图发起，只修改实际单价和手工定金，数量、货件与采购行身份保持冻结。请求携带 `expectedVersion`、原因和全部采购行；服务端重算行小计、总价和尾款，不信任客户端总额。
- 金额修订要求采购单为 `CONFIRMED`/`COMPLETED` 且没有任何有效付款；已付款必须先通过付款记录作废。修订、采购行、订单头、两条应付与审计共用一个事务；`purchase_order_amount_revisions` 保存修订前后四个订单金额，数据库触发器另行限制 `due_amount` 只能在无有效付款时受控更新。
- 已发货/已签收订单允许修订，但只更新当前订单和应付，不回写货件、归档采购单图片或历史对账单。行间调价但订单总额、定金和尾款都未变化时，现有修订快照没有可持久化差异，接口明确拒绝。
