# 千树 DMS 后端架构

## 1. 文档定位

本文记录当前 Server 的工程事实、运行时边界、接口契约和开发约束。当前已实现健康检查、Cookie Session 认证、用户管理、RBAC、审计事件查询，以及 `system_admin` 的本机初始化与离线恢复能力。

当前技术基线为 Node.js 24、pnpm 11.9、NestJS 11.1、TypeScript 5.9、Prisma ORM 7.8、`@prisma/adapter-pg` 7.8、`pg` 8.22 和 PostgreSQL 16。Server 使用 CommonJS，`tsconfig.json` 的 `module` 为 `commonjs`，Prisma Client generator 的 `moduleFormat` 为 `cjs`。

## 2. 工程与依赖边界

仓库采用“一个 Git 仓库、两个独立依赖域、根目录无依赖编排”的组合式结构：

- 根目录不是 pnpm workspace，不保留根 `pnpm-workspace.yaml`、`pnpm-lock.yaml` 或 `node_modules/`。
- `server/` 是单一、可独立移植的 package，拥有自己的 `server/package.json` 与 `server/pnpm-lock.yaml`。
- `web/` 是另一个独立依赖域；Server 不读取 Web 的源码、生成物或依赖目录。
- 前后端不通过 `file:`、`link:`、`portal:`、`workspace:*` 或跨目录源码引用连接，只通过 HTTP 与提交 Git 的 OpenAPI snapshot 协作。

pnpm 11 把项目级安装和部署配置放在 `server/pnpm-workspace.yaml`；其中 `allowBuilds` 负责精确审批依赖 lifecycle scripts。该文件当前内容为：

```yaml
injectWorkspacePackages: true
allowBuilds:
  '@prisma/engines': true
  # Swagger UI 的 Scarf 脚本仅用于安装分析；明确拒绝执行，保证 fresh install 可重复且不发送遥测。
  '@scarf/scarf': false
  # argon2 通过 node-gyp-build 选择已发布的 N-API 预构建二进制；密码 Hash/verify 需要其原生实现。
  argon2: true
  prisma: true
```

它不声明 `packages`，不会形成多 package dependency graph。根目录本身也不是 workspace，因此这里不存在把 Root、Server 和 Web 合并为统一 pnpm package graph 的嵌套 workspace。

`injectWorkspacePackages` 只服务现代 production deploy：正式 Server 归档通过 `pnpm deploy --prod` 生成自包含的 production 目录，不得使用 `--legacy`。这个开关不声明 `packages`、不扩张 Server workspace，也不改变 Root、Server 与 Web 相互独立的依赖域。

## 3. 运行时结构

当前运行时依赖关系如下：

```text
main.ts
  -> AppModule
       -> ConfigModule
       -> requestIdMiddleware -> ValidationPipe -> ApiExceptionFilter
       -> PrismaModule -> PrismaService -> PrismaPg -> pg.Pool -> PostgreSQL
       -> CsrfProtectionGuard -> AuthenticationGuard
          -> PasswordChangeRequiredGuard -> PermissionGuard
       -> PrivateNoStoreInterceptor
       -> HTTP_MODULES
          -> HealthModule
          -> AuthModule
          -> UsersModule
          -> RolesModule
          -> PermissionsModule
          -> AuditModule
```

当前各业务模块遵循固定方向：

```text
Controller -> Service -> PrismaService -> PostgreSQL
```

- Controller 负责 HTTP 协议边界、输入 DTO 与 OpenAPI decorators。
- Service 负责业务规则、事务边界和流程编排。
- `PrismaService` 负责数据库客户端与连接池生命周期。
- 当前不预先引入 Repository、UseCase、Domain Entity 或其他尚无真实需求的抽象。
- `AuthSession` 使用数据库服务端 Session，空闲过期 48 小时，绝对过期 30 天；不存在 RememberCredential 或设备级凭证。
- 认证保护由全局 Guard 实施，管理 API 通过 permission code 鉴权；强制改密期间只允许查询当前上下文、修改密码与登出。

## 4. 启动配置与 HTTP 基线

`ConfigModule` 以 global、cache 模式加载配置，并在应用模块创建时执行环境校验：

| 变量 | 当前规则 |
| --- | --- |
| `NODE_ENV` | 只允许 `development`、`test`、`production`，默认 `development`。 |
| `PORT` | 只允许 `1` 到 `65535` 的整数，默认 `3000`。 |
| `DATABASE_URL` | 必填，且必须是合法的 `postgres://` 或 `postgresql://` 分层 URL。 |
| `APP_ORIGIN` | production 必填且必须是 HTTPS origin；development/test 默认 `http://127.0.0.1:9000` 且只允许精确回环 origin。 |
| `TRUST_PROXY_HOPS` | 只允许 `0` 到 `2` 的整数，默认 `0`。 |
| `AUTH_ARGON2_CONCURRENCY` | 只允许 `1` 到 `64` 的整数，默认 `2`。 |
| `AUTH_ARGON2_QUEUE_LIMIT` | 只允许 `0` 到 `4096` 的整数，默认 `32`。 |
| `AUTH_USERNAME_HMAC_KEY`、`AUTH_USER_ID_HMAC_KEY`、`AUTH_IP_HMAC_KEY` | production 必须分别提供三个不同的 32-byte canonical base64url key；development/test 留空时由进程随机生成。 |

校验异常只包含变量名和固定约束，不回显输入值或底层解析异常。`main.ts` 也只输出固定的 `Server bootstrap failed`，不记录原始启动异常、连接字符串或驱动详情。

`configureApplication()` 为 production bootstrap 与 E2E 提供同一组 HTTP 和生命周期配置：

- 全局路由前缀为 `/api`。
- `requestIdMiddleware` 在其他 HTTP 处理之前生成并写入 `X-Request-Id`，忽略客户端提供的同名值。
- 全局 `ValidationPipe` 启用 `whitelist`、`forbidNonWhitelisted` 与 `transform`。
- DTO 校验失败使用 HTTP `422`，字段路径与安全中文文案进入 `ApiError.fieldErrors`。
- `ApiExceptionFilter` 将应用级 JSON 错误统一为 `ApiError`；未知异常只按 Server-generated Request ID 记录固定日志。
- `enableShutdownHooks()` 确保终止信号能够进入 Nest 模块销毁流程。

Nest 初始化期间暂时关闭框架 logger，成功监听后再启用运行时 logger。初始化或监听失败时会尽力关闭已创建的 application，清理失败不会覆盖原始失败，也不会把原始异常写入日志。

## 5. Prisma 与 PostgreSQL 生命周期

`prisma/schema.prisma` 使用 `prisma-client` generator，并把生成结果写入 `src/generated/prisma/`。该目录是可重建生成物，已被 Git 与 ESLint 忽略，不允许手工修改或提交。

当前 schema 通过 `20260717090000_user_auth_rbac` migration 实现以下持久化模型：

- `User`：用户身份、状态、密码 hash、强制改密标记与 `authVersion`。
- `Role`、`Permission`、`UserRole`、`RolePermission`：用户、角色与权限的多对多 RBAC 结构。
- `AuthSession`：只保存 Session token hash、滑动空闲期、绝对过期时间与吊销状态。
- `AuthRateLimit`：按 username、user ID 或 IP 的 HMAC 主体键记录认证限流桶。登录和普通改密在 Argon2 前用同一短事务原子预占全部相关桶，并按固定顺序取得行锁；事务提交后才执行 Argon2，不跨 Argon2 持锁。凭证错误保留计数，成功或非凭证错误只释放本次预占，不清除并发请求已经形成的真实失败计数。正确凭证在业务事务前通过独立短事务单次释放；释放提交结果未知时不重试，最多保留一次有界预占，避免重复释放误减其他失败计数。
- `AuditEvent`：记录认证、用户、角色、系统初始化与离线恢复等审计事件，不保存明文密码、Cookie 或 token。

`PrismaService` 负责以下完整生命周期：

1. 从 `ConfigService` 取得 `DATABASE_URL`。
2. 创建外部 `pg.Pool`，设置连接数、连接超时和查询超时。
3. 使用 `PrismaPg` 包装该 Pool，再创建 Prisma Client。
4. 在 `onModuleInit()` 调用 `$connect()`。
5. 在 `onModuleDestroy()` 先尝试 `$disconnect()`，再显式调用 `pool.end()`；前一步失败不能阻止后一步执行。

`PrismaPg` 不负责关闭外部创建的 Pool，因此 Prisma Client 和 `pg.Pool` 必须双重释放。初始化失败时服务也会自行收口部分资源，并只抛出固定的 `Database initialization failed`；关闭失败只抛出固定的 `Database shutdown failed`。idle client 的错误日志同样只使用固定文本，不带底层 error。

`@prisma/adapter-pg` 的 `prisma:*` debug namespace 可能输出底层 Pool 错误，其中可能包含连接细节。生产环境必须保持 `DEBUG` 未设置；若确需启用其他 namespace，必须显式排除 `prisma:*`，并在上线前检查日志不会包含 `DATABASE_URL`、密码、SQL 或堆栈中的敏感内容。

## 6. 健康检查

当前提供 `GET /api/health`。`DatabaseHealthIndicator` 使用无插值的 Prisma tagged query 执行常量 `SELECT 1`：

- 数据库可用时返回 HTTP `200` 和 Terminus 的完整 success body。
- 数据库不可用时返回 HTTP `503` 和仅含 `database: down` 的脱敏 Terminus body。
- `GET /health` 不存在，健康检查始终受全局 `/api` 前缀约束。
- `HealthModule` 关闭 Terminus 自带的失败日志，避免 indicator 详情泄露。
- success 与 failure response 都携带 Server-generated `X-Request-Id`。

健康响应是 Terminus 的接口专属结构，不套用全局成功 envelope。只有路径、status 与 body 都满足严格 guard 的 Terminus failure 才绕过 `ApiError`；任何 health 失败响应都不得包含连接 URL、密码、SQL、堆栈或底层驱动异常。

## 7. 接口契约与 OpenAPI

- NestJS Controller、DTO 和 OpenAPI decorators 是定义真相源；正式 snapshot 为 `server/openapi/openapi.json`。
- 当前 snapshot 覆盖 `health`、`auth`、`users`、`roles`、`permissions` 和 `audit-events` 路由，不再是 health-only 契约。
- 每个 operation 使用稳定 `operationId` 与 `x-qianshu-contract` 元数据；应用操作由 `ApiApplicationContract` 声明适用错误矩阵。
- success、`204`、binary 与 error response 统一通过 `ApiContractResponse` 描述并添加 `X-Request-Id`；`204` 禁止声明 body。
- `ApiError` schema 与 `400/401/403/404/409/422/500` 中适用的 response 必须进入文档，不能只存在于 Exception Filter。
- `openapi:generate` 先执行包含 `prisma generate` 的 build，再通过 preview application 离线扫描 metadata；preview 本身不读取 `.env`、不连接数据库、不监听端口。若需隔离整个命令加载本地环境文件，显式设置 `DOTENV_CONFIG_PATH=/dev/null`。
- 正式运行时不开放 Swagger route 或 Swagger UI；契约只通过 snapshot 交付。
- 根 `contract:sync` 是跨端唯一写同步，`contract:check` 只读验证 snapshot、契约结构与 Web types。

详细约束见[接口契约规范](./接口契约规范.md)。

## 8. 测试与命令边界

| 层级 | 位置与命令 | 数据库要求 |
| --- | --- | --- |
| unit | 源码旁 `*.spec.ts`；`pnpm -C server test` | 不连接数据库，使用 fake 或 mock 隔离外部资源。 |
| integration | 后续有真实跨组件需求时放入 `server/test/` 下的明确文件 | 必须使用隔离的临时 PostgreSQL。当前尚无独立 integration suite。 |
| E2E | `server/test/app.e2e-spec.ts`、`auth-*.e2e-spec.ts`、`contract.e2e-spec.ts`、`management-api.e2e-spec.ts`；`pnpm -C server test:e2e` | 使用真实、隔离的 PostgreSQL，并由进程环境注入 `DATABASE_URL`。 |
| 隔离 Browser Auth E2E | `node --run ci:browser-auth-e2e` | 根脚本管理临时 PostgreSQL、Server、Web 与系统 Chrome，验证真实 Cookie 和浏览器恢复行为。 |

`pnpm -C server check` 依次执行 Prisma schema 校验、typecheck、只读 lint 与 unit tests；它不执行 migration 或 E2E，也不要求数据库在线。`pnpm -C server build` 会重新生成 Prisma Client 后编译 `src/`，生产入口为 `dist/main.js`。

E2E 创建真实 `AppModule` 并复用 `configureApplication()`，验证 `/api`、健康检查、认证 schema、登录限流、Session 生命周期、CSRF、强制改密、用户/RBAC/审计管理 API、过期数据清理，以及应用关闭后的资源释放。测试不得使用 `--forceExit` 掩盖连接泄漏。

OpenAPI unit tests 还验证 preview 隔离、operation metadata、响应矩阵、Request ID Header、`204`、binary schema 与固定失败输出。根 Contract tests 验证 snapshot 同步、只读检查、baseline 和事务回滚。

## 9. CI、发布与部署边界

当前 `.github/workflows/ci.yml` 包含 `root-governance`、`server-check-build`、`server-e2e`、`contract`、`web-check-build` 和 `browser-auth-e2e` 六个正式验证 Job，`ci-gate` 要求六者全部成功。其中 Server E2E 在隔离 PostgreSQL 16 上执行 migration 与全部 Server E2E，Browser Auth E2E 则验证前后端联调下的真实 Cookie、浏览器重启恢复和多标签同步。

`v0.1.2` 的 Main CI Run `29317624359` 是当时五个正式验证 Job 的历史平台证据。`browser-auth-e2e` 是后续新增的第六个 Job，尚无真实 GitHub Run 结果；不得把 `29317624359` 冒充为 Browser Job 已通过的证据。

正式 Server 归档只承诺 `Ubuntu 24.04` / `glibc` / `x64` / `Node 24` 运行时兼容范围。Alpine / `musl`、其他 CPU 架构或其他 Node.js 大版本不属于当前已验证能力。

Release 工作流负责验证、构建、归档、smoke test 和 GitHub Release 发布，不负责自动部署，不连接生产数据库，也不执行生产 migration。Server 归档 smoke test 会在隔离的临时 CI PostgreSQL 中执行 `pnpm -C server db:migrate:deploy`，这不代表生产 migration；真实部署与 migration 必须由下游运维流程单独审查和执行。

历史五 Job 版本的 GitHub 平台验证以 `v0.1.2` 记录为准；当前六 Job 版本必须等未来真实 GitHub Run 后才能宣称 Browser Job 的平台验收完成。

## 10. 当前阶段边界

`ApiError`、`X-Request-Id`、OpenAPI 离线生成与 snapshot 同步、认证、用户管理、RBAC、审计查询、Server E2E 和 Browser Auth E2E 代码均已实施。当前明确边界为：

- 不引入全局成功 envelope；健康检查继续使用 Terminus 专属 body，其他接口使用各自的 Response DTO。
- 不使用 Redis、RememberCredential 或设备级管理；Session、限流和审计持久化使用 PostgreSQL。
- 当前新增 Browser Job 只有本地与 Workflow 配置事实，尚待未来真实 GitHub Run 平台证据。
- Release 不自动部署，不连接生产数据库，不执行 production migration；真实生产部署仍未完成。
