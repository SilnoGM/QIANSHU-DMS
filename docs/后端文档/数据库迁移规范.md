# 千树 DMS 数据库迁移规范

## 1. 目的与真相源

Prisma migration 是 PostgreSQL schema 演进的可审计历史。以下文件共同构成数据库结构真相源：

- `prisma/schema.prisma`：当前期望 schema。
- `prisma/migrations/`：按时间顺序追加的不可变 migration 历史。
- `prisma/migrations/migration_lock.toml`：数据库 provider 锁定信息。

`src/generated/prisma/` 是由 `prisma generate` 重建的 Prisma Client，不是 schema 历史，必须忽略且不得提交。真实 `.env`、数据库 URL、密码、运行日志和临时数据库文件同样不得提交。

`20261019140000_money_precision_two_decimals` 把销售域、产品价格、包装费用与对账销售金额快照统一收窄为 `NUMERIC(30,2)`：迁移先摘除依赖金额列的销售触发器与勾稽约束，收窄后按有效明细重算订单金额、定金/尾款和付款状态，再恢复触发器与更严格的 `scale <= 2` 约束；收款审批的人民币入账金额或待审核收款占用若会因收窄而变化，迁移失败关闭并交财务先核对。`20261019141000_measurement_integer_precision` 把装柜明细与账单明细的重量按 ROUND HALF_UP 收窄为 `NUMERIC(18,0)`、尺寸按 CEIL 收窄为 `NUMERIC(18,0)`；历史 `volume_cai` / `chargeable_volume_cai` 不在迁移内重算，保留已发生的计费事实，新写入由应用按整数尺寸重算。`20261019142000_exchange_rate_four_decimals` 把六列汇率收窄为 `NUMERIC(30,4)`、金流费率收窄为 `NUMERIC(30,3)`，并以前置检查拒绝会让收款入账金额或费率归零的历史值。`20261019143000_invoice_decimal_integer_invariants` 把开票五个金额列从 `BIGINT` 改为 `NUMERIC(30,0)`，并以延迟约束触发器强制「至少一条明细」和「销售额等于明细金额之和」；退回重填的删除/重建在提交时才校验。`20261020120000_data_scope_permissions` 不修改 schema，只追加两条可委派的数据范围权限：`data-scope:self`（运营内置角色默认持有，表示只能读取本人归属数据）与 `data-scope:all`（财务、采运与系统管理员持有，表示全量数据并优先于 self）。迁移在同一事务内授予内置 `system_admin` 两条、`operations_staff` self、`finance_staff`/`purchasing_staff` all，并自检目录与授权；服务端以角色码 `operations_staff` 作为 self 的安全兜底，避免误删授权后静默放开。数据范围只影响业务查询与写接口的资源定位，不替代接口权限码。

`20261020140000_user_profile_avatar_media` 把个人头像接入统一媒体生命周期：给 `user_profiles` 增加可空 `avatar_media_asset_id`（唯一索引与 `media_assets` 外键），把 `USER_AVATAR` 追加到 `media_assets_upload_purpose_check`，并在通用 READY 引用函数与 `user_profiles` 延迟约束触发器中增加头像分支。`avatar_url` 仍是客户端可见的绝对地址；新列只负责「READY 必须有活跃引用」与换头像后的回收，不进入任何公共 DTO。迁移纯 additive，存量外链头像保持 `avatar_media_asset_id = NULL`，不回填、不重写 URL。

`20261021170000_purchase_shipment_delivery` 给采购货件增加客户签收事实四列（`delivered_at`、`delivered_by_id`、`delivered_recorded_at`、`delivery_remark`）：要么同时为空，要么同时有值且要求货件有效、已装柜、签收时间不早于装柜且不晚于记录时间；货件不可变触发器只放行签收事实的一次写入，之后不可改写、不可清空。迁移追加 `PURCHASE_SHIPMENT_DELIVERED` 审计类型，并以延迟约束触发器强制「销售订单履约状态为 `SIGNED` 时，其下未取消的有效货件必须全部已签收」；存量已签收订单按最近一次履约签收历史（缺失时退回有效签收单创建时间）回填签收事实，存在待审核或未装柜货件、或签收时间早于装柜时间时失败关闭并交人工核对。它不新增表、不改变采购单签收（仓库入仓）语义，也不把客户签收与 `warehouse_received_at` 混用。

`20261022120000_container_loading_delivered_guard` 收紧装柜关联的数据库兜底：在既有 `enforce_container_loading_shipment_batch` 触发器里，锁定货件行后若 `delivered_at` 非空即拒绝新增或换绑装柜明细（约束名 `container_loading_items_shipment_delivered_check`），已有关联的同货件同柜次普通编辑仍由函数开头的快速放行分支保持可编辑。它不修改存量数据、不新增列，也不尝试用触发器判断「历史解绑后的已装柜」——装柜事实先于明细写入，该规则只能在应用层按 `loaded_at` 与本柜明细是否存在判断。迁移末尾自检签收列与覆盖函数均已落库。

`20261022130000_user_profile_issuer_prefix` 给 `user_profiles` 增加可空 `issuer_prefix VARCHAR(3)`，用于采购单复制信息和采购单图片中的出单人前缀展示：最多 3 个汉字、允许为空，应用层校验汉字范围，数据库约束拒绝首尾空白与空串。迁移纯 additive，不 backfill、不改变编号规则、派发流水或唛头字段。

`20261023120000_perf_indexes` 为采购货件列表补充两个 B-tree 索引：`purchase_order_parts_shipment_view_idx` 覆盖「状态 + 到仓时间 + 发货时间」的视图过滤与计数，`purchase_order_parts_destination_warehouse_idx` 覆盖按目的地仓库分组的计数查询。迁移只创建索引，使用 `IF NOT EXISTS` 支持重放，不修改任何列、约束或存量数据；关键词搜索使用的 `pg_trgm` GIN 索引需要 `CREATE EXTENSION` 权限，仍保留在 `deploy/ops/performance-search/` 运维脚本中，不进入 migration。

`20261025120000_purchase_order_rejection` 为采购审核驳回增加可空元数据 `rejected_at`、`rejected_by_user_id`、`rejection_reason`，并以两条 CHECK 固定形状：三列必须同时为空或同时有值、原因非纯空白、驳回时间只允许出现在 `CANCELLED` 状态；新增驳回人外键与 `(rejected_at, order_date DESC, id DESC)` 部分索引，并向 `audit_event_type` 追加 `PURCHASE_ORDER_REJECTED`。迁移纯 additive，不新增采购状态枚举、不回填、不修改既有采购行或货件/唛头事实；驳回仍复用 `CANCELLED` 的生效性语义，从而让来源销售数量、覆盖、发货/装柜与销售订单门禁继续按「非取消」判断。

`20261026120000_purchase_payment_shared_voucher` 以 `CREATE OR REPLACE` 放宽付款凭证的延迟触发器 `enforce_purchase_payment_voucher`：批量付款只上传一张截图，同一媒体资产可归档到本批多笔付款，因此数据库兜底从「凭证必须绑定当前应付款（`media_assets.purchase_payable_upload_id = NEW.payable_id`）」改为「同一操作人上传的 READY 付款截图（`media_assets.created_by_user_id = NEW.created_by_user_id`）」。每笔付款仍必须恰好一张未解除的 `PAYMENT_VOUCHER` 文档，用途、图片类型、READY 状态与未删除条件保持不变；「凭证属于本批」的范围校验由 `payBatch` 事务在写资金前完成，单笔付款仍由应用层要求阶段独占消费。迁移不新增列、不回填、不修改既有付款或媒体行，末尾自检旧绑定条件已移除且上传人校验已生效；回滚方式是重新执行 `20260917043000_purchase_payment_receipts` 中的原函数定义。

`20261026130000_purchase_order_amount_revision` 以 `CREATE OR REPLACE` 放宽 `enforce_purchase_payable_identity`，把 `due_amount` 加入受控可变字段：仅当采购单为 `CONFIRMED`/`COMPLETED`、该单没有任何有效付款、应付未关闭、其余身份字段逐字节不变且 `version + 1` 时，才允许更新供应商应付款金额；`closed_at` 的取消路径保持原语义。旧金额由既有的不可变 `purchase_order_amount_revisions` 快照保存，迁移同时向 `audit_event_type` 追加 `PURCHASE_ORDER_AMOUNT_REVISED`，不新增表、不回填、不修改既有订单、应付、付款或资金行。该迁移仍需显式授权后应用到业务库；回滚方式是重新执行 `20260916160000_purchase_order_payables` 中的原函数定义（已发生的金额修订数据不会自动回滚）。

## 3. 不可变与只追加原则

- migration 一旦提交并在共享环境应用，就不得修改、重命名、重排或删除。
- schema 变化必须创建新的 migration，只追加历史，不重写既有 SQL。
- 新增或修改 `schema.prisma` 前必须单独获得用户确认；既定阶段计划不能替代这次确认。
- 已应用 migration 存在问题时采用向前修复：恢复期望 schema、创建新的修复 migration，并在隔离数据库重新验证完整历史。
- 不通过修改 `_prisma_migrations`、伪造 checksum 或删除历史来掩盖漂移。
- `prisma migrate resolve` 只在明确调查失败状态并获得单独授权后使用，不作为日常修复手段。

## 4. 命令使用边界

| 命令 | 允许场景 | 约束 |
| --- | --- | --- |
| `prisma migrate dev` | 开发者本地创建新 migration | 只能连接可丢弃、隔离的开发数据库；会检测漂移并可能提示重置，不用于 CI 或生产。 |
| `prisma migrate deploy` | 测试、CI、预发布与生产 | 只应用已经提交的 migration，不创建或改写 migration 文件。 |
| `prisma migrate status` | 部署前后只读核对历史状态 | 必须确认结果为 up to date；非零退出必须阻断后续发布。 |
| `prisma db push` | 可立即丢弃且不需要迁移历史的本地原型 | 禁止用于共享、测试、预发布、生产或任何持久环境，也不能代替正式 migration。 |

项目脚本映射如下：

```bash
: "${DATABASE_URL:?DATABASE_URL must reference the isolated database}"
export DOTENV_CONFIG_PATH=/dev/null
unset DEBUG
unset PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION

pnpm -C server db:migrate:dev
pnpm -C server db:migrate:deploy
pnpm -C server exec prisma migrate status
```

上述 guard 必须在调用任何 Prisma 或 E2E 命令前由同一受控 shell 执行，且错误文本不得回显 URL。`DOTENV_CONFIG_PATH=/dev/null` 只限制 `prisma.config.ts` 的 `dotenv/config`，不会改变 Nest `ConfigModule` 默认读取 `server/.env` 的行为；因此 `test:e2e` 同样必须在启动 Node.js 前先通过 shell guard 确认临时 `DATABASE_URL` 已存在。清除 `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` 可以避免继承其他会话对 Prisma 危险操作的确认状态；临时验证流程不得预授权破坏性数据库操作。

创建 migration 前先确认 schema 修改已经获得授权，并检查 `git status`。创建后必须人工审查生成 SQL，确认没有意外删除、隐式数据转换或与需求无关的对象。

## 5. 空库部署验证

每一组新的 migration 至少在一个全新的 PostgreSQL 16 数据库完成以下验证：

```bash
pnpm -C server db:migrate:deploy
pnpm -C server db:migrate:deploy
pnpm -C server exec prisma migrate status
```

验收要求：

1. 首次 deploy 从空库完整成功。
2. 第二次 deploy 成功并报告没有待应用 migration，证明幂等。
3. `prisma migrate status` 报告 up to date。
4. `_prisma_migrations` 中每个预期 migration 恰有一条记录，`finished_at` 非空且 `rolled_back_at` 为空。
5. 实际表、索引、约束和类型与本次 schema 变更一致，不存在示例表或额外对象。

预期 migration 集合必须从当前提交的 `prisma/migrations/` 目录推导，并与第 2 节列出的当前历史保持一致。新增 migration 后必须同步更新当前历史说明和验收预期；运维脚本不得永久写死 migration 数量、最后一条名称或业务表数量。

### 5.1 隔离 schema 回放的 public 前置条件

业务 E2E 把正式 migration 重放到一次性的隔离 schema（`purchase_mark_e2e_*` 等），而不是重放进 public。但历史 migration 里有四处结构自校验把表名写死在 public（`20260926130000_slh_bill_management`、`20260926131000_slh_bill_reported_amounts`、`20260926133000_slh_bill_comparison_columns`、`20260927100000_slh_bill_archive_fields`），隔离回放时在 public 查不到这些表就会以 `SLH bill tables missing` 失败。因此这类 E2E 的前置条件是：**目标库的 public 已经应用过迁移**。

- CI 与本地标准流程都满足该条件：`scripts/ci-server-e2e.mjs` 在 `test:e2e` 之前连着执行两次 `db:migrate:deploy`，本地开发库也早已应用过完整历史。
- 面对全新库时，先对目标库执行 `pnpm -C server db:migrate:deploy` 再跑 E2E；`server/test/isolated-replay-precondition.ts` 会在回放前提前失败并给出这条命令，而不是让流程卡在一句看不出原因的迁移错误上。
- 上述四处自校验属于已提交的不可变历史，不得改写（改文件会变更 checksum，导致所有已应用环境需要 `prisma migrate resolve`）。

## 6. 临时 PostgreSQL 安全流程

创建和验证 migration 使用全新的 PostgreSQL 16 容器，并遵守以下规则：

- 在创建任何资源前启用 `set -euo pipefail`、`umask 077` 和清理 `trap`。
- 使用 `openssl rand` 生成随机密码并写入权限受限的临时文件，不把密码放入仓库、命令历史或日志。
- 容器使用会话唯一名称、专属 label 与 `--cidfile`；清理时只操作记录的精确容器 ID。
- 只绑定 IPv4 loopback `127.0.0.1`，通过 `--publish 127.0.0.1::5432/tcp` 让 Docker 动态分配端口，不固定占用或复用本机已有端口。
- 用容器内 `pg_isready` 等待就绪，并通过 `SHOW server_version_num` 确认 major 为 16。
- `DATABASE_URL` 只在同一受控 shell 中通过进程环境临时注入；结束时 `unset DATABASE_URL DOTENV_CONFIG_PATH DEBUG PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`。
- 禁止 `set -x`，禁止打印、回显或把完整 URL 传入会在失败时展示原值的断言。
- `DEBUG` 保持未设置；如确需其他 debug namespace，必须排除 `prisma:*`。
- `trap` 无论成功、失败、`SIGINT` 或 `SIGTERM` 都删除精确容器、匿名 volume、密码文件和临时目录，同时保留原始非零退出码。

通用 label 只用于最终残留审计，不得据此批量删除容器。发现不属于本次会话的资源时只报告，不停止、不复用、不清理。

## 7. 失败处理与发布纪律

- migration 创建或验证命令失败时，立即停止后续步骤并如实保留错误状态；先清理临时资源，再调查根因。
- 不把失败环境的 URL、密码、SQL 参数或驱动堆栈复制到文档、提交信息和公开日志。
- 开发库漂移不能通过改写已提交 migration 解决；确认目标结构后创建向前修复 migration。
- 部署失败时停止应用发布，保留已提交历史并评估新的修复 migration；不要在生产库运行 `prisma migrate dev` 或 `prisma db push`。
- 每次提交前检查 `schema.prisma`、新增 migration SQL 和 lock file 的暂存范围，确保没有 generated client、`.env`、日志或数据库转储。

migration 与应用构建独立但发布有顺序约束。涉及兼容性变化时采用 expand/contract：先追加兼容 schema，再发布兼容代码，确认旧代码退出后再通过后续 migration 收缩结构。
