# 后端接口契约规范

本文记录千树 DMS Server 当前已经实施的 HTTP 与 OpenAPI 契约。新增或修改公共 API、请求响应数据结构、错误码或数据库 schema 前，仍须先取得用户确认。

## 1. 契约真相源

Server 的 NestJS Controller、DTO 和 OpenAPI decorators 是接口定义真相源。运行时代码与文档扫描共同消费 `server/src/http.modules.ts` 中的 `HTTP_MODULES`，避免正式路由和离线快照使用两份手写模块清单。

正式快照是 `server/openapi/openapi.json`。该文件提交 Git，但由生成流程维护，不得手工编辑。当前正式契约包含 `GET /api/health`，以及 `/api/auth`、`/api/users`、`/api/roles`、`/api/permissions`、`/api/audit-events` 下的已实施操作；具体 operation 以快照为准。fake routes 只服务 Web 基座开发，不加入 Server OpenAPI。

每个公开操作必须同时具备：

- 稳定且显式的 `operationId`；
- 明确的成功 response；
- 适用的错误 response；
- 每个 response 上的 `X-Request-Id` Header；
- `x-qianshu-contract` 元数据，用于区分 health 与 application contract。

## 2. Request ID 与 ApiError

### 2.1 Request ID

`requestIdMiddleware` 为每个请求生成新的 Server-generated `X-Request-Id`，格式为 `req_<uuid-v4>`。客户端传入的同名 Header 不会成为服务端 Request ID；Header 写入响应后，同一个值在请求对象内供后续错误映射使用。

任意成功或失败 response 都必须返回 `X-Request-Id`。普通应用错误的 `ApiError.requestId` 必须与响应 Header 相同。日志只能使用 Request ID 关联未知错误，不能输出请求体、凭据、数据库详情或异常对象。

### 2.2 ApiError

除严格限定的 health failure 豁免外，应用级 JSON 错误统一为：

```ts
interface ApiError {
  code: string
  message: string
  fieldErrors?: Record<string, string[]>
  requestId: string
}
```

基础 status 映射如下：

| HTTP status | 默认 `code` | 公开中文 `message` |
| --- | --- | --- |
| `400` | `BAD_REQUEST` | `请求格式错误` |
| `401` | `UNAUTHORIZED` | `未登录或登录已失效` |
| `403` | `FORBIDDEN` | `没有权限执行此操作` |
| `404` | `NOT_FOUND` | `请求的资源不存在` |
| `409` | `CONFLICT` | `请求与当前资源状态冲突` |
| `422` | `VALIDATION_FAILED` | `请求参数校验失败` |
| `500` | `INTERNAL_ERROR` | `服务器内部错误` |

业务需要稳定的自定义 `code` 和公开文案时使用 `ApiException`。普通 `HttpException` 的原始 body、未知异常的 `message`、`stack` 和底层错误都不能直接返回客户端。

对表中未列出的普通 `HttpException` status，`4xx` 保留原 status 但收敛为 `REQUEST_REJECTED`；未知 `5xx` 收敛为 `INTERNAL_ERROR`。非 `HttpException` 一律返回 HTTP `500 INTERNAL_ERROR`，不得把原始异常公开给客户端。

### 2.3 中文 validation

全局 `ValidationPipe` 启用 `whitelist`、`forbidNonWhitelisted` 和 `transform`，校验失败使用 HTTP `422`。`createValidationException` 把嵌套字段路径展开为 `fieldErrors`，已知 class-validator 默认英文约束转换为中文；只有显式、纯中文的 decorator 文案可以作为公共契约保留，其余内容收敛为安全的中文文案。

### 2.4 health 豁免

`GET /api/health` 保留 Terminus 专用成功和失败 body，不套用全局成功 envelope。只有请求路径、HTTP status 和 Terminus failure 结构全部满足 guard 时，失败 body 才可绕过 `ApiError`；其他异常仍进入统一映射。health 成功或失败 response 都继续携带 Server-generated `X-Request-Id`。

## 3. OpenAPI 响应描述

### 3.1 application operation

新增应用操作使用 `ApiApplicationContract` 声明稳定 `operationId` 和 `x-qianshu-contract` 判定元数据。根据实际能力开启 `badRequest`、`authentication`、`authorization`、`resourceLocator`、`conflict`、`validation`；`authorization` 只能建立在 `authentication` 之上。该 decorator 总是声明 `500 ApiError`，其他错误 status 由明确选项加入。

### 3.2 success、204、binary 与 error response

所有 response 均通过 `ApiContractResponse` 描述，它会合并调用方 Header 并统一补充 `X-Request-Id`：

```ts
@ApiContractResponse({ status: 200, type: ResultDto })
@ApiContractResponse({ status: 201, type: CreatedDto, headers: { Location: locationHeader } })
@ApiContractResponse({ status: 204 })
@ApiContractResponse({
  status: 200,
  content: {
    'application/pdf': {
      schema: { type: 'string', format: 'binary' },
    },
  },
})
```

- JSON success 必须提供 DTO `type`，不使用全局成功 envelope。
- `204` 必须无 body；decorator 会拒绝同时声明 `type`、`schema` 或 `content`。
- binary response 必须用实际 media type 和 `format: 'binary'` 描述。
- error response 由 `ApiApplicationContract` 使用 `ApiError` schema 声明，不能只存在于 Exception Filter 的运行时代码里。

health 是专用协议，使用显式 `ApiOperation`、`ApiContract` 和 `ApiContractResponse` 分别描述 `200` 与 `503` DTO。

## 4. 生成、同步与检查

### 4.1 Server 离线生成

```bash
pnpm -C server openapi:generate
```

`openapi:generate` 先构建 Server，再以 Nest preview application 扫描 metadata。preview 配置不读取 `.env`、不连接数据库、不监听端口，并在成功或失败后关闭 application。生成过程不会创建 Swagger UI，也不开放 Swagger route。

生成器原子替换 `server/openapi/openapi.json`，错误边界只输出固定消息，不回显路径、文档内容或底层异常。缺失 `operationId`、不合法的 `x-qianshu-contract`、错误 response matrix 或 Request ID Header 都由契约检查拒绝。

### 4.2 根级同步与只读检查

```bash
node --run contract:sync
node --run contract:check
node --run contract:check -- --baseline server/openapi/openapi.json
```

- `contract:sync` 是跨端快照唯一显式写入口：在临时目录生成并验证 Server snapshot 与 Web types，随后事务式发布 Server snapshot、Web snapshot 和 ignored generated directory；任一发布校验失败都会回滚。
- `contract:check` 将待比较的 snapshot 与 Web types 生成到临时目录，不修改已跟踪快照；前置 Server build 仍允许重建 ignored `server/dist/` 与 Prisma Client。它验证 Server snapshot 未过期、两端字节与 SHA-256 一致，以及 generated 产品结构正确。
- `--baseline` 额外保护已存在的 `operationId`，避免无意重命名破坏调用方。

## 5. 安全边界

- 正式 Server 不开放 Swagger route 或 Swagger UI；OpenAPI 只以离线 snapshot 交付。
- 不在 OpenAPI example、错误 body、日志或命令输出中放入 token、Cookie、密码、连接字符串、SQL、堆栈或驱动错误。
- 不记录完整请求体或响应体；未知异常日志只包含固定文案与 Server-generated Request ID。
- `.env`、`dist/`、`coverage/`、`src/generated/prisma/` 和 `*.log` 不得提交 Git。
- OpenAPI preview、contract check 和类型生成不能依赖本地数据库或真实环境文件。

## 6. 新增接口检查清单

1. 先确认公共 API 与数据结构变更已获批准。
2. 为请求 DTO 添加明确校验与中文公共文案。
3. 使用 `ApiApplicationContract` 声明稳定 `operationId` 与真实错误矩阵。
4. 使用 `ApiContractResponse` 声明 success、`204` 或 binary response。
5. 添加 Controller、错误映射和 OpenAPI contract 测试。
6. 运行 `node --run contract:sync` 后检查 snapshot diff，再运行 `node --run contract:check`。
7. 同步更新前后端接口规范与调用代码，不手工编辑 snapshot 或 generated types。
