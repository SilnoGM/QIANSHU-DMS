# 媒体对象存储路径规范

> **状态：代码已实施，存量迁移未执行。**
>
> 新键生成、业务池、共桶环境段、`_ops/{env}/` 探针键、对账环境过滤、受控改键通道（登记表 +
> 触发器白名单）、`media:keys:replan` 命令与 L1 缓存放宽均已落地并通过测试。**存量对象仍停留在旧布局**
> ——迁移必须按第 6 节在独立的生产授权下执行，本文不构成执行授权。
>
> 第 7 节列出实施状态；已知与规范定稿的差异见第 9 节。

本文定义媒体对象键（object key）的组织方式、命名规则、数据库衔接、访问控制、扩展规则，
以及存量对象按新布局重命名的迁移流程。它承接 [`媒体存储部署与恢复`](./媒体存储部署与恢复.md)
的存储驱动合同，不改变该文件定义的驱动语义、探针合同、备份与恢复边界。

## 1. 现状与适用范围

### 1.1 接入方式

- 存储驱动由 `MEDIA_STORAGE_DRIVER` 选择，只允许 `local` 与 `cos`；两侧的键布局完全一致，
  因此切换驱动不重算键（`server/src/config/media.config.ts`、`cos-media-storage.ts`）。
- `cos` 是复合驱动：`assets/`、`trash/` 在私有桶内，**`staging/` 永远在本地磁盘**
  （`MEDIA_STORAGE_ROOT`），`ffprobe`/`qpdf`/`sharp` 面对真实本地文件。
- 凭据只从 `MEDIA_COS_SECRET_ID` / `MEDIA_COS_SECRET_KEY` 环境变量读取，不进入任何冻结配置对象、
  日志或异常序列化。
- 投递统一走 `/api/**/content` 同源路由 + 会话鉴权 + 权限装饰器；`cos` 下**强制**
  `MEDIA_CONTENT_DELIVERY_MODE=application`（应用流式返回），**不使用预签名 URL**。
  `local` 下可选 `internal_redirect`（`X-Accel-Redirect` + Nginx `alias`）。
- 桶约束：私有读写、与服务器同地域、凭据来自只授权该桶（共桶后收紧为只授权该环境前缀）的
  CAM 子账号。

### 1.2 既有路径规则

| 命名空间 | 现状格式 | 生成位置（全仓唯一） |
| --- | --- | --- |
| `assets/` | 新写入为 `assets/{env}/{pool}/{YYYY}/{MM}/{assetId}{ext}`；存量仍是 `assets/{YYYY}/{MM}/{assetId}{ext}` | `media-object-key.ts` 的 `buildMediaObjectKey` |
| `staging/` | `staging/{assetId}.{randomUuid}.part`（永远本地） | `local-media-storage.ts` 的 `createStagingWrite` |
| `trash/` | `trash/` + assets 键去掉 `assets/` 前缀，其余逐字保留 | `media-retention.service.ts` 的 `trashKeyFor` |
| `_ops/` | `_ops/{env}/health-probe-read` / `_ops/{env}/health-probe-{uuid}` | `media-operational-health.ts` |

### 1.3 不得违反的既有约束

- 数据库只保存 `storageDriver + objectKey + sizeBytes + checksumSha256`，**不保存绝对路径**。
- 键长度 ≤512 字符，字符集 `[A-Za-z0-9._/-]`，禁止空段、`.`、`..`、反斜杠、NUL 与前导 `/`
  （`media-storage.ts` 的 `normalizeMediaObjectKey`）。
- `object_key` 有唯一约束；**READY/TRASHED/PURGED 状态下含 `object_key` 在内的 14 列被数据库触发器
  锁死**（`media_assets_content_identity_immutable_check`）。
- 领域引用是 10 张表的显式白名单：新增引用表必须同时扩展 `MEDIA_ASSET_REFERENCE_TABLES`、
  数据库延迟约束触发器与 `media-reference.contract.spec.ts`，否则门禁失败。
- **上传时拿不到任何业务维度**：`MediaAssetService.prepare()` 只接收
  `actorUserId / allowedTypes / requestedType / declaredMimeType / originalFilename / stream`；
  `uploadPurpose` 是上传成功后由业务服务回填的。因此业务分类若要进键，必须作为**上传时入参**传入。

| --- | --- | --- | --- | --- | --- | --- | --- |

`uploadPurpose` 现有取值与目标池的对应：
`PURCHASE_PAYMENT_VOUCHER` / `PACKAGING_PAYMENT_VOUCHER` → `voucher`；
`PAYMENT_RECIPIENT_QR` → `payment-recipient`；`SLH_BILL_SOURCE_XLSX` → `bill`；
`OCEAN_FREIGHT_SOURCE_XLSX` → `container`。

### 1.5 现状的问题

1. 桶内对象不可读：仅凭 `assets/{YYYY}/{MM}/{uuid}.png` 无法判断业务归属，运维、清理、成本分摊
   只能回库逐条解析。
2. 没有业务维度，无法按业务做前缀级生命周期规则、CAM 子账号策略与容量归集。
3. 键无法反查业务，迁移、对账、审计工具链都要回连数据库。
4. 临时上传（UPLOADING）与正式资产混放在同一前缀下。
5. 键内年月是 UTC，与业务口径（东八区）差 8 小时，跨月边界会「看起来放错月份」。

## 2. 路径规范

### 2.1 设计原则

1. **键只包含「上传瞬间已确定且不可变」的信息。** 业务单据号不满足：采购单图片草稿、柜次来源文件
   都是先暂存文件、业务主体尚未创建，且单据号可能被修正。
2. **敏感级别、访问策略、环境以外的策略维度不进键。** 策略会演进，键是不可变事实。
3. **键必须可反解 `assetId`，首段恒为命名空间。** 存量迁移、对账、`trash` 映射与
   `requireMediaObjectKeyNamespace` 校验全依赖这两点。

### 2.2 目录结构

```
<桶>
├── assets/
│   └── {env}/                          # dev | test | prod
│       └── {pool}/                     # 业务池，kebab-case，≤32 字符
│           └── {YYYY}/{MM}/            # UTC 上传年月，仅作分片，不作业务口径
│               └── {assetId}{ext}
├── trash/
│   └── {env}/{pool}/{YYYY}/{MM}/{assetId}{ext}
├── staging/                            # 永远本地磁盘，无环境段
│   └── {assetId}.{randomUuid}.part
└── _ops/
    └── {env}/health-probe-{read|<uuid>}
```

- `{env}` **必须位于命名空间之后**：首段是命名空间契约，被 19 个生产文件的 64 处
  `requireMediaObjectKeyNamespace` / `requireManagedNamespace` 调用依赖，也是 `trashKeyFor`
  前缀替换与 Nginx `alias` 的锚点。
- `trash` 键由 `trashKeyFor` 前缀替换得出，新布局零改动即正确。
- `staging` 永远在本地磁盘，各环境物理隔离，不需要环境段。
- 池与环境的取值都**禁止匹配 `^\d{4}$`**，`{env}` 另禁取值 `staging`（与命名空间同名）。

### 2.3 业务池

| 池 | 覆盖场景 | 定义 |
| --- | --- | --- |
| `product` | #1 #2 | 商品素材，无资金与第三方个人信息 |
| `purchase` | #3 #5 | 采购单据凭据（非资金） |
| `sales` | #6 | 销售单据凭据（非资金） |
| `packaging` | #8 | 打木架提报证据 |
| `voucher` | #4 #7 #9 | **资金流出/流入的事实凭证** |
| `payment-recipient` | #10 | **收款通道配置**（收款码） |
| `bill` | #11 | 外部账单原件 |
| `container` | #12 | 装柜来源资料 |
| `misc` | 存量遗留 | 无引用或已终态对象，**禁止业务模块主动选用** |

`voucher` 与 `payment-recipient` 都是 L3：前者是一次性事实凭证，后者是可复用、可长期存在的
配置态，生命周期与处置策略不同，因此分池。

**已知偏差（销售收款凭证）**：销售出单凭证与销售收款凭证**共用同一个上传入口**
（`POST /api/sales-orders/document-uploads`，multipart 只带 `mediaType` 一个字段），上传瞬间无法判定
凭证最终用途，因此两者的对象键都落在 `sales` 池。采购侧之所以能拆分，是因为付款截图走的是独立的
`voucher-uploads` 入口。销售收款凭证的敏感级别与权限判定不受影响（仍按 `sales-receipts:read` 与服务层
归属校验收敛），只是它不在 `voucher` 前缀下。若要真正拆开，需二选一：给上传入口增加可选的 `purpose`
字段（公共 API 变更 + 前端同步），或新增一个专用上传入口（与采购侧保持一致）——两者都属需单独授权的
变更，见第 9 节。

pool 判定必须细化到**列与枚举值级**，因为拆分 `voucher` 后同一张表会跨池：

| 表 / 列 | 判据 | 池 |
| --- | --- | --- |
| `purchase_order_documents.document_type` | `PAYMENT_VOUCHER` | `voucher` |
| 同上 | `ORDER_ISSUANCE_VOUCHER` / `DELIVERY_RECEIPT` | `purchase` |
| `sales_order_documents.document_type` | `PAYMENT_VOUCHER` | `voucher` |
| 同上 | 其余取值 | `sales` |
| `packaging_cost_requests.payment_voucher_media_asset_id` | 非空 | `voucher` |
| `packaging_cost_requests.packaging_image / quotation_image_media_asset_id` | 非空 | `packaging` |

已核实的「同一 asset 被双引用」场景在拆分后仍落在同一池内，不需要人工裁决：

| 同一 asset | 引用 A | 引用 B | 结论 |
| --- | --- | --- | --- |
| 采购单图片草稿（`attachForReview` 后升为出单凭证） | `purchase_order_image_drafts` → `purchase` | `purchase_order_documents(ORDER_ISSUANCE_VOUCHER)` → `purchase` | 一致 |
| 销售收款凭证（审核通过后挂到订单凭证） | `sales_receipt_requests.voucher_media_asset_id` → `voucher` | `sales_order_documents(PAYMENT_VOUCHER)` → `voucher` | 一致 |
| 收款码（配置 + 付款快照） | `payment_recipient_accounts.qr_media_asset_id` → `payment-recipient` | `purchase_order_payments.recipient_qr_media_asset_id` → `payment-recipient` | 一致 |

### 2.5 命名规则

- **文件名**：`{assetId}{canonicalExt}`。**不保留原始文件名**——原始名是用户输入，含 Unicode、
  空格与引号，与键字符集冲突，且会把客户/供应商名称泄漏到对象列表；原始名已存
  `media_assets.original_filename`（≤255，NFC + 去控制字符 + 保留扩展名截断），下载时经
  `Content-Disposition` 还原。
- **唯一性**三层保障：① `assetId` 在 `prepare()` 第一步由 `gen_random_uuid()` 生成，生成键时已全局
  唯一；② `object_key` 唯一约束；③ 写入前冲突即失败（`cos` 用 `headObject` → `MEDIA_STORAGE_CONFLICT`，
  `local` 用 `O_EXCL` 与 `rename` 前判存在）。不引入随机后缀，避免同一内容出现多个键。
- **扩展名**：只接受内容校验器给出的 canonical extension 白名单（`.jpg .png .webp .mp4 .mov .webm
  .m4v .pdf .docx .xlsx`），不信任用户声明。
- **大小写**：键全小写。
- **`{env}` / `{pool}` 段**：`^[a-z][a-z0-9-]{1,30}$`，不得匹配 `^\d{4}$`。
- **长度预算**：最长键 ≈ `assets/prod/payment-recipient/2026/10/` + 36 + 5 ≈ 78 字符，
  远低于 512 与对象存储的键长上限。

### 2.6 规范约束

**校验位置**：格式、类型与体积校验全部在**服务端入库前**完成，客户端校验只做体验提示、不作为依据。

| 校验 | 位置 | 规则 |
| --- | --- | --- |
| 传输上限 | Nginx / 前端 | `client_max_body_size 501m`；前端提示不构成校验 |
| 流式体积上限 | `MEDIA_CONTENT_SIZE_LIMITS` | IMAGE 10 MiB、DOCUMENT 50 MiB、VIDEO 500 MiB，写入与解析共用同一份上限 |
| 内容嗅探 | 内容校验器 | magic bytes + 解析器（`sharp` / `qpdf` / `ffprobe`） |
| 声明一致性 | `MediaAssetService.prepare()` | `trustedMetadata.mediaType` 必须等于 `requestedType`，且尺寸与摘要与流式守卫一致 |
| 业务二次校验 | 各领域服务 | 例如收款码与付款凭证额外要求 mime ∈ `image/jpeg|png|webp` 且 `sizeBytes ≤ 10 MiB`；xlsx 上传要求 mime 与文件名后缀同时匹配 |
| 键字符集 | `normalizeMediaObjectKey` | 见 1.3，不含 `{env}` / `{pool}` 的额外枚举校验 |

**键中不允许出现的字符**：除 `[A-Za-z0-9._/-]` 之外的一切字符，以及空段、`.`、`..`、反斜杠、NUL、
前导 `/`；键长不得超过 512 字符。**原始文件名不参与键**，只进数据库列。

## 3. 数据库衔接

### 3.1 只存 object key

`media_assets.object_key` 永远存**相对键**。任何形态的 URL——桶域名、预签名地址、CDN 地址——
都不得入库：URL 是「驱动 + 桶 + 地域 + 域名 + 部署形态」的函数，一旦入库，换桶或换域名就变成全表
数据迁移；而键在驱动切换中是恒定的。

### 3.2 访问地址还原

```
object_key（数据库）
  → 领域服务按业务主体做权限与归属校验，服务端拼装相对路径 contentUrl
  → Web 得到 /api/<domain>/.../content（同源相对路径）
  → 请求进入服务端，再次鉴权与归属校验
  → MediaContentDeliveryService.open(objectKey)（只接受 assets/ 命名空间）
  → cos：应用流式返回；local：应用流式或 X-Accel-Redirect 交 Nginx
```

Web 侧对 `contentUrl` 做**精确字符串比对**，与服务端契约不一致时失败关闭、不把不可信地址交给 DOM
（`web/apps/qsmds-arco/src/api/modules/product-media.ts`）。因此拼装格式属于对外契约，不得改为绝对地址、
桶域名或签名地址。

### 3.3 兼容方式

`object_key` 的语义不变（仍是相对键），新旧布局共存靠**键形态判别**，不引入版本字段：

| 形态 | 段数 | 判别 |
| --- | --- | --- |
| `assets/{YYYY}/{MM}/{id}{ext}`（旧） | 4 | 段数 4，或第 2 段匹配 `^\d{4}$` |
| `assets/{env}/{pool}/{YYYY}/{MM}/{id}{ext}`（新） | 6 | 段数 6 |

读路径、回收路径、`checksumSha256`、`normalizeMediaObjectKey` 对新旧布局均无差异；
需要识别两种形态的只有解析键的工具（迁移与对账，见 6.7）。

### 3.4 不新增 pool 列

不新增 `media_assets.pool`：键是池的真相源，`poolFromObjectKey(key)` 是纯函数，可单测、无需迁移。
若将来确需按池落列以满足统计或策略需求，必须同时做到：① 该列与 `object_key` 在同一事务内的
`markPrepared` 阶段写入；② 该列纳入不可变元组，否则会出现「键说 `voucher`、列说 `purchase`」的
不一致数据。该变更属于需单独授权的 schema 变更。

## 4. 访问控制

### 4.1 敏感分级

分级的差异全部体现在**应用层策略**：桶始终私有读写，COS 下始终由应用鉴权后流式返回。

| 级别 | 池 | 权限与归属 | 加固要求 |
| --- | --- | --- | --- |
| **L1 低敏** | `product` | `product-media:read`；订单侧复用主图的 4 组路由沿用各自权限 | 无额外要求 |
| **L2 中层** | `purchase`（出单凭证/签收单/图片草稿）、`sales`（出单凭证/签收单）、`packaging`、`container`、`bill` | 各业务读权限即可 | 保持不暴露 `objectKey`、不返回绝对 URL |
| **L3 高敏** | `voucher`、`payment-recipient` | 必须叠加主体归属校验。现有最佳范式：付款凭证校验 `payableId` 匹配 + `purchase-orders:payment`；收款码走「仅登录 + 服务层多分支 + 不满足一律 404 防枚举」 | 建议把 L3 其余场景（销售收款凭证、打木架付款截图）补齐到同等强度 |

### 4.2 缓存策略

- **L1 放宽**：`product` 池的 content 路由返回
  `Cache-Control: private, max-age=31536000, immutable`（内容按 `assetId` 不可变，URL 含不可复用的
  ID）。**绝不使用 `public`**：会话鉴权下 `public` 会被共享缓存绕过鉴权。
- **L2 / L3 保持** `private, no-store`（全局 interceptor 默认行为），**L3 永不放宽**。
- 实现方式：给 L1 路由加元数据标记，由 interceptor 通过 `Reflector` 读取后改写 `Cache-Control`，
  **不要用 URL 正则匹配**——路由改名时正则会静默失效，失效方向虽安全但会变成难查的性能问题。
- 残余风险（已知并接受）：`product` 池图片在 detach 后仍可能留在浏览器私有缓存中（仅本机可见）。

### 4.3 预签名 URL

**不引入预签名 URL。** 它会绕过应用层权限与归属校验，且签名有效期内撤权不同步。若将来确需直传或
直出（大视频播放、批量下载），单独设计并限定：有效期 ≤5 分钟、限定单对象前缀、
**只对 L1/L2 开放，L3 永远走应用路径**。

**已决：不引入媒体读取审计。** 该结论为明确取舍，不作为遗漏项。

### 4.4 共桶环境隔离

同一桶承载 `dev` / `test` / `prod` 时：

1. **`_ops/` 探针键必须带环境段**：写探针是「PUT 后立即 DELETE」，共桶且不带环境段时会删掉其它环境
   正在使用的探针对象。
2. **对账必须按环境段分类过滤，不能只用前缀**：另一环境的对象要被整体跳过（既不算 `orphanObject`
   也不算 `unmappableObject`）。这里不能简单地把扫描前缀改成 `assets/{env}/`——迁移期存量对象是旧布局、
   没有环境段，只用前缀会把本环境自己的存量全部漏扫。实现按「解析键 → 环境段是否属于本环境 → 是
   旧布局则视为本环境」分类（`belongsToMediaStorageEnvironment`）。
3. **CAM 子账号策略收紧**为只授权该桶的 `assets/{env}/*`、`trash/{env}/*`、`_ops/{env}/*`。
4. **`MEDIA_STORAGE_ENV` 为显式配置**，取值 `dev|test|prod`，校验强度与驱动一致；
   **`cos` 驱动下必填、无默认值**（缺失即启动失败），`local` 驱动默认 `dev`。理由：生产漏配而回落到
   `dev` 会把生产存量写成错误前缀，属于静默数据污染，必须失败关闭。
5. 桶的生命周期规则按 `assets/{env}/`、`trash/{env}/` 前缀分别配置。

## 5. 扩展性

新增媒体类型的标准动作：

1. **新池**：仅当不属于现有 9 个池且权限口径不同时新建；追加到池枚举常量。
2. **新调用点**：`prepare()` 的 `pool` 为**必填入参**，由编译期强制调用方声明，避免漏传退化为默认值。
3. **新内容格式**：扩 canonical extension 白名单、对应校验器与体积上限。
4. **新引用表**：必须同时扩展 `MEDIA_ASSET_REFERENCE_TABLES`、数据库延迟约束触发器与
   `media-reference.contract.spec.ts`。

硬边界：

- `{env}` 与 `{pool}` 固定在命名空间之后，且不得匹配 `^\d{4}$`；
- 末段恒为 `{uuid}{ext}`，键恒可反解 `assetId`；
- 不引入 `v2/`、`rekey/` 之类版本前缀或额外层级——版本由键形态本身承载。

明确不做：按单据 ID 分目录、按用户分目录、按 `media_type` 分目录、一类型一池的粒度膨胀。

## 6. 存量迁移

### 6.1 范围与评估

1. **先修对账前缀**（4.4 第 2 条），否则基线本身是错的。
2. 只读对账基线：`media:recovery:dry-run`，记录 `complete / matched / databaseScanned / storageScanned`
   与 7 类 mismatch 计数（`orphanObject`、`missing`、`sizeMismatch`、`checksumMismatch`、
   `duplicateLocation`、`unexpectedLocation`、`unmappableObject`）。
3. 只读分布统计：

   ```sql
   SELECT storage_driver, status, media_type,
          count(*) AS objects, pg_size_pretty(sum(size_bytes)) AS total_bytes
   FROM media_assets
   GROUP BY 1, 2, 3
   ORDER BY 1, 2, 3;
   ```

4. 按 6.2 判据生成 `(asset_id, old_key, new_key, pool)` 全量映射清单并人工复核。

**迁移范围**：`READY` 与 `TRASHED` 全量重命名；`UPLOADING`（含已过期）与 `FAILED` **不迁移**，
交给 `cleanup-expired-uploads` 回收。

**环境取值**：各环境用自己的 `MEDIA_STORAGE_ENV`，在各自的数据库与前缀内迁移，天然隔离。

### 6.2 映射规则

```
assets/{YYYY}/{MM}/{id}{ext}  →  assets/{env}/{pool}/{YYYY}/{MM}/{id}{ext}
trash/{YYYY}/{MM}/{id}{ext}   →  trash/{env}/{pool}/{YYYY}/{MM}/{id}{ext}
```

pool 判定优先级：**引用列（含枚举值，见 2.3）→ `uploadPurpose`（见 1.4）→ `misc`**。
清单中任一 asset 落在两个池即为冲突，必须人工裁决；已核实的 3 处双引用均同池，预期为 0 冲突。

### 6.3 顺序

| 阶段 | 动作 | 门禁 |
| --- | --- | --- |
| **0 评估** | 修对账前缀 → dry-run 基线 → 分布统计 → 映射清单复核 | 基线计数已存档 |
| **1 发布新键生成** | `prepare()` 增必填 `pool`、键生成改 6 段、8 个调用点按 2.3 传池、新增 `MEDIA_STORAGE_ENV`、`_ops` 加环境段、对账与迁移正则改段数判别、两个 env 模板与部署契约测试同步。发布后新上传即进新布局，存量不动 | 新布局上传可读写 |
| **2 登记映射** | 复核后的清单写入 `media_object_key_migrations`（`planned_at`），触发器白名单自此放行这批键对。**由 `media:keys:replan apply` 的第一阶段执行**（幂等；同一 asset 已登记不同键对时以 `conflicts > 0` 停在改键之前） | 行数 = READY + TRASHED 数 |
| **3 复制** | `media:keys:replan copy`：从旧键流式读取并 `putObject` 到新键（写入 `x-cos-meta-sha256` 元数据），随后立即用 `verifyStoredObject` 复核；目标已通过校验即 `skipped`；幂等、**不删源**、失败只计数。**只支持 `cos` 驱动**（本地驱动没有跨键复制端口，dev 媒体按约定直接重建） | `failed = 0` |
| **4 切换键** | `media:keys:replan apply` 的第二阶段：按批（500 行/事务）更新 `object_key`（带 `object_key = old_key` 条件，保证幂等与并发安全），同事务写 `applied_at`。**目标对象缺失或长度与数据库不一致时拒绝改键并计入 `missingTarget`**，因此跳过阶段 3 直接 apply 不会产生悬空键 | 每批可中断，旧对象仍在 |
| **5 验证** | dry-run 要求 `missing / sizeMismatch / checksumMismatch` 全为 0；`unexpectedLocation` 必须能被映射表解释；`applied_at` 全非空 | 三零 + 映射全应用 |
| **6 观察** | **7 天**（与 `MEDIA_TRASH_RETENTION_DAYS` 默认值对齐），期间不删旧键 | 这 7 天内至少完成一次可验证的数据库备份与桶内对象核对；未完成则**推迟阶段 7**——阶段 7 之后唯一回滚面就是备份 |
| **7 清理旧键** | 先确认新键存在且 size 一致，再删旧键；支持 dry-run；结束后按 7.1 的回收迁移 `DROP TABLE media_object_key_migrations` | 删除前后各一次对账 |

命令语义（`node dist/commands/media-key-migration.js <mode>`）：`preview` 只读统计工作量与登记进度；
`copy` 只复制字节、不写数据库；`apply` 先登记、再改键。三者都必须按 `preview → copy → apply` 顺序执行，
`apply` 在目标对象缺失时失败关闭，所以顺序颠倒不会造成悬空键，只会得到一批拒绝改键的行与 `missingTarget > 0`。
`copy` 选择「应用进程流式读写 + `putObject(sha256)`」而不是桶内服务端复制：写入时落下的 `x-cos-meta-sha256`
由命令自己控制，不依赖「服务端复制是否保留自定义元数据」这一未核实项；代价是字节要过一次应用进程，
大对象迁移时可按需改回服务端复制（校验逻辑不变）。

### 6.4 数据库改键通道

READY/TRASHED/PURGED 状态下 `object_key` 由触发器保护，直接 `UPDATE` 会被拒绝。本项目采用
**映射表白名单**，不使用会话开关：

- 会话级自定义参数是会话变量，不受对象权限体系保护——任何能连库的角色都能设置它，等于把守卫降级为
  约定。白名单表把「允许改键」从运行时可变的开关变成**事先登记、可复核、可审计的数据**。

```sql
-- 迁移专用表；迁移完成后 DROP（属需单独授权的 schema 变更）
CREATE TABLE media_object_key_migrations (
  asset_id   uuid PRIMARY KEY REFERENCES media_assets(id) ON DELETE CASCADE,
  old_key    varchar(512) NOT NULL,
  new_key    varchar(512) NOT NULL,
  planned_at timestamptz NOT NULL DEFAULT now(),
  applied_at timestamptz
);
```

触发器规则：`object_key` 发生变更时，**当且仅当**存在一行满足
`(OLD.object_key, NEW.object_key) = (old_key, new_key)` 或其反方向时放行；其余 13 列保持原有不可变
语义。正向用于迁移，反向用于回滚，两个方向都必须先登记。

诚实的边界说明：这一步**不引入新的权限边界**（应用账号本来就能写这张表），它的价值在于「改键必须先
登记」，把随机或意外的改键变成有记录、可复核、可回滚的操作；对账与回滚读取同一张表。

### 6.5 回滚

| 已执行到 | 回滚动作 | 风险 |
| --- | --- | --- |
| 1 | 回滚发布 | 无（仅布局混放） |
| 2 | 删除映射行 | 无 |
| 3 | 删除新键副本 | 无（数据库未变） |
| 4 / 5 / 6 | 按映射表反向更新 `object_key`，旧对象仍在 | 低 |
| **7 之后** | **不可原地回滚**，只能靠备份或桶版本控制（若开启，删除只产生 delete marker） | **高** |

回滚脚本与迁移脚本同批交付、同批评审。

### 6.6 过渡期兼容

**读路径不需要双读代码或灰度开关**：读取是「按数据库中的键去存储取对象」，复制阶段不删源，
因此任何时刻「数据库键所指对象都存在」。需要同步的只有解析键的消费方：

| 消费方 | 是否受影响 | 处置 |
| --- | --- | --- |
| 全部 content 路由与 `MediaContentDeliveryService` | 否 | 不改 |
| `trashKeyFor` 前缀替换 | 否 | 不改 |
| `staging` 键与清理前缀 | 否 | 不改 |
| `X-Accel-Redirect`（9 处，`local` 专属） | 否（拼的是数据库键，Nginx `alias` 覆盖整个前缀） | 不改 |
| `normalizeMediaObjectKey` | 否 | 不改 |
| 迁移正则（现只认旧布局） | **是** | 改段数判别，并增加键重写能力 |
| 对账正则（现只认旧布局） | **是** | 改段数判别；阶段 3–5 期间必须把映射表的 `new_key` 也算作合法位置，否则复制出的新键会被判 `unexpectedLocation` |
| 对账与清理扫描前缀 | **是**（共桶新增） | 加 `{env}/` 前缀过滤 |
| `_ops` 探针键 | **是**（共桶新增） | 加 `{env}/` 段 |
| COS 验收脚本硬编码键 | 是 | 同步 |
| 两个 env 模板与部署契约测试 | 是 | 新增 `MEDIA_STORAGE_ENV`，同步模板与文档措辞 |
| 存储驱动 CHECK 约束 | 否 | 不改（迁移命令不写 `storage_driver`） |

### 6.7 验收门禁

- 阶段 0 / 5 / 7 各留存一次 dry-run 计数快照作为前后对比证据。
- 阶段 4 每批：`已切换 + 未切换 = 总数`，且 `misc` 归类行数必须有逐条解释，不得静默扩大。
- 测试覆盖：pool 判定 12 类场景与 3 处双引用一致性；键形态判别（4 段 / 6 段）；
  触发器正反例（**无映射行改键必须失败、有映射行成功、反方向成功、改其余 13 列仍失败**）；
  共桶回归（`dev` 对账不得出现 `prod` 对象）。
- 迁移窗口内不得依赖对账告警；无法暂停告警时，必须让对账读取映射表。

## 9. 残余风险

1. **打木架付款截图归入 `voucher`** 是按池定义统一处理的结果（其业务父单据属 `packaging`）；
   若要严格限定为「只拆采购与销售的两类凭证」，把它改回 `packaging` 即可，规范其余部分不受影响。
2. **销售收款凭证未落入 `voucher` 池**（见 2.3 偏差说明）：受限于销售侧共用上传入口，需要在
   「给上传入口加可选 `purpose` 字段」与「新增专用上传入口」之间选一条才能真正拆分；两者都是公共 API
   变更，须单独授权。在此之前，`sales` 池同时含 L2 与 L3 两种敏感级别的对象——敏感级别的判定本来就
   不依赖键，仍由权限与服务层归属校验收敛。
3. **L1 长缓存的残余**：已 detach 的产品图片仍可能留在浏览器私有缓存中。
4. **7 天观察期短于通用建议**（≥14 天），其成立前提是阶段 6 的备份门禁；备份未完成就进入阶段 7，
   回滚面将只剩桶版本控制（若开启）。
5. **触发器白名单不构成新权限边界**：应用账号本来就能写映射表；它的价值在可审计与可复核。
6. **登记表未清理前，触发器依赖它**：先删表再恢复严格函数会让每次改键报缺表错误——回收迁移必须
   按 7.1 的顺序一次完成。
