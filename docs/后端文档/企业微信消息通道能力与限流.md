# 企业微信应用消息与群机器人消息能力及 DMS 处理方案

本文只记录官方能力与限流口径、当前 DMS 实现事实，以及建议的响应处理方案。未列出的代码改动均未实施。

## 1. 结论摘要

- **应用消息**通过 `/cgi-bin/message/send` 发送，面向成员、部门或标签，消息类型更丰富，支持视频、文件、文本卡片、企业微信图文、小程序通知和交互型模板卡片。
- **群机器人**通过 `/cgi-bin/webhook/send?key=` 发送，只能发到 webhook 绑定的内部群，消息类型较少，但支持表格类 Markdown（`markdown_v2`）。
- 限流口径不同：
  - 应用消息按**人次**限流：每应用每天 `账号上限 × 200 人次`；同一应用对同一成员 `30 次/分钟`、`1000 次/小时`。
  - 群机器人按**消息条数**限流：每个 webhook `20 条/分钟`。
- 当前 DMS 只接入 `text` 与 `image`；没有主动节流；正文限流会重试，附件限流会直接失败。详见第 4、5 节。

## 2. 消息类型支持

### 2.1 中文对照表

| 中文名称 | msgtype | 应用消息 | 群机器人 | 关键限制 |
| --- | --- | --- | --- | --- |
| 文本消息 | `text` | 支持 | 支持 | 均 ≤2048 字节；应用支持 `<a>` 链接；机器人支持 `mentioned_list`、`mentioned_mobile_list`、`<@userid>` |
| Markdown 消息 | `markdown` | 支持 | 支持 | 应用 ≤2048 字节；机器人 ≤4096 字节；均只支持语法子集 |
| Markdown 增强版消息 | `markdown_v2` | 不支持 | 支持 | 机器人 ≤4096 字节；支持表格、代码块、列表、图片；不支持 @ 和字体颜色；客户端需 ≥4.1.36（安卓 4.1.38+） |
| 图片消息 | `image` | 支持 | 支持 | 应用先上传素材，≤10MB；机器人直接传 `base64 + md5`，编码前 ≤2MB；均仅 JPG/PNG |
| 语音消息 | `voice` | 支持 | 支持 | 均 ≤2MB、≤60 秒、仅 AMR；应用先上传素材 |
| 视频消息 | `video` | 支持 | 不支持 | 应用先上传素材，≤10MB、MP4 |
| 文件消息 | `file` | 支持 | 支持 | 均 ≤20MB；应用走 `media/upload`，机器人走 `webhook/upload_media`；素材 3 天有效 |
| 文本卡片消息 | `textcard` | 支持 | 不支持 | 标题 ≤128 字符、描述 ≤512 字符、URL ≤2048 字节 |
| 图文消息（外链） | `news` | 支持 | 支持 | 均 1–8 条；标题 ≤128 字节、描述 ≤512 字节 |
| 图文消息（企业微信图文） | `mpnews` | 支持 | 不支持 | 1–8 条；正文 HTML ≤666KB；需要缩略图 `thumb_media_id` |
| 小程序通知消息 | `miniprogram_notice` | 支持 | 不支持 | 仅绑定了小程序的应用可发 |
| 模板卡片消息 | `template_card` | 支持 | 支持 | 应用支持 5 种卡片；机器人仅支持 `text_notice`、`news_notice` 两种展示型 |
| 交互任务卡片消息 | `interactive_taskcard` | 支持 | 不支持 | 需要配置应用回调 URL；属于旧版任务卡片能力 |

### 2.2 模板卡片子类型

| 中文名称 | card_type | 应用消息 | 群机器人 |
| --- | --- | --- | --- |
| 文本通知型 | `text_notice` | 支持 | 支持 |
| 图文展示型 | `news_notice` | 支持 | 支持 |
| 按钮交互型 | `button_interaction` | 支持，可回调、72 小时内更新卡片 | 不支持 |
| 投票选择型 | `vote_interaction` | 支持 | 不支持 |
| 多项选择型 | `multiple_interaction` | 支持 | 不支持 |

### 2.3 关键差异

1. **应用消息独有的类型**：`video`、`textcard`、`mpnews`、`miniprogram_notice`、`interactive_taskcard`。
2. **群机器人独有的类型**：`markdown_v2`。应用消息的 `markdown` 不支持表格和代码块。
3. **模板卡片能力差距最大**：应用消息可以带按钮、投票、多选和回调；群机器人只能展示 `text_notice` / `news_notice`。
4. **图片上传链路不同**：
   - 应用消息：`media/upload` 拿 `media_id`，再用 `media_id` 发消息，图片上限 10MB。
   - 群机器人：直接把 `base64` 和 `md5` 放进消息体，原图上限 2MB。
5. **群目标不同**：
   - 应用消息的 `touser` / `toparty` / `totag` 面向成员、部门、标签，不直接面向群聊。
   - 群机器人只能发到 webhook 绑定的那个内部群；客户群/外部群不在当前能力范围内（既有调研结论）。

## 3. 限流规则

### 3.1 应用消息

| 限制维度 | 规则 | 计数口径 | 超限表现 |
| --- | --- | --- | --- |
| 每应用每日总量 | 账号上限 × 200 人次/天 | 按实际收件人累计；一次 API 发 1000 人算 1000 人次 | 文档未单列错误码；可能命中 `45009` |
| 同一成员每分钟 | 30 次/分钟 | 每应用对每个成员单独计数 | 超过部分被丢弃、不下发 |
| 同一成员每小时 | 1000 次/小时 | 同上 | 超过部分被丢弃、不下发 |

补充说明：

- “账号上限”是购买/授权人数上限，不是当前在职人数。例如上限 500 人，每个应用每天可发 10 万人次。
- 批量发送只减少 API 调用次数，不减少人次计数。一次调用最多 1000 个 `touser`，每个人各算 1 人次。
- `30 次/分钟` 与 `1000 次/小时` 同时生效。持续发送时，小时上限更紧：1000 ÷ 60 ≈ 16.7 次/分钟的平均值。
- 文档明确“超过部分会被丢弃不下发”，但没有为这种情况定义单独错误码；紧随其后的返回示例仍是 `errcode: 0`。因此不能仅靠 `errcode` 判断某个成员是否被丢弃。
- 官方调用建议：尽量避开每小时的 0 分和 30 分，这两个时间点集中推送容易造成资源挤占和投递延迟。

### 3.2 群机器人/群消息推送

| 限制维度 | 规则 | 计数口径 | 超限表现 |
| --- | --- | --- | --- |
| 每个 webhook | 20 条/分钟 | 按 API 调用/消息条数，不按群成员数 | 文档未写具体错误码；代码按 `45009` 处理 |

补充说明：

- 一条文本算 1 条；每张图片算 1 条；一个文件算 1 条；一条图文消息即使包含 8 篇文章也只算 1 条；一张模板卡片算 1 条。
- 一条通知带 N 张图，占用 `1 + N` 条额度。例如“正文 + 3 张图”占 4 条。
- 文档没有写日配额或小时配额，只给了 20 条/分钟的窗口限制。
- `webhook/upload_media` 是独立接口，不占这 20 条消息额度；但它自身也可能命中通用 `45009`。

### 3.3 计数示例

| 场景 | 应用消息 | 群机器人 |
| --- | --- | --- |
| 一次调用发给 1000 人 | 1000 人次 | 不适用 |
| 同一成员一分钟内第 31 条 | 第 31 条被丢弃、不下发 | 不适用 |
| 正文 + 3 张图 | 4 次消息发送，按收件人各算人次 | 4 条消息，占 4/20 额度 |
| 一条 8 篇文章的图文 | 1 条消息，按收件人算人次 | 1 条消息 |
| 20 条投递、每条 1 图，同一群 | 不适用 | 40 条消息，超过 20 条/分钟 |

### 3.4 通用 `45009`

- `45009` 的官方含义是“接口调用超过限制”。
- 官方说明：频率拦截时长一般与限制周期相同。分钟级限制通常在触发后约 1 分钟解除；小时、天级限制同理。
- 官方建议只对系统失败重试；其他错误码应先排查原因。限流更适合退避，而不是立即重试。
- 由于 `45009` 不区分具体限制维度，DMS 无法仅凭错误码判断是“成员 30 次/分钟”“群 20 条/分钟”还是“应用日配额”。

## 4. DMS 当前实现

### 4.1 已接入的通道能力

| 通道 | 传输实现 | 当前支持 | 说明 |
| --- | --- | --- | --- |
| 应用消息 | `wecom-app.transport.ts` | `text`、`image` | 图片先 `media/upload` 拿 `media_id`，再 `message/send` |
| 群机器人 | `wecom-robot.transport.ts` | `text`、`image` | 文本支持 `mentioned_list`；图片传 `base64 + md5` |

图片适配在 `wecom-media.service.ts`：

- 应用消息图片保留到 10MB，超过则压缩。
- 群机器人图片压缩到 2MB，无法压到上限时返回 `WECOM_MEDIA_TOO_LARGE`。
- 当前只处理 `mediaAsset.mediaType === 'IMAGE'`；`voice`、`video`、`file` 尚未接入。

### 4.2 派发流程

`wecom-dispatch.service.ts` 的当前行为：

1. 单实例租约下运行，默认每 5 秒轮询一次，每批最多 20 条投递（`WECOM_WORKER_BATCH`，范围 1–100）。
2. 批内按顺序串行处理，不并发。
3. 每条投递先发正文，再逐张发附件；每张图片是一次独立 API 调用。
4. 正文发送成功后记录 `contentSentAt`；附件全部成功才把投递标为 `ACCEPTED`，任一附件失败则标为 `PARTIAL`。
5. 应用消息的 `media_id` 会缓存，过期时间按上传后 3 天计算；过期后重新上传。
6. 正文失败按 `RATE_LIMITED`（`45009`）延迟 60 秒重试，最多 3 次（`MAX_ATTEMPTS`）。
7. 附件失败走 `markMediaFailure()`，直接置为 `FAILED`，不重试。

### 4.3 当前响应处理

| 上游响应/场景 | 分类 | 当前处理 |
| --- | --- | --- |
| `errcode: 0` | 成功 | 投递记为 `ACCEPTED`；不代表成员一定已读或已收到 |
| `45009`（正文） | `RATE_LIMITED` | 60 秒后重试，最多 3 次 |
| `45009`（附件上传/发送） | `RATE_LIMITED` | 附件直接 `FAILED`，不重试 |
| `40001` / `42001` / `40014` | `TOKEN_INVALID` | 失效 token 后重试 |
| `81013` / `81014` / `invaliduser` | `INVALID_RECIPIENT` | 标记应用成员关系 `INVALID`，投递 `FAILED` |
| `60020` | `REJECTED` | 投递 `FAILED`，需运维补充可信 IP |
| `93000`（机器人） | `WEBHOOK_INVALID` | 投递 `FAILED`，需修正 webhook |
| `40006`（附件） | `REJECTED` | 附件 `FAILED` |
| `40007`（附件） | `REJECTED` | 附件 `FAILED`；应用消息需重新上传素材 |
| HTTP 5xx / 网络错误 / 超时 | `NETWORK` / `TIMEOUT` | 按退避重试 |
| 正文成功、附件失败 | 部分成功 | 投递记为 `PARTIAL` |

### 4.4 已识别风险

1. **群机器人 20 条/分钟容易被批量放大。** 默认一批 20 条投递，如果都发到同一个群、每条带 1 张图，就是 40 次调用，必然超过 20 条/分钟。
2. **配置中的节流参数未生效。** `wecom.config.ts` 定义了 `appMinSendIntervalMs = 1000` 和 `robotMinSendIntervalMs = 3000`，但生产代码没有引用，当前没有主动节流。
3. **附件限流是终态。** 附件遇到 `45009` 会直接 `FAILED`，不会像正文一样重试；图片可能永久丢失，整条投递变成 `PARTIAL`。
4. **应用消息的成员级丢弃是静默的。** 同一成员超过 30 次/分钟的部分不会下发，但接口可能仍返回成功；DMS 会把投递记为 `ACCEPTED`。
5. **没有发送速率监控。** 当前没有按 webhook/成员统计发送条数，也没有 `45009` 或 `PARTIAL` 的告警阈值。
6. **日配额没有本地守卫。** 500 人上限对应 10 万人次/天/应用，日常量级很难触顶，但一旦异常放量，没有提前阻断手段。

## 5. DMS 处理方案

以下为建议方案，尚未实施。

### 5.1 设计原则

1. **主动节流优先于被动重试。** 按上游计数口径在本地做预算，避免依赖 `45009` 才发现超限。
2. **按不同维度建模。** 应用消息按 `(appId, wecomUserId)` 计人次；群机器人按 `targetId`（webhook）计条数。
3. **区分“接口接受”和“实际送达”。** `ACCEPTED` 只代表企业微信接口返回成功，不代表成员未被静默丢弃。
4. **只对可恢复错误重试。** 限流、网络、超时、token 失效可重试；配置错误、收件人无效、素材非法不重试。
5. **按目标隔离。** 某个群或某个成员被限流时，只延迟该目标，不阻塞其他目标。

### 5.2 应用消息处理

1. **成员级滑动窗口**
   - 以 `(appId, wecomUserId)` 为键，维护 `30 次/60 秒` 和 `1000 次/3600 秒` 两个窗口。
   - 发送前先检查；任一窗口已满，不调用 API，直接把投递的 `nextAttemptAt` 推到最早可用时间，并加少量随机抖动。
   - 这样可以从源头避免“第 31 条被静默丢弃”。

2. **日配额**
   - 初期只监控，不做硬阻断：按应用统计每天发送人次，接近 `账号上限 × 200` 时告警。
   - 若观测到连续 `45009` 且本地成员级窗口未满，优先怀疑日配额或应用级限制，转为熔断并告警，避免 60 秒重试风暴。

3. **重试**
   - `45009`：延迟 60 秒 + 抖动后重试，最多 3 次。
   - 连续多次 `45009`：标记 `FAILED`，记录 `RATE_LIMITED` 并告警，不继续高频重试。
   - `60020`、`81013`、`81014`、`invaliduser`：终态，等待配置或成员关系修复。
   - `40001`、`42001`、`40014`：失效 token 后重试。

4. **调用时间**
   - 非紧急通知尽量避开每小时的 0 分和 30 分；可在派发层加一个可配置的“避开窗口”。

5. **批量发送**
   - 同一内容发给多个成员时，可合并为一次最多 1000 人的调用，减少 API 调用次数。
   - 但人次配额不变，且当前 DMS 的内容按投递渲染，一期不建议为此改造渲染链路。

### 5.3 群机器人处理

1. **webhook 级滑动窗口**
   - 以 `targetId` 为键，维护 `20 条/60 秒` 的滑动窗口。
   - 每次 `webhook/send` 前检查；窗口已满时延迟该投递，不阻塞其他群。
   - 计数必须包含正文、每张图片、文件、语音、图文和模板卡片。

2. **不要用全局 sleep 做节流**
   - 全局 sleep 会让一个繁忙的群拖慢所有群。
   - 推荐“检查目标窗口 → 满则把该投递 `nextAttemptAt` 推后 → 继续处理其他投递”。

3. **批量与合并**
   - 同一群短时间内的多条业务事件，可在发布/派发层合并为一条消息，减少条数。
   - 合并时注意：每条附件都占额度；不要把“1 条通知”误当成“1 条消息”。
   - 如果附件很多，优先保证正文送达，附件失败时明确标记 `PARTIAL`。

4. **重试**
   - `45009`：延迟到下一个可用窗口，建议 60 秒 + 抖动；最多 3 次。
   - `93000`：终态，修正 webhook 后重新投递。
   - 网络、超时、5xx：按现有退避重试。
   - 机器人没有“成员级”概念，`@` 失败不影响消息本身；`mentioned_list` 中的无效 userid 由群成员关系决定，当前无法通过接口校验。

### 5.4 媒体附件处理

1. **应用消息**
   - 保留现有 `media_id` 缓存和 3 天过期重传逻辑。
   - 附件上传/发送遇到 `45009`、网络、超时：应可重试，而不是直接 `FAILED`。
   - `40006`（压缩后仍超限）：终态。
   - `40007`（`media_id` 无效/过期）：清除缓存并重新上传一次；再次失败才终态。
   - 正文已成功、附件最终失败：保持 `PARTIAL`，并记录具体附件失败原因。

2. **群机器人**
   - 继续使用 `base64 + md5`，发送前压缩到 2MB。
   - `45009`、网络、超时：可重试。
   - 压缩后仍超 2MB：终态 `WECOM_MEDIA_TOO_LARGE`。

3. **重试载体**
   - `wecom_delivery_media` 已有 `attempt_count` 和 `next_attempt_at` 字段，但当前附件失败没有使用 `next_attempt_at`。
   - 建议复用这两个字段，把可恢复失败置回 `PENDING` 并设置 `next_attempt_at`，由派发器按时间重试；不要新增表。

### 5.5 目标响应分类

| 场景 | 是否重试 | 目标状态 | 处理要点 |
| --- | --- | --- | --- |
| 正常 `errcode: 0` | 否 | `ACCEPTED` | 记录 `providerMsgId`；不要把它当送达凭证 |
| 成员级限流静默丢弃 | 无法感知 | 仍为 `ACCEPTED` | 只能靠本地 30/分钟、1000/小时预算提前避免 |
| `45009`（正文） | 是，60 秒 + 抖动 | `PENDING` → 成功或 `FAILED` | 最多 3 次；连续失败告警 |
| `45009`（附件） | 建议改为是 | `PENDING` → 成功或 `FAILED` | 复用 `next_attempt_at`；当前是终态 |
| `40001` / `42001` / `40014` | 是 | `PENDING` | 先失效 token，再重试 |
| `81013` / `81014` / `invaliduser` | 否 | `FAILED` | 标记成员关系 `INVALID`，等待人工修复 |
| `60020` | 否 | `FAILED` | 运维补充可信 IP |
| `93000` | 否 | `FAILED` | 管理员修正 webhook |
| `40006` | 否 | `FAILED` | 压缩后仍超限 |
| `40007` | 一次 | `PENDING` | 清除 `media_id` 并重新上传；再次失败才 `FAILED` |
| 网络 / 超时 / 5xx | 是 | `PENDING` | 现有退避即可 |
| 正文成功、附件失败 | 附件按类型判断 | `PARTIAL` | 记录具体附件失败原因，便于补发 |

### 5.6 监控与告警

建议至少采集以下指标：

| 指标 | 维度 | 用途 |
| --- | --- | --- |
| 每分钟发送条数 | `targetId`（webhook） | 发现接近 20 条/分钟 |
| 每分钟发送人次 | `(appId, wecomUserId)` | 发现接近 30 次/分钟 |
| `45009` 次数 | 通道、目标 | 识别限流风暴 |
| 附件失败数 / `PARTIAL` 比例 | 通道、目标 | 识别图片丢失 |
| 投递延迟 | 通道 | 识别节流导致的积压 |
| 日发送人次 | `appId` | 观察是否接近日配额 |

建议告警阈值：

- 单 webhook 达到 15 条/分钟：预警；达到 20 条/分钟：告警。
- 单成员达到 25 次/分钟：预警；达到 30 次/分钟：告警。
- 同一目标连续出现 `45009`：告警并检查节流是否生效。
- `PARTIAL` 比例持续升高：告警并检查附件链路。

日志只记录 `deliveryId`、`targetId`、`appId`、`attempt`、`errcode`、`msgId` 等非敏感字段；不得记录 `access_token`、应用 Secret、webhook key 或完整请求体。

### 5.7 配置建议

| 配置 | 当前默认 | 建议 |
| --- | --- | --- |
| `WECOM_WORKER_BATCH` | 20 | 群机器人占比高时先降到 10 或更低，并按附件数估算；最终以按 webhook 节流为准 |
| `WECOM_WORKER_POLL_MS` | 5000 | 保持；它是轮询间隔，不是发送速率控制 |
| `WECOM_APP_MIN_SEND_INTERVAL_MS` | 1000 | 当前未使用；建议改为按成员滑动窗口，而不是全局间隔 |
| `WECOM_ROBOT_MIN_SEND_INTERVAL_MS` | 3000 | 当前未使用；建议改为按 webhook 滑动窗口，而不是全局间隔 |
| `WECOM_REQUEST_TIMEOUT_MS` | 10000 | 保持 |

### 5.8 分阶段落地

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| P0 | 先按本文口径运营：群播降批、避开整点/半点、监控 `45009` 与 `PARTIAL` | 无代码改动，但限流仍可能发生 |
| P1 | 实现应用成员级窗口、群 webhook 级窗口；限流时延迟目标而不是全局 sleep | 需要新增内存状态与派发逻辑 |
| P2 | 附件 `45009`/网络/超时改为可重试，复用 `next_attempt_at` | 需要调整附件状态机 |
| P3 | 增加指标与告警；按需做同群消息合并 | 需要监控基础设施 |
| P4 | 如需严格日配额，再增加按应用的日人次预算 | 依赖企业账号上限配置 |

## 6. 验证建议

代码实施后至少覆盖：

1. **边界用例**
   - 群机器人第 20 条发送成功，第 21 条被延迟。
   - 应用消息同一成员第 30 条发送成功，第 31 条被延迟。
   - 应用消息第 1000 条/小时成功，第 1001 条被延迟。

2. **响应处理**
   - 正文 `45009`：投递回到 `PENDING`，`nextAttemptAt` 约 60 秒后；不是直接 `FAILED`。
   - 附件 `45009`：附件回到 `PENDING` 并重试，而不是终态。
   - `60020`、`93000`、`40006`：终态且不重试；`40007` 清除 `media_id` 后重新上传一次。
   - `81013` / `invaliduser`：成员关系标记 `INVALID`，投递 `FAILED`。

3. **真实环境**
   - 同一群 1 分钟内发 21 条，观察第 21 条被延迟而不是收到 `45009`。
   - 同一成员 1 分钟内发 31 条，观察第 31 条被延迟。
   - 正文成功、附件限流时，最终状态为 `PARTIAL`，并可通过补发恢复。
