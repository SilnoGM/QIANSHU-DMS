# 媒体存储部署与恢复

本文定义单台 Ubuntu 24.04 Server 的媒体部署合同。部署载体与操作步骤以 [`腾讯云 Docker 部署手册`](../全局文档/腾讯云Docker部署手册.md) 为准：Docker 形态下进程、站点与清理调度由 `deploy/docker/` 资产承担，本文中的 systemd 与 Nginx 模板保留为目录语义、探针合同与未来切换 `internal_redirect` 的参考。仓库中的 Nginx、systemd、环境变量和监控文件均为
模板；把它们写入 `/etc`、创建系统用户或持久目录、安装系统包、重启服务、执行数据库命令或恢复备份，
都属于生产变更，必须先取得独立的生产授权。提交或验证本模板不代表已经部署。

## 1. 固定边界

- 存储驱动由 `MEDIA_STORAGE_DRIVER` 选择，只允许 `local` 与 `cos`：
  - `local`：`assets/`、`trash/`、`staging/` 都在持久 root `/var/lib/qianshu-dms/media` 下。
  - `cos`：`assets/`、`trash/` 在对象存储桶内，**对象键布局与 `local` 完全一致**，因此切换驱动不重算键；
    `staging/` 与 ffprobe/qpdf/sharp 的校验源仍在本地磁盘，`MEDIA_STORAGE_ROOT` 只承担 staging 与容量告警。
- 持久 root 必须位于源码、release、`server/dist` 和系统临时目录之外。
- 约 10GB 媒体规模的目标卷最低 30GB，建议 50GB；`cos` 驱动下该容量只约束 staging 峰值与大文件校验缓存。
- 可用空间低于 20% 为 warning，低于 10% 为 critical。`local` 下 critical 只影响新上传与本地直读；
  `cos` 下 critical 只影响新上传，既有媒体读取经对象存储进行。
- critical 时新建 staging 失败关闭并返回固定 storage 错误；已有 `assets/` 仍必须可读，不能因
  写能力故障停止私有媒体读取。
- 数据库只保存 `storageDriver + objectKey + sizeBytes + checksumSha256`，不保存绝对路径。
- 对象键的布局、业务池划分、敏感分级与共桶环境前缀以
  [`媒体对象存储路径规范`](./媒体对象存储路径规范.md) 为准。该规范的目标布局**尚未实施**：
  实施前键布局仍为 `assets/{YYYY}/{MM}/{assetId}{ext}`，本节的驱动语义、探针合同、备份与恢复边界
  不受其影响。
- `ffprobe` 是 VIDEO 验证的生产依赖，`qpdf` 是 PDF 验证的生产依赖；二者均使用绝对路径且不经 shell。
- `cos` 驱动额外约束：桶与服务器必须**同地域**（内网访问、流量免费、请求次数计费）；桶权限为私有读写；
  凭据来自只授权该桶的 CAM 子账号，只写入 `server.env`（0600），不得进入文档、工单或日志。
- `MEDIA_CONTENT_DELIVERY_MODE` 的 `internal_redirect` 只对 `local` 驱动成立：`cos` 模式下不存在
  可供 Nginx `alias` 直读的本地文件，显式配置两者并存会被启动校验直接拒绝。

## 2. Release 外持久目录与身份

建议使用以下固定身份：Server 用户 `qianshu-dms`，共享只读组 `qianshu-media`，Nginx worker 用户加入
`qianshu-media`。媒体 root 和目录权限为 `0750`，文件权限为 `0640`；共享组只读，不得拥有写权限。
部署人员在获得生产授权后创建并验证：

```bash
sudo install -d -o qianshu-dms -g qianshu-media -m 0750 /var/lib/qianshu-dms/media
sudo install -d -o qianshu-dms -g qianshu-media -m 0750 /var/lib/qianshu-dms/media/staging
sudo install -d -o qianshu-dms -g qianshu-media -m 0750 /var/lib/qianshu-dms/media/assets
sudo install -d -o qianshu-dms -g qianshu-media -m 0750 /var/lib/qianshu-dms/media/trash
```

不得把示例命令当成仓库测试执行，也不得把真实 root 下的文件名、`objectKey` 或用户上传内容粘贴到工单
和日志。

## 3. 环境、Nginx 与 systemd

- 环境模板：`server/deploy/environment/server.env.example`。复制到受限的
  `/etc/qianshu-dms/server.env` 后再通过 Secret 管理流程填写；权限建议 `0600`。不得提交生成的实际文件。
- Nginx 片段：`server/deploy/nginx/qianshu-dms-media.conf`。必须放入已有 `server {}`，并保留
  `internal`、精确 `alias`、`max_ranges 1`、`client_max_body_size 501m` 与
  `proxy_request_buffering off`。不得建立对外可访问的媒体 root、目录索引或 public alias。
  该片段只在 `local` 驱动下有效；`cos` 驱动使用 `application` 交付，不需要也不得保留对外媒体 alias。
- systemd 模板位于 `server/deploy/systemd/`：HTTP Server 使用 `qianshu-dms-server.service`；到期媒体清理
  使用 `qianshu-dms-media-cleanup.service` 与 `qianshu-dms-media-cleanup.timer`。二者的 `WorkingDirectory`
  均指向 release symlink，媒体 root 通过 `ReadWritePaths` 单独开放；release 自身保持只读。
- Server release archive 必须包含整个 `deploy/` 目录，但模板不会被 release pipeline 自动安装。

上线前先用 Nginx 自带配置检查和 systemd 静态检查；只有检查通过且变更窗口获批后才能 reload/restart：

```bash
sudo nginx -t
systemd-analyze verify \
  /etc/systemd/system/qianshu-dms-server.service \
  /etc/systemd/system/qianshu-dms-media-cleanup.service \
  /etc/systemd/system/qianshu-dms-media-cleanup.timer
```

## 4. 双探针健康合同

`GET /api/health` 继续表示 Server 进程与 PostgreSQL 健康，不扩展媒体字段。媒体使用 release 内的独立命令：

```bash
pnpm media:ops:health
```

它只输出固定 JSON 和低基数指标，并分别报告：

| Capability | local 驱动的检查 | cos 驱动的检查 | 失败影响 |
| --- | --- | --- | --- |
| `read` | root、`assets/`、`trash/` 的安全目录与读取权限 | 桶可达（HeadBucket）＋对象级读取链路（HEAD 固定探针键） | 媒体读取告警 |
| `write` | root、`staging/` 写权限与磁盘容量 | 本地 `staging/` 写权限与磁盘容量 **＋** 桶写入探针（PUT 后立即 DELETE） | 新上传失败关闭；读取继续 |
| `video_validator` | 受限执行 `ffprobe -version` | 同左 | VIDEO 上传失败关闭；图片读取不受影响 |

`cos` 模式的写入探针对象位于 `_ops/` 前缀，刻意落在 `assets/`、`staging/`、`trash/` 三个对账命名空间
之外：对账不会把它计入 orphan，也不会污染「零 mismatch」判定；崩溃残留由桶上针对 `_ops/` 的生命周期
规则回收。

systemd 的 `ExecStartPre` 使用同一探针实现 preflight。

**启动语义按驱动分级**：

- `local`：`read` 不可用或命令配置失败会阻止启动；仅 `write` 或 `video_validator` degraded 时仍允许启动。
- `cos`：`read` 依赖外部服务，物理上不存在「读取不可用时保留既有读取」的路径，因此 `read` 不可用
  **不阻止启动**（`preflight` 退出码为 0），但聚合状态为 `degraded`，`health` 仍以非零退出码持续告警。
  这条差异是刻意的：桶侧抖动不应连带阻断与媒体无关的订单、账单与对账业务。

部署验收仍应把缺少 `ffprobe`、桶不可达或桶不可写视为未通过，不能因为允许降级启动而忽略告警。
运行期监控应同时采集 `/api/health` 和媒体 `health` 命令，不得用媒体写能力告警自动摘除仍可提供
既有媒体读取的实例。

## 5. 指标与告警

`server/deploy/monitoring/media-observability.json` 是指标名、类型、固定 Label 集合和阈值的真相源，至少
覆盖容量、staging 最老年龄、FAILED 数量、reconciliation mismatch、上传失败率和清理结果。采集器可把
Server 单行 JSON 转换到现有监控系统，但不得增加 `assetId`、`productId`、`objectKey`、filename、
requestId 或任意用户输入 Label。

容量 critical、读取不可用、对账 mismatch 应为 critical；容量 warning、staging 超过 24 小时、存在
FAILED、上传失败率升高或清理失败为 warning。监控后端的查询语言可以适配，指标名、Label 枚举和阈值
不得静默放宽。

## 6. 到期媒体自动清理

`cleanup-expired-trash` 每轮最多领取 100 条候选并限制在 60 秒内。每条候选都必须满足
`status=TRASHED`、`retentionUntil <= now`，并在持锁后重新确认全部已实现领域引用为零；物理文件位置或
size 不可信时只返回 isolated，不执行删除。成功删除物理文件后只把 `MediaAsset` 转为 `PURGED`，仍保留
`MediaAsset` 和已软解除 `ProductMedia` 的生命周期事实。`PURGED` 文件无法恢复。

`cos` 驱动下的搬运语义：对象存储没有原子 rename，`moveToTrash` / `restoreFromTrash` 采用
「先服务端复制、校验尺寸、再删除源」的顺序。进程在两步之间中断最多留下「assets 与 trash 同时存在」
的重复对象，对账会把它计为 `duplicateLocation` 交由人工处理，不会静默丢失任何一个副本；重新执行
回收动作前必须先消解该重复。
`purge` 对应 DeleteObject，幂等；若桶开启了版本控制，删除只产生删除标记，非当前版本由桶的生命周期
规则清除，`PURGED` 的「不可恢复」语义相应延后到该生命周期到期——启用版本控制时必须同步改写本条。

取得生产授权后，把两个模板安装到 `/etc/systemd/system/`，静态校验通过后启用 timer：

```bash
sudo install -o root -g root -m 0644 \
  server/deploy/systemd/qianshu-dms-media-cleanup.service \
  /etc/systemd/system/qianshu-dms-media-cleanup.service
sudo install -o root -g root -m 0644 \
  server/deploy/systemd/qianshu-dms-media-cleanup.timer \
  /etc/systemd/system/qianshu-dms-media-cleanup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now qianshu-dms-media-cleanup.timer
systemctl list-timers qianshu-dms-media-cleanup.timer
```

timer 使用 `OnCalendar=hourly`，`Persistent=true` 会在主机恢复后补执行错过的周期；oneshot unit 仍在运行时
不会并发启动同名 unit，数据库领取同时使用 `SKIP LOCKED` 和旧状态条件保证幂等。需要受控手工验证时执行：

```bash
sudo systemctl start qianshu-dms-media-cleanup.service
sudo systemctl status qianshu-dms-media-cleanup.service
sudo journalctl -u qianshu-dms-media-cleanup.service --since today
```

输出只包含 scanned/completed/failed/isolated 计数和固定低基数指标。failed 或 isolated 都会令 unit 失败，
必须结合只读 `media:recovery:dry-run` 在新的生产授权下排查；不得绕过引用、位置或 size 检查直接删除。

## 7. 备份合同

- PostgreSQL 与媒体数据可以分别备份，但每一组必须记录同一恢复点标识、UTC 时间、数据库备份摘要、媒体
  备份摘要和 release commit。两者不能从不同恢复点拼接。
- 业务备份包含数据库以及 `assets/`、`trash/`；`staging/` 不作为业务备份，恢复后的超期 UPLOADING 由
  既有状态机处理。`cos` 驱动下这一组对应桶内 `assets/` 与 `trash/` 前缀。
- `cos` 驱动下的媒体备份至少满足其一：开启桶版本控制并记录恢复点时间（按版本回溯），或定期把
  `assets/`、`trash/` 前缀同步到离机桶/前缀后记录同步完成的恢复点；两者都必须能与同一时刻的数据库
  备份配对。不得用「对象存储自带多副本」替代离机备份。
- 至少保留一份加密的离机备份，离开生产单机与其本地磁盘故障域。离机副本的加密密钥不得与备份存放在
  同一位置。
- `local` 驱动切换到 `cos`（或反向）后，**旧驱动一侧的数据在确认稳定前不得删除**；它就是回滚面。
- 备份成功不能只依赖命令退出码；应记录文件总数、总字节数、备份摘要和可读取性验证。记录中不得列出
  真实用户文件名或 objectKey。

## 8. 恢复与只读 dry run

恢复必须在隔离目录或未开放流量的目标机完成，固定顺序如下：

1. 核对同一恢复点和 release commit，先恢复数据库。
2. 恢复 `assets/` 与 `trash/`，不恢复 staging，不开放 Nginx 读取。
   `cos` 驱动下这两组对应桶内同名前缀；恢复目标桶必须与生产桶隔离，验收通过前不切换生产配置。
3. 从 Server release 目录运行只读 dry run：

   ```bash
   pnpm media:recovery:dry-run
   ```

4. 确认 `complete=true` 且 missing、size、checksum、location、orphan 等全部 mismatch 为零。
5. 再运行媒体 health、`/api/health` 与授权 GET/HEAD Range 验收，最后开放读取。

dry run 只读取数据库引用和 `assets/`、`trash/`、`staging/` inventory，并对 READY/TRASHED 的实际字节数
和 SHA-256 逐项校验；inventory 与读取都经过存储驱动，因此 `cos` 下对账的是桶内对象而不是本地目录。
结果只输出计数。它不得删除或修复文件，不得更新数据库，不得打印资产 ID、
objectKey、原始文件名、绝对路径或底层异常。出现任一 mismatch、超时或批次未完成时退出非零，由人工在
新的生产授权下分析；严禁把对账结果直接转成自动删除或自动修复。

## 8.1 上传后校验的强度分级

每个对象在写入后都会校验，但强度按驱动分级，这是经过确认的取舍：

- `local`：回读全文逐字节比对（本地读取没有流量成本）。
- `cos`：HEAD 比对长度 + 上传时写入的 `x-cos-meta-sha256` 对象元数据；**元数据缺失时必须回退为
  回读全文**（例如从本地迁移进来、没有元数据的历史对象），不允许只凭长度放行。
- 全量字节比对始终由只读 `dry run` 承担，它是唯一的强校验关口；`cos` 下这次读取走内网（流量免费、
  请求次数计费）。

代价与收益：`cos` 不再为每次上传回读整份对象（500 MiB 视频的重复下载代价高于收益），换来的是传输层
校验（TLS 与 COS 侧写入校验）加对象元数据比对；若桶侧接受了损坏字节，`dry run` 与对账是发现途径。

切换驱动前后的真实桶验收用 `pnpm -C server media:accept:cos`（需先 `pnpm build` 且具备 `MEDIA_COS_*`）：
它在桶里创建**一个**临时对象，依次验证上传（含元数据）、HEAD 长度/摘要/CRC64、`verifyStoredObject`、
全文与 Range 读取、摘要计算、列举、搬入回收站与复原、删除，并在结束时清理；只输出布尔与计数。
该脚本不进入发布归档，被强杀时可能留下一个孤儿对象（由 `dry run` 的 `orphanObject` 暴露后人工清理）。

## 8.2 存量迁移（驱动切换）

从 `local` 切到 `cos`（或反向评估）必须先迁移存量，且**迁移完成前不允许新写入**：

0. **前置（只做一次）**：确认数据库已应用"放松驱动枚举"的迁移
   （`20261007120000_media_storage_driver_cos_allowed`）。建表时的
   `media_assets_storage_driver_check` 只允许 `local`，未放松前 cos 模式的**新上传会在写库时被拒绝**
   （`23514`，表现为接口 500）；该迁移只扩展枚举，不改列类型、默认值或既有数据。
1. **备份（同一恢复点）**：`pg_dump` + `tar` 打包 `assets/`、`trash/`（跳过 staging），记录 UTC 时间、
   数据库摘要、媒体摘要与 release commit。
2. **停写**：停止 Server 进程/容器；此后不再接受上传。
3. **预览**：`node dist/commands/media-migration.js preview`（容器形态用
   `docker compose run --rm -e MEDIA_STORAGE_DRIVER=cos server node dist/commands/media-migration.js preview`）。
   只读，输出 `scanned`、`skipped` 计数；桶不可达时直接失败退出，不给出误导性工作量。
4. **搬运**：同命令的 `apply`。逐个对象读取本地字节、上传到桶、立即用驱动校验确认；任一对象失败即整轮
   退出非零，本地源对象始终保留；命令幂等，中断后重跑只会按校验结果补齐缺失对象。
   **命令不写数据库**：`media_assets.storage_driver` 记录"物化时的驱动"，被不可变触发器保护
   （`media_assets_content_identity_immutable_check`），迁移不改写它——切换由部署配置决定，
   与运行期分派解耦，因此回滚同样只改配置。
5. **对账**：在 `MEDIA_STORAGE_DRIVER=cos` 下运行只读 `dry run`，要求 `complete=true` 且全部 mismatch 为 0。
   若 `apply` 中途异常退出（只输出固定失败事件、无计数），用"复跑 `preview` 应全部 `skipped`"与
   `dry run` 零 mismatch 判断搬运是否已完成——能走到失败事件之前，通常字节已就位。
6. **启动与验收**：启动服务，确认 `preflight`/`health`、三类媒体上传、预览、Range 读取与
   删除→回收→恢复→清理链路正常。
7. **保留回滚面**：本地 `assets/`、`trash/` 原样保留至少一个保留期或直到首次成功备份，之后才按独立
   生产授权清理。

回滚：把 `MEDIA_STORAGE_DRIVER` 改回 `local` 并重启服务（**不要**改写 `storage_driver` 列，它受不可变
触发器保护且不参与分派）；桶内对象不删除，留作离线副本。回滚只能回到停写窗口之前的状态，窗口内新增的
对象需要单独补回本地。

本节只处理**驱动切换**，不改变对象键。按 [`媒体对象存储路径规范`](./媒体对象存储路径规范.md) 第 6 节
重命名存量对象键是另一件事：它需要受控的数据库改键通道（该节 6.4）、映射表与更长的观察期，实施前
必须在独立的生产授权下单独评审，不得与驱动切换合并执行。

## 9. 回退边界

应用回退只切换 `/opt/qianshu-dms/server/current` 到已验证 release，不回退或覆盖媒体数据。数据库 migration
和媒体恢复各自需要独立回退方案；未经数据库门禁不得运行 migration，未经生产授权不得修改 Nginx、
systemd、用户/组、目录权限、媒体内容、桶配置或备份。任何回退后都必须重新执行双探针、只读对账和
