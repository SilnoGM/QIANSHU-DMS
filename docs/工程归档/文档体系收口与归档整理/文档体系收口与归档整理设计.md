## 2. 背景与问题

项目工程组织、根级治理、Web 边界、Server 初始化、接口契约、CI、Release 和 GitHub 平台配置均已落地，但文档结构仍保留实施期间的平铺形态，存在以下问题：

1. `docs/全局文档/` 同时混放当前指导文档、阶段设计、阶段实施计划和故障修复记录，读者无法快速判断哪一份是当前执行依据。
2. `docs/文档索引.md` 逐篇列出阶段文档，却漏掉四份服务器发布故障文档，不能完整表达现有文档集合。
3. `docs/全局文档/项目工程组织方案.md` 仍含“Task 14 待平台验证”等过期描述，根版本示例仍为 `0.0.0`，目录树尚未包含 `开发工作流.md`。
4. 工程方案中的环境变量描述使用“不读取、复制环境变量”，与当前脚本为执行子进程而受控传递环境的真实行为不完全一致。
5. 已完成的阶段资料如果继续平铺，后续每增加一个分阶段任务或故障复盘都会再次污染全局入口；如果直接删除，又会失去决策过程、时间线和验收证据。

因此需要在不丢失历史的前提下完成一次文档信息架构收口，并用根级治理测试持续约束该结构。

4. 为归档建立根索引、工程归档索引和任务归档说明三层导航。

- 不创建根 pnpm workspace、根 lockfile、根 `node_modules/` 或根第三方依赖。

## 5. 文档分类原则

### 5.1 当前指导文档

满足以下条件的文档属于当前指导文档：

- 描述当前有效的架构边界、日常操作流程或正式发布流程。
- 内容会随工程现状持续维护。
- 新成员应从该文档开始，而不是从某一阶段计划开始。
- 文档中的命令、版本、目录和平台状态必须与仓库当前事实一致。

### 5.2 过程与历史文档

满足以下任一条件的文档应归档：

- 为一次具体任务编写的设计文档或实施计划。
- 记录阶段一至阶段五的落地过程。
- 记录一次具体故障的诊断、修复方案或验证闭环。
- 主要价值是解释“当时为什么这样做、按什么顺序完成、证据是什么”，而不是指导当前日常操作。

### 5.3 以任务为归档主键

归档目录必须以任务名命名，而不是建立通用的“阶段实施”“故障复盘”“设计文档”目录。每个任务目录内部可同时容纳设计、实施计划、阶段资料和归档说明。

这一规则确保：

- 同一任务的上下文、决策、计划和证据彼此相邻。
- 新任务不会继续向一个无限增长的“阶段实施”目录堆积。
- 故障设计和修复计划不会被拆散到不同文档类型目录。
- 工程归档索引可以按任务而不是按文件维护。

## 8. 三层索引设计

### 8.1 第一层：项目文档索引

`docs/文档索引.md` 是当前正式文档的总入口，职责如下：

- 详细列出三份全局指导文档。
- 保留现有前端与后端正式文档入口。
- 只增加一个“工程归档”入口和明确免责声明。
- 不逐篇展开历史设计和实施计划，避免根索引再次退化为过程文件清单。

工程归档入口必须说明：归档内容仅用于历史追溯，不作为当前执行依据。

### 8.2 第二层：工程归档索引

`docs/工程归档/归档索引.md` 每个任务使用一行，至少包含以下字段：

| 字段 | 定义 |
| --- | --- |
| 任务名称 | 对应唯一任务目录 |
| 任务类型 | 分阶段落地、故障修复、文档治理等 |
| 首次产出日期 | 该任务最早文档首次进入 Git 的日期 |
| 完成日期 | 任务达到最终验收的日期 |
| 归档日期 | 从当前入口迁入工程归档或正式完成归档的日期 |
| 最终结果 | 一句话说明交付结果 |
| 归档原因 | 说明为何退出当前指导入口 |
| 当前真相源 | 当前仍生效的正式文档 |
| 归档说明 | 指向任务目录内 `归档说明.md` |

该索引按任务维护，不按单份文档膨胀。未来新增任务目录时，必须同步增加一行。

### 8.3 第三层：任务归档说明

每个任务目录必须包含 `归档说明.md`，并详细记录：

1. 任务背景和目标。
2. 起始、关键节点、完成与归档时间线。
3. 目录内每份文档的阅读顺序。
4. 每份文档的首次产出日期、文档声明日期、用途和所处阶段。
5. 原路径与当前归档路径。
6. 相关 Commit、PR、Actions Run、Release 或其他验收证据。
7. 最终结果和已完成边界。
8. 归档原因。
9. 当前有效真相源及其链接。

## 9. 时间与证据真相源

### 9.1 日期规则

- “首次产出日期”以 Git 首次新增该文件的 Commit 日期为准，使用 `git log --follow --diff-filter=A` 追溯。
- 文档正文若明确声明日期，同时记录为“文档声明日期”；它不能替代 Git 首次产出日期。
- “完成日期”以任务最终验收证据为准。
- “归档日期”以归档变更正式进入 Git 的日期为准。
- 没有可靠证据的字段必须明确说明证据缺失，不得推测或补造日期。

推荐核对命令：

~~~text
git log --follow --diff-filter=A --format='%ad %H %s' --date=short -- <path>
git log --follow --format='%ad %H %s' --date=short -- <path>
~~~

## 12. 链接与历史保留规则

1. 所有现有历史文件使用 `git mv`，以便 `git log --follow` 继续追溯。

## 18. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 迁移后相对链接失效 | 自动遍历全部 Markdown 本地链接，并在完整验证前修复 |
| 文件移动导致历史难以追溯 | 只使用 `git mv`，索引同时记录原路径、当前路径和首次提交 |
| 归档再次变成杂物目录 | 强制一个任务一个目录、每目录一个归档说明、总索引一任务一行 |
| 当前文档继续混入实施历史 | 当前指导文档只保留可重复执行的现行规则，过程证据指向归档 |
| 全局禁词误伤历史正文 | 过期状态检查只扫描当前指导文档，归档正文保留原始语境 |
| 为整理文档顺带扩大工程改动 | 限定只修改 Markdown 与已确认的根治理测试，不触碰产品与 Workflow |
| 日期和证据依赖聊天记忆 | 以 Git、GitHub 和仓库文件重新核对，无法证明的内容明确标注证据缺失 |

本设计的最终判断标准不是“文件看起来整齐”，而是读者能够清楚区分当前规则与历史过程、每份历史资料都可追溯、全部链接可验证，并且该结构能通过自动化治理长期保持。
