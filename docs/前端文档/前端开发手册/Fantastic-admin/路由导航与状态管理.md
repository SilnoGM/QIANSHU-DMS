# 路由导航与状态管理

本文说明正式应用当前如何把 Vue Router、导航菜单和 Pinia Store 串成一条运行链路。应用级开关见[应用配置](./应用配置.md)，身份、权限与保活见[权限保活与国际化](./权限保活与国际化.md)。

## 路由（导航菜单）

上游[《路由（导航菜单）》](https://fantastic-admin.hurui.me/guide/router.md)说明了“路由生成菜单”的模型；本项目没有文件路由，实际装配由以下文件共同完成：

| 文件 | 职责 |
| --- | --- |
| `web/apps/qsmds-arco/src/router/index.ts` | 按 `settings.app.routeMode` 创建 hash 或 HTML5 history，注册守卫与 Router 扩展 |
| `web/apps/qsmds-arco/src/router/routes.ts` | 汇总 `constantRoutes`、`systemRoutes`、`asyncRoutes` |
| `web/apps/qsmds-arco/src/router/modules/*.ts` | 一个文件维护一个路由模块；当前正式导航由运营、财务、采购运输、管理员与系统管理五组业务模块加组件库模块组成，多级菜单文件保留为路由结构参考 |
| `web/apps/qsmds-arco/src/router/guards.ts` | 登录、动态注册、授权子路由、进度条、布局、标题、保活和 iframe 生命周期 |
| `web/apps/qsmds-arco/src/router/extensions.ts` | 扩展 `push`、`replace`、`go`、`back`、`close` 与标签页的联动 |
| `web/apps/qsmds-arco/src/store/modules/app/route.ts` | 前端/后端路由生成、排序、格式化、matcher 与卸载回调 |
| `web/apps/qsmds-arco/src/store/modules/app/menu.ts` | 把已生成路由转换、过滤为主菜单和侧边菜单 |

### 三类路由与启动顺序

`routes.ts` 中三类数据用途不同：

- `constantRoutes` 在 `createRouter()` 时直接注册，目前是各业务历史路径的兼容重定向（`finance-legacy-redirects.ts`、`management-legacy-redirects.ts`）、`/login` 与 `/:all(.*)*`。只有固定路由上的 `meta.whiteList` 才参与免登录判断；兼容重定向只负责换地址，访问权限仍由目标业务路由校验。
- `systemRoutes` 在登录后的首次导航中动态加入，目前承载首页和 `reload`；它们不是业务导航模块。
- `asyncRoutes` 是前端模式下的导航输入，当前装配“千树运营工作台”“财务工作台”“采购运输工作台”“管理员工作台”“系统管理”主导航分组，并在环境策略允许时增加“组件库”分组。管理员工作台与系统管理按职责切分：基础数据、产品管理、用户与角色、收款资料配置归管理员工作台，系统管理下只保留审计日志与应用配置。

登录后的首次导航按以下顺序执行：

1. `guards.ts` 读取账号、设置、偏好、路由、菜单和标签栏 Store。
2. 若 `app.account.auth` 开启则获取权限；若用户偏好有可开放项则恢复偏好。
3. `app.routeBaseOn === 'frontend'` 时调用 `generateRoutesAtFront(asyncRoutes)`；`backend` 时调用 `generateRoutesAtBack()`。
4. route Store 排序路由、转换 `singleMenu`、删除多级中间节点的 `component`，建立 matcher。
5. 守卫调用 `router.addRoute()` 注册业务路由和系统路由，并保存返回的 remove callback 供登出清理。
6. 标签栏开启时恢复持久化数据，最后以 `replace: true` 重新进入原路径。

当前配置来自 `web/apps/qsmds-arco/src/settings.ts`，没有覆盖 `app.routeBaseOn`，因此有效值是默认的 `frontend`。`backend` 分支及 `apiApp.routeList()`/fake route 已存在，但不是当前启用模式，更不是已接入的 Server 路由接口。

### 模块、多级菜单与 meta

真实多级结构可直接参考 `web/apps/qsmds-arco/src/router/modules/multilevel.menu.example.ts`：入口加载 `@/layouts/index.vue`；中间层只保留 `path`、`name`、`meta`、`children`；叶子节点才加载页面组件。`route.ts` 会再次删除中间层 `component`，以配合多级保活。

`web/packages/types/types.ts` 是当前 `RouteMetaRaw` 的类型真相源。常用字段按职责分组如下：

| 目的 | 字段 | 当前运行位置 |
| --- | --- | --- |
| 标题与展示 | `title`、`icon`、`badge`、`sort`、`breadcrumb` | route/menu/tabbar/settings Store 与布局组件 |
| 菜单行为 | `menu`、`activeMenu`、`expand`、`singleMenu`、`query` | `route.ts`、`menu.ts`、菜单组件 |
| 访问筛选 | `auth`、`auths`、`localeAuth`、`whiteList` | `App.vue`、menu Store、守卫；`auths` 本身只描述权限池 |
| 标签与缓存 | `tabPermanent`、`tabMerge`、`keepAlive`、`noKeepAlive` | tabbar/keepAlive Store 与守卫 |
| 页面能力 | `maximize`、`layout`、`copyright` | 守卫和布局组件 |
| 外部内容 | `newWindow`、`link`、`iframe` | 菜单、`views/link.vue`、`views/iframe.vue` |

`meta.menu: false` 只隐藏菜单，不自动禁止访问；`meta.activeMenu` 用于详情页等场景高亮另一个菜单；`meta.auth` 才参与访问判断，而且当前只有开启 `app.account.auth` 后才会实际限制权限。

### 主导航分组的门槛约束

`asyncRoutes` 顶层分组的 `meta.auth` 是 any-of 数组，但它在运行时有两个叠加位置：`route.ts` 会把这个数组覆盖到该分组的每个一级子路由，`App.vue` 又要求 `route.matched` 的每一条都通过校验。**因此顶层分组的 `meta.auth` 就是该工作台的准入集合，它必须与组内业务码彻底分开**；组内一级子模块只声明自己的 any-of 数组用于分组菜单过滤，叶子继续声明精确 `auth`。

历史教训（已修复）：管理员工作台曾用「四个子模块读取权限的并集」（`ADMIN_WORKBENCH_PERMISSIONS`）做门槛，于是并集中的任意一条共享业务码都会放行该工作台——2026-10-15 授予运营与财务 `exchange-rates:read` 后，两个业务角色立即看到并进入了管理员工作台。管理员工作台现已与三个业务工作台同构：`meta.auth` 只声明准入码 `workbench:admin`，业务读码不再参与工作台准入。**在任何顶级分组上用业务读码做门槛，都要先按「该码会不会被组外角色持有」复核一次。**

### 工作台准入码（四个业务区域 + 管理员区域）

业务域权限码会在工作台之间共享：`purchase-orders:payment` 既是运营侧「申请付款」的门槛，也是财务侧「采购付款」的门槛；`purchase-orders:read` 同时服务运营与采运工作台。用共享业务码做分组门槛，一个角色会同时看到多个工作台；反向收紧业务码又会破坏角色在自己工作台内的既有功能。

因此「千树运营工作台」「财务工作台」「采购运输工作台」「管理员工作台」四个分组的 `meta.auth` 只声明**工作台准入码**（`workbench:operations`、`workbench:finance`、`workbench:purchase-transport`、`workbench:admin`，定义在 `router/modules/workbench-access.ts`；前三条由 `20261001180000_workbench_access_permissions` 建入，管理员准入码由 `20261016140000_workbench_admin_permission` 建入）：分组门槛决定工作台本身是否可见、可进入，组内页面继续用业务码收敛（叶子 `meta.auth` 与页面内 `auth()` 都不变）。准入码是必要而非充分条件——只持有它而没有任何组内业务码时，组内模块会被逐个过滤，主导航不显示该工作台。系统管理分组同理收敛到系统专用 `audit:read`（只有内置 `system_admin` 持有）。新增工作台时必须同步服务端权限目录迁移，不能只在前端出现；给角色开通工作台的正确做法是在角色权限里勾选对应准入码，而不是改路由。

接入新分组或迁移页面时按以下顺序核对：顶层分组只声明准入码 → 组内每个一级子模块声明自己的菜单过滤集合 → 每个叶子都有精确 `auth` → 有权限与无权限两类角色的菜单、面包屑、`activeMenu` 高亮和 403 兜底。

历史路径迁移沿用 `finance-legacy-redirects.ts` 的既有范式：在 `constantRoutes` 注册旧地址到新地址的函数式重定向并保留 `query` 与 `hash`，只换地址、不转移权限；`management-route-migration.test.ts` 一类契约测试会用真实 Router 解析旧地址，验证最终命中的路由名、查询参数与目标权限。

### Redirect、外链与 iframe 的当前边界

- 组件库的基础组件和业务组件父路由使用命名 `redirect` 进入首个组件；其他没有 `redirect` 的父路由仍由守卫尝试进入第一个 `menu !== false` 且有权限的子路由。新增显式 redirect 时要使用 Vue Router 的真实路径或命名路由，并验证目标存在。
- `meta.link`、`meta.newWindow` 和 `LinkView` 的实现已存在：菜单会生成外部目标，布局中的 `link.vue` 提供链接确认与复制界面。但当前路由模块没有实际 `link` 项，不能写成产品已有外链菜单。
- `meta.iframe`、`IframeView`、iframe Store 和最大保活数量已实现；值可以是 URL 字符串，或由 query 提供 `iframe`。当前路由模块同样没有 iframe 项。引入时必须评估可信域、`frame-ancestors`/`X-Frame-Options`、消息通信与敏感数据泄露，不能把任意用户输入直接作为 `src`。

### 路由修改与排障

新增业务页面时，优先在 `web/apps/qsmds-arco/src/router/modules/` 创建单一职责模块，再由 `routes.ts` 放入明确的主导航分组；不要把业务路由塞入 `constantRoutes` 或 `systemRoutes`。路由 `name` 与需要保活的页面组件 `name` 都必须唯一。

最小检查顺序：

```bash
pnpm -C web typecheck
pnpm -C web build
```

运行时再用 Vue DevTools/Router 检查 `router.getRoutes()`，用 Pinia 检查 `appRoute.isGenerate`、`appRoute.routesRaw`、`appMenu.allMenus` 和 `appMenu.actived`。如果地址可访问但菜单不显示，依次核对 `meta.menu`、`meta.auth`、`meta.localeAuth` 以及父节点过滤结果；如果刷新后 404，先确认 `routeMode` 与部署服务器对 HTML5 fallback 的配置，不要只改前端路径。

## 全局状态管理

上游[《全局状态管理》](https://fantastic-admin.hurui.me/guide/store.md)建议按模块维护 Pinia Store。正式应用入口 `web/apps/qsmds-arco/src/store/index.ts` 创建唯一 Pinia，并安装 `pinia-plugin-persistedstate`；`main.ts` 在 Router 之前执行 `app.use(pinia)`。

### 框架 Store 责任表

| Store | 唯一 ID | 当前职责 |
| --- | --- | --- |
| `account.ts` | `appAccount` | token/account/avatar、登录状态、权限、多账号、登录/登出/锁屏 |
| `favorites.ts` | `appFavorites` | 从可见菜单生成收藏候选、增删排序、按账号恢复本地或服务端数据 |
| `iframe.ts` | `appIframe` | iframe 打开、关闭、加载状态与最近使用顺序，限制最大保活数 |
| `keepAlive.ts` | `appKeepAlive` | 维护 Vue `<KeepAlive :include>` 使用的组件名列表 |
| `menu.ts` | `appMenu` | 路由转菜单、权限/语言过滤、主菜单激活、侧栏首个深层路径和展开项 |
| `notification.ts` | `appNotification` | 三类通知、未读总数、列表与演示已读状态 |
| `preferences.ts` | `appPreferences` | 判断偏好是否开放、恢复/保存去掉 `app` 的配置差异 |
| `route.ts` | `appRoute` | 前端/后端路由生成、matcher、动态注册所需数据与卸载回调 |
| `settings.ts` | `appSettings` | 合并配置、主题/语言/响应式模式、页面标题、刷新和最大化状态 |
| `tabbar.ts` | `appTabbar` | 标签创建/关闭/固定/排序/标题、Storage 恢复，并联动缓存和 iframe |
| `watermark.ts` | `appWatermark` | 按应用设置、账号与主题创建、更新或销毁水印 |

这些 Store 通过 `web/apps/qsmds-arco/vite/plugins.ts` 的 `autoImport.dirs` 自动导入，不需要在组件中手写 import。自动导入不等于隐式依赖可以无限增长；组件仍应只读取与当前职责相关的 Store。

### 业务 Store 的放置边界

新的业务状态放在 `web/apps/qsmds-arco/src/store/modules/` 下，文件名、`defineStore()` 的唯一 ID 和领域职责保持一致。例如，尚未落库的资源领域 Store 可按 `resource.ts` 采用以下最小结构：

```ts
export const useResourceStore = defineStore(
  'resource',
  () => {
    const selectedId = ref<string>()

    return {
      selectedId,
    }
  },
)
```

这只是 Store 结构示例，不声明任何资源 API 或字段契约。以下边界必须保留：

- `web/apps/qsmds-arco/src/store/modules/app/*` 只维护框架壳状态；业务列表、筛选、表单草稿等不要写入 `appSettings` 或 `appRoute`。
- `web/packages/*` 只承载跨应用可复用的框架能力；带千树 DMS 业务语义的 Store 不上提到共享包。
- 页面私有且生命周期短的状态优先留在组件/composable；只有跨页面共享、需要统一失效或持久化时才进入 Pinia。
- 公共 API 响应仍由 API module 读取和校验，Store 不自行猜测 DTO，也不保存完整 Axios error 或敏感请求体。

### 状态流与调试

典型状态流是“组件触发 action → API module 返回完整 Axios response → Store 从 `res.data` 提取契约字段 → computed 派生布局/菜单 → 组件渲染”。不要让组件、Store 和 interceptor 同时各维护一份相同业务状态。

排障时优先观察：

1. action 是否真正执行，以及是否因 route guard 的空 `catch` 回到重新导航。
2. `settings.ts` 的有效配置与 `preferences.ts` 恢复后的差异是否符合预期。
3. Storage 数据是否按账号和 `VITE_APP_STORAGE_PREFIX` 隔离；不要在截图、日志或 DevTools 导出中暴露 token。
4. 登出后 `permissions`、tabbar、动态路由和菜单激活状态是否按 `logoutCleanStatus()` 清理。

修改 Store 后至少运行 `pnpm -C web typecheck`；涉及框架交互时还应运行 `pnpm -C web build` 并在真实页面验证刷新、登录、登出与窄屏布局。
