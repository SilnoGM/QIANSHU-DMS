# 权限、保活与国际化

身份、路由可见性、页面访问、按钮显示和服务端授权是不同层次；页面保活也不等于标签栏记忆。本册按正式应用当前实现逐层说明，未启用或未配置的能力会明确标出。

## 权限验证

上游[《权限验证》](https://fantastic-admin.hurui.me/guide/auth.md)提供 `meta.auth`、`v-auth`、`AppAuth` 与 `useAppAuth()` 四类入口。本项目的代码入口均存在，但正式应用当前有效配置是 `app.account.auth: false`，因此权限字符串比较不会限制访问或显示。

### 四个必须分开的概念

| 层次 | 当前实现 | 当前状态 |
| --- | --- | --- |
| 身份/登录 | `account.ts` 以 token 非空作为 `isLogin`；Router guard 保护非白名单页面 | 已运行，但当前登录接口为 fake |
| 菜单可见性 | `menu.ts` 用 `useAppAuth().auth()` 和 `useAppLocaleAuth().auth()` 递归过滤 | 代码已运行；权限开关关闭时 `auth()` 恒通过 |
| 路由页面访问 | `App.vue` 对全部 matched route 的 `meta.auth`/`meta.localeAuth` 求交，不通过时渲染 `AppNotAllowed` 403 页面 | 已实现；现有路由模块没有配置 `auth`/`localeAuth` |
| 页面内功能显示 | `v-auth`、`<AppAuth>`、`useAppAuth().auth/authAll` | 已实现；权限开关关闭时不隐藏功能 |

权限数据来自 `web/apps/qsmds-arco/src/api/modules/app.ts` 的 `permission()`，由 `account.ts#getPermissions()` 从 `res.data.permissions` 保存。该调用当前是 `fake: true`，fake route 只为 `admin` 和 `test` 的 token 前缀返回演示权限；这不是 Server 已提供的角色/权限模型。

`web/apps/qsmds-arco/src/composables/app/auth.ts` 的实际语义是：

- 单个字符串传给 `auth()` 时要求存在于 `permissions`。
- 字符串数组传给 `auth()` 时满足任意一个即可。
- 数组传给 `authAll()` 时必须全部满足。
- 空字符串/空数组通过；`app.account.auth` 为 `false` 时所有权限检查通过。

页面内可按真实实现使用：

```vue
<AButton v-auth="'pages.general:browse'">
  浏览通用示例页
</AButton>

<AppAuth :value="['pages.general:browse', 'pages.form:browse']" all>
  <AButton>浏览通用与表单示例页</AButton>
  <template #no-auth>
    <span>无操作权限</span>
  </template>
</AppAuth>
```

示例复用了当前 fake route 已返回的演示权限字符串，只说明组件契约，不代表千树 DMS 的真实业务权限。新增真实权限值、权限 API 或角色数据结构前，必须先获得公共契约确认。

### 安全边界

`v-auth` 的实现只是切换 `el.style.display`，`AppAuth` 只是条件渲染，菜单过滤与 403 页面也都运行在用户可修改的浏览器里。它们用于体验和误操作防护，不是安全控制。Server 必须从可信身份重新鉴权每个接口，不能因为按钮隐藏或路由不可见便放过写操作。

当前 token 存在 `localStorage`，因此还要把 XSS 防护、CSP、第三方脚本和日志脱敏视为认证边界的一部分。不要把 token、完整 permissions 或敏感请求体写入调试日志。

### 启用前的验证路径

1. 先确认真实 permission API、错误结构和权限命名，再替换 fake 调用。
2. 为匿名、普通用户、具有任一权限、具有全部权限分别验证菜单、直达 URL、按钮和 Server 响应。
3. 复用 `web/apps/qsmds-arco/test/api/fake-routes.test.ts` 的裸 DTO 约定，并为真实契约补充 API 测试。
4. 运行：

```bash
pnpm -C web test:api
pnpm -C web typecheck
pnpm -C web build
```

5. 在浏览器中直接输入受限 URL，确认 `AppNotAllowed` 与返回首页行为；再绕过 UI 发起请求，确认 Server 仍拒绝无权限操作。

## 页面保活

上游[《页面保活》](https://fantastic-admin.hurui.me/guide/keep-alive.md)的前提在本项目同样成立：被缓存的页面组件必须通过 `defineOptions({ name: '...' })` 提供唯一组件名。当前 `web/apps/qsmds-arco/src/router/modules/*.ts` 没有配置 `meta.keepAlive`，所以正式路由尚未启用页面缓存策略。

### 当前实现链路

1. `web/apps/qsmds-arco/src/router/guards.ts#setupKeepAlive` 在导航完成后读取目标叶子组件名。
2. `meta.keepAlive: true` 表示持续保活；字符串或字符串数组表示只有从指定 route name 进入时才保活。
3. `meta.noKeepAlive` 可按离开来源 route name 清除缓存；从 `reload` 路由返回也会先清除。
4. `web/apps/qsmds-arco/src/store/modules/app/keepAlive.ts` 维护唯一组件名列表。
5. `web/apps/qsmds-arco/src/layouts/index.vue` 将列表传给 `<KeepAlive :include="appKeepAliveStore.list">`。

例如，业务路由真正需要从列表进入详情再返回时，才为列表页配置 `keepAlive`，同时让 route name 和页面组件 name 可追踪。不要为了“页面快一些”给所有页面设置 `true`；未释放的表格、订阅、表单草稿和大对象会持续占用内存。

iframe 走独立链路：`setupIframeCache()` 与 `appIframe` Store 按 `meta.iframe`、`keepAlive/noKeepAlive` 和 `page.iframeKeepAliveMax` 开关 item，不进入 Vue `<KeepAlive>`。关闭标签页时，`appTabbar` 会同步删除组件缓存或关闭 iframe。

开发环境发现组件缺少 name 时，guard 会调用 `virtual:fantastic-admin/turbo-console` 的提示函数；只有启用 Turbo Console 时它才提供可点击定位，否则 bridge 是空实现。因此不能把“没有控制台警告”当成组件名正确的证明。

### 保活验收

- 从允许来源进入后返回，筛选条件、滚动位置或草稿按设计保留。
- 从不允许来源进入、执行页面 reload、关闭对应 tab、登出后，缓存按设计清除。
- 多级路由中间节点不设置页面组件；叶子 route name、组件 name 和 tab merge 规则不冲突。
- iframe 缓存数量不超过 `page.iframeKeepAliveMax`，被淘汰项重新进入时显示 loading。
- 用 Vue DevTools 观察组件激活/失活与 Pinia `appKeepAlive.list`，同时检查内存和未清理订阅。

## 国际化

上游[《国际化》](https://fantastic-admin.hurui.me/guide/i18n.md)涵盖语言包、路由、单页组件、Header 与 RTL。正式应用已安装 i18n 运行时，但工具栏语言切换默认关闭。

### 当前语言链路

| 环节 | 当前实现 |
| --- | --- |
| Vue I18n | `web/apps/qsmds-arco/src/locales/index.ts` 使用 `legacy: false`、`flatJson: true`、`fallbackLocale: 'zh-cn'` |
| 消息收集 | `web/apps/qsmds-arco/vite/plugins.ts` 同时收集 `@fantastic-admin/locales` 与 `src/locales/lang/**/*` |
| 路由语言包 | `web/apps/qsmds-arco/src/locales/lang/route/zh-cn.json`、`zh-tw.json`、`en.json` |
| 单页语言包 | `web/apps/qsmds-arco/src/views/index.vue`、`web/apps/qsmds-arco/src/views/[...all].vue` 已使用 `<i18n>` custom block |
| 当前语言 | `appSettings.lang` 读取 `toolbar.i18n.defaultLang`；空值时匹配浏览器语言，否则回退 `zh-cn` |
| 方向 | `localesInfo` 提供 direction，Store 把 `dir` 写入 `<html>` |
| Arco | `web/apps/qsmds-arco/src/ui/provider/index.vue` 把 `zh-cn`、`zh-tw`、`en` 映射给 `AConfigProvider` |
| HTTP | API Client 每次请求设置当前 `Accept-Language` |

路由文件中的 `$t()` 只原样返回 key，目的是让路由 meta 保留稳定 i18n key；真正渲染时由 `useAppMenu().generateI18nTitle()` 用全局 `te/t` 查找翻译。不要在 `routes.ts` 模块加载时调用运行时翻译并固化结果。

当前 `toolbar.i18n.enable` 为 `false`，因此工具栏不显示语言选择器，但页面、路由与 Arco Provider 仍具备多语言运行链路。新增语言时要同时补充应用消息、route JSON、`web/apps/qsmds-arco/src/ui/provider/index.ts` 的 Arco locale；若 Arco 没有对应语言包，需要明确 fallback，而不是传入 `undefined` 后假设组件已翻译。

`meta.localeAuth` 是按当前语言限制页面/菜单的可选能力，不是用户权限，更不是数据合规策略。现有路由没有使用该字段。涉及区域数据访问时，Server 仍需根据可信业务规则判断，不能依靠浏览器语言。

验证国际化时至少切换 `zh-cn`、`zh-tw`、`en`，检查路由标题、页面文案、Arco 组件、日期 locale、`Accept-Language`、RTL 布局和缺失 key；同时运行 `pnpm -C web lint:eslint` 捕获应用/共享语言包问题。

## 快捷键

上游[《快捷键》](https://fantastic-admin.hurui.me/guide/hotkeys.md)展示 registry 与业务扩展模式。本地实现已经拆成共享 registry 与应用扩展层，路径与官网示例不同：

- 框架定义：`web/packages/hotkeys/src/registry.ts`。
- 绑定/解绑与开发期一致性检查：`web/packages/hotkeys/src/createHotkeys.ts`。
- 正式应用装配：`web/apps/qsmds-arco/src/hotkeys/index.ts`。
- 业务扩展：`web/apps/qsmds-arco/src/hotkeys/extend.ts`；当前 `EXT_HOTKEY_ID` 和两组 binding 均为空。
- 帮助弹窗：`web/apps/qsmds-arco/src/layouts/components/Hotkeys/index.vue`。

当前配置下可见的主要全局能力包括 `Ctrl/⌘+I` 系统信息、`Ctrl/⌘+K` 菜单搜索，以及由 `page.hotkeys: true` 开启的页面最大化/恢复；菜单热键因 `menu.hotkeys: false` 关闭，标签热键因标签栏和 `tabbar.hotkeys` 均关闭。`F5` 由布局注册为框架页面 reload，但 registry 没有为它提供帮助项。

业务扩展必须在 `extend.ts` 声明唯一 ID、keys、enabled/help 元数据，再在对应组件用 `useHotkey()` 或 `useHotkeyBindings()` 注册 handler。局部弹窗用 `active` 控制生命周期；不要在组件中直接调用 `hotkeys-js`，也不要覆盖浏览器/辅助技术的关键组合键。新增后验证输入框焦点、组合键冲突、Mac/Windows 展示和组件卸载后的解绑。

## 私有 Storage 数据

上游[《私有 Storage 数据》](https://fantastic-admin.hurui.me/guide/storage.md)用前缀避免同源多应用 key 冲突。本项目在 `web/apps/qsmds-arco/src/main.ts` 启动时导入 `web/apps/qsmds-arco/src/utils/storage.ts`，用 Proxy 替换 `window.localStorage` 和 `window.sessionStorage`：

- `getItem/setItem/removeItem/has` 自动拼接 `VITE_APP_STORAGE_PREFIX`。
- `key(index)` 返回去掉前缀后的 key。
- `length` 只统计当前前缀的数据。
- `clear()` 只删除当前前缀的数据，不清理同源其他应用。

三套安全示例文件当前都设置 `VITE_APP_STORAGE_PREFIX=qianshu-dms`。这只是公开命名空间，不是密钥；生产环境可以使用同样的公开前缀，但真实 `.env` 仍不得提交。

当前业务壳使用的逻辑 key 包括：

| Storage | key | 内容 |
| --- | --- | --- |
| `localStorage` | `token`、`account`、`avatar` | 当前账号状态 |
| `localStorage` | `login_account` | 用户主动选择的“记住账号”，不存密码 |
| `localStorage` | `preferences`、`favoritesData`、`tabbarPinData` | 按账号保存的偏好、收藏和固定标签 |
| `localStorage` | `tabbarScrollTip` | 标签栏滚动提示状态 |
| `sessionStorage` | `tabbarTempData` | `tabbar.memory` 开启时的临时标签 |
| `sessionStorage` | `errorLog` | `app.errorLog` 开启后的前端错误记录 |

`pinia-plugin-persistedstate` 还会持久化 `appAccount.multipleAccounts`。所有这些值都可被同源 JavaScript 读取和修改；前缀不加密、不防 XSS、也不建立账号安全边界。敏感身份应由 Server 校验，错误日志不得记录 token、密码、Cookie 或完整敏感 payload。改变前缀会让旧数据不可见，应作为有迁移影响的发布变更验证登录、登出和清理行为。
