# 服务器发布打包故障诊断与修复设计

## 1. 背景

`v0.1.1` 的 Release Run `29303611007` 已完成全部验证 Job 和 Web 打包，但 `package-server` Job `86992756386` 在 `Package Server` step 中退出 `1`。随后 `manifest` 与 `publish` 被跳过，因此没有创建 Draft 或 Published GitHub Release，也没有 Server 或 final artifact。

现有日志只能看到：

```text
.../node_modules/prisma preinstall: Done
Release package failed
Process completed with exit code 1.
```

当前实现会把 `pnpm deploy`、开发文件清理、发布树校验、GNU tar 创建、archive 检查、digest 读取和 cleanup 的错误统一收敛为 `Release package failed`。失败路径还会删除 staging 与半成品 archive，因此无法从既有 GitHub 日志恢复底层异常。

本地已使用真实 `pnpm deploy`、GNU tar 和 archive inspector 完整复现成功。该结果证明现有参数或 inspector 并非在所有环境中必然失败，但不能替代 GitHub-hosted Ubuntu 24.04 x64 的真实验证。

## 2. 目标

本次修复必须同时达到以下目标：

1. 在不泄露参数、路径、环境变量、连接字符串或底层异常正文的前提下，稳定标识 Server packaging 的失败阶段。
2. 在普通 PR 和 `main` CI 中真实运行 `pnpm deploy → prune → validate → GNU tar → inspect`，把发布时才出现的环境集成问题前移。
3. 通过同一个 Ubuntu 24.04 x64 CI step 取得失败阶段证据，再针对证实的根因做最小修复。
4. 保持现有发布安全边界、cleanup 首错语义和 `v0.1.1` Tag 不变。

## 3. 非目标

本次不处理以下事项：

- 不移动、删除或复用 `v0.1.1` Tag。
- 不创建、修改或发布 GitHub Release。
- 不修改产品版本、公共 API、数据结构、数据库 schema 或 migration。
- 不把 Server smoke test 和 PostgreSQL 生命周期加入每个 PR。
- 不扩展根依赖域，不创建根 workspace、lockfile 或 `node_modules/`。
- 不重构与发布打包故障无关的代码。

## 4. 方案比较

### 4.1 方案 A：现有 Server CI Job 增加真实打包并提供白名单阶段错误码

在 `server-check-build` 已完成 frozen install、check 和 build 后，直接调用现有 `release:package:server`。归档只写入 `$RUNNER_TEMP`，不上传、不发布。`release-package.mjs` 通过专用阶段错误类型对失败进行固定分类。

优点：

- 覆盖真实 CLI、真实 `pnpm deploy`、真实 GNU tar 与 inspector。
- 复用既有 Job，预计只增加约 26 秒，不增加 Required Job 数量。
- 失败阶段可长期观察，能够防止同类发布回归。

代价：

- 普通 PR 和 `main` CI 会多执行一次 Server archive 构建。

结论：采用。

### 4.2 方案 B：新增独立 integration test 或独立 Job

独立测试可以直接调用 `packageServer()` 并获得更细的异常对象；独立 Job 可以让 packaging 成为单独的 Required Check。

优点是隔离性强，缺点是需要重复 checkout、setup、install 和 build，或者增加仅为测试服务的代码入口。当前问题不需要新的 Required Job，因此暂不采用。

### 4.3 方案 C：只增强 Release 日志并使用下一个 Tag 探测

该方案改动最少，但仍然要到正式 Tag 发布时才首次运行真实链路。如果第一次探测仍失败，会继续消耗版本号且无法在 PR 内完成红绿闭环，因此不采用。

## 5. 错误分类设计

### 5.1 专用错误边界

`release-package.mjs` 内部新增专用阶段错误。它只接受代码中声明的固定白名单 code，并通过 `cause` 保存原始错误供测试和进程内判断使用。

候选阶段 code：

```text
RELEASE_PACKAGE_OUTPUT_PREPARE_FAILED
RELEASE_PACKAGE_STAGE_CREATE_FAILED
RELEASE_PACKAGE_SERVER_DEPLOY_FAILED
RELEASE_PACKAGE_SERVER_PRUNE_FAILED
RELEASE_PACKAGE_STAGE_VALIDATE_FAILED
RELEASE_PACKAGE_ARCHIVE_CREATE_FAILED
RELEASE_PACKAGE_ARCHIVE_INSPECT_FAILED
RELEASE_PACKAGE_ARCHIVE_DIGEST_FAILED
RELEASE_PACKAGE_STAGE_CLEANUP_FAILED
RELEASE_PACKAGE_UNKNOWN_FAILED
```

最终实现可在不降低诊断精度的前提下合并无法独立注入和验证的阶段，但不得使用任意底层 `error.code` 作为公开输出。

### 5.2 CLI 输出

CLI 只输出单行固定文本：

```text
Release package failed [code=RELEASE_PACKAGE_ARCHIVE_INSPECT_FAILED]
```

约束如下：

- 不输出 `cause.message`、stack、argv、env 或绝对路径。
- 只有内部专用阶段错误可以提供白名单 code。
- 任意未知错误或伪造对象统一降级为 `RELEASE_PACKAGE_UNKNOWN_FAILED`。
- `CommandExecutionError` 的合法非零 exit code 继续向上传播；其他阶段使用 exit code `1`。

### 5.3 Cleanup 首错语义

现有语义保持不变：

1. 主流程已有错误时，staging 或 archive cleanup 错误不得覆盖主错误阶段。
2. 主流程成功但 staging cleanup 失败时，archive 必须删除，并报告 `RELEASE_PACKAGE_STAGE_CLEANUP_FAILED`。
3. 删除半成品 archive 或本次创建的 output directory 再次失败时，不得覆盖更早的错误。

## 6. CI 集成设计

在 `.github/workflows/ci.yml` 的 `server-check-build` 中，将真实打包 step 放在 `Verify Server entrypoint` 之后、`Verify tracked files are unchanged` 之前。

目标结构：

```yaml
- name: Package Server release archive
  if: inputs.release_tag == ''
  run: |
    package_tag="v$(node -p 'require("./package.json").version')"
    output="$RUNNER_TEMP/release-server-ci"
    node --run release:package:server -- \
      --tag "$package_tag" \
      --output "$output"
    archive="$output/qsmds-server-${package_tag}-linux-x64.tar.gz"
    test -f "$archive"
    test ! -L "$archive"
    test -s "$archive"
```

设计约束：

- Tag 从根 `package.json.version` 动态生成，不增加硬编码版本。
- `inputs.release_tag == ''` 时才执行；正式 Release 复用 CI 时传入 Tag，因此跳过该重复打包。
- 不调用 `release:check`，因为 PR checkout 不具备 annotated Release Tag。
- 不上传 Actions artifact，不设置 `contents: write`，不增加 secret。
- 不运行 `release:smoke:server`；runtime smoke 仍属于正式 Release Job。
- 不修改 `ci-gate` 的五 Job 结构和成功判定。

## 7. TDD 与证据闭环

### 7.1 第一轮 RED：安全阶段诊断

先在 `scripts/release-package.test.mjs` 中加入失败测试：

- 注入 deploy、prune、validate、tar、inspect、digest 与 cleanup 失败。
- 断言固定 code、原始 cause 身份和 exit code。
- 在 cause 中放入 token、连接字符串和路径 canary，断言 stderr 完全不包含这些内容。
- 伪造任意 `error.code` 时必须降级为 `UNKNOWN`。
- 主错误与 cleanup 同时失败时必须保留主阶段。

测试必须先因当前实现缺少阶段分类而失败，再实施最小代码使其转绿。

### 7.2 第二轮 RED：真实 PR CI packaging

先更新 `scripts/ci-workflows.test.mjs`，要求 `server-check-build` 包含固定顺序和安全约束；确认当前 Workflow 因缺少 step 而失败，再修改 `.github/workflows/ci.yml` 使测试转绿。

推送 Draft PR 后，GitHub-hosted Ubuntu 24.04 x64 会首次在 PR 中真实运行 packaging。若该 step 失败，白名单 code 必须给出精确阶段。

### 7.3 根因修复

只有取得真实 CI 阶段证据后才允许修改对应逻辑：

1. 为已证实的触发条件增加最小失败测试。
2. 只修改该阶段的根因。
3. 运行局部测试、完整根测试、Server check/build。
4. 推送同一 PR，要求同一个真实 packaging step 转绿。

不得基于概率猜改 prune、tar、archive limit 或依赖内容。

## 8. 验收标准

满足以下全部条件才可进入合并评估：

- 阶段诊断测试经历可证明的 RED → GREEN。
- Workflow source test 经历可证明的 RED → GREEN。
- CLI 只输出固定白名单 code，不泄露测试 canary。
- cleanup 首错与 archive 删除语义保持不变。
- 普通 PR 的 Ubuntu 24.04 x64 真实 Server packaging 成功。
- Release workflow_call 不重复执行 PR packaging step。
- `node --test scripts/release-package.test.mjs scripts/ci-workflows.test.mjs` 通过。
- `node --run test:root`、`pnpm -C server check`、`pnpm -C server build` 通过。
- `git diff --check` 通过，工作树没有意外 tracked 变更。
- 没有修改或复用 `v0.1.1`，没有创建 GitHub Release。
