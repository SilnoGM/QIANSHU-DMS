# 服务器发布归档硬链接根因修复设计

## 1. 背景

Draft PR `#6` 在 GitHub-hosted Ubuntu 24.04 x64 上执行真实 Server
packaging 后，`Server check and build` Job `87008346584` 的
`Package Server release archive` step 失败。该 step 从
`2026-07-14T05:36:42Z` 运行至 `2026-07-14T05:37:08Z`，稳定输出：

```text
Release package failed [code=RELEASE_PACKAGE_ARCHIVE_INSPECT_FAILED]
```

对应证据如下：

- Actions Run：`29308944673`
- Job：`87008346584`
- Commit：`327fb7ac24565355401f7609a1060aa8f4bf7bdf`
- 失败阶段：`RELEASE_PACKAGE_ARCHIVE_INSPECT_FAILED`
- Step 耗时：`26` 秒

该结果证明 `pnpm deploy`、development artifact prune、release tree
validation 和 GNU tar archive creation 已完成，失败只发生在 archive
inspector。

## 2. 根因证据

在与 CI 对齐的 `linux/amd64` 容器中使用 Node.js `24.16.0`、pnpm
`11.9.0` 和当前提交执行完整 Server packaging，底层 inspector 断言为：

```text
Tar member type is unsupported
```

保留该受控诊断 archive 并逐个读取 POSIX tar header 后，得到以下 member
统计：

```text
tar-bytes=370728960
type-counts={"0":15300,"1":1208,"2":628,"5":2198,"x":15215}
```

其中 `1208` 个 type `1` 是 POSIX tar hardlink member。Linux 上 `pnpm
deploy` 会利用 content-addressable store 与目标目录之间的硬链接复用文件；GNU
tar 默认保留这种 inode 关系，因此把后续同 inode 路径编码为 type `1`。当前
inspector 只接受 regular file、directory、受约束的 Server symlink 和 PAX
extended header，并按既有安全设计拒绝 hardlink。

此前 macOS arm64 本地验证成功，是因为本地文件系统与 pnpm import method
没有生成相同的 Linux hardlink tree。它不能证明 Ubuntu x64 archive 与
inspector 兼容。

## 3. 目标

本次修复必须同时满足以下目标：

1. 让 GNU tar 在创建 archive 时把 filesystem hardlink 的每个路径写为独立
   regular file member。
2. 保持 inspector 对输入 archive 中 type `1` hardlink 的拒绝策略不变。
3. 保持 symlink、portable path、PAX、checksum、metadata、size limit 和
   cleanup 安全规则不变。
4. 在普通 PR 的 Ubuntu 24.04 x64 CI 中完成真实 Server packaging。
5. 不修改版本、Tag、Release、公共 API、数据结构或数据库 schema。

## 4. 非目标

本次不处理以下事项：

- 不让 inspector 接受或提取 hardlink member。
- 不使用 `--dereference` 跟随 symlink。
- 不增加 archive input/output limit。
- 不改变 `pnpm deploy` 的 store、import method 或依赖布局。
- 不增加 staging tree 的第二次复制。
- 不修改 Web/Server 构建内容或运行时依赖。
- 不移动、删除或复用 `v0.1.1` Tag，不创建 GitHub Release。

## 5. 方案比较

### 5.1 方案 A：GNU tar 使用 `--hard-dereference`

在共享的 archive creation argv 中加入：

```text
--hard-dereference
```

GNU tar 会读取 hardlink 指向的文件内容，并为 archive 中的每个路径写入
regular file，而不是 type `1` member。该选项不同于 `--dereference`，不会
跟随 symlink。

优点：

- 只需修改一个 tar argv 项。
- 不扩大 inspector 或 extractor 的输入能力。
- 消除 pnpm import method 和 filesystem inode 行为造成的环境差异。
- Web 与 Server 共用同一个“archive 不得包含 hardlink”创建契约。

代价：

- 同 inode 文件会在未压缩 tar stream 中分别保存，archive 可能增大。

结论：采用。

### 5.2 方案 B：inspector 接受 hardlink

该方案需要验证 hardlink target 的路径、类型、声明顺序、ancestor、重复路径和
extractor 行为，并扩大不可信 archive 的攻击面。它与现有“提取前拒绝
hardlink”的安全边界冲突，因此不采用。

### 5.3 方案 C：archive creation 前复制 staging tree

第二次复制可以打断 inode 关系，但会增加磁盘占用、I/O、文件身份检查和清理
路径。GNU tar 已提供直接表达目标语义的参数，因此不采用。

## 6. 最终设计

### 6.1 Archive creation

`scripts/release-package.mjs` 中的 `tarArguments()` 保持现有参数顺序，并在
top-level directory 参数之前加入 `--hard-dereference`：

```text
--create
--gzip
--file <archive>
--sort=name
--mtime=@0
--owner=0
--group=0
--numeric-owner
--format=posix
--pax-option=delete=atime,delete=ctime
--hard-dereference
<top-level-directory>
```

该函数同时服务 Web 与 Server。统一加入该参数可保证 archive creator 与
inspector 对两类 artifact 使用同一契约：filesystem hardlink 必须序列化为
regular file，symlink 继续保留为 symlink。

### 6.2 Inspector 与 extractor

`inspectTarGzipArchive()` 不做修改，继续拒绝 type `1` 和其他未明确允许的
member type。Server smoke extraction 参数也不做修改，因为修复发生在可信
archive creation 边界，提取端仍保持 fail-closed。

### 6.3 Determinism

`--sort=name`、`--mtime=@0`、固定 owner/group、numeric owner、POSIX format
和 PAX metadata 删除规则保持不变。展开 hardlink 后，相同路径读取相同文件
字节；archive 不再依赖 pnpm 是否选择 hardlink、clone 或 copy，因此跨环境的
结构契约更稳定。

不同文件系统上的压缩结果是否逐字节一致不作为新增承诺；现有同环境双次构建
确定性测试继续保留。

### 6.4 Size limit

方案 A 已在完整 `linux/amd64` Server tree 上验证，结果为：

```text
archive-bytes=102330004
tar-bytes=388700160
type-counts={"0":16508,"2":628,"5":2198,"x":15186}
```

压缩 archive 低于 `256 MiB` input limit，解压 tar stream 低于 `512 MiB`
output limit，且 type `1` 已归零。未来依赖增长若超过现有边界，inspector 仍应
按当前限制失败；本次不得为规避 size failure 提高上限。

## 7. TDD 设计

### 7.1 RED

先修改 `scripts/release-package.test.mjs`：

1. Web exact GNU tar argv 必须包含 `--hard-dereference`。
2. Server packaging 必须找到 tar call，并断言 top-level directory 前紧邻
   `--hard-dereference`。
3. 现有 inspector hardlink attack fixture 必须继续断言拒绝 type `1`。

当前实现缺少该参数，因此前两项必须失败；第三项必须保持通过，以证明 RED
不是通过放宽 inspector 获得。

### 7.2 GREEN

只在 `tarArguments()` 中加入一个 `--hard-dereference` argv 项，不新增分支、
配置或兼容逻辑。局部测试转绿后，不对 inspector、extractor、limit 或 cleanup
做任何修改。

### 7.3 Integration evidence

单元测试使用现有 fake runner 固定命令契约；真实语义由两层 Linux 证据覆盖：

1. 本地 `linux/amd64` 容器执行 frozen install、Server build 和完整
   `packageServer()`。
2. Draft PR 的 Ubuntu 24.04 x64 `Package Server release archive` step。

真实验证必须确认 packaging 成功，而不只是 tar 命令退出 `0`。

## 8. 验收标准

满足以下全部条件才可声明根因修复完成：

- 根因专属测试经历可证明的 RED → GREEN。
- `tarArguments()` 包含且只新增 `--hard-dereference` 语义。
- inspector 仍拒绝 type `1` hardlink fixture。
- `linux/amd64` 完整 Server archive 通过 inspector 和 digest。
- 实际 archive 中不存在 type `1` member。
- archive input/output 均未超过现有限制。
- Root、Server、Contract、Web 的完整 check/build 通过。
- Draft PR `#6` 的 Ubuntu 24.04 x64 required checks 全部通过。
- 工作树无意外文件，未修改版本、Tag、Release、API 或数据库。
