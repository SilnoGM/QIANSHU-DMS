## 2. 产品版本与准备

千树 DMS 产品版本使用三个物理镜像：

| 位置 | 含义 |
| --- | --- |
| `package.json.version` | 单 Git 仓库的统一产品版本 |
| `server/package.json.version` | Server 产品版本，也是 OpenAPI `info.version` 的生成来源 |
| `web/apps/qsmds-arco/package.json.version` | 正式 Web app 的产品版本 |

`web/package.json.version = 6.3.0` 是 Fantastic Admin 上游基座版本，不是千树 DMS 产品版本，不参与 Release 一致性校验，也不能随产品版本更新。

版本准备还要求 `server/openapi/openapi.json` 与 `web/openapi/openapi.json` 的 `info.version` 等于上述产品版本，且两份 snapshot 原始字节一致。修改公共 OpenAPI version、三个产品 version 或正式 snapshot 属于公共契约或数据结构变更，执行前必须单独确认。

取得确认后按以下顺序准备版本：

1. 从最新 `origin/main` 创建独立版本准备分支。
2. 将三个产品 version 改为同一个严格稳定 SemVer；不要修改 Web 基座版本。
3. 通过根入口 `contract:sync` 运行 `node --run contract:sync`，由 Server 定义真相源生成并同步两份 snapshot 与 Web types。
4. 运行 `node --run check` 和 `node --run build`，确认两端与契约完整通过。
5. 只暂存三个产品 manifest、两份 OpenAPI snapshot 与发布文案文件 `release/notes/vX.Y.Z.md`；出现 lockfile、源码或其他文件时停止审计。
6. 创建独立版本准备 Commit，经 PR 合并到 `main` 后才能创建正式 Tag。

可以使用以下守卫校验输入版本；它只验证变量，不修改任何文件：

```bash
set -euo pipefail
: "${RELEASE_VERSION:?RELEASE_VERSION must be an approved stable version}"
export RELEASE_VERSION
node -e "if(!/^(0|[1-9]\\d*)\\.(0|[1-9]\\d*)\\.(0|[1-9]\\d*)$/.test(process.env.RELEASE_VERSION)) process.exit(1)"
```

## 3. Annotated Tag

正式 Release 只接受严格 `vX.Y.Z` annotated Tag。Tag 必须直接指向已经合并到远端 `main` 的精确 Commit；lightweight Tag、递归 Tag、prerelease、build metadata 或不可从 `origin/main` 到达的 Commit 都会被拒绝。

以下命令包含 Git push 外部写入，只能在版本准备 PR 已合并、工作树干净且用户已单独授权后执行：

```bash
set -euo pipefail
: "${RELEASE_VERSION:?RELEASE_VERSION must be an approved stable version}"
: "${RELEASE_NOTES:?RELEASE_NOTES must point to the prepared release notes file}"
export RELEASE_VERSION
node -e "if(!/^(0|[1-9]\\d*)\\.(0|[1-9]\\d*)\\.(0|[1-9]\\d*)$/.test(process.env.RELEASE_VERSION)) process.exit(1)"
test -s "$RELEASE_NOTES"
test -z "$(git status --porcelain)"
git switch main
git fetch origin main --tags
git merge --ff-only origin/main
source_commit="$(git rev-parse refs/remotes/origin/main)"
test "$source_commit" = "$(git rev-parse HEAD)"
git tag -a "v${RELEASE_VERSION}" "$source_commit" -F "$RELEASE_NOTES"
test "$(git cat-file -t "refs/tags/v${RELEASE_VERSION}")" = tag
test "$(git rev-parse "v${RELEASE_VERSION}^{commit}")" = "$source_commit"
node --run release:check -- --tag "v${RELEASE_VERSION}" --source-commit "$source_commit"
git push origin "v${RELEASE_VERSION}"
```

annotated Tag 的 message 承载 **Tag 文案（技术视角）**，面向开发者与运维：变更范围（相对上一个 Tag）、主要改动点与涉及模块，可含关键提交摘要，允许技术名词。message 不得为空。模板与撰写要求见[发布与部署流程](./发布与部署流程.md)第 4 节。

GitHub Release 正文承载 **Release 文案（用户视角）**，与 Tag 文案**相互独立、不得照搬**：来源是仓库 `release/notes/vX.Y.Z.md`，`publish` 步骤把正文写成「机器所有权标记 + 该文件内容」并关闭 `generate_release_notes`，因此不会出现 PR 列表式的自动正文。`release:check` 在打 Tag 之前就要求该文件存在、非空、不含技术词汇与代码痕迹，并**按「角色头行 + 四个固定分类」组织**：第一个非空行必须是 `本版影响角色：`，只列实际出现的角色；业务工作台的功能只标运营人员、财务人员、采运人员，不标系统管理员（它当前持有全部权限），只有管理员工作台改动或只影响管理员的条目才加入系统管理员；功能新增 / 功能优化 / 缺陷修复 / 已知问题四个分类各出现一次、每个分类下都要有内容（该版没有的写「无」），每条正文必须以 `【角色】` 标签开头、`- 无` 不带标签且不能与真实条目混排，头行集合必须等于所有条目标签的并集；缺头行、未知或重复角色、标签与头行不一致、缺分类、重复分类、留空节或混排都失败关闭。缺失、为空、含所有权标记或非文本字节同样在创建 Draft 前失败关闭。该角色结构自下一个正式版本起生效；历史 `release/notes` 文案保持原格式，不回溯改写，旧 Tag 不重新执行 `release:check`。正文由 Workflow 写入，不需要也不允许手工编辑；附件与 Tag 身份保持不可变。确需修正历史正文时，只允许把它重新对齐到该 Tag 对应的用户文案（不改附件、不改 Tag、不改 Commit），并在发布记录中登记这一次修正。

正式 Tag 是不可变发布身份。禁止移动 Tag、禁止复用已经存在或删除过的版本号，也禁止用强制更新把失败版本指向另一个 Commit。版本或产物有问题时应准备更高的新版本。

## 4. GitHub Actions 工作流

仓库使用三份相互分工的 Workflow：

| Workflow | 触发方式 | 作用与门禁 |
| --- | --- | --- |
| `ci.yml` | 面向 `main` 的 pull request、`main` push、`release.yml` 的 `workflow_call` | 运行 Root、Server、Server E2E、Contract、Web、Browser auth E2E、Browser dictionaries E2E 与 Browser business E2E 八个验证 Job；Server E2E 与 Browser auth E2E 各分两片，Browser business E2E 以 numbering、regions、fund-accounts 三个 matrix leg 运行；`ci-gate` 通过 `if: always()` 汇总，任一前置结果不是 `success` 都失败 |
| `examples.yml` | 每月定时和 `workflow_dispatch` | 只安装、检查和构建三个参考应用；结果可见但属于非阻断任务，不进入 `ci-gate` 或 Release |
| `release.yml` | `v*.*.*` Tag push | 调用完整 `ci.yml` 复验，然后重新构建双端、生成 Manifest 并协调 GitHub Release；触发 glob 后仍由严格版本校验器拒绝非法 Tag |

主 CI 不按路径跳过 Required Job。Job ID `ci-gate` 对应 GitHub platform context `CI gate`，已配置为 `main` 的 Required Check。

`release.yml` 先执行 `verify`，随后双端 package Job 并行运行；`package-web` 与 `package-server` 都成功后才执行 `package-images`（只消费两个归档构建镜像），随后是 `manifest`，最后进入 `publish`。Actions 默认 `contents: read`；只有 `release.yml` 的 `publish` Job 按任务需要取得 `actions: read` 与最小 `contents: write`。Workflow 不创建、移动或删除 Tag，也不自动部署附件。

`package-server` 在打包后执行归档 smoke：先对隔离 PostgreSQL 执行 migration，再从归档启动 `dist/main.js` 校验 `/api/health`，最后在归档内运行媒体 preflight（`node dist/commands/media-operations.js preflight`）。该步骤保证 production 依赖集合足以运行 preflight、health 与 cleanup：模块解析失败、生产配置校验失败或媒体读取不可用都会使 preflight 判定 `down` 并以非零退出码结束 smoke。容量告警与缺少 `ffprobe` 属于运行环境属性（CI Runner 既没有 `ffprobe`，可用空间也常低于 20%），保持 `degraded` 不阻断发布。

匹配 `v*.*.*` 的 Tag ruleset 已限制正式 Tag 创建者并禁止更新和删除，Release immutability 已启用。Required Check、Tag ruleset、Actions 默认权限与 Release immutability 都是 GitHub 外部状态，仓库文件自身不能证明这些设置已经生效；第 1 节平台证据表是当前验收记录。

## 5. Release 附件与校验

每个正式 GitHub Release 恰好包含六个固定附件：

| 附件 | 内容 |
| --- | --- |
| `qsmds-web-vX.Y.Z.tar.gz` | `web/apps/qsmds-arco/dist/` 的 production 静态文件 |
| `qsmds-server-vX.Y.Z-linux-x64.tar.gz` | Server `dist/`、生产 `node_modules/`、dedicated lockfile、`package.json`、Prisma schema 与 migrations |
| `qsmds-server-image-vX.Y.Z-linux-x64.tar.gz` | 由 Server 归档构建的 `qsmds-server:vX.Y.Z` 镜像（`docker save` 结果，含 ubuntu:24.04、Node 24、ffprobe、qpdf） |
| `qsmds-web-image-vX.Y.Z-linux-x64.tar.gz` | 由 Web 归档构建的 `qsmds-web:vX.Y.Z` 镜像（nginx 静态托管与 `/api` 反代） |
| `release-manifest.json` | Tag/Commit、Workflow run、真实构建 runtime、双端 archive、双端镜像 reference/digest/摘要、OpenAPI、Prisma schema 和 migration 摘要 |
| `SHA256SUMS` | 前五个附件的 SHA-256 固定顺序清单；不包含自身 |

镜像附件由 `release.yml` 的 `package-images` Job 在双端 package 成功后构建：只解包并校验两个归档，镜像内不执行依赖安装，也不执行前端/后端构建，因此镜像内容与归档严格同源。镜像平台固定为 `linux/amd64`，与 Server 归档的 `linux-x64` 口径一致。

`package-web`、`package-server` 与 `package-images` 的中间 Workflow artifacts 保留 1 天；包含六个固定附件的 final bundle Workflow artifact 保留 7 天，用于同一 run 的 publish-only 恢复。正式 GitHub Release assets 不依赖这些临时 artifact 的保留期。

从可信的已发布 Release 下载附件：

```bash
set -euo pipefail
: "${RELEASE_TAG:?RELEASE_TAG must be an existing published version}"
release_dir="$(mktemp -d)"
gh release download "$RELEASE_TAG" --dir "$release_dir"
```

Linux 使用：

```bash
(cd "$release_dir" && sha256sum -c SHA256SUMS)
```

macOS 使用：

```bash
(cd "$release_dir" && shasum -a 256 -c SHA256SUMS)
```

校验成功后还应人工确认目录中只有四个 archive（双端产物与双端镜像）、`release-manifest.json` 与 `SHA256SUMS`，并核对 Manifest 的 Tag、source Commit、run ID、runtime、`images.*.reference`、`images.*.digest`、OpenAPI 和 migration 信息；镜像内容以 tar 内嵌 Config digest 与 `images.*.digest` 比对（跨镜像存储一致），`docker image inspect` 的 `Id` 随镜像存储后端变化，不作判据。`SHA256SUMS` 只能证明下载集合内部一致，不能替代可信 Release 来源、不可变 Tag 和平台保护设置。

## 6. Server 兼容范围

`qsmds-server-vX.Y.Z-linux-x64.tar.gz` 的兼容目标严格限定为 Ubuntu 24.04、glibc、x64 和 Node 24。它不承诺兼容 Alpine/musl、ARM、其他 CPU 架构、其他 Node major 或任意 Linux 发行版。

Server 归档通过 pnpm 11 的现代 `pnpm deploy --prod` 构造独立 production `node_modules`，不得使用 `--legacy`。归档内的 Prisma schema 和 migrations 只用于审计与未来部署输入；production 依赖不包含 Prisma CLI，因此归档不会自行执行 migration。

Web 附件是与 Server 分离的静态文件归档。公共契约兼容的常规版本可按单独批准的部署方案独立部署或回滚，但正式产品 Tag 总是从同一 Tag Commit 重新构建 Web 与 Server，不能沿用上一 Release 的组件或 digest。首次从 fake/Token Header 切换到 Cookie Session，以及任何不兼容回退，必须按第 8 节在维护窗口使用同一 release manifest 的 Web/Server 整组切换和整组回滚。

## 7. Draft 恢复与不可变发布

GitHub Release 采用 Draft → 上传六附件 → 远端摘要校验 → 再次复验 Tag → 发布的顺序。任一验证失败都保留安全失败状态，不覆盖或删除已有附件。

部分发布失败后，只重跑失败的 `publish` Job 必须同时满足：

- 原 run 的 `verify`、双端 package 与 `manifest` 已成功。
- 同一 workflow run 的 final bundle artifact 仍在 7 天保留期内。
- source Commit、artifact ID、artifact digest、artifact name 和生成 bundle 的 run attempt 与原始记录一致。
- Draft 由受控 GitHub Actions 身份创建，Tag、target Commit 和机器标记完全匹配。
- 已存在附件的 uploader、名称、大小和 digest 与原 bundle 一致；只允许补传缺失附件。

`v0.4.0` 的 Release Run `37594095891` 与 `v0.1.2` 的 Release Run `29317866199` 都在 attempt `2` 完成受控自然恢复，两次 attempt `1` 都只有 `publish` Job 失败、其余 Job 全部成功。这证明同一 Run 身份、同一产物身份与受控 Draft 可以在上述约束内续跑。该证据不放宽新 run 遇到旧 Draft 必须安全失败、已发布 Release 不可编辑、正式 Tag 不可移动等规则，也不授权 Workflow 自动删除 Draft、移动 Tag 或部署附件。

完整重跑 package/manifest 会产生新的 artifact identity，不属于自动续传。新 run 遇到旧 Draft 时必须安全失败；管理员应先人工核对来源和附件，确认它确实是未发布 Draft 后再按平台流程删除，然后从同一不可变 Tag 完整重跑。Workflow 本身不执行删除。

相同 Tag 已有 published Release 时，任何 rerun 都必须失败且不得编辑。已发布 Release 发现问题时，修复方式是新 Commit、新的 Patch 版本、新 annotated Tag 和新 Release，不能修改既有附件或 Release 身份。

## 8. Migration 与部署边界

PostgreSQL migration 只向前：已经提交并在共享环境应用的 migration 不得修改、重命名或删除，问题通过新增 migration 向前修复。需要移除字段时采用 expand/contract，并在后续版本确认旧代码不再运行后完成清理。

CI 与 Release smoke 只使用隔离的临时 PostgreSQL 16。发布流程不连接生产数据库、不执行生产 migration、不自动部署，也不执行环境晋级、流量切换或在线回滚。

生产环境应用 migration 和部署 Web/Server 是 Release 之外的独立运维流程，需要单独审批、凭据、备份、监控和回滚方案。Release 附件只提供版本化、可校验的部署输入。

每次生产部署前还必须执行独立的 [`生产部署与 Gate OPS 检查清单`](<./生产部署与Gate OPS检查清单.md>)。安全 P0、运行准备、备份恢复或环境实时证据未通过时保持 `BLOCKED`，不得以 GitHub Release、历史审计结果或本地 smoke 代替生产门禁。

### 8.1 首次 Cookie Session 协议切换

状态：**已于 2026-10-05 首次生产上线时完成**（当时站点尚未对外承载业务流量，因此未启用维护页）。本节保留为后续任何不兼容认证协议切换的执行模板与回滚口径。

首次从旧 fake/Token Header 链路切换到 Cookie Session 是不兼容认证协议切换，不能对外滚动混跑新旧 Web/Server，也不提供双协议兼容窗口。批准后的维护窗口按固定顺序执行：

1. 将入口切换到维护页并停止新业务请求。
2. 备份并核对 migration，按只向前策略执行已验证 migration。
3. 从同一 `release-manifest.json` 校验并解包对应的 Web 与 Server 归档，整组部署两端。
4. 失效旧入口 HTML，确保入口只引用当前版本的带 Hash 静态资源。
5. 执行 health、login、`GET /api/auth/me`、logout 和关键权限 smoke。
6. 全部通过后恢复入口流量。

任一步失败都保持维护页，将 Web 与 Server 一起回到同一个已验证兼容版本。数据库不执行破坏性降级；新增认证表和字段保留，由后续向前 migration 修复。不得只回滚一端、临时恢复 `Token` Header 或把旧 HTML 重新暴露给用户。

### 8.2 同 manifest 双端 smoke 边界

当前 Release Workflow 自动执行的是 Server archive runtime smoke，然后生成包含双端归档的 Release Manifest；它尚未自动执行同 manifest 双端归档的浏览器配对 smoke。因此该项是**每次不兼容双端切换**（含认证协议切换）的人工发布门禁，不得在 GitHub Release 成功时自动视为通过。首次 Cookie Session 切换已随 2026-10-05 上线完成，本节门禁对后续同类切换继续有效。

人工门禁必须使用最终 bundle 中 `release-manifest.json` 记录并由 `SHA256SUMS` 校验的两个 archive，不得使用工作区 `dist` 或不同 Run 的产物。执行记录至少保留 release Tag、source Commit、Workflow Run、双端摘要、migration 结果、smoke 结果和整组回滚结论；没有这些证据时保持未验收。

## 9. 平台治理基线
