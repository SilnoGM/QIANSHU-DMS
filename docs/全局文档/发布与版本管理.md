# 千树 DMS 发布与版本管理

## 1. 状态与边界

阶段五代码与本地验证已实施，包括三份 GitHub Actions Workflow、产品版本与 Tag 校验、双端归档、Server runtime smoke、Release Manifest、`SHA256SUMS` 和 GitHub Draft Release 协调器。

当前尚未进行 GitHub 平台验收。真实 PR/main CI、Ubuntu 24.04 Release 生产路径、仓库保护设置和首个正式 Release 必须按阶段五实施计划的 `Task 14` 单独授权、执行并保存平台证据。在取得成功的 GitHub Actions run URL 前，只能表述为“本地 workflow 验证通过”，不能声称 GitHub CI 已通过。

阶段五不包含自动部署、环境晋级、流量切换、在线回滚或生产数据库操作。发布流程生成并发布可审计附件，不决定附件最终部署到哪个环境。

## 2. 产品版本与准备

千树 DMS 产品版本使用三个物理镜像：

| 位置 | 含义 |
| --- | --- |
| `package.json.version` | 单 Git 仓库的统一产品版本 |
| `server/package.json.version` | Server 产品版本，也是 OpenAPI `info.version` 的生成来源 |
| `web/apps/qsmds-arco/package.json.version` | 正式 Web app 的产品版本 |

`web/package.json.version = 6.3.0` 是 Fantastic Admin 上游基座版本，不是千树 DMS 产品版本，不参与 Release 一致性校验，也不能随产品版本更新。

版本准备还要求 `server/openapi/openapi.json` 与 `web/openapi/openapi.json` 的 `info.version` 等于上述产品版本，且两份 snapshot 原始字节一致。修改公共 OpenAPI version、三个产品 version 或正式 snapshot 属于公共契约或数据结构变更，执行前必须单独确认。

取得确认后按以下顺序准备版本：

1. 从最新 `origin/main` 创建独立版本准备分支。
2. 将三个产品 version 改为同一个严格稳定 SemVer；不要修改 Web 基座版本。
3. 通过根入口 `contract:sync` 运行 `node --run contract:sync`，由 Server 定义真相源生成并同步两份 snapshot 与 Web types。
4. 运行 `node --run check` 和 `node --run build`，确认两端与契约完整通过。
5. 只暂存三个产品 manifest 和两份 OpenAPI snapshot；出现 lockfile、源码或其他文件时停止审计。
6. 创建独立版本准备 Commit，经 PR 合并到 `main` 后才能创建正式 Tag。

可以使用以下守卫校验输入版本；它只验证变量，不修改任何文件：

```bash
set -euo pipefail
: "${RELEASE_VERSION:?RELEASE_VERSION must be an approved stable version}"
export RELEASE_VERSION
node -e "if(!/^(0|[1-9]\\d*)\\.(0|[1-9]\\d*)\\.(0|[1-9]\\d*)$/.test(process.env.RELEASE_VERSION)) process.exit(1)"
```

## 3. Annotated Tag

正式 Release 只接受严格 `vX.Y.Z` annotated Tag。Tag 必须直接指向已经合并到远端 `main` 的精确 Commit；lightweight Tag、递归 Tag、prerelease、build metadata 或不可从 `origin/main` 到达的 Commit 都会被拒绝。

以下命令包含 Git push 外部写入，只能在版本准备 PR 已合并、工作树干净且用户已单独授权后执行：

```bash
set -euo pipefail
: "${RELEASE_VERSION:?RELEASE_VERSION must be an approved stable version}"
export RELEASE_VERSION
node -e "if(!/^(0|[1-9]\\d*)\\.(0|[1-9]\\d*)\\.(0|[1-9]\\d*)$/.test(process.env.RELEASE_VERSION)) process.exit(1)"
test -z "$(git status --porcelain)"
git switch main
git fetch origin main --tags
git merge --ff-only origin/main
source_commit="$(git rev-parse refs/remotes/origin/main)"
test "$source_commit" = "$(git rev-parse HEAD)"
git tag -a "v${RELEASE_VERSION}" "$source_commit" -m "千树 DMS v${RELEASE_VERSION}"
test "$(git cat-file -t "refs/tags/v${RELEASE_VERSION}")" = tag
test "$(git rev-parse "v${RELEASE_VERSION}^{commit}")" = "$source_commit"
node --run release:check -- --tag "v${RELEASE_VERSION}" --source-commit "$source_commit"
git push origin "v${RELEASE_VERSION}"
```

正式 Tag 是不可变发布身份。禁止移动 Tag、禁止复用已经存在或删除过的版本号，也禁止用强制更新把失败版本指向另一个 Commit。版本或产物有问题时应准备更高的新版本。

## 4. GitHub Actions 工作流

仓库使用三份相互分工的 Workflow：

| Workflow | 触发方式 | 作用与门禁 |
| --- | --- | --- |
| `ci.yml` | 面向 `main` 的 pull request、`main` push、`release.yml` 的 `workflow_call` | 运行 Root、Server、Server E2E、Contract、Web 五个验证 Job；`ci-gate` 通过 `if: always()` 汇总，任一前置结果不是 `success` 都失败 |
| `examples.yml` | 每月定时和 `workflow_dispatch` | 只安装、检查和构建三个参考应用；结果可见但属于非阻断任务，不进入 `ci-gate` 或 Release |
| `release.yml` | `v*.*.*` Tag push | 调用完整 `ci.yml` 复验，然后重新构建双端、生成 Manifest 并协调 GitHub Release；触发 glob 后仍由严格版本校验器拒绝非法 Tag |

主 CI 不按路径跳过 Required Job。仓库管理员必须将稳定的 `ci-gate` 配置为 `main` 的 Required Check；配置前不能仅凭仓库文件声称分支保护已经生效。

`release.yml` 先执行 `verify`，随后双端 package Job 并行运行；`package-web` 与 `package-server` 都成功后才执行 `manifest`，最后进入 `publish`。只有 `publish` Job 拥有 `actions: read` 与 `contents: write`；其他 Job 继承只读权限。Workflow 不创建、移动或删除 Tag，也不自动部署附件。

## 5. Release 附件与校验

每个正式 GitHub Release 恰好包含四个固定附件：

| 附件 | 内容 |
| --- | --- |
| `qsmds-web-vX.Y.Z.tar.gz` | `web/apps/qsmds-arco/dist/` 的 production 静态文件 |
| `qsmds-server-vX.Y.Z-linux-x64.tar.gz` | Server `dist/`、生产 `node_modules/`、dedicated lockfile、`package.json`、Prisma schema 与 migrations |
| `release-manifest.json` | Tag/Commit、Workflow run、真实构建 runtime、双端 archive、OpenAPI、Prisma schema 和 migration 摘要 |
| `SHA256SUMS` | 前三个附件的 SHA-256 固定顺序清单；不包含自身 |

`package-web` 与 `package-server` 的中间 Workflow artifacts 保留 1 天；包含四个固定附件的 final bundle Workflow artifact 保留 7 天，用于同一 run 的 publish-only 恢复。正式 GitHub Release assets 不依赖这些临时 artifact 的保留期。

从可信的已发布 Release 下载附件：

```bash
set -euo pipefail
: "${RELEASE_TAG:?RELEASE_TAG must be an existing published version}"
release_dir="$(mktemp -d)"
gh release download "$RELEASE_TAG" --dir "$release_dir"
```

Linux 使用：

```bash
(cd "$release_dir" && sha256sum -c SHA256SUMS)
```

macOS 使用：

```bash
(cd "$release_dir" && shasum -a 256 -c SHA256SUMS)
```

校验成功后还应人工确认目录中只有两个 archive、`release-manifest.json` 与 `SHA256SUMS`，并核对 Manifest 的 Tag、source Commit、run ID、runtime、OpenAPI 和 migration 信息。`SHA256SUMS` 只能证明下载集合内部一致，不能替代可信 Release 来源、不可变 Tag 和平台保护设置。

## 6. Server 兼容范围

`qsmds-server-vX.Y.Z-linux-x64.tar.gz` 的兼容目标严格限定为 Ubuntu 24.04、glibc、x64 和 Node 24。它不承诺兼容 Alpine/musl、ARM、其他 CPU 架构、其他 Node major 或任意 Linux 发行版。

Server 归档通过 pnpm 11 的现代 `pnpm deploy --prod` 构造独立 production `node_modules`，不得使用 `--legacy`。归档内的 Prisma schema 和 migrations 只用于审计与未来部署输入；production 依赖不包含 Prisma CLI，因此归档不会自行执行 migration。

Web 附件是与 Server 分离的静态文件归档。两端可以独立部署和回滚，但正式产品 Tag 总是从同一 Tag Commit 重新构建 Web 与 Server，不能沿用上一 Release 的组件或 digest。

## 7. Draft 恢复与不可变发布

GitHub Release 采用 Draft → 上传四附件 → 远端摘要校验 → 再次复验 Tag → 发布的顺序。任一验证失败都保留安全失败状态，不覆盖或删除已有附件。

部分发布失败后，只重跑失败的 `publish` Job 必须同时满足：

- 原 run 的 `verify`、双端 package 与 `manifest` 已成功。
- 同一 workflow run 的 final bundle artifact 仍在 7 天保留期内。
- source Commit、artifact ID、artifact digest、artifact name 和生成 bundle 的 run attempt 与原始记录一致。
- Draft 由受控 GitHub Actions 身份创建，Tag、target Commit 和机器标记完全匹配。
- 已存在附件的 uploader、名称、大小和 digest 与原 bundle 一致；只允许补传缺失附件。

完整重跑 package/manifest 会产生新的 artifact identity，不属于自动续传。新 run 遇到旧 Draft 时必须安全失败；管理员应先人工核对来源和附件，确认它确实是未发布 Draft 后再按平台流程删除，然后从同一不可变 Tag 完整重跑。Workflow 本身不执行删除。

相同 Tag 已有 published Release 时，任何 rerun 都必须失败且不得编辑。已发布 Release 发现问题时，修复方式是新 Commit、新的 Patch 版本、新 annotated Tag 和新 Release，不能修改既有附件或 Release 身份。

## 8. Migration 与部署边界

PostgreSQL migration 只向前：已经提交并在共享环境应用的 migration 不得修改、重命名或删除，问题通过新增 migration 向前修复。需要移除字段时采用 expand/contract，并在后续版本确认旧代码不再运行后完成清理。

CI 与 Release smoke 只使用隔离的临时 PostgreSQL 16。发布流程不连接生产数据库、不执行生产 migration、不自动部署，也不执行环境晋级、流量切换或在线回滚。

生产环境应用 migration 和部署 Web/Server 是 Release 之外的独立运维流程，需要单独审批、凭据、备份、监控和回滚方案。Release 附件只提供版本化、可校验的部署输入。

## 9. 管理员一次性配置

首次正式发布前，仓库管理员必须在 GitHub 平台完成并核验以下外部设置：

1. 将 `ci.yml` 的 `ci-gate` 配置为 `main` 的 Required Check。
2. 建立匹配 `v*.*.*` 的 Tag ruleset，限制正式 Tag 创建者并禁止更新和删除。
3. 启用 Release immutability，防止已发布附件和 Tag 被修改。
4. 复核 Actions 默认 token 权限；仓库 Workflow 中只有 `publish` Job 使用最小写权限。

这些配置不由仓库代码或 Workflow 自动修改。它们的真实状态、平台 run URL、Ubuntu 24.04 生产路径和首个正式 Release 结果统一由 `Task 14` 验收记录证明。

## 10. 发布检查清单

- 公共版本变更已单独确认，三个产品 version 与两份 OpenAPI `info.version` 一致。
- 版本准备 Commit 已通过 PR 合并到远端 `main`，本地 checkout 与 `origin/main` 精确一致。
- 正式 annotated Tag 是新版本且直接指向该 Commit，没有移动或复用历史 Tag。
- `ci-gate`、Tag ruleset 和 Release immutability 已由管理员在平台核验。
- `release.yml` 的真实 run URL 与五个 Job 结果已保存。
- 四个固定附件已下载并通过 `SHA256SUMS`，Manifest 身份与实际 Release 一致。
- 部署与生产 migration 另有审批，不把 GitHub Release 成功等同于自动上线。
