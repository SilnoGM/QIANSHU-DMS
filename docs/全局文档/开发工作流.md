# 千树 DMS 开发工作流

| 项目 | 说明 |
| --- | --- |
| 状态 | 当前有效 |
| 适用范围 | 根仓库、`server/` 独立 package、`web/` 独立 workspace |

本文档是日常开发、验证和提交的当前流程入口。工程边界以[项目工程组织方案](./项目工程组织方案.md)为准；本文只说明如何在既定边界内完成变更。

## 1. 工程边界速查

- 根目录只负责 Git、文档和 Node.js 标准库编排，不是 pnpm workspace，也不声明第三方依赖。
- 根目录禁止执行 `pnpm install`，禁止生成根 `pnpm-workspace.yaml`、`pnpm-lock.yaml`、`node_modules/` 或 `.pnpm-store/`。
- `server/` 与 `web/` 是两个独立依赖域，分别维护自己的 `package.json` 和 lockfile；安装、检查和构建必须在对应依赖域内执行。
- Web 与 Server 只通过 HTTP 和 OpenAPI 契约协作，禁止跨目录读取源码，也禁止使用 `file:`、`link:`、`workspace:*` 建立跨依赖域关系。`workspace:*` 只允许用于 `web/` 内部 packages。
- `web/apps/qsmds-arco/` 是正式业务应用；其余前端应用属于 examples，不得混入正式主质量门禁或正式发布产物。

## 2. Runtime 前置检查

Node.js 版本真相源为根 `.node-version` 与 `package.json#engines.node`，当前要求 `^24.15.0`。pnpm 版本真相源为根 `package.json#packageManager`，当前要求 `pnpm@11.9.0`。

首次安装、切换终端或执行验证前，必须先运行：

```bash
set -euo pipefail
node --version
pnpm --version
node -e 'const [major, minor] = process.versions.node.split(".").map(Number); if (major !== 24 || minor < 15) process.exit(1)'
test "$(pnpm --version)" = "11.9.0"
```

任一版本不符时，先切换到受支持的 runtime，再重新执行完整检查。不得在错误版本下安装依赖，也不得把错误版本下产生的测试、检查或构建结果作为验收证据。

## 3. 安装与启动

首次安装或 lockfile 更新后，分别在两个依赖域安装：

```bash
pnpm -C server install --frozen-lockfile
pnpm -C web install --frozen-lockfile
```

根入口用于双端开发或不需要键盘交互的统一编排：

```bash
node --run dev
node --run dev:server
node --run dev:web
```

需要 Nest 或 Vite 的键盘交互时，直接启动对应依赖域：

```bash
pnpm -C server dev
pnpm -C web dev
```

真实 `server/.env` 只能基于 `server/.env.example` 或对应 example 文件在本地创建，不得提交。环境文件中不得写入无关凭据，日志中不得打印 token、密码、Cookie、数据库连接字符串或完整敏感请求体。

首次连接新的本地开发数据库时，先确认目标库允许写入，再执行 `pnpm -C server db:migrate:deploy` 和 `pnpm -C server build`，然后通过交互式 `pnpm -C server auth:bootstrap-admin` 初始化首个 `system_admin`，最后执行 `pnpm -C server seed:run --apply` 写入上线内置基础数据（汇率与启用币种、字典、业务角色、编号规则、供应商唛头绑定、打木架资金类型）。`seed:run` 默认只预览，幂等且不覆盖已有记录，输出非空 `conflicts` 时以非零码退出并交人工处理。永久密码只能在隐藏的 TTY 提示中输入，不得写入 argv、环境变量、脚本或文档。

## 4. 标准变更流程

1. 阅读根 `AGENTS.md`、本工作流以及与变更有关的当前指导文档，确认仓库边界和真相源。
2. 按根 `AGENTS.md` 区分检查、规划和执行；复杂工作明确目标、范围、真相源、约束、验收、验证与 Git 要求。只读和明确授权的低风险任务不重复确认；用户要求的阶段门保留。
3. 在功能分支工作；需要隔离依赖、并行任务或保护现有工作树时使用 worktree。
4. 前端文字、颜色和明确配置等简单变更可直接修改；行为变更、新功能和 BUG 默认先写有意义的失败测试并核实 RED 原因。无法合理建立失败测试时说明原因，并采用可复现步骤或真实运行验证。
5. 完成最小实现，先运行定向验证，按变更风险运行受影响依赖域的 check、集成或真实运行检查。通过后仅因新改动、失败或未解风险扩测；不做无关兼容或抽象。
6. 检查暂存范围，以验证通过的完整逻辑变更为单位小步提交，不混入用户已有修改。Commit Message 使用英文 type 与中文描述，例如 `fix: 修复登录状态恢复`。
7. `push`、创建 PR、合并、打 Tag 和发布等外部 Git 动作只按本次明确授权执行；命令失败必须如实报告；可在授权范围内修复并重试，不得带着失败验证推进发布。

## 5. HTTP 与 OpenAPI 契约

新增或修改公共 API 前必须单独获得确认。Server Controller、DTO 和 OpenAPI decorators 是定义真相源；Web 只消费提交到自身依赖域的 OpenAPI snapshot 和生成类型。

唯一写同步入口、只读检查入口和 Web 生成入口依次为：

```bash
node --run contract:sync
node --run contract:check
pnpm -C web api:generate
```

- `node --run contract:sync` 是唯一允许写入并同步两端 OpenAPI snapshot 与 Web types 的入口。
- `node --run contract:check` 用于只读检查已提交契约、兼容性和生成结果。
- 禁止手工修改 generated types，禁止 Web 跨目录读取 Server 源码，也禁止绕过同步入口分别维护两份 snapshot。

## 6. Prisma 与数据库验证

新增或修改 Prisma schema、migration 或数据库数据结构前必须单独获得确认。开发迁移、部署迁移和状态检查分别使用：

```bash
pnpm -C server db:migrate:dev
pnpm -C server db:migrate:deploy
pnpm -C server exec prisma migrate status
```

部署验证只允许连接全新、隔离的 PostgreSQL 16。必须通过当前进程显式注入 `DATABASE_URL`，并设置 `DOTENV_CONFIG_PATH=/dev/null`，防止静默回退到本地环境文件：

```bash
set -euo pipefail
: "${DATABASE_URL:?DATABASE_URL must reference the isolated test database}"
export DOTENV_CONFIG_PATH=/dev/null
pnpm -C server db:migrate:deploy
pnpm -C server exec prisma migrate status
```

不得回显或记录连接字符串，不得连接个人持久数据库、共享环境或生产数据库。临时数据库凭据、端口和清理动作必须由受控测试流程管理。

## 7. 验证矩阵

按实际变更范围先跑定向验证，再按风险选择必要的完整验证；纯文档和局部低风险修改不机械运行所有入口：

| 范围 | 定向/快速验证 | 完整验证 |
| --- | --- | --- |
| 根治理与编排 | `node --test scripts/root-governance.test.mjs` | `node --run test:root` |
| Server | 相关 Jest test | `env -u DATABASE_URL DOTENV_CONFIG_PATH=/dev/null pnpm -C server check` |
| Web | 相关 Node/tsx test | `pnpm -C web check` |
| OpenAPI | `node --run contract:check` | `node --run ci:contract` |
| PostgreSQL E2E | 相关 E2E test | `node --run ci:server-e2e` |
| 浏览器认证 E2E | 相关 Web API/View test | `node --run ci:browser-auth-e2e` |
| 正式双端 | 各依赖域 check | `env -u DATABASE_URL DOTENV_CONFIG_PATH=/dev/null node --run check` |
| 正式构建 | 单端 build | `env -u DATABASE_URL DOTENV_CONFIG_PATH=/dev/null node --run build` |
| 参考应用 | `pnpm -C web check:examples` | `pnpm -C web build:examples` |

examples 不属于正式主质量门禁。只有变更触及参考应用、共享 packages 或 examples workflow 时，才按触发范围单独运行其 check 与 build；不得用 examples 结果替代正式业务应用验证。

## 8. Git 与平台流程

标准协作路径为：功能分支 → 小步提交 → PR → Required Check job `ci-gate`（平台 context `CI gate`）→ 审阅 → Squash Merge。不得用强制推送绕过分支保护、Required Check 或审阅流程。

正式版本准备、Annotated Tag、Release 附件、失败恢复与平台保护规则统一参阅[发布与版本管理](./发布与版本管理.md)，本工作流不复制正式发布步骤。

## 9. 异常诊断与失败报告

端口冲突或浏览器结果与预期不符时，先检查端口与进程归属，再检查实际 CLI 版本。端口、PID、command 和 cwd 检查是只读操作；Nest 与 Vite 版本检查必须使用 fail-closed 的 `verifyDepsBeforeRun=error`，防止诊断命令自动或交互安装依赖：

```bash
set -euo pipefail
lsof -nP -iTCP:3000 -sTCP:LISTEN || true
lsof -nP -iTCP:9000 -sTCP:LISTEN || true
server_pid="$(lsof -tiTCP:3000 -sTCP:LISTEN 2>/dev/null | head -n 1 || true)"; test -z "$server_pid" || { ps -p "$server_pid" -o pid=,ppid=,command=; lsof -a -p "$server_pid" -d cwd -Fn; }
web_pid="$(lsof -tiTCP:9000 -sTCP:LISTEN 2>/dev/null | head -n 1 || true)"; test -z "$web_pid" || { ps -p "$web_pid" -o pid=,ppid=,command=; lsof -a -p "$web_pid" -d cwd -Fn; }
pnpm_config_verify_deps_before_run=error pnpm -C server exec nest --version
pnpm_config_verify_deps_before_run=error pnpm -C web --filter qsmds-arco exec vite --version
```

必须先核对监听 PID、完整 command 和 cwd，确认进程确实属于当前仓库与目标依赖域，再决定是否终止；不得仅凭端口号清理进程。若版本检查因依赖缺失或不同步而报 `ERR_PNPM_VERIFY_DEPS_BEFORE_RUN`，立即停止诊断，按“安装与启动”章节有意识地完成对应依赖域安装后再重试；不得在诊断阶段改用 `install` 或 `prompt`，也不得把报错掩盖为成功。命令报错或测试失败时，交付说明必须列出原命令、退出状态和失败阶段，不得跳过失败后声称通过。

## 10. Definition of Done

- [ ] 已完成确认过的需求范围，没有夹带无关变更。
- [ ] 需要 TDD 的变更已经历正确的 RED → GREEN，并保留可重复运行的测试证据。
- [ ] 公共 API、公共或持久化数据结构、数据库 schema 或删除文件等高风险变更均有明确覆盖对象和范围的实施授权。
- [ ] 当前指导文档、索引和相关契约说明已按事实同步。
- [ ] 定向验证与风险要求的完整验证均已运行；测试例外、所有失败及未验证项已如实记录。
- [ ] 真实 `.env`、密钥、敏感日志、构建产物和依赖目录均未进入暂存或提交，根目录仍无依赖目录。
- [ ] 暂存范围准确，`git diff --cached --check` 通过。
- [ ] 已按小步提交要求完成标准 Git 提交，Commit Message 符合英文 type、中文描述规则。
- [ ] `push`、PR、合并、Tag 和发布等外部 Git 动作均符合本次授权边界。

本页所有“单独确认”均要求明确覆盖操作对象和范围；既有精确实施批准持续有效，方案或设计确认不构成实施授权。
