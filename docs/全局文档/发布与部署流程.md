| 项目 | 说明 |
| --- | --- |
| 状态 | 当前有效 |

- 服务器部署、更新、回滚、备份的逐步命令：[`腾讯云Docker部署手册`](./腾讯云Docker部署手册.md)
- 日常开发、验证矩阵与 Git 协作：[`开发工作流`](./开发工作流.md)
- 生产安全门禁与部署记录格式：[`生产部署与 Gate OPS 检查清单`](<./生产部署与Gate OPS检查清单.md>)

## 1. 环境对照

本文统一使用环境标识（测试环境 / 生产环境）与占位符，真实公网地址、SSH 目标、凭据不在本文记录，映射关系在文档之外维护。

| 项目 | 测试环境（预发布） | 生产环境 |
| --- | --- | --- |
| 服务器 | `<测试服务器>` | `<生产服务器>` |
| SSH 入口 | `<服务器SSH用户>@<测试服务器>`（需要 `sudo`） | `<服务器SSH用户>@<生产服务器>`（需要 `sudo`） |
| 对外域名 | `https://<测试域名>` | `https://<生产域名>` |
| 部署形态 | 与生产一致：Compose 三容器（`web` / `server` / `db`） | Compose 三容器 |
| 编排路径 | `/srv/qianshu-dms/docker-compose.yml` | 同左 |
| 镜像归档与回滚点 | `/srv/qianshu-dms/images/<tag>/` | 同左 |
| 媒体存储 | `MEDIA_STORAGE_DRIVER=cos`、`MEDIA_STORAGE_ENV=test` | `MEDIA_STORAGE_DRIVER=cos`、`MEDIA_STORAGE_ENV=prod` |
| COS 桶 | 与生产共桶，按 `assets/{env}/`、`trash/{env}/` 前缀隔离 | 同左 |
| 版本切换方式 | 改 `/srv/qianshu-dms/.env` 的 `QIANSHU_IMAGE_TAG` 后 `up -d` | 同左 |
| 迁移执行通道 | 本地 SSH 隧道指向 `db` 容器的 compose 网络地址 | 同左 |
| 功能定位 | 生产同款形态的实测与验收环境 | 真实业务流量 |
| 门禁 | 本文第 5 节出口闸门 | 本文第 6 节与 Gate OPS 检查清单 |

两个环境使用同一套 `deploy/docker/` 编排与同一组 Release 附件，差异只在环境段、域名与门禁强度。镜像从不在服务器构建，只 `docker load` 发布附件。

### 1.1 测试环境的数据与媒体边界

- 测试库可以来自生产 dump 恢复。恢复后必须清空 `auth_sessions`，并在部署记录中登记数据来源、恢复时间与保留期。
- 测试环境的媒体与生产共用同一个 COS 桶，仅按前缀隔离：测试环境的写入与删除只作用于 `test` 前缀。
- 测试环境不是生产数据的长期留存位置，也不是生产数据的唯一副本。

### 1.2 回滚面要求

两个环境都必须保留**至少上一个版本**的回滚面：`/srv/qianshu-dms/images/<上一tag>/` 目录与已 `docker load` 的镜像同时在场。清理历史归档时不得删除上一版本。

部署新版本前，先把**当前正在运行的版本**固定为回滚点并逐项核对，任一项不通过都不得开始部署：

```bash
tag="$(sudo grep '^QIANSHU_IMAGE_TAG' /srv/qianshu-dms/.env | cut -d= -f2)"
sudo ls -l "/srv/qianshu-dms/images/$tag"                                  # 应为完整六个附件
sudo bash -c "cd /srv/qianshu-dms/images/$tag && sha256sum -c SHA256SUMS"   # 应 5/5 OK
sudo docker image inspect "qsmds-server:$tag" "qsmds-web:$tag" >/dev/null && echo images-ok
```

`images/<当前tag>/` 缺件时按[`腾讯云Docker部署手册`](./腾讯云Docker部署手册.md)第 4 节从 Release 重新下载补齐，不能用「镜像还在本地」跳过：归档目录是重建与审计的唯一来源，缺件会让摘要校验出现 `FAILED open or read`。测试环境缺少回滚面时，不得开始本轮的部署与实测。

## 2. 阶段闸门总表

| 阶段 | 出口判据（全部满足才可进入下一阶段） | 决策与授权 |
| --- | --- | --- |
| 一 本地开发完成 | `check` 与 `build` 全绿；Definition of Done 全项；改动已推送到功能分支 | 开发者自证 |
| 二 发版 | 版本准备 PR 已合并；annotated Tag 已推送；Release 非 Draft 且六附件摘要自校验通过 | 版本号与发版时机由用户拍板 |
| 三 测试环境部署与实测 | 部署验证全过 + 变更专项实测全过 + 无 P0 级缺陷 + 回滚点可用 | 用户验收 |
| 四 生产上线 | Gate OPS 重新审计 `PASS` + 上线前备份完成 + 上线验证全过 + 观察窗口无异常 | 用户明确授权 |

**硬闸门：阶段三未通过，不得进入阶段四。** 本流程不设「带病上线 + 限期修复」例外。实测或验证发现的缺陷必须回到阶段一修复，经阶段二发布新的 Patch 版本后重新走阶段三；不得用「生产上手工替换文件」或「跳过失败项」绕过闸门。

## 3. 阶段一：本地开发完成

**目标**：在功能分支上完成变更，本地门禁全绿，推送到远端形成可发版的候选状态。

**前置条件（准入）**

- 需求范围与实施授权明确；公共 API、公共或持久化数据结构、数据库 schema 与删除文件已单独确认。
- runtime 合规：Node `^24.15.0`、pnpm `11.9.0`，先按[`开发工作流`](./开发工作流.md)第 2 节执行 fail-closed 版本检查。
- 两个依赖域已安装：`pnpm -C server install --frozen-lockfile` 与 `pnpm -C web install --frozen-lockfile`。
- 功能分支从最新 `origin/main` 切出；需要隔离依赖或并行任务时使用 worktree。

**操作清单**

| # | 步骤 | 命令或动作 | 判据 |
| --- | --- | --- | --- |
| 1 | 建立失败测试并确认 RED 原因 | 相关 Jest 或 Node test | 失败来自目标行为，不是测试配置或环境 |
| 2 | 完成最小实现 | — | 测试转 GREEN |
| 3 | 契约变更（如涉及） | `node --run contract:sync` | 两份 snapshot 字节一致；不手改 generated types |
| 4 | schema 或迁移变更（如涉及） | `pnpm -C server db:migrate:dev` | 迁移只向前，不回改历史迁移 |
| 5 | 全量门禁 | `env -u DATABASE_URL DOTENV_CONFIG_PATH=/dev/null node --run check`、`env -u DATABASE_URL DOTENV_CONFIG_PATH=/dev/null node --run build` | 均成功 |
| 6 | 按变更域补跑 | `node --run ci:server-e2e`、`node --run ci:browser-auth-e2e`、`node --run ci:contract` | 按[`开发工作流`](./开发工作流.md)第 7 节矩阵选择 |
| 7 | 暂存审查 | `git diff --cached --check` | 只含本任务改动，无 `.env`、产物与依赖目录 |
| 8 | 小步提交 | Commit Message 用英文 type 与中文描述 | 以验证通过的完整逻辑变更为单位 |
| 9 | 推送功能分支 | `git push -u origin <branch>`（外部写入，按授权） | 远端分支可用 |

**产出物**：功能分支上的提交序列；本地验证输出；需要 TDD 的变更保留 RED → GREEN 证据。

**验收标准**：[`开发工作流`](./开发工作流.md)第 10 节 Definition of Done 全项通过；`check` 与 `build` 结论来自最新一次输出；未验证项与失败已如实记录。

**异常处理**

- 验证失败：如实报告原命令、退出码与失败阶段，修复后重试。不得跳过断言、隐藏失败或将失败描述为通过。
- `ERR_PNPM_VERIFY_DEPS_BEFORE_RUN` 报 `enableGlobalVirtualStore`：属本机 pnpm 误报，用 `--config.verifyDepsBeforeRun=false` 绕过，不要改 `web/pnpm-workspace.yaml`。
- 隔离库全量 e2e 偶发 404：单跑复核，不作为阻塞判据，但必须记录，见本文第 8 节。
- 端口冲突或浏览器结果异常：按[`开发工作流`](./开发工作流.md)第 9 节做只读诊断，核对 PID、command 与 cwd 后再决定是否终止进程。

**回滚方式**：未推送时丢弃分支或本地重置；已推送时以新提交修复，不改写已推送历史。无明确授权不得 force push 或 rebase 已推送提交。

## 4. 阶段二：发版

**目标**：生成不可变的版本身份——版本准备提交、annotated Tag 与 GitHub Release 六附件。

**前置条件（准入）**

- 阶段一完成，功能 PR 的 `CI gate` 为 `success`。
- 版本号与粒度已由用户拍板；已使用或已删除的版本号禁止复用。
- 五个产品版本源的改动已获确认：根 `package.json`、`server/package.json`、`web/apps/qsmds-arco/package.json` 与两份 OpenAPI snapshot。`web/package.json` 的 Fantastic Admin 基座版本不参与。
- 本地工作区干净，`gh` 已登录且有仓库权限。

**操作清单**

| # | 步骤 | 命令或动作 | 判据 |
| --- | --- | --- | --- |
| 1 | 建版本准备分支 | 从最新 `origin/main` 建 `release/vX.Y.Z` | — |
| 2 | 改产品版本 | 三个 `package.json` 改为同一严格稳定 SemVer | 不动 Web 基座版本 |
| 3 | 同步契约 | `node --run contract:sync` | 由 Server 真相源生成两份 snapshot 与 Web types |
| 4 | 本地门禁 | `node --run check`、`node --run build` | 均成功 |
| 5 | 版本准备提交 | 只暂存三份产品 manifest 与两份 snapshot | Commit 用 `chore: 版本准备 vX.Y.Z` |
| 6 | PR 并合并 | 推分支 → PR 标题 `release: vX.Y.Z 版本准备` → 等 `CI gate` 绿 → Create a merge commit | 合并后本地 `main` 与 `origin/main` 一致 |
| 7 | 撰写版本说明 | 写入 notes 文件 | 见下方模板 |
| 8 | 打 Tag | `git tag -a vX.Y.Z <source-commit> -F <notes>` → `node --run release:check -- --tag vX.Y.Z --source-commit <source-commit>` → `git push origin vX.Y.Z` | Tag 为 annotated，指向 `origin/main` 可达的精确 Commit |
| 9 | 观察发布流水线 | `verify → package-web / package-server → package-images → manifest → publish` | 记录 Run URL 与 attempt |
| 10 | 下载并校验附件 | `gh release download vX.Y.Z` → `shasum -a 256 -c SHA256SUMS`（macOS）或 `sha256sum -c`（Linux） | 恰好六个附件、5 行摘要逐行 OK |
| 11 | 核对清单身份 | 打开 `release-manifest.json` | Tag、source Commit、Run、runtime、`images.*.digest`、migration 摘要与实际一致 |

精确命令与守卫脚本以[`发布与版本管理`](./发布与版本管理.md)第 2 至第 5 节为准，本节不复制。

**版本说明模板**（写入 annotated Tag 的 message，也是唯一面向使用者的版本说明）

```text
千树 DMS vX.Y.Z

<一到三句：本版主题与用户可感知的变化>

新功能
- <面向使用者的描述，不复述 commit>

修复
- <现象 + 已修复的结果>

改进
- <性能、体验、稳定性的可感知变化>

文档与运维
- <文档、部署、运维口径的变化>

说明
- <默认形态是否变化、需要运维额外动作的事项>
```

撰写要求：按分类分组，面向使用者与运维者描述可感知结果，不逐条搬运 commit；剔除无业务影响的纯流程提交（例如重复的版本准备动作）。

**产出物**：版本准备提交；含版本说明的 annotated Tag；GitHub Release（六附件）；平台证据（Run URL、attempt、附件摘要）。

**验收标准**：[`发布与版本管理`](./发布与版本管理.md)第 10 节发布检查清单全项通过；六附件齐全且摘要自校验通过；`release-manifest.json` 与本地 Tag、source Commit 一致；Release 非 Draft；Tag 未被移动、复用或强制更新。

**异常处理**

- `publish` 作业首跑失败：属可复现的既有现象，执行 `gh run rerun --failed`。前置条件是同一 Run 的 `verify`、双端 package 与 `manifest` 已成功，且 final bundle artifact 仍在 7 天保留期内。见本文第 8 节。
- `package-*` 或 `manifest` 失败：不属于自动续传，需要完整重跑；残留 Draft 由人工核对来源后按平台流程删除。
- Tag 已推送但产物不可用：**不回滚、不移动 Tag**，按[`发布与版本管理`](./发布与版本管理.md)第 7 节发布新的更高 Patch 版本。
- 功能代码有问题：修复走普通 PR，重新准备版本，不得修改已发布的 Release 或附件。
- `CI gate` 失败：按阶段一的异常处理修复后重新推 PR。

**回滚方式**：已发布 Release 与 annotated Tag 都是不可变身份，本阶段没有回滚动作；纠正方式是发布新版本。部署侧回退到上一 Tag 属于阶段四的回滚方式。

## 5. 阶段三：测试环境部署与实测

**目标**：在测试环境实机部署本轮版本，完成生产同款冒烟与变更专项实测，决定是否放行生产。

**前置条件（准入）**

- 阶段二完成：Release 已发布，六附件可下载且摘要已自校验。
- 测试环境 SSH 通道可用，且具备 `sudo` 权限。
- 已按第 1.2 节把当前运行版本固定为回滚点并通过三项核对（归档目录完整、`sha256sum -c SHA256SUMS` 5/5、两个镜像在场）。
- 磁盘余量足够容纳本轮归档与镜像。

**操作清单**（命令细节沿用[`腾讯云Docker部署手册`](./腾讯云Docker部署手册.md)第 4、7、11 节）

| # | 步骤 | 命令或动作 | 判据 |
| --- | --- | --- | --- |
| 1 | 本地下载并校验 | `gh release download <tag>` → `shasum -a 256 -c SHA256SUMS` → 打开 `release-manifest.json` 核对 | 5/5 OK，恰好六个文件 |
| 2 | 备份同一恢复点 | 数据库 dump 加媒体；媒体在 COS 时按桶侧口径（本地 `tar` 不构成媒体备份） | 摘要、文件数、可读取性可核对 |
| 3 | 上传归档 | 四个归档、`release-manifest.json` 与 `SHA256SUMS` 上传到 `/srv/qianshu-dms/images/<tag>/`，保留上一 Tag 目录 | — |
| 4 | 服务器复核摘要 | `sudo bash -c "cd /srv/qianshu-dms/images/<tag> && sha256sum -c SHA256SUMS"` | 5/5 OK |
| 5 | 载入镜像并核对 digest | `docker load` 两个镜像，以 tar 内嵌 `Config` digest 与 `images.*.digest` 比对 | 一致；`docker image inspect` 的 `Id` 只作参考 |
| 6 | 执行迁移（有新迁移时） | 本地 SSH 隧道指向 `db` 容器 compose 网络地址 → `DATABASE_URL=…@127.0.0.1:15432/… pnpm db:migrate:deploy` → 重跑一次 | 第二次输出 `No pending migrations` |
| 7 | 切换版本 | `.env` 的 `QIANSHU_IMAGE_TAG=<tag>` → `sudo docker compose -f /srv/qianshu-dms/docker-compose.yml up -d` | 三个服务 Up，`db` 与 `server` 为 healthy |
| 8 | 部署验证全表 | 手册第 10 节清单：health、监听面、前端、登录、低权限权限收敛、媒体上传预览、视频 Range、订单图片、媒体探针、迁移状态、定时任务、重启存活、备份 | 逐项通过 |
| 9 | 变更专项实测 | 按本轮改动逐条列出可复核步骤与期望，用真实浏览器与真实账号执行，至少含一条负向用例 | 全过，无 P0 级缺陷 |
| 10 | 相邻回归 | 与变更相邻的既有功能抽查（列表、详情、上传、下载、删除等） | 无回归 |
| 11 | 记录证据 | Tag、镜像 digest、实测步骤与结果、异常、结论 | 可复核，见第 7 节 |

第 9 步的清单必须由本轮改动推导，不能沿用上一版。示例（媒体类改动）：图板缩略图派生、记录位视频封面、`poster` 失败时不下发整段视频、响应头 `Cache-Control` 取值、`variant` 查询参数白名单。

**产出物**：测试环境运行 `<tag>` 的实机证据；部署验证与变更专项的实测记录；回滚面就绪的证据。

**验收标准（出口闸门，三项同时成立）**

1. 第 8 步部署验证全表通过。
2. 第 9 步变更专项实测全过，且没有 P0 级缺陷。
3. 回滚点可用：上一版本目录与镜像同时在场，回退命令已验证可行。

**异常处理**

- `server` 反复重启或 preflight 失败：按手册第 14 节核对媒体目录属主 `10001:10001` 与权限 `0750`、容量与 `ffprobe`。
- 迁移失败：停止切换，按[`数据库迁移规范`](../后端文档/数据库迁移规范.md)只向前修复（新增 migration），不得修改已应用的迁移；必要时先回退 Tag。
- 媒体异常：执行媒体 `health` 并核对桶侧 CAM 策略、桶名与地域。`cos` 驱动下探针非零退出属于刻意设计的降级告警，不放宽。
- 实测发现功能缺陷：回到阶段一修复，经阶段二发布新 Patch 版本，禁止在生产或测试环境手工替换文件。
- 环境性问题（证书、网络、云平台中间件切断）：记录并与版本问题区分，不据此宣称版本通过，也不据此阻塞版本。

**回滚方式**：把 `.env` 的 `QIANSHU_IMAGE_TAG` 改回上一 Tag 后 `up -d`，旧镜像仍在本地，无需重新上传。数据库不降级；破坏性恢复需要单独批准并在维护窗口执行。媒体驱动回退见手册第 11.3 节。

## 6. 阶段四：正式服务器上线

**目标**：把阶段三已验证的版本部署到生产，完成上线验证与观察，全程保持可回滚。

**前置条件（准入，缺一不可）**

- **阶段三已通过（硬闸门）**。
- 上线、生产迁移与必要时的维护窗口已获明确授权。
- 当前生产版本的回滚面已按第 1.2 节核对通过（归档目录完整、`sha256sum -c` 5/5、两个镜像在场）。
- [`生产部署与 Gate OPS 检查清单`](<./生产部署与Gate OPS检查清单.md>)按**当前**服务器状态重新审计并标记为 `PASS`；不得沿用历史审计结论。
- 上线前备份已完成，且数据库与媒体来自同一恢复点。
- 选择低峰时段；保留第二个管理会话或救援入口。

**操作清单**

| # | 步骤 | 命令或动作 | 判据 |
| --- | --- | --- | --- |
| 1 | 本地下载并校验 | 同阶段三第 1 步 | 5/5 OK |
| 2 | **上线前备份** | 手册第 13.2 节：数据库 dump、媒体（COS 走桶侧）、`restore-point.txt` | 摘要、文件数、可读取性可核对 |
| 3 | 上传并载入 | 同阶段三第 3 至 5 步，保留上一 Tag 目录与镜像 | 摘要与 digest 一致 |
| 4 | 生产迁移 | 隧道路径同阶段三第 6 步，执行前确认快照已完成 | 无 pending migrations |
| 5 | 切换版本 | `.env` 的 `QIANSHU_IMAGE_TAG=<tag>` → `up -d` | 三个服务 Up，`db` 与 `server` 为 healthy |
| 6 | 上线验证全表 | 手册第 10 节全表，含 COS 对账 `recovery-dry-run` | `complete=true`，全部 mismatch 为 0 |
| 7 | 观察窗口 | 上线后 30 至 60 分钟，并在次日上午复查 | 见下方观察要点 |
| 8 | 记录证据 | 按 Gate OPS 第 7 节脱敏记录 | 字段齐全 |
| 9 | 收尾 | 清理历史 `images/`（保留至少上一版本）；确认离机备份在保留期内 | — |

**观察要点**

- `sudo docker compose -f /srv/qianshu-dms/docker-compose.yml logs --tail=100 server` 无环境校验、preflight 或未预期堆栈。
- `/api/health` 与媒体 `health` 持续正常；`cos` 降级告警按刻意设计处理，不放宽。
- 容器重启计数、`mem_limit`（`db` 768m、`server` 1024m、`web` 128m）无持续逼近。
- 磁盘与 inode 余量、日志轮转、媒体清理 timer 执行记录。
- 认证、数据库、媒体、容量或错误率出现异常时停止放量并执行已批准的回滚方案。

**产出物**：生产运行 `<tag>`；Gate OPS 部署记录；可用的备份恢复点；观察结论。

**验收标准**：手册第 10 节全表通过；Gate OPS 为 `PASS`（`BLOCKED` 或缺失证据都阻止部署）；观察窗口内无认证、数据库、媒体、容量与错误率异常。

**异常处理**

| 场景 | 处置 |
| --- | --- |
| 容器起不来或 preflight 失败 | 立即回退 Tag，保留日志与现场 |
| 登录被拒或 CSRF 类错误 | 核对 `server.env` 的 `APP_ORIGIN` 与 `TRUST_PROXY_HOPS`，改后 `up -d server` |
| 媒体 404 或 500 | 媒体 `health` 加桶侧核对；`cos` 写入失败优先检查 CAM 策略 |
| 迁移后业务异常 | 向前修复（新增 migration）；不得手工修改生产数据 |
| 磁盘告警 | 清理历史归档（不删上一版本）、核对日志轮转与备份保留期 |
| 出现 P0 级故障 | 执行应用回滚、停止放量并进入复盘 |

**回滚方式**

- 应用：把 `.env` 的 `QIANSHU_IMAGE_TAG` 改回上一 Tag 后 `up -d`；回滚后同样执行手册第 10 节验证，并记录回滚原因与结果。
- 数据：不降级。确需恢复时使用快照或手册第 13.2 节备份，属破坏性操作，必须明确批准后在维护窗口执行。
- 媒体：把 `MEDIA_STORAGE_DRIVER` 改回 `local` 并重建 `server`（保留回滚面），不得改写 `media_assets.storage_driver` 列。

## 8. 已知例外与豁免

以下现象已确认属于可复现的既有行为，不构成版本缺陷。它们的处理方式已固化在本流程的对应阶段；除这两项外，任何验证失败都必须按阶段三与阶段四的异常处理处置，不得自行豁免。

1. **`publish` 作业首跑失败**：正式发布 Run 的第一个 attempt 会在 `publish` 阶段失败，其余 Job（含 `verify`、双端 package、`package-images`、`manifest`）全部成功，日志只保留 `Command failed unexpectedly`。处置方式为 `gh run rerun --failed`。证据：`v0.1.2` Run `29317866199` 与 `v0.4.0` Run `37594095891` 都在 attempt `2` 完成受控自然恢复。
2. **本地隔离库全量 e2e 偶发 404**：形态固定为「期望 2xx 得到 404」、失败 spec 每次不同、单跑必绿，属尚未归因的环境级偶发。处置方式为单跑复核并记录，不作为阶段一的阻塞判据。

`cos` 驱动下媒体探针非零退出但服务继续运行是**刻意设计**（桶不可达只降级并持续告警），见[`腾讯云Docker部署手册`](./腾讯云Docker部署手册.md)第 11.3 节，不属于缺陷豁免。
