## 1. 评估范围与约束

### 1.1 目标

评估通过 GeWeAPI 将 DMS 的业务通知推送到内部员工个人微信的技术可行性，覆盖接入方式、能力边界、账号管理、回调机制、稳定性、合规风险与管理员侧需求。

### 1.2 约束

- 只读评估：未注册账号、未登录控制台、未扫码授权、未调用任何 GeWe 接口。
- 只访问 `https://www.geweapi.com` 与 `https://doc.geweapi.com` 及其同域文档链接。
- 结论以公开文档与业务方确认口径为依据；文档未说明的部分明确标注。
- 本文不提出代码改动，不包含数据库结构、接口契约与迁移设计。

### 1.3 不在本文范围

- 企业微信、公众号、短信等其他通道的对比选型。
- GeWeAPI 私有化部署的具体架构、部署要求与报价。
- 计费单价、SLA 条款、数据处理协议等商务与法务结论。

## 2. 结论摘要

1. 接口层面可行：标准 HTTP REST、Token 鉴权，支持文本、图片、文件、链接等消息，支持好友与群聊，提供账号登录、在线检测与 Webhook 回调。
2. 只能作为补充通道：无 SLA、无送达回执、无发送幂等键、离线不缓冲不补发、回调无签名；厂商文档明确非官方环境账号「最终一律封杀」。
3. 首期形态：单个公司号，群为主、1:1 为辅；多公司号留到后期做冗余或业务范围区分【业务方确认】。
4. 真正的复杂度不在接口对接，而在账号运营（扫码登录、养号、掉线重登、封号换号）与投递治理（限速、TTL、重试、降级、台账）。
5. 单号意味着单点：掉线需人工扫码，封号恢复以天计，必须保留站内或其他通道的降级路径。

## 3. 技术能力

### 3.1 接入方式与鉴权

| 项目 | 事实 | 依据 |
| --- | --- | --- |
| 协议 | HTTP REST，`POST` + `application/json` | 【文档】 |
| Base URL | `https://api.geweapi.com`，路径前缀 `/gewe/v2/api/...` | 【文档】+【业务方确认：支持 HTTPS】 |
| 鉴权 | 请求头 `X-GEWE-TOKEN`，值来自控制台「Token 中心」 | 【文档】 |
| 响应结构 | `{ ret, msg, data }`，`ret=200` 为成功 | 【文档】 |
| SDK | 仅提供标准 HTTP API，不提供封装 SDK | 【文档】常见问题 |
| 错误码 | API 参考页只定义 200 成功响应，无完整错误码表 | 【文档】 |

注意事项：

- 官网宣称「多语言 SDK」，文档 FAQ 明确「不提供封装 SDK」，两处不一致，以文档为准。
- 官网演示文案出现过 400、403、404、500、503 等示例错误码，但不构成正式契约；重试分类只能按 `ret` / `msg` 保守处理，并在试用期校准。

### 3.2 消息能力

发送接口均为单条发送：

- 文字 `postText`、图片 `postImage`、文件 `postFile`、语音、视频、链接、名片、emoji、小程序、定位。
- `postAppMsg` 可发送带 `appmsg` 节点的消息（含引用、合并消息），但需要从回调中取原始 XML 修改字段，属于非稳定契约。
- 转发接口支持文件、图片、视频、链接、小程序；撤回接口可用。
- 群聊发送时 `toWxid` 传 `xxx@chatroom`；群内 `@` 某人依赖 `content` 文本中带 `@昵称` 加 `ats` 参数，属于文本拼接。

能力边界：

| 能力 | 是否存在 | 说明 |
| --- | --- | --- |
| 模板消息 | 否 | 只能发普通聊天消息；无微信原生服务通知或卡片模板 |
| 群发/广播接口 | 否 | 只能按接收人循环调用，节奏由接入方控制 |
| 送达回执 | 否 | 发送只返回 `msgId` / `newMsgId` / `createTime`，无投递结果查询 |
| 发送结果回调 | 否 | 【文档】接口发送的消息不会触发回调 |
| 图片/文件发送 | 是 | 传入公网可访问 URL，由对方服务器拉取；重复发送可复用 CDN 信息转发 |

### 3.3 账号管理

| 能力 | 事实 | 依据 |
| --- | --- | --- |
| 登录方式 | `getLoginQrCode` 返回 `qrImgBase64` 与 `appId`；`type` 取 `ipad` 或 `mac`，`regionId` 必填 | 【文档】 |
| 登录确认 | 轮询 `checkLogin`，建议每 5 秒一次，二维码有效期 150 秒，`status` 0/1/2 | 【文档】 |
| `appId` 复用 | 首次登录传空；后续必须复用上次返回的 `appId`，频繁变更会导致掉线或登录异常 | 【文档】 |
| 在线检测 | `checkOnline` 返回 `data: true/false` | 【文档】 |
| 掉线重连 | `reconnection` 可在「系统判离线但手机仍显示在线」时尝试；失败必须重新扫码 | 【文档】 |
| 退出 | `logout` | 【文档】 |
| 弹框登录 | `dialogLogin` 可在部分场景免扫码；手机手动退出、新设备次日、官方风控下线不可用 | 【文档】 |
| 多账号 | 一个 Token 可绑定多个微信节点，数量取决于采购授权 | 【文档】 |
| 回调隔离 | 单个 Token 只支持一个回调地址；多 Token 可配置多个回调 | 【文档】 |
| 授权到期 | 部分服务到期后，系统每日随机下线超出授权数量的微信账号 | 【文档】 |

掉线规律（文档「调试指南」）：

- 新账号前 24 小时掉线属正常，用上次 `appId` 重新扫码后一般能在线约 3 个月。
- 异地登录会秒掉；手机、iPad、电脑同时登录会互相挤掉（iPad 支持三端在线）。
- 新号先在线 3~5 天再做高频操作；反复重新生成二维码会被判异常。

### 3.4 回调机制

| 项目 | 事实 | 依据 |
| --- | --- | --- |
| 配置方式 | 控制台「访问控制」或 `setCallback` 接口，按 Token 配置 | 【文档】 |
| 地址要求 | 必须公网可访问 | 【文档】 |
| 报文 | `POST` + `application/json` | 【文档】 |
| 响应时限 | 3 秒内必须返回，否则本次回调被丢弃（可返回空字符串） | 【文档】 |
| 平台重试 | 不做自动重试 | 【业务方确认】 |
| 消息范围 | 接口发送的消息不触发回调；手机端发送的消息会触发 | 【文档】 |
| 重复投递 | 可能因服务重启、历史消息同步等原因重复 | 【文档】 |
| 去重键 | `appid + newMsgId` | 【文档】 |
| 签名校验 | 文档未提供签名、时间戳或 IP 白名单机制 | 【文档：未说明】 |

版本差异：

- v1：全量事件集合，`TypeName` + `Data.MsgType` 数字码，包含 `Offline`、`ModContacts`、`DelContacts` 等系统事件【业务方确认：v1 为全量】。
- v2：优化版结构，扁平 `msgType` 字符串，补齐 `LOGIN_SUCCESS`、`LOGIN_ERROR`、`LOGOUT`、`RECONNECT_SUCCESS/FAIL` 等登录生命周期事件；文档未列 `Offline` 与联系人变更事件【文档】+【业务方确认：v2 为优化版】。
- 版本如何选择、能否切换，文档未说明；接入层需做版本归一，不能只实现一套解析。

### 3.5 文本与内容限制

【业务方确认】微信侧字数限制：

| 场景 | 限制 |
| --- | --- |
| 微信好友聊天与群聊 | 单条约 5000~6000 字，受表情、链接等元素影响 |
| 企业微信会话 | 4000 字符（汉字按 2 字符计） |
| 朋友圈纯文字 | 约 1500 个汉字 |
| 公众号图文正文 | 无硬性上限，建议 3000~5000 字 |
| 公众号自动回复 | 约 300 个汉字 |

对本场景的结论：

- 当前只使用个人微信好友与群聊，单条 5000~6000 字远高于业务通知需求，不构成限制。
- 真正的约束是可读性与降权：长且高度同质的文本更容易被判定为营销内容，建议内部阈值控制在 1000~2000 字。
- 超长内容没有「笔记」类发送能力，只能改走链接（`postLink`）或文件（`postFile`，需公网 URL）。

## 4. 已确认的关键口径

| 事项 | 口径 | 来源 | 影响 |
| --- | --- | --- | --- |
| 传输加密 | 支持 HTTPS | 【业务方确认】 | Token 与内容可安全过网；配置层应禁止回落到 http |
| 发送重试 | 平台不重试，超时由接入方处理 | 【业务方确认】 | 需自建有界重试；无幂等键，须接受重复风险 |
| 离线缓冲 | 不缓冲、不补发 | 【业务方确认】 | 离线期间消息永久丢失；发送前需在线预检与 TTL |
| 好友前提 | 非好友不可发送 | 【业务方确认】 | 员工必须先加公司号为好友；需绑定与好友关系巡检 |
| filehelper | 可长期依赖的稳定发送目标 | 【业务方确认】 | 仅对执行节点本账号有效【推断】；公司号发 filehelper 只有本号可见，不能投递给员工 |
| 回调版本 | v1 全量，v2 优化版 | 【业务方确认】+【文档】 | 接入层需兼容两套结构并按 `appid + newMsgId` 去重 |
| 首期账号 | 仅一个公司号，好友或群发送 | 【业务方确认】 | 单点风险集中；多号冗余留到后期 |
| 员工账号模式 | 不使用员工本人微信作为执行节点 | 【业务方确认】 | 个人号封禁、隐私与离职回收风险不进入方案 |

## 5. 业务形态与账号模型

### 5.1 候选模型

| 模式 | 形态 | 结论 |
| --- | --- | --- |
| A 公司号 1:1 | 公司号与员工互为好友，逐个发送 | 采用，用于指派型通知 |
| B 员工本人号 + filehelper | 员工个人微信登录为执行节点，发给自己的文件传输助手 | 不采用 |
| C 公司号 + 内部群 | 公司号在内部群，一条消息覆盖多人 | 采用，用于广播型通知 |

### 5.2 1:1 与群的差异

| 维度 | 公司号 1:1 | 公司号在内部群 |
| --- | --- | --- |
| 好友前提 | 必须加该号好友 | 不需要（靠群成员身份）【推断】 |
| 单条覆盖 | 1 人 | 全群 |
| 账号故障转移 | 不能自动：员工只加了一个号，其他号发不进去 | 可以：备用号也在群里即可换号发 |
| 主要风险 | 1 分钟 10~15 人有风控线 | 部分成员不可见（降权），无法检测 |
| 适用 | 指派型通知 | 广播型通知 |

### 5.3 定稿形态

- 首期仅一个公司号，绑定关系按「员工 + appId + wxid」三元组记录，即使当前只有一个 `appId`。
- 广播型通知走内部群，指派型通知走 1:1，默认做聚合摘要，避免按业务事件逐条发送。
- 1:1 的全员通知本质上要分批：受「1 分钟 10~15 位好友」限制，不应作为默认形态。
- 后期新增公司号时，按业务范围或冗余目的扩展；数据模型与路由需预留选号位置，避免历史绑定迁移。

## 6. 与系统的集成点

### 6.1 现状

- 服务端没有通知或消息模块，没有队列、Redis、调度器，也没有领域事件或 outbox 机制。
- `User` 模型没有微信或 wxid 字段，员工与微信身份的映射不存在。
- 前端 `notification/unread`、`notification/list` 只是演示用的 fake 路由，服务端无对应实现。
- 业务侧已有「人工复制并发送到微信群」的动作，例如柜次改单要求确认已发送到顺联航群、货件出货资料复制后人工粘贴。

因此接入属于绿地建设，不是复用现有通知模块。

### 6.2 员工绑定

绑定的最小闭环：

1. 管理员生成公司号二维码或一次性绑定码。
2. 员工扫码加公司号为好友，发送一次性绑定码。
3. 回调收到消息，取 `fromUser`（员工 wxid）与内容，匹配绑定码后落库。
4. 后续按「员工 → 公司号 appId → wxid」发送。

约束：

- `wxid` 与微信号 alias 不是一回事，绑定键必须使用 `wxid`。
- 好友关系按账号建立，换号后需要员工重新加好友。
- 需要覆盖换号、离职、被删好友三种失效状态，并用「检测好友关系」接口定期巡检。

### 6.3 事件触发与投递

- 业务事务提交后触发通知，不能在事务内直接调用外部 HTTP。
- 需要持久化发送台账，记录通知、接收人、渠道、状态、重试次数、`msgId` / `newMsgId` 与失败原因。
- 需要串行队列与按 `appId` 的限速器；文档明确要求队列发送、禁止并发。
- 需要按业务时效设置 TTL：过期通知不再发送，重连后不回放过期内容。
- 发送前做在线预检；节点离线时直接走降级通道，不做无意义重试。
- 重试需有界；由于没有幂等键，重试可能产生重复消息，应在内容中带业务单号以便识别。

### 6.4 回调处理

- 回调接口必须立即返回 200 并异步入库，否则 3 秒超时会被丢弃且平台不重试。
- 回调内容按不可信输入处理：不可猜路径、限制请求体大小与频率；离线事件先反查 `checkOnline` 再改状态。
- 回调层做 v1/v2 归一，统一映射为内部事件：消息、离线、登录成功、联系人变更、未知。
- 去重键统一为 `appid + newMsgId`。
- 回调仅建议用于账号健康与绑定确认，不用于确认发送结果。

### 6.5 内容与模板

- 没有平台模板消息，模板由系统内维护：事件类型、标题、正文变量、适用目标、启用状态。
- 模板变量需要白名单，避免把敏感字段拼进消息。
- 通知内容默认只带单号与提示，金额与客户明细不进入微信。
- 链接消息可跳回系统页面，但 `linkUrl` 与 `thumbUrl` 必须是微信端可访问的公网地址。

### 6.6 安全要求

- 出站请求仅允许 http/https；发请求前校验 host，拒绝 localhost、回环、私有与保留地址。
- 实际出站目标应限定为 GeWe 域名白名单；签名媒体 URL 不得指向内网。
- `X-GEWE-TOKEN` 只能通过环境变量或密钥服务注入，不得入库明文、不得进前端、不得写日志。
- 强制 HTTPS，禁止回落到 http。
- 回调无签名，必须通过不可猜路径、限流与「只作提示」的策略降低伪造风险。

## 7. 系统管理员侧需求

### 7.1 四块管理面

**渠道与账号**

- 渠道配置：GeWe 地址、Token（掩码写入、不可读回、可轮换）、启停开关、测试与生产区分。
- 回调地址展示：展示系统生成的回调 URL，供管理员粘贴到 GeWe 控制台；显示最近回调时间与验证结果。
- 连通性自检：用公司号自己的文件传输助手发送测试消息，不打扰员工。
- 公司号管理：备注名、`appId`、微信昵称头像、在线状态、最近在线与登录时间、绑定员工数。
- 扫码登录：发起登录、展示二维码、轮询状态、150 秒过期重取；重登必须复用上次 `appId`。
- 掉线处置：重连、退出登录；展示登录成功、掉线、退出、重连失败事件记录。
- 登录区域与代理配置：`regionId`、`proxyIp`。

**绑定与目标**

- 绑定列表：员工、微信昵称、wxid（脱敏）、`appId`、绑定时间、好友状态、最后校验时间、状态。
- 绑定操作：生成一次性绑定码或二维码、解绑、重绑、停用（离职时随账号失效）。
- 好友关系巡检：手动或定时调用「检测好友关系」，输出失效名单。
- 未绑定员工清单：按角色或部门筛选。
- 群目标管理：同步群列表（只返回已保存到通讯录的群）、人工命名用途、绑定事件与群、测试发送。

**模板与策略**

- 通知模板：事件类型、标题、正文变量、适用目标、启用状态；变量白名单与样例预览。
- 字数提示：内部阈值 1000~2000 字，超长引导改走链接。
- 通知策略：事件到目标的映射、是否聚合成摘要、静默时段、TTL、单号限速、重试次数与间隔。
- 内容脱敏规则：允许进入微信的业务字段范围。

**记录与止血**

- 发送台账：通知、事件、接收人、状态（待发/已发/失败/过期/跳过）、`appId`、`msgId` / `newMsgId`、失败原因、重试次数、时间；支持按人、事件、状态筛选。
- 重发与取消：重发需二次确认且受 TTL 限制；过期通知不允许再发。
- 回调记录：时间、`appid`、消息类型、`newMsgId`、是否重复、处理耗时与结果；原始报文脱敏并设保留期。
- 一键停发：全局停发与按事件停用。
- 概览：今日发送数、失败数、通道在线状态；只能统计发送结果，无法统计送达率。

### 7.2 权限点

按现有 `module:action` 约定：

- `wechat-channel:read` / `wechat-channel:update`
- `wechat-account:read` / `wechat-account:operate`
- `wechat-binding:read` / `wechat-binding:manage`
- `wechat-target:read` / `wechat-target:manage`
- `notification-template:read` / `notification-template:update`
- `notification-policy:read` / `notification-policy:update`
- `notification-record:read` / `notification-record:resend`
- `notification-callback:read`

建议将「登录/退出公司号」与「修改渠道配置」分开授权：前者是高频运维动作，后者能更换 Token，属于高权。

### 7.3 审计事件

按现有 UPPER_SNAKE 约定，只记录元数据，不记录消息正文、金额与客户名称：

- `WECHAT_CHANNEL_UPDATED`、`WECHAT_TOKEN_ROTATED`
- `WECHAT_ACCOUNT_LOGIN_STARTED`、`WECHAT_ACCOUNT_LOGGED_IN`、`WECHAT_ACCOUNT_LOGGED_OUT`、`WECHAT_ACCOUNT_RECONNECTED`
- `WECHAT_BINDING_CREATED`、`WECHAT_BINDING_REVOKED`、`WECHAT_BINDING_INVALIDATED`
- `NOTIFICATION_TEMPLATE_UPDATED`、`NOTIFICATION_POLICY_UPDATED`
- `NOTIFICATION_SENT`、`NOTIFICATION_RESENT`、`NOTIFICATION_CHANNEL_DISABLED`

### 7.4 管理员仍需在系统外完成的动作

- 注册 GeWe、购买授权、获取 Token。
- 在 GeWe 控制台粘贴回调地址。
- 在手机端同意员工的好友申请；文档写明每日 20~50 人上限。
- 掉线时人工扫码。
- 被封后解封或换号，并让员工重新加好友。
- 续费；到期会每日随机下线超出授权数量的账号。

### 7.5 首期不做

- 多账号池、选号路由、按业务范围分流；数据模型保留 `appId` 字段即可。
- 模板版本管理与审批流。
- 微信内回复指令、群内 @ 人。
- 图片与文件发送开关；先把纯文本跑顺。
- 触达率看板；没有回执，无法得出真实触达率。

### 7.6 最小上线判据

三条同时满足才具备交付条件：

1. 管理员能看到公司号当前是否在线。
2. 管理员能在不打扰员工的情况下完成连通性自检。
3. 一条通知失败时，能查到具体接收人、内容与失败原因。

## 8. 稳定性与触达

### 8.1 服务可用性与 SLA

文档与官网均未提供 SLA、可用性百分比、故障响应时限或赔付条款；官网只有「稳定」「高可用」等营销表述。官网也没有服务协议、隐私政策与免责声明页面，仅显示备案主体与 `苏ICP备2023019401号`。

对内部通知的含义：故障时没有契约救济，只能依靠自有降级通道。

### 8.2 投递语义

- 发送方向：平台只保证「请求被接受」，没有送达回执与幂等键；接入方重试只能提高到达概率，代价是可能重复。对外应描述为「尽力送达，可能重复」。
- 回调方向：平台不重试，3 秒不返回即丢；语义接近 at-most-once，丢失后无法感知。
- 结论：不存在 exactly-once；通知内容应可重复消费，且在关键业务节点不能只依赖微信提醒。

### 8.3 频率与容量

【文档】频率建议：

- 每分钟不超过 40 条；单用户发送间隔不少于 1 秒；群消息间隔随机 2~5 秒；必须队列发送，禁止并发。
- 1 分钟内给超过 10~15 位好友发送消息存在风控风险；群发公告建议半小时 200 人以内。

按 10 人/分钟估算全员 1:1 通知的最短耗时：

| 接收人数 | 1:1 全员最短耗时 | 群通知 |
| --- | --- | --- |
| 20 人 | 约 2 分钟 | 1 条 |
| 50 人 | 约 5 分钟 | 2~3 条 |
| 100 人 | 约 10 分钟 | 3~5 条 |

结论：单号做全员 1:1 通知会贴近风控线，广播应默认走群。

### 8.4 离线与恢复时间

- 掉线：需要人工扫码；若夜间或周末无人处理，中断持续到有人扫码为止。
- 封号：需辅助解封（要求协助人注册满 6 个月、1 个月内未辅助过他人、6 个月内不超过 2 位），或换新号；新号需先在线 3~5 天再承担高频发送，员工还需重新加好友。
- 因此封号的恢复时间以天计，不是以小时计。

### 8.5 消息丢失与重复

- 离线期间不缓冲、不补发，消息直接丢失。
- 发送超时后重试可能造成重复；没有幂等键，只能靠发送台账与内容中的业务单号降低影响。
- 回调可能重复，需按 `appid + newMsgId` 去重。
- 群消息可能「部分成员不可见」，且无法通过接口检测。

## 9. 合规与账号风险

### 9.1 封号风险

文档「风险说明」原文：

> 业务风控系统用正常人的方式来判断一个号是否是真人。不是真人操作且运行在非官方环境的，账号最终一律封杀掉。

同页列出的常见封号原因包括：非官方客户端注册、大量添加好友或大量群发、被投诉、频繁切换账号、24 小时充电状态、位置长期不动等。另有明确结论：新号 2 个月内做营销被封率极高；同 WiFi 批量养号会批量封号；连号段批量注册必封。

这意味着厂商并不承诺账号长期存活，只提供降低风险的使用规范。

### 9.2 数据隐私

- 厂商声明 SaaS「仅作为消息路由转发，不存储用户敏感数据」，私有化部署可做到数据本地化；这是厂商自述，没有公开的隐私政策、数据处理协议或审计报告可供核对。
- 发往员工微信的内容必然经过第三方服务器与微信本身；待审核、对账、金额、客户名称属于业务敏感数据。
- 建议通知内容只带单号与提示，完整明细留在系统内查看。

### 9.3 风险矩阵

| 风险 | 依据 | 影响 | 缓解思路 |
| --- | --- | --- | --- |
| 通知号被封 | 【文档】「最终一律封杀」 | 通道整体中断，需人工解封或换号 | 多号轮换、低频聚合、养号、降级通道、封号告警 |
| 异地或多设备掉线 | 【文档】 | 单次通知失败，恢复需扫码 | 固定区域与网络、单设备在线、在线巡检 |
| 新号初期不稳定 | 【文档】前 24 小时掉线、一般在线 3 个月 | 上线初期触达率低 | 提前养号，灰度验证后再承担高频 |
| 消息未送达或部分不可见 | 【文档】无回执、降权 | 误以为已通知，业务漏处理 | 只作补充通道；关键节点回系统确认 |
| 回调重复或丢失 | 【文档】重复有说明；超时即丢 | 绑定错乱、事件漏处理 | 去重键 `appid + newMsgId`；回调只作提示 |
| 回调被伪造 | 【文档】无签名机制 | 虚假离线事件或绑定请求 | 不可猜路径、限流、反查 `checkOnline`、索取出口 IP |
| 供应商单点、无 SLA | 【文档】无承诺 | 故障无赔偿、无响应时限 | 合同约定、自有降级通道、渠道抽象 |
| 计费到期随机下线 | 【文档】 | 非预期中断 | 续费提醒、授权数冗余 |
| 明文传输凭据与内容 | 【业务方确认】支持 HTTPS | 若配置错误仍可能走 http | 强制 HTTPS，禁止回落 |

## 10. 可行性与前提条件

### 10.1 结论

技术可行，但只能作为补充通道。理由：

- 支持可行：接入形态简单，文本、链接、文件覆盖业务通知需求；账号生命周期与掉线事件有 API；回调可支撑绑定与账号监控。
- 不能作为唯一通道：无 SLA、无送达回执、无发送幂等、离线不补发、无模板消息、无群发接口、回调无签名，且厂商明确非官方环境账号最终会被封。

### 10.2 前提条件

1. 业务侧接受「尽力而为」定位：待审核、对账完成等有时效要求的通知保留站内、邮件或其他主通道。
2. 账号模型定稿：公司专用通知号，不使用员工个人号作为执行节点。
3. 强制 HTTPS，禁止 http 回落。
4. 自建投递基础设施：发送台账、串行队列、按 `appId` 限速、有界重试、TTL、失败告警。
5. 回调立即返回 200 并异步处理，兼容 v1/v2 并按 `appid + newMsgId` 去重。
6. 员工绑定流程与好友关系巡检，覆盖换号、离职、被删好友。
7. 内容降敏与聚合，默认只发单号与提示；全员通知走群。
8. 账号运营准备：养号窗口、固定区域与网络、掉线扫码值班、封号换号预案。
9. 出站请求只允许 http/https，发请求前校验 host，拒绝 localhost、回环、私有与保留地址。
10. 采购前完成商务与合规确认：计费、授权数、SLA、数据处理与删除条款。

## 12. 后续验证建议

若进入实施前的技术验证，建议在 7 天试用期内确认以下事实，均需真实环境实测：

1. 认证方式：使用 `https://api.geweapi.com` 完成一次发送，确认 TLS 与 Token 传递正常。
2. 回调实测：记录实际推送的版本、报文结构、重复率与处理耗时。
3. 错误码分布：统计 `ret` / `msg` 的实际取值，校准重试分类。
4. 掉线事件：验证 `checkOnline` 与回调登录事件的一致性与延迟。
5. 限速阈值：在测试号上验证 40 条/分钟与「1 分钟 10~15 人」的实际表现，不触碰生产员工。
6. 管理员闭环：确认在线状态、连通性自检、发送台账三项能力可支撑日常运维。
