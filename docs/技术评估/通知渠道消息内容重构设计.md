## 1. 已确认决策

| 编号 | 决策 |
| --- | --- |
| D1 | 只有两个通知渠道：站内 `IN_APP` 与企业微信 `WECOM`。 |
| D2 | 企微发送方式只有 `APP`（应用消息）和 `ROBOT`（群机器人）两种，同一事件只能二选一；不同事件可以选择不同方式。 |
| D3 | 收件人留在各渠道配置内部，不做事件级受众层，不做目标矩阵，不做站内与企微之间的收件人共享/去重。 |
| D4 | 模板不通用、不共享；一个事件的一个渠道独享一份内容。 |
| D5 | 取消“模板”作为独立实体：没有模板表、模板 key、模板库、模板选择器、使用次数、模板 domain。 |
| D6 | 内容作为事件渠道配置的 1:1 组成部分存在，保留“消息组”作为有序消息项集合。 |
| D7 | 收件人、内容、发送方式、TTL/静默等由同一角色维护；一次保存、一个权限，不拆独立内容权限。 |
| D8 | 只做审计，不保留配置历史和回滚；配置版本只用于并发控制。 |
| D9 | 发布 API 不再传 `templateKey`，完全由事件渠道配置决定内容。 |
| D10 | 消息类型按“渠道 + 发送方式”校验：站内只允许一条 `TEXT`；企微应用消息和群机器人各自使用自己的能力集合。 |
| D11 | `mpnews` 需要支持，且只允许 `WECOM + APP`，固定 1 篇文章。 |
| D12 | `mpnews` 封面由管理员固定上传为 DMS 媒体资产；建议 1068×455 或其等比例倍数；只做比例提示 + 预览，不做硬校验。 |
| D13 | `mpnews` 正文使用 Tiptap 富文本编辑器。 |
| D14 | `mpnews` 正文图片单张 ≤2MB，不限制张数。 |
| D15 | 只禁止外部域名图片；普通外部链接允许。 |
| D16 | 正文图片源为 DMS 媒体资产；发布时调用企业微信 `media/uploadimg` 换成永久 URL，最终 HTML 不引用 DMS 域名。 |
| D17 | 预览时正文图片使用 DMS 签名 URL，不消耗企业微信 `uploadimg` 配额。 |
| D18 | `safe=2` 只加在 `mpnews` 消息项上。 |
| D19 | 接受“长文被覆盖后无法还原”，只保留审计摘要与已发送快照。 |

## 2. 目标模型

```text
事件
├─ 站内渠道配置
│  ├─ 收件人
│  ├─ 消息内容（只允许一条 TEXT）
│  └─ 启用状态
└─ 企业微信渠道配置
   ├─ 发送方式：APP / ROBOT（二选一）
   ├─ 收件人或群目标
   ├─ TTL / 静默 / 敏感策略
   ├─ 消息内容（有序消息项）
   └─ 启用状态
```

关键约束：

- 一个事件在每个渠道最多一条配置。
- 一个事件最多一条企微配置，因此不可能同时启用 APP 和 ROBOT。
- 每个渠道配置独享自己的内容，不存在跨事件、跨渠道、跨发送方式的模板引用。
- 消息组是渠道配置内部的有序消息项集合，不是独立的配置层或可复用实体。

## 3. 数据模型

### 3.1 事件渠道配置

```text
notification_event_channels
  id
  event_type
  channel              -- IN_APP | WECOM
  send_method          -- IN_APP | APP | ROBOT
  enabled
  target_mode
  target_config        -- JSONB
  ttl_seconds          -- 仅 WECOM
  quiet_hours          -- 仅 WECOM
  allow_sensitive      -- 仅 WECOM
  version
  updated_by
  created_at / updated_at

  UNIQUE(event_type, channel)
  CHECK (channel = 'IN_APP' AND send_method = 'IN_APP')
     OR (channel = 'WECOM' AND send_method IN ('APP', 'ROBOT'))
```

- `IN_APP` 和 `WECOM_APP` 的收件人可以是用户、角色、权限或动态目标。
- `WECOM_ROBOT` 的目标是内部群，不使用用户收件人。
- `ttl_seconds`、`quiet_hours`、`allow_sensitive` 仅对企微渠道有意义。
- 优先级建议放事件级，避免站内与企微冲突。

### 3.2 内容消息项

```text
notification_event_channel_messages
  id
  channel_config_id
  sort_order
  kind                 -- TEXT / IMAGE / FILE / NEWS / MPNEWS / ...
  payload              -- JSONB
  media_policy         -- JSONB
  content_hash
  enabled
  created_at / updated_at

  UNIQUE(channel_config_id, sort_order)
```

- 每条消息项对应一次实际发送；`IMAGE` 项如果绑定多张图，发布时展开成多条投递消息。
- 站内渠道只允许一条启用的 `TEXT`。
- 企微 APP / ROBOT 按各自能力集合校验 `kind`。
- 内容消息项不属于模板，不能被其他渠道配置引用。

### 3.3 内容媒体引用

富文本正文里的图片不是普通字段，必须有显式引用关系，否则媒体清理无法判断资产是否仍在使用：

```text
notification_event_channel_message_media
  message_id
  media_asset_id
  role                 -- COVER | INLINE
  sort_order
  created_at

  UNIQUE(message_id, media_asset_id, role)
```

- `COVER` 用于 mpnews 固定封面。
- `INLINE` 用于富文本正文图片。
- 保存内容时从 HTML 的 `data-asset-id` 提取并同步引用；删除图片时移除引用。
- 媒体清理任务必须把这些引用视为“使用中”。

### 3.4 通知级渲染快照

`mpnews` 单篇 HTML 最大 666KB，不能按收件人复制。渲染结果按通知共享：

```text
notification_rendered_messages
  id
  notification_id
  channel
  send_method
  sort_order
  kind
  payload_snapshot     -- JSONB，渲染后的内容
  content_hash
  created_at
```

### 3.5 投递与投递消息

```text
notification_deliveries
  id
  notification_id
  channel              -- WECOM
  send_method          -- APP | ROBOT
  recipient_user_id    -- APP
  target_id            -- ROBOT
  channel_config_version
  content_hash
  status
  attempt_count
  next_attempt_at
  accepted_at
  failure_code
  created_at / updated_at

notification_delivery_messages
  id
  delivery_id
  rendered_message_id
  sort_order
  status
  attempt_count
  next_attempt_at
  provider_msg_id
  media_id             -- mpnews 封面在 APP 侧上传后的 media_id
  media_id_expires_at
  failure_code
  accepted_at
  created_at / updated_at
```

- 投递消息只引用通知级快照，不复制大 HTML。
- 每条投递消息独立状态、独立重试；已 `ACCEPTED` 的项不重发。
- 站内渠道不生成 `notification_deliveries`，直接写收件箱条目。

## 4. 内容模型

### 4.1 消息组

消息组是渠道配置内部的有序消息项集合，按 `sort_order` 发送。每个消息项对应一次企业微信 API 发送（媒体项可能展开成多次），不是企业微信的服务端批量概念。

建议默认失败策略为 `STOP`；如果产品要求尽量送达，可改为 `CONTINUE`。`STOP` 的行为是：

- 某项最终失败后，后续项标记 `SKIPPED`。
- 整条投递标记 `PARTIAL` 或 `FAILED`。
- 重试只重试失败项，不重发已成功项。

### 4.2 类型范围

| 渠道/方式 | 允许内容 |
| --- | --- |
| `IN_APP` | 仅一条 `TEXT` |
| `WECOM + APP` | 应用消息支持的类型，包括 `text`、`markdown`、`image`、`voice`、`video`、`file`、`textcard`、`news`、`mpnews`、`miniprogram_notice`、`template_card`、`interactive_taskcard` 等 |
| `WECOM + ROBOT` | 群机器人支持的类型：`text`、`markdown`、`markdown_v2`、`image`、`voice`、`file`、`news`、`template_card`（仅 `text_notice` / `news_notice`） |

类型是否在本期实现可以分批；模型层先支持判别和校验，未实现的类型在管理端隐藏、API 拒绝。

### 4.3 内容示例

文本项：

```json
{
  "kind": "TEXT",
  "payload": { "content": "采购单 {{orderNo}} 已审核通过" }
}
```

图片项：

```json
{
  "kind": "IMAGE",
  "mediaPolicy": {
    "sourceKeys": ["purchase.orderImage"],
    "maxCount": 1
  }
}
```

`sourceKeys` 为空表示事件契约声明的全部来源；`maxCount` 只限制该消息项实际发送的图片张数。图片附件在全部文本/mpnews 消息之后发送。

`mpnews` 项：

```json
{
  "kind": "MPNEWS",
  "payload": {
    "cover": { "mediaAssetId": "uuid" },
    "title": "采购流程调整通知",
    "author": "千树 DMS",
    "digest": "自下周起采购审核流程调整如下……",
    "contentSourceUrl": "https://dms.example.com/purchase/notice/123",
    "content": "<p>各位同事：</p><p>{{noticeBody}}</p><img data-asset-id=\"uuid\" alt=\"示意图\">"
  }
}
```

- 标题、作者、摘要、阅读原文与正文都支持事件契约变量；保存按模板原文校验字节上限，发布渲染后再按 UTF-8 字节截断，超限会在预览 warnings 与发布 `MPNEWS_METADATA_TRUNCATED` 警告中提示。
- 正文 HTML 中只存 `data-asset-id`，不存 DMS 域名、外部图片 URL 或 base64。
- 普通外链允许，限 `http/https`。

## 5. mpnews 专项

### 5.1 约束

| 项目 | 规则 |
| --- | --- |
| 支持端 | 仅 `WECOM + APP` |
| 文章数量 | 固定 1 篇；发送时包装成 `articles: [article]` |
| 标题 | 必填，≤128 字节；支持变量，渲染后按字节截断 |
| 作者 | 可选，≤64 字节；支持变量，渲染后按字节截断 |
| 摘要 | 可选，≤512 字节；支持变量，渲染后按字节截断 |
| 正文 | Tiptap HTML，最终 HTML ≤666KB |
| 阅读原文 | 可选，`http/https`；变量只能放在固定 URL 内 |
| 封面 | 固定 DMS 媒体资产，JPG/PNG，≤10MB |
| 正文图片 | 静态 DMS 资产或业务图片占位；单张 ≤2MB，占位总数 ≤ 事件媒体上限 |
| 安全级别 | `safe=2`，只加在 mpnews 消息项 |

正文静态图片使用 `data-asset-id`；业务图片使用 `data-media-source` 占位（如 `salesOrder.issuanceVoucher`），每个占位在发布时按消息组顺序消费一张 `command.media` 图片，替换成真实 `data-asset-id` 后进入现有 `media/uploadimg` 链路。缺少匹配图片、资产不可用或敏感限制时移除占位并返回 `MPNEWS_INLINE_MEDIA_SKIPPED`，不阻断整条通知；保存时要求带业务图片占位的正文仍保留静态文字。动态内联图片发布后写入 `notification_rendered_message_media`，参与媒体回收保护并供记录页展示。

### 5.2 封面

- 管理员上传固定封面，内容存 `mediaAssetId`，不存 `thumb_media_id`。
- 建议尺寸 1068×455 或其等比例倍数。
- 只做比例提示和预览，不做硬校验；预览使用 1068:455 框展示可能被裁剪的区域。
- 发布时调用 `media/upload?type=image` 获取临时 `thumb_media_id`，3 天有效。
- 按“应用 + 封面资产”缓存 `media_id`，过期重传，不按收件人重复上传。
- 封面资产纳入媒体引用登记，避免清理任务误删。

### 5.3 Tiptap 编辑器

已确认采用 Tiptap。选型对比：

| 编辑器 | 优势 | 局限 | 结论 |
| --- | --- | --- | --- |
| Tiptap | Vue 3 官方绑定；Schema/Node 可控；自定义图片节点和 `assetId` 属性容易；粘贴规则强 | 学习曲线和体积中高；需确认各扩展许可 | 采用 |
| wangEditor 5 | 中文文档友好、上手快、工具栏完整 | 图片资产属性、外链图片拦截、HTML 清洗需要更多自定义 | 备选 |
| Quill 2 | 轻量、稳定 | 自定义图片资产节点和粘贴清洗工作较多 | 备选 |
| Lexical | 现代、可扩展 | Vue 3 绑定不成熟，落地成本高 | 不采用 |

Tiptap 的关键优势是能把图片节点限制为“只有 `assetId`、没有 `src`”，从编辑器层面阻止外部图片进入内容。

建议：

- 使用 `@tiptap/vue-3`、StarterKit、Link 扩展；不使用自带 `Image` 扩展。
- 自定义图片节点：
  - 属性：`assetId`、`alt`、可选 `width/height`。
  - 序列化：`<img data-asset-id="uuid" alt="...">`，不存 `src`。
  - NodeView 根据 `assetId` 请求 DMS 签名 URL 显示。
- 自定义变量节点：
  - 序列化为 `<span data-var="orderNo">{{orderNo}}</span>`。
  - 避免编辑时把 `{{variable}}` 拆散。
- 工具栏只开放标题、加粗、斜体、下划线、列表、引用、链接、DMS 图片上传、撤销/重做、清除格式。
- 不开放颜色、字体、表格、视频、iframe，待企业微信客户端实测后再评估。
- 粘贴图片文件：上传 DMS 后插入图片节点。
- 粘贴外部 `<img src="...">`：直接丢弃并提示，不服务端抓取。
- 链接只允许 `http/https`，禁止 `javascript:`、`data:`。

### 5.4 正文图片链路

```text
编辑器上传图片
  → DMS 媒体资产（assetId，单张 ≤2MB）
  → 内容 HTML 只存 data-asset-id
  → 预览使用 DMS 签名 URL
  → 发布时 media/uploadimg 换取永久企业微信 URL
  → 最终 HTML 使用企业微信 URL
```

官方 `media/uploadimg` 规则：

| 项目 | 规则 |
| --- | --- |
| 返回 | 永久有效的图片 URL |
| 用途 | 仅用于 mpnews 正文图片展示；非企业微信页面会被屏蔽 |
| 大小 | 5B–2MB |
| 配额 | 每个企业每月最多 3000 张，每天最多 1000 张 |

实现要求：

- 单张超过 2MB 在编辑器上传阶段拒绝或压缩；不在发布时才失败。
- 不限制张数，但每张新图片首次发布消耗一次 `uploadimg` 配额；同一资产复用缓存不重复消耗。
- 按“企业 + assetId”缓存永久 URL。
- 监控 1000/天、3000/月配额；配额耗尽时 mpnews 发布失败并告警。
- 最终 HTML 替换 URL 后会变长，保存时和发布时都要校验 666KB。
- 预览使用 DMS 签名 URL，不调用 `uploadimg`，不消耗配额。

### 5.5 发送

- `safe=2` 只加在 mpnews 消息项。
- 同一消息组里的其他消息项不会被 `safe=2` 覆盖；如果整体需要内部限制，需要另行决定其他项的 `safe` 策略。
- `safe=2` 不阻止正文里的普通外链点击；如果内部内容不能外链，需要另行限制。
- 渲染后的 mpnews HTML 存通知级共享快照，投递消息只引用快照。
- 每个投递消息保存封面 `media_id` 和过期时间；正文图片 URL 使用企业级缓存。

## 6. 发布与投递

### 6.1 发布命令

业务发布不再选择模板：

```text
publish({
  eventType,
  source,
  variables,
  media,
  target?,        // 仅 target_mode = COMMAND_TARGET 时使用
  dedupeKey?,
  priority?,
  expiresAt?
})
```

- 事件渠道配置决定内容。
- 静态收件人由配置解析；动态目标才由命令传入。
- 事件渠道未配置内容时，该渠道应视为未启用/跳过；管理端保存时不允许“启用了渠道但没有内容”。

### 6.2 发布流程

1. 读取事件的全部渠道配置。
2. 对每个启用渠道解析收件人或群目标。
3. 读取该渠道配置的内容消息项。
4. 按事件契约渲染变量、校验媒体、sanitize HTML。
5. 站内：写入收件箱条目。
6. 企微：写入通知级渲染快照、投递信封和投递消息项。
7. 派发器按 `sort_order` 顺序发送，逐项重试。

### 6.3 限流

- 应用消息：同一应用对同一成员 ≤30 次/分钟、≤1000 次/小时；每日按账号上限 ×200 人次。
- 群机器人：每个 webhook ≤20 条/分钟。
- 消息组会把 API 调用数乘以消息项数；必须按目标/成员做主动节流，不能只依赖 `45009` 重试。
- `mpnews` 的正文图片上传还有独立的 `uploadimg` 企业级配额。

具体限流口径见[企业微信消息通道能力与限流](../后端文档/企业微信消息通道能力与限流.md)。

## 7. 审计与版本

- 事件渠道配置使用 `version` 做乐观并发控制；内容或路由变化都会递增。
- 审计记录：操作人、时间、事件、渠道、发送方式、内容哈希、消息项数量/类型、正文字节数、封面资产 ID、正文图片资产 ID。
- 不保存旧内容快照，不提供回滚。
- 已发送通知的 `notification_rendered_messages` 保留当时渲染结果，可以回答“当时发出去的是什么”；配置覆盖前的旧内容无法还原。
- 不保留模板使用次数、模板变更审计等模板概念。

## 8. 安全边界

- 所有富文本保存和预览必须服务端 sanitize；不能只依赖 Tiptap schema。
- 允许标签以企业微信实际支持范围为准；禁止 `script/iframe/object/embed/form/style`、事件属性、`javascript:`、`data:`。
- 存储态 HTML 的 `<img>` 只允许 `data-asset-id`、`alt`、`width`、`height`，禁止 `src`；发布渲染时替换为最终 `<img src="企业微信URL">` 后再次 sanitize。
- 普通链接只允许 `http/https`；变量在 HTML 上下文 escape，在 URL 上下文 encode + 校验。
- 外部图片禁止：粘贴的外部 `<img>` 直接丢弃，不服务端下载、不转存。
- 如果后续增加服务端 URL 抓取能力，必须仅允许 `http/https`，发请求前校验 host，拒绝 localhost、回环、私有和保留地址，避免 SSRF。
- `uploadimg` 返回的是图片直链，`safe=2` 只控制消息分享范围，不保护图片 URL；不要在图片中放敏感信息。

## 9. 前端页面方案

### 9.1 信息架构与路由

```text
通知中心
├─ 事件配置
│  ├─ /system/notifications/events              事件列表
│  └─ /system/notifications/events/:eventType   事件详情
├─ 发送记录
├─ 企业微信设置
└─ 个人通知偏好
```

- 菜单名称从“通知策略”改为“事件配置”。
- 模板库、模板页签、模板选择器、模板卡片、模板使用次数全部移除。
- 原 `/system/notifications/policies` 直接移除，不做重定向；旧书签会命中 404，发版说明需提示新入口。
- 内容编辑并入事件渠道配置，使用 `notification-policy:update` 权限；模板相关前端路由/API/权限在实施时清理。

### 9.2 事件列表

```text
[关键字] [业务域] [渠道/方式] [配置状态]

事件             站内     企业微信        内容       更新时间      操作
采购审核         已启用   应用消息 3人    3 条消息   11-25 10:20   配置
发票申请         已启用   群机器人 2群    2 条消息   11-25 09:10   配置
```

- 桌面端用表格，窄屏用卡片。
- 列：事件（名称 + `eventType`）、站内状态、企微方式/目标摘要、内容摘要、更新时间、操作。
- 状态由服务端计算，列表接口不返回完整内容，只返回 `inAppEnabled`、`wecomEnabled`、`wecomSendMethod`、目标摘要、消息项数量、内容状态、更新人/时间。
- 整行点击进入详情；只读用户可查看但不能编辑。
- 支持按业务域、渠道/方式、配置状态筛选。

### 9.3 事件详情

```text
← 事件配置
采购审核  [PURCHASE]  purchase.review.approved
最后更新：张三 11-25 10:20                 [预览] [保存]

[ 站内通知 ]  [ 企业微信 ]

启用 [开关]
收件人 [选择器]
消息内容 3 条：文本 → 图片 → 图片  [编辑内容] [预览]

（企微页签额外）
发送方式 [ 应用消息 ] [ 群机器人 ]
TTL / 静默时段 / 敏感内容 / 群目标
```

- 页签徽章显示 `已启用`、`未启用`、`内容未配置`。
- 站内页签只允许一条 `TEXT` 内容。
- 企微页签根据发送方式切换目标与内容类型范围。
- 收件人：
  - 站内 / 企微应用：指定成员、角色、权限、动态目标。
  - 群机器人：内部群多选 + @ 配置。
- 不做站内与企微共享收件人；不提供“从其他事件复制内容”入口。
- 群目标为空时提示先到企业微信设置配置内部群。

发送方式切换：

- 弹确认框，说明会清空目标并重新校验内容。
- 切换后清空目标，保留内容。
- 不兼容消息项高亮，保存按钮禁用，直到用户删除或切回。
- 例如 APP → ROBOT 时，`video`、`textcard`、`mpnews` 等项不兼容；ROBOT → APP 时，`markdown_v2` 不兼容。

### 9.4 保存与草稿

- 事件详情页级一次保存；两个页签共用一个保存按钮。
- 消息内容全屏抽屉的“完成”只把草稿写回详情页，不单独保存。
- 保存提交两个渠道配置 + 内容，服务端事务处理；每个渠道携带 `expectedVersion`。
- 页签显示未保存标记；离开路由时拦截。
- 版本冲突提示刷新，不静默覆盖。
- 预览使用当前草稿，不要求先保存。

### 9.5 消息内容编辑器

全屏抽屉：

```text
消息内容 · 企业微信 / 应用消息                    [预览] [完成]

┌ 消息列表 ────────────┬ 编辑区 ─────────────────────────────┐
│ 1  文本   采购单已通过 │ 类型：文本                          │
│ 2  图片   1 张        │ 内容：                              │
│ 3  mpnews 采购通知    │ [textarea / 富文本编辑器]           │
│                       │ 变量：[插入变量]                    │
│ [+ 添加消息]          │ 字节：128 / 2048                    │
└───────────────────────┴─────────────────────────────────────┘
```

- 左侧消息项使用稳定 `clientId`，支持上移/下移/删除；删除需确认。
- 显示顺序、类型、摘要、校验状态、实际发送条数。
- 类型选择器按 `channel + send_method` 过滤；未实现/不支持的项禁用并显示原因。
- 校验汇总在顶部，错误定位到具体消息项/字段；存在阻断错误时禁用保存。
- 站内只允许 `TEXT`；企微应用与群机器人分别使用各自类型集合。
- 内容编辑不提供模板选择、模板库跳转或“从其他事件复制”。

### 9.6 mpnews 编辑器

```text
mpnews · 采购流程调整通知                         [预览] [完成]

封面 [上传/选择]  [1068:455 预览框]
标题 [____]  作者 [____]  摘要 [____]  原文 [____]

正文
[B] [I] [U] [H1] [列表] [引用] [链接] [图片] [撤销] [重做]
┌──────────────────────────────────────────────┐
│ Tiptap 编辑区                                │
└──────────────────────────────────────────────┘
字节：12.4KB / 666KB        [仅企业内分享 safe=2]
```

- 封面只做 1068:455 比例提示 + 预览，不硬校验；超过 10MB 拒绝。
- Tiptap 图片节点只存 `assetId`，NodeView 用 DMS 签名 URL 显示。
- 图片按钮只允许 DMS 上传；粘贴外部 `<img>` 直接丢弃并提示。
- 正文单张 ≤2MB，不限张数；实时字节计数，发布前最终 HTML 再校验 666KB。
- 变量用自定义 inline node 插入。
- `safe=2` 固定显示在 mpnews 项上，不允许其他类型设置。
- 移动端 mpnews 富文本编辑提示“请在桌面端编辑”，移动端保留预览。

### 9.7 预览

[站内] [企微应用] [企微群]

- 预览使用当前草稿，由服务端渲染；不实际发送。

- mpnews 预览在 sandbox iframe 中渲染，禁止脚本；显示封面、标题、作者、摘要、正文。
- 群机器人预览显示发送顺序和 @ 配置。

### 9.11 API 与前端状态

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/notifications/event-configs` | 列表 + 状态摘要 |
| `GET` | `/notifications/event-configs/:eventType` | 详情 + 渠道配置 + 内容 |
| `PUT` | `/notifications/event-configs/:eventType` | 聚合保存渠道 + 内容 |
| `POST` | `/notifications/event-configs/:eventType/preview` | 基于已保存配置的预览 |
| `POST` | `/notifications/content-media` | Tiptap 正文图片与 mpnews 封面草稿上传 |
| `GET` | `/notifications/content-media/:assetId/content` | 已被事件配置引用的内容图片私有读取 |
| `HEAD` | `/notifications/content-media/:assetId/content` | 内容图片缓存头校验 |

- 不再有模板 CRUD、模板选择、模板预览接口；旧 `/notifications/templates` 与 `/notifications/channel-policies` 已移除。
- 发布命令不再接收 `templateKey`；记录页的 `templateKey` 字段已改名为 `contentKey`（历史值为旧模板键，新值为事件类型）。
- 内容图片上传只创建 `UPLOADING` 草稿资产，由事件配置保存事务激活为 `READY`；未保存的草稿按上传过期清理。
- 内容图片读取只放行已被事件配置引用的资产；草稿阶段前端使用本地 blob 预览，不暴露跨业务域媒体。
- 前端草稿包含两个渠道配置、消息项数组、稳定 `clientId`、`dirty`、`validation`、每个渠道的 `expectedVersion`。
- 服务端错误按 item/field 映射回草稿。

### 9.12 前端验证

- 内容抽屉：添加/删除/上移/下移、类型切换、校验定位。
- 草稿保存：页签级 dirty、离开拦截、版本冲突。
- 预览：草稿、DMS 签名图片、mpnews sandbox iframe。
- mpnews：封面比例提示、Tiptap 图片上传、外链图片粘贴丢弃、2MB/666KB 限制、`safe=2` 标识。
- 移动端：复杂编辑器提示桌面端、预览可用。
- 发送记录：方式徽章、逐消息项状态、mpnews 预览。

## 10. 迁移与实施顺序

1. 数据模型、内容校验与 `TEXT` / `MPNEWS` / `IMAGE` 发布派发已落地。
2. 旧策略/模板已由 `20261125150000_notification_legacy_content_copy` 按事件渠道复制为内容消息项；共享模板按事件拆开，不再保留共享引用。
3. 发布 API / `SystemNotificationPublishCommand` 的 `templateKey` 已移除，业务发布点不再传模板键。
4. 旧模板/策略 API、DTO、权限、前端页面与旧发布回退分支已下线；`notification_templates` / `notification_channel_policies` 表按约定保留一个发布周期供回滚核对，代码不再读写。删除旧表需单独迁移和明确授权。
5. 新迁移已登记到[数据库迁移规范](../后端文档/数据库迁移规范.md)。
6. Tiptap 已接入；服务端对 mpnews 正文执行严格标签/属性白名单校验（未知标签、属性、未加引号属性、注释与错误嵌套直接拒绝），保存和渲染两条路径都校验，未引入第三方 sanitizer 库。
7. 主动节流应与消息组同批落地，否则多消息项会放大限流风险。
8. 先选择一个事件做端到端试点，再逐步开放更多消息类型。

## 11. 剩余确认与风险

| 项目 | 状态 |
| --- | --- |
| Tiptap 与 HTML 校验 | Tiptap 已接入；服务端使用内置严格白名单校验，不引入第三方 sanitizer 库 |
| `uploadimg` 配额监控 | 未做；告警阈值、配额耗尽时的失败与重试策略待定 |
| 封面预览 | 已做固定 1068:455 预览框与比例提示，不做硬校验 |
| 主动节流 | 未做；按 webhook / 按成员滑动窗口的实现方式待定 |
| 消息类型分期 | 已开放 `TEXT`、`MPNEWS`、`IMAGE`；其余类型仍为模型枚举 |
| 迁移窗口 | 旧表保留一个发布周期；删除旧表需单独迁移与明确授权 |
| 其他消息项的 `safe` | 仍只对 `MPNEWS` 设置 `safe=2` |
| 图片数量提示 | 由 `IMAGE` 项的 `maxCount` 与事件能力上限共同约束，前端做输入上限收敛 |
| 页面级验收 | 事件列表/详情、图片附件编辑、记录页尚未做浏览器人工验收 |
