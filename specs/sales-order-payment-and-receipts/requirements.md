# 销售订单收款与凭证需求规格

## 1. 文档状态

- 状态：需求、技术方案与增量实施均已完成聚焦验证
- 确认日期：2026-08-25
- 依赖规格：[销售订单域需求规格](../sales-order-domain/requirements.md)
- 目标页面：`/operations/sales-orders`、`/operations/sales-orders/create`

## 2. 目标

把销售订单的媒体文件按业务事件拆分为出单凭证、收款凭证和签收单三条明确链路，消除“订单级凭证是否漏关联收款”的歧义，并为后续管理员审批货物签收建立稳定边界。

## 3. 业务边界

- 销售总价按含税总价处理。
- 约定定金、约定尾款继续与实际收款分开保存。
- 每张新订单必须且只能保存一份出单凭证；出单凭证是订单级凭证，不关联实际收款。
- 每笔实际收款必须且只能保存一份收款凭证；收款记录与凭证必须在同一事务内建立关联。
- “货物签收”操作只要求上传一份签收单；签收单是订单级凭证，不关联实际收款。
- 上传签收单暂不自动把订单进度更新为 `SIGNED`；管理员审批不在本期范围。
- 收款不保存交易流水号；内部记录身份继续使用系统生成的 `SalesOrderPayment.id`。
- 本期不建设退款、签收审批、签收驳回、凭证替换和补录出单凭证流程。

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| 出单凭证 | 创建订单时必须上传的唯一订单级凭证 |
| 收款凭证 | 与一笔实际收款一一关联的付款证明 |
| 签收单 | 用户通过“货物签收”操作上传的订单级履约材料 |
| 订单级凭证 | `paymentId = null`，不属于任何一笔实际收款的凭证 |
| 有效收款 | 未作废的实际收款记录 |

## 5. 需求与验收标准

### R1 - 新增订单出单凭证

**User Story：** 作为出单人员，我希望新增订单只要求一份明确的出单凭证，避免在创建阶段误传收款凭证或签收单。

#### Acceptance Criteria

1. 当用户进入新增订单的凭证步骤时，销售订单系统应只显示“出单凭证”上传入口，不得提供凭证类型选择器。
2. 当用户尚未上传出单凭证时，销售订单系统应阻止进入最终提交状态并提示“请上传出单凭证”。
3. 当用户已经上传一份出单凭证时，销售订单系统应禁止继续添加第二份文件，但允许用户在正式提交前移除并重新上传。
4. 当用户正式提交订单时，销售订单系统应在服务端再次校验出单凭证数量恰好为一份。
5. 当订单创建成功时，销售订单系统应把出单凭证保存为订单级凭证，不得设置 `paymentId`。
6. 当用户没有订单凭证管理权限时，销售订单系统应阻止其创建订单并明确说明缺少 `sales-orders:document` 权限，不得退化为无凭证创建。
7. 当订单已经创建时，销售订单系统不得允许通过通用凭证删除操作移除唯一的出单凭证。

### R2 - 凭证自动命名

**User Story：** 作为订单操作人员，我希望所有凭证使用统一且可辨识的系统标题，便于查询和核对。

#### Acceptance Criteria

1. 当任意订单凭证正式关联业务记录时，销售订单系统应按“客户名-凭证类型-时间戳”生成凭证标题。
2. 当生成时间戳时，销售订单系统应使用 `yyyyMMddHHmmssSSS` 格式，不包含空格或标点。
3. 当生成凭证标题时，销售订单系统应使用最终保存的客户姓名和受信任的凭证类型，不得信任客户端提交的任意标题。
4. 当完整标题超过 128 个 Unicode code point 时，销售订单系统应只截断客户名部分，保留完整凭证类型和时间戳。
5. 当系统生成标题时，销售订单系统应保留媒体资产的原始文件名、MIME 类型和大小，不得覆盖审计所需的原始文件元数据。
6. 当凭证尚处于上传或弹窗编辑阶段时，Web 应使用相同规则显示预览标题；服务端保存结果仍为最终真相源。
7. 当凭证进入业务记录后，用户不得手工修改系统生成的凭证标题。

自动命名中的凭证类型文案固定为：

| 业务场景 | 凭证类型文案 |
| --- | --- |
| 新增订单 | 出单凭证 |
| 定金收款 | 定金凭证 |
| 过程款收款 | 过程款凭证 |
| 开票税金收款 | 开票税金凭证 |
| 尾款收款 | 尾款凭证 |
| 其他收款 | 其他收款凭证 |
| 货物签收 | 签收单 |

### R3 - 实际收款类型与字段

**User Story：** 作为销售或财务人员，我希望按真实业务阶段登记收款，以便准确统计累计已收和付款状态。

#### Acceptance Criteria

1. 当用户打开“添加收款”弹窗时，销售订单系统应提供 `DEPOSIT`、`PROGRESS`、`INVOICE_TAX`、`BALANCE` 和 `OTHER` 五种收款类型。
2. 当用户提交收款时，销售订单系统应要求收款类型、正数金额、有效收款时间、有效收款方式和一份收款凭证完整存在。
3. 当用户登记收款时，销售订单系统应要求从 `payment.method` 字典选择收款方式，允许填写备注，但不得显示、接收或保存交易流水号。
4. 当收款时间晚于当前时间时，销售订单系统应硬拦截保存。
5. 当订单已经取消时，销售订单系统应拒绝新增实际收款。
6. 当用户不同时具备 `sales-orders:payment` 和 `sales-orders:document` 权限时，销售订单系统应禁用“添加收款”操作并显示权限原因。

### R4 - 收款与凭证原子保存

**User Story：** 作为财务人员，我希望收款记录和凭证同时成功或同时失败，避免出现缺少凭证的到账记录。

#### Acceptance Criteria

1. 当用户提交有效收款时，销售订单系统应在同一数据库事务中创建实际收款、激活临时媒体、创建收款凭证关联、更新付款状态并写入审计记录。
2. 当任一事务步骤失败时，销售订单系统应回滚收款、凭证关联和付款状态，不得留下部分成功的业务记录。
3. 当临时媒体不可用、已被使用、不属于当前用户或类型不允许时，销售订单系统应拒绝整笔收款。
4. 当创建收款凭证时，销售订单系统应要求其 `paymentId` 指向同一订单内刚创建的收款记录。
5. 当查询收款详情时，销售订单系统应返回该笔收款关联的唯一凭证。
6. 当收款被作废时，销售订单系统应保留原收款凭证和关联关系用于审计，不得删除凭证。

### R5 - 含税累计收款与付款状态

**User Story：** 作为管理人员，我希望所有真实到账都按含税销售总价计算付款进度。

#### Acceptance Criteria

1. 当收款类型为开票税金时，销售订单系统应把该金额计入累计有效收款。
2. 当任意有效收款新增或作废时，销售订单系统应按全部有效收款重新计算累计已收和待收金额。
3. 当累计有效收款为零时，付款状态应为 `UNPAID`。
4. 当累计有效收款大于零且小于含税销售总价时，付款状态应为 `PARTIALLY_PAID`。
5. 当累计有效收款等于含税销售总价时，付款状态应为 `PAID`。
6. 当新增任意类型收款将导致累计有效收款超过含税销售总价时，销售订单系统应硬拦截保存。

### R6 - 货物签收

**User Story：** 作为订单操作人员，我希望通过独立的货物签收入口上传签收单，为后续管理员审批提供材料。

#### Acceptance Criteria

1. 当用户点击“货物签收”时，销售订单系统应打开包含签收单上传控件和选填备注的弹窗。
2. 当用户尚未上传签收单时，销售订单系统应禁止提交货物签收操作。
3. 当用户提交货物签收时，销售订单系统应一次只接收一份签收单并保存为订单级凭证，不得设置 `paymentId`。
4. 当签收单保存成功时，销售订单系统不得自动修改 `fulfillmentStatus`。
5. 当签收单保存成功时，销售订单系统应记录上传人、上传时间和凭证审计事件。
6. 当同一订单再次执行货物签收时，销售订单系统应允许继续新增一份签收单；本期不判断或展示审批结果。
7. 当用户没有 `sales-orders:document` 权限时，销售订单系统应禁用“货物签收”操作并显示权限原因。

### R7 - 凭证展示语义

**User Story：** 作为订单查看人员，我希望凭证详情准确表达其业务归属，而不是把正常的订单级凭证显示成异常状态。

#### Acceptance Criteria

1. 当凭证类型为出单凭证时，销售订单系统应显示“订单级凭证”。
2. 当凭证类型为签收单时，销售订单系统应显示“订单级凭证”。
3. 当凭证类型为收款凭证时，销售订单系统应显示关联的收款类型、金额、收款时间和有效/已作废状态。
4. 当数据异常导致收款凭证没有 `paymentId` 时，销售订单系统才应显示“未关联实际收款”。
5. 当展示图片凭证时，销售订单系统应继续使用 `FaImagePreview` 提供预览。

### R8 - 历史兼容与物理删除流水号

**User Story：** 作为系统维护人员，我希望历史订单可继续查看，同时彻底移除已经不使用的交易流水号字段。

#### Acceptance Criteria

1. 当部署数据库迁移时，销售订单系统应物理删除 `sales_order_payments.reference_no` 列，不保留兼容字段。
2. 当生成 Prisma、OpenAPI 和 Web 类型时，销售订单系统不得再出现 `referenceNo`。
3. 当迁移现有未关联收款的 `DEPOSIT_VOUCHER` 或 `OTHER` 凭证时，销售订单系统应将其归类为出单凭证。
4. 当迁移现有已关联收款的凭证时，销售订单系统应将其归类为收款凭证并保留 `paymentId`。
5. 当迁移现有 `DELIVERY_RECEIPT` 时，销售订单系统应保留其签收单语义并保持 `paymentId = null`。
6. 当历史订单没有出单凭证时，销售订单系统应允许继续读取该订单，但不得伪造或自动生成不存在的凭证。

### R9 - 实际收款继承订单币种

**User Story：** 作为财务人员，我希望实际收款金额始终使用订单币种，避免在同一订单中误录其他币种。

#### Acceptance Criteria

1. 当用户打开实际收款表单时，销售订单系统应按当前订单的 `currencyCode` 显示金额符号、精度和币种代码。
2. 当订单币种为 `TWD` 时，销售订单系统应只允许录入 TWD 金额，不得提供 MYR 或其他币种选项。
3. 当订单币种为 `MYR` 时，销售订单系统应只允许录入 MYR 金额，不得提供 TWD 或其他币种选项。
4. 当用户查看或提交实际收款时，销售订单系统应把金额解释为订单币种，不得在收款请求或收款记录中建立独立币种字段。
5. 当订单币种描述不存在、未加载或无效时，销售订单系统应阻止提交收款，不得使用其他币种兜底。

### R10 - 收款方式字典化

**User Story：** 作为财务人员，我希望从统一字典选择收款方式，以便后续统计和审计使用稳定口径。

#### Acceptance Criteria

1. 当系统提供收款方式时，销售订单系统应从代码为 `payment.method` 的系统字典读取当前有效条目。
2. 当初始化 `payment.method` 字典时，系统应创建 `BANK_TRANSFER`（银行转账）、`CASH`（现金付款）、`CHECK`（支票支付）和 `LETTER_OF_CREDIT`（信用证 L/C）四个有效条目。
3. 当用户新增实际收款时，销售订单系统应要求选择一个当前有效的收款方式，不得接受自由文本、空值、未知值或已停用值。
4. 当服务端保存收款时，销售订单系统应在同一收款事务中再次校验字典类型和条目均有效，并保存条目的稳定 `value`，不得保存展示 `label` 或字典条目 UUID。
5. 当展示历史收款时，销售订单系统应优先显示字典 `label`；对于历史空值应显示缺省占位，对于未知或已停用的历史值应保留可审计的原始值且不得阻止查询。
6. 当 `payment.method` 字典缺失、停用、为空或加载失败时，销售订单系统应关闭收款方式选择并阻止新增收款提交。

### R11 - 单弹窗操作流

**User Story：** 作为订单操作人员，我希望点击收款或签收入口时只看到一个稳定弹窗，避免父子弹窗依次出现造成闪屏和层级混乱。

#### Acceptance Criteria

1. 当用户从订单表格操作列点击“新增实际收款”时，销售订单系统应先确定收款视图再打开唯一弹窗，不得先显示记录列表弹窗。
2. 当用户从订单表格操作列点击“货物签收”时，销售订单系统应先确定签收视图再打开唯一弹窗，不得先显示订单凭证弹窗。
3. 当用户从记录列表弹窗进入收款或签收操作时，销售订单系统应在同一弹窗容器内切换标题、内容和底部操作，不得叠加第二个可见弹窗。
4. 当用户从记录列表进入操作表单并取消时，销售订单系统应返回原记录视图；当用户从表格直接进入操作表单并取消时，系统应关闭弹窗。
5. 当收款或签收保存成功时，销售订单系统应刷新对应记录和订单列表汇总，并保持任一时刻最多一个可见 `role="dialog"`。
6. 当操作表单正在上传或提交时，销售订单系统应锁定视图切换、关闭和重复提交，避免丢失编辑状态或产生重复业务记录。

## 6. 非功能要求

- 金额继续使用十进制定点计算，客户端展示不得成为付款状态真相源。
- 收款、凭证与付款状态变更必须在订单行锁保护下串行完成。
- Mutation 禁止自动重试；重复点击由前端提交锁控制，不新增未确认的幂等协议。
- 临时媒体上传不得提前修改订单、付款状态或履约状态。
- 审计和日志不得记录媒体内容、完整客户信息或完整请求体。
- Web 延续现有 `Industrial/utilitarian` 视觉方向、主题 Token、Noto 字体和 Lucide 图标。
- 桌面与窄屏必须提供相同的“添加收款”“货物签收”能力及明确的权限、上传和提交状态。
- 收款方式必须存储字典稳定值，并沿用现有字典 Catalog 的失败关闭和历史值可审计边界。
- 表格快捷入口与记录弹窗内部入口必须共享同一表单逻辑，不得复制两套校验或提交实现。

## 7. 本期不包含

- 管理员签收审批、驳回及审批意见。
- 上传签收单后自动进入 `SIGNED`。
- 退款、冲销到退款账户或负数收款。
- 收款凭证、出单凭证的事后替换。
- 为缺少出单凭证的历史订单自动生成文件。
