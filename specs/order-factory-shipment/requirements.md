# 销售与采购订单工厂发货需求规格

## 2. 背景与目标

销售订单可以关联多张采购订单，因此销售待办中的“工厂发货”不能直接把销售订单推进到下一履约状态，而应先明确本次实际发货的采购订单。待办采购中的“发货”已经具备唯一采购单上下文，不需要再次选择。

本需求以采购订单作为工厂发货事实的唯一归属：两个入口复用同一套采购发货规则；销售订单只在全部有效关联采购订单均已发货且销售产品仍然全部采购覆盖时，自动从 `PREPARING` 推进到 `LAND_TRANSIT`。

## 3. 已确认需求基线

1. 单张采购订单首期只支持整单发货，不支持按采购明细或数量部分发货。
2. 首期只记录操作时间、操作人和可选发货说明，不录入物流公司、运单号或发货附件。
3. 当采购订单当前为 `ORDERED` 时，确认发货应由服务端在同一事务中依次补齐 `ORDERED -> PREPARING -> SHIPPED`，不得放宽既有严格顺序状态机。
4. 销售入口允许一次选择一张或多张采购订单，也允许一次发货全部剩余待发货采购订单。
5. 发货事实写入采购订单；销售履约状态由全部有效关联采购订单的最新事实自动汇总，不允许 Web 端直接推断或写入。

## 4. 术语与计算口径

### 4.1 有效关联采购订单

销售订单的有效关联采购订单必须同时满足：

- `purchaseType = SALES_LINKED`；
- `salesOrderId` 等于当前销售订单 ID；
- `orderStatus != CANCELLED`。

独立备货采购不属于任何销售订单的发货范围。已取消采购订单不参与候选数量、待发货数量或销售履约状态汇总。

### 4.2 待发货采购订单

待发货采购订单必须同时满足：

- `orderStatus = CONFIRMED`；
- `fulfillmentStatus IN (ORDERED, PREPARING)`。

### 4.3 已满足发货事实

当有效关联采购订单的 `fulfillmentStatus IN (SHIPPED, SIGNED)` 时，该采购订单视为已经满足发货事实。`SIGNED` 是 `SHIPPED` 的后续状态，不得因为销售订单汇总而回退。

### 4.4 整体发货

“全部待发货采购单”或“整体发货”指：在服务端正式提交事务中，当前销售订单下全部有效且尚处于 `ORDERED` 或 `PREPARING` 的关联采购订单。

Web 端弹窗加载时的候选快照只用于展示，不能作为整体范围的最终真相源。

### 4.5 销售订单进入陆运中的条件

销售订单只有同时满足以下条件时，才允许自动从 `PREPARING` 推进到 `LAND_TRANSIT`：

- `orderStatus = CONFIRMED`；
- 当前 `fulfillmentStatus = PREPARING`；
- 销售订单至少存在一张有效关联采购订单；
- 当前全部有效销售明细仍然被有效采购明细数量完整覆盖；
- 每张有效关联采购订单的履约状态均为 `SHIPPED` 或 `SIGNED`。

任一条件不满足时，销售订单不得进入 `LAND_TRANSIT`。

## 5. 功能需求与验收标准

### R1 - 待办采购单张发货入口

**User Story：** 作为采购人员，我希望在待办采购的待发货视图中直接确认当前采购单发货，以免重复选择已经明确的采购单。

#### Acceptance Criteria

1. 当用户在待办采购的待发货视图点击“发货”时，Web 应打开当前采购订单的发货确认弹窗，不得打开采购详情抽屉。
2. 当发货确认弹窗打开时，Web 应展示采购单号、供应商、销售来源或“独立备货”、产品项数、产品总数量和当前履约状态。
3. 当用户尚未提交时，Web 应允许填写最多 500 个 Unicode code point 的可选发货说明。
4. 当用户点击“确认本单发货”时，系统应只处理弹窗对应的唯一采购订单。
5. 当采购订单属于独立备货采购时，系统应完成采购发货，但不得读取或修改任何销售订单。
6. 当销售关联采购订单发货成功时，系统应在同一事务中重新计算其销售订单是否满足整体发货条件。

### R2 - 销售待办选择发货范围

**User Story：** 作为销售订单运营人员，我希望从销售订单中选择实际发货的采购单或整体发货，以准确处理一张销售订单拆分为多张采购单的情况。

#### Acceptance Criteria

1. 当用户在销售待办订单的待发货视图点击“工厂发货”时，Web 应打开该销售订单的关联采购发货弹窗。
2. 当弹窗加载时，系统应只返回属于当前销售订单的有效关联采购订单，不得混入独立备货、其他销售订单或已取消采购订单。
3. 当弹窗展示采购订单时，Web 应按“待发货在前、已发货在后”的顺序显示。
4. 当采购订单处于 `ORDERED` 或 `PREPARING` 时，Web 应允许用户选择该采购订单。
5. 当采购订单处于 `SHIPPED` 或 `SIGNED` 时，Web 应以灰色只读行展示其已发货状态，不得允许重复选择。
6. 当用户选择“指定采购单发货”时，Web 应允许选择一张或多张待发货采购订单，并且至少选择一张后才能提交。
7. 当用户选择“全部待发货采购单”时，Web 应清晰提示整体发货影响，并由服务端在提交时重新确定全部剩余待发货采购订单。
8. 当销售订单只剩一张待发货采购订单时，Web 可以默认选中该订单，但仍应展示确认弹窗和状态影响。
9. 当销售订单已不存在待发货采购订单时，Web 应禁止提交并提示刷新订单状态。

### R3 - 提交前结果预告

**User Story：** 作为业务人员，我希望提交前知道本次发货是否会推进销售订单，以避免误以为部分发货已经完成整个销售订单的工厂发货。

#### Acceptance Criteria

1. 当指定范围未覆盖全部剩余待发货采购订单时，Web 应显示本次发货采购单数量、剩余待发货采购单数量，并说明销售订单将保持 `PREPARING`。
2. 当指定范围覆盖全部剩余待发货采购订单时，Web 应说明销售订单在服务端复核全部条件后将进入 `LAND_TRANSIT`。
3. 当用户选择整体发货时，Web 应使用明确的强调提示说明“全部剩余待发货采购单将被确认发货”。
4. 当候选采购订单或销售订单状态在弹窗打开后发生变化时，最终结果必须以服务端提交时重新读取的事实为准。

### R4 - 采购订单严格顺序推进

**User Story：** 作为审计人员，我希望发货操作仍然保留完整的采购履约路径，以便追溯采购单从已下单、备货中到已发货的过程。

#### Acceptance Criteria

1. 当待发货采购订单当前为 `PREPARING` 时，确认发货应把履约状态更新为 `SHIPPED`。
2. 当待发货采购订单当前为 `ORDERED` 时，确认发货应在同一事务中依次写入 `ORDERED -> PREPARING` 和 `PREPARING -> SHIPPED`。
3. 当系统补齐 `ORDERED -> PREPARING` 时，系统应写入独立的履约状态历史，并明确标识该步骤由确认发货自动补齐。
4. 当系统写入 `PREPARING -> SHIPPED` 时，系统应记录本次操作用户、操作时间和用户填写的可选发货说明。
5. 当采购订单已经处于 `SHIPPED` 或 `SIGNED` 时，相同目标的安全重试应视为已经满足，不得重复写入状态历史或审计事件。
6. 当采购订单已经取消、关联关系不匹配或处于其他非法状态时，系统应拒绝整个发货请求，不得修改任何目标订单。

### R5 - 销售履约状态自动联动

**User Story：** 作为销售订单运营人员，我希望所有关联采购单发货后销售订单自动进入陆运中，同时部分发货时继续留在待发货视图。

#### Acceptance Criteria

1. 当本次发货完成后仍存在 `ORDERED` 或 `PREPARING` 的有效关联采购订单时，系统应保持销售订单 `fulfillmentStatus = PREPARING`。
2. 当本次发货完成后全部有效关联采购订单均处于 `SHIPPED` 或 `SIGNED`，并且销售产品仍然全部采购覆盖时，系统应自动把销售订单从 `PREPARING` 更新为 `LAND_TRANSIT`。
3. 当销售订单自动进入 `LAND_TRANSIT` 时，系统应写入销售履约状态历史和审计事件，并标识由采购发货汇总触发。
4. 当销售订单已经进入 `LAND_TRANSIT` 或后续状态时，安全重试不得倒退、重复推进或重复写入历史。
5. 当销售订单不再是 `CONFIRMED`、不再处于 `PREPARING` 或产品覆盖不完整时，系统不得推进销售履约状态。
6. 当单张销售关联采购单通过待办采购入口完成最后一张发货时，系统应执行与销售入口相同的销售状态联动。

### R6 - 批量原子性与并发一致性

**User Story：** 作为系统维护人员，我希望多张采购单发货要么全部成功、要么全部失败，并且并发操作不会造成错误的销售进度。

#### Acceptance Criteria

1. 当用户一次提交多张采购订单发货时，系统应在单个数据库事务中处理全部采购状态、历史、审计和销售状态联动。
2. 当任一目标采购订单校验失败时，系统应回滚本次请求中的全部变更，不得产生部分成功。
3. 当多个用户同时处理同一采购订单或同一销售订单下的不同采购订单时，系统应使用稳定锁顺序和服务端重算保证最终状态一致。
4. 当“全部待发货采购单”与新增、取消或其他发货操作并发发生时，系统应以事务中的可信事实重新计算，不得遗漏仍有效的待发货采购单后错误推进销售订单。
5. 当客户端重复点击或网络结果未知后安全重试时，系统应对已经达到 `SHIPPED` 或后续状态的相同目标执行无副作用响应。

### R7 - 权限与跨域边界

**User Story：** 作为系统管理员，我希望只有同时具备相应销售和采购权限的人员才能从销售入口操作采购发货。

#### Acceptance Criteria

1. 当用户从待办采购入口发货时，系统应要求 `purchase-orders:update` 权限。
2. 当用户从销售待办入口读取关联采购发货上下文时，系统应要求销售订单读取权限和采购订单读取权限。
3. 当用户从销售待办入口提交采购发货时，系统应同时要求 `sales-orders:update` 和 `purchase-orders:update` 权限。
4. 当用户缺少实际发货所需权限时，Web 不得展示可操作的发货按钮，服务端仍必须独立执行权限校验。
5. 当用户提交其他销售订单、独立备货采购或已取消采购订单的 ID 时，服务端应拒绝整个请求。

### R8 - 用户反馈与列表刷新

**User Story：** 作为操作人员，我希望发货后立即知道处理结果以及销售订单是否进入下一阶段。

#### Acceptance Criteria

1. 当单张独立备货采购发货成功时，Web 应以成功轻提示告知采购单已发货。
2. 当销售关联采购部分发货成功时，Web 应以成功轻提示告知本次完成数量和剩余待发货数量，并说明销售订单仍为备货中。
3. 当全部有效关联采购订单已发货且销售订单成功进入 `LAND_TRANSIT` 时，Web 应以成功轻提示明确告知销售订单已进入陆运中。
4. 当服务端发现状态或关联关系已经变化时，Web 应显示可理解的失败提示，并刷新当前列表及状态计数。
5. 当发货成功时，Web 应刷新当前列表、工具栏计数和受影响订单，不得仅在本地修改当前行形成陈旧数据。
6. 当请求正在提交时，Web 应锁定关闭和重复提交动作；请求失败后应保留用户已填写的发货说明以便重试。

## 6. UI 设计规格

### 6.1 Purpose Statement

在不增加页面跳转的前提下，让采购人员快速确认单张采购发货，让销售运营人员准确选择实际发货的关联采购单，并在提交前理解销售状态是否会联动推进。

### 6.2 Aesthetic Direction

- `Industrial/utilitarian`
- 延续当前千树运营工作台的高密度业务表格和 `QsGenericModal` 交互体系。
- 不引入与现有订单页面冲突的新视觉语言。

### 6.3 Color Palette

- 确认与完成：绿色 `#16A34A`
- 部分发货提示：琥珀色 `#D97706`
- 陆运状态：天蓝色 `#0284C7`
- 次要信息和只读行：灰色 `#6B7280`
- 错误与失效状态：红色 `#DC2626`

实现时应优先使用现有主题 Token 和对应 UnoCSS 语义类，以上色值用于固定视觉意图。颜色不得成为表达状态的唯一方式。

### 6.4 Typography

- 中文与普通业务文本：项目现有 `Noto Sans`。
- 采购单号、销售单号、数量和状态影响数据：项目现有 `Noto Sans Mono` 或 `qs-type-data-*` 类型类。

### 6.5 Layout Strategy

- 销售“工厂发货”弹窗采用较宽的非对称布局：左侧为采购单范围选择和列表，右侧为固定的发货影响摘要；窄屏降级为上下排列。
- 待办采购“发货”弹窗采用紧凑单列布局，不重复提供采购单选择。
- 待发货采购单优先展示；已发货采购单置后、灰色只读展示。
- 桌面和窄屏均保持订单号、状态文字和确认按钮完整可读，不依赖横向拖动才能完成提交。

### 6.6 Icons

- 工厂发货：项目现有 Lucide `factory`。
- 采购单发货：项目现有 Lucide `truck`。
- 已发货：Lucide `package-check`。
- 不使用 Emoji 作为业务图标。

## 7. 非功能要求

1. 服务端状态机、事务内数据库事实和权限校验是最终真相源，Web 只负责表达用户意图。
2. 任何批量发货不得通过 Web 循环调用单张状态接口实现。
3. 发货请求不得自动重试未知结果；客户端应刷新服务端状态并提供安全重试。
4. 操作不得在日志、轻提示或审计元数据中泄露客户电话、地址或其他不必要的个人信息。
5. 新功能、BUG 修复和复杂状态联动采用 TDD，覆盖服务、状态机、Controller/OpenAPI、页面逻辑和真实浏览器主路径。
6. 本期确认的信息均可由现有采购状态历史和审计能力承载，不新增数据库表或字段，不新增 migration。
7. 技术设计阶段如需新增或修改公共 API、DTO 或 OpenAPI 契约，必须在实施前另行获得确认。

## 8. 非目标

- 单张采购订单按产品、明细或数量部分发货。
- 物流公司、运单号、车牌号、司机、预计到达时间等结构化物流信息。
- 发货单、装箱单或物流凭证上传。
- 发货撤回、履约状态倒退或管理员强制覆盖。
- 独立的采购发货记录表或多次发货记录模型。
- 自动对接供应商、物流商、仓库或第三方物流接口。
- 修改“货物入仓”“装柜出货”或“货物签收”的现有业务规则。

## 9. 核心验收场景

| 场景 | 发货前采购状态 | 其他有效采购单 | 采购结果 | 销售结果 |
| --- | --- | --- | --- | --- |
| 独立备货单发货 | `PREPARING` | 不适用 | `SHIPPED` | 不影响销售 |
| 已下单采购直接确认发货 | `ORDERED` | 不适用 | 依次补齐至 `SHIPPED` | 视销售关联情况重算 |
| 销售订单指定一张发货 | `PREPARING` | 仍有待发货 | 当前单 `SHIPPED` | 保持 `PREPARING` |
| 销售订单选择多张但未全部 | `ORDERED/PREPARING` | 仍有待发货 | 所选单全部 `SHIPPED` | 保持 `PREPARING` |
| 销售订单整体发货 | `ORDERED/PREPARING` | 无剩余 | 全部 `SHIPPED` | `PREPARING -> LAND_TRANSIT` |
| 采购入口完成最后一张 | `PREPARING` | 其余均已发货 | 当前单 `SHIPPED` | `PREPARING -> LAND_TRANSIT` |
| 存在已签收采购单 | `PREPARING` | 其他均 `SHIPPED/SIGNED` | 当前单 `SHIPPED` | `PREPARING -> LAND_TRANSIT` |
| 产品覆盖已经不完整 | `PREPARING` | 全部已发货 | 采购发货成功 | 销售不得推进 |
| 并发中一张采购被取消 | `PREPARING` | 集合发生变化 | 事务内重算或整体失败 | 不得错误推进 |
| 重复提交相同已发货目标 | `SHIPPED` | 不变 | 无重复历史 | 无重复销售推进 |
