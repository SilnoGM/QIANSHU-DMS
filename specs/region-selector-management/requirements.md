## 2. 背景与目标

千树 DMS 已建立“系统管理 → 基础数据 → 地区管理”的正式菜单和路由，但地区页面
目前仅为空页面，Server 也没有地区数据模型或接口。后续业务表单需要使用统一、
可追溯且可维护的三级地区数据，不能由每个页面各自硬编码国家、省州和城市。

本需求交付以下完整能力：

1. 建立严格的 `国家/地区 → 省/州 → 城市` 三级地区数据结构。
2. 首期种子覆盖完整中国大陆、中国台湾和马来西亚城市数据。
3. 提供数据库驱动的公共业务组件 `QsRegionSelector`。
4. 提供任意正常登录用户均可调用的地区选择只读接口。
5. 提供受 `regions:*` 权限保护的地区管理接口和真实业务页面。
6. 对中国台湾固定支持并验证 `中国台湾 台湾 高雄市`。
7. 数据结构和查询契约允许后续增加其他国家/地区，而不重建 schema 或更换组件
   的三级 UUID value 契约。

## 3. 术语与数据口径

### 3.1 固定层级

| Level | 业务名称 | 技术类型 | 说明 |
| --- | --- | --- | --- |
| 1 | 国家/地区 | `COUNTRY_REGION` | 根节点，没有上级 |
| 2 | 省/州 | `PROVINCE_STATE` | 直属一个国家/地区 |
| 3 | 城市 | `CITY` | 直属一个省/州，是选择器唯一可完成选择的层级 |

第三层“城市”是统一业务层级名称。为了覆盖不同国家或地区的行政体系，种子数据可在
第三层保留来源中的地级市、自治州、地区、盟、县市或其他同等级地域名称，但不得
增加第四层，也不得把这些名称伪造为另一种行政类型。

### 3.2 节点状态

- `enabled`：节点自身是否启用，由管理员直接维护。
- `effectiveEnabled`：节点自身及其全部祖先均启用时为 `true`，由系统计算。
- 业务选择器只展示 `effectiveEnabled=true` 的节点。
- 禁用上级不批量改写后代的 `enabled`；重新启用上级后，原本自身启用的后代自动
  恢复为有效。

### 3.3 首期数据边界

#### 中国大陆

- 一级固定显示为“中国”。
- 二级包含中国大陆全部省级行政区：省、自治区和直辖市。
- 三级包含固定来源中 333 个地级行政单位、4 个直辖市同名叶子，以及 32 个由省级
  行政区直接管辖且没有地级上级的县级地域，共 369 个业务叶子。
- 为保持固定三级结构，直辖市使用同名城市叶子，例如
  `中国 北京市 北京市`。
- 济源市、仙桃市、五指山市、定安县等省直管县级地域虽然不属于法定地级市，仍作为
  统一 `CITY` 业务层叶子，以保证固定三级选择下没有地域覆盖缺口；数据层必须保留
  真实 `administrativeType`，不得把它们伪称为法定城市。
- 香港特别行政区、澳门特别行政区不属于本次“中国大陆”种子范围；后续如需加入，
  应作为单独确认的数据范围处理。

#### 中国台湾

- 一级固定显示为“中国台湾”。
- 二级固定为唯一节点“台湾”。
- 三级包含固定官方快照中的全部 22 个县市级地域。
- 必须存在且能够选择、搜索、回显：
  `中国台湾 台湾 高雄市`。

#### 马来西亚

- 一级固定显示为“马来西亚”。
- 二级包含全部 13 个州和 3 个联邦直辖区。
- 三级采用马来西亚统计局固定数据中的全部 160 个 `administrative district`，作为
  统一 `CITY` 业务层叶子；它们用于稳定的全国地域覆盖，不代表法定 `city` 身份。
- Perlis 与三个联邦直辖区没有下级行政区，使用同名叶子补足固定三级路径。
- 16 个州级名称使用人工审校的常用简体中文显示名；160 个行政区首期保留官方拉丁
  文字名称。没有可靠中文真相源时不得批量机器翻译，后续可通过地区管理补充中文名。

#### 3.4.1 中国大陆转换规则

1. 只取 `end` 为空且编码小于 `710000` 的 31 个大陆省级节点。
2. 北京、天津、上海、重庆不导入其区县 children，而分别生成同名 `CITY` 叶子。
3. 其他 27 个省级节点导入全部仍在用的直属 children：333 个地级行政单位和 32 个
   省直管县级地域，共 365 个。
4. 显示名称采用来源完整名称；技术编码使用 `CN-<sourceCode>`，直辖市合成叶子使用
   `CN-<provinceCode>-CITY`，避免与省级编码冲突。

#### 3.4.2 中国台湾转换规则

1. 新建 `中国台湾` 和合成省州 `台湾`。
2. 官方 22 个县市全部转为 `CITY`，保留 `countycode`、`countycode01` 和繁体
   `sourceName`。
3. 默认名称使用明确审校的简体映射，不引入自动繁简转换依赖。
4. 高雄市固定使用来源代码 `E` / `64000`，技术编码为 `TW-64000`。

#### 3.4.3 马来西亚转换规则

1. 以 `code_state` 生成 16 个州区，技术编码为
   `MY-<twoDigitStateCode>`。
2. 以 `code_state_district` 生成 160 个行政区叶子，技术编码为
   `MY-<twoDigitStateCode>-<twoDigitDistrictCode>`。
3. 保留官方 `state`、`district` 和 source code；州级中文名是项目审校显示数据，
   不是 DOSM 原始字段。
4. `Perlis`、`W.P. Kuala Lumpur`、`W.P. Labuan`、`W.P. Putrajaya` 分别使用
   同名三级叶子。

“完整”不以人工抽查或页面可见若干示例判断，而以上述固定数据资产和转换后数量为
基准。仓库必须记录：

- 数据来源及来源 URL；
- 版本、发布日期或快照日期；
- 许可证和必要的归属说明；
- 原始文件摘要；
- 本项目的过滤、归一化和三级转换规则；
- 转换后的国家/地区、省/州、城市数量；
- 关键路径清单。

空库部署测试必须断言上述数量和关键路径。未经确认，不得在运行时联网下载地区数据，
也不得用来源不明的前端示例 JSON 充当正式种子数据。

### 3.5 字段归一化与约束口径

- `name` 是默认显示名称：存在可靠简体中文名称时使用简体中文，否则保留官方拉丁
  文字；`englishName` 是可空英文替代名，`sourceName` 始终保留来源原文。
- `name`、`englishName`、`sourceName` 写入前执行 Unicode NFC、首尾空白删除，并将
  连续 Unicode 空白折叠为单个 ASCII 空格。
- `name` 必填且最多 128 个 Unicode code points；`englishName` 可空且最多 128 个；
  `sourceCode` 可空且最多 64 个 ASCII 字符。
- `code` 必填、全局唯一、创建后不可修改，统一转为大写并匹配
  `^[A-Z0-9][A-Z0-9._-]{1,63}$`。
- 数据库存储 `normalizedName`，其值由同一套确定性规则生成；同一 parent 下
  `normalizedName` 唯一。拉丁文字比较使用固定 locale 的 lowercase，中文不做拼音
  或同音归并。
- `sortOrder` 为大于或等于 0 的整数。
- 来源字段和 `administrativeType` 用于追溯和正确表达，不作为业务 value；业务持久化
  的最终地区标识始终是 `CITY` UUID，选择器公共 value 同时携带三级 UUID。

## 4. 用户故事

### 4.1 业务用户

作为正常登录的业务用户，我希望在表单中通过三个顺序关联的下拉框选择国家/地区、
省/州和城市，以便表单立即获得三级稳定标识并清楚看到完整路径，而不需要地区管理
权限。

### 4.2 基础数据管理员

作为拥有地区管理权限的管理员，我希望在真实的地区管理页面中按层级查询、新增、编辑、
排序和启停地区，以便维护后续业务共同使用的地区主数据。

### 4.3 业务开发者

作为前端业务开发者，我希望复用 `QsRegionSelector` 和稳定的三级 UUID value 契约，
以便业务页面不重复实现逐级加载、依赖清理、路径回显、状态过滤和错误处理。

### 4.4 系统维护者

作为系统维护者，我希望地区 schema、种子来源、OpenAPI、权限、审计和测试均可追溯，
以便后续扩展更多国家/地区时不会破坏已有业务引用。

## 5. UI 设计规格

```text

====================
1. Purpose Statement:
   地区管理页服务于低频但高影响的主数据维护，必须让管理员快速理解层级、当前作用域、
   节点状态和可执行操作。QsRegionSelector 服务于高频业务录入，必须把三级路径、加载

   桌面地区管理页采用非对称双区布局：左侧窄层级导航区，右侧宽直属下级数据区；
```

### 5.1 页面呈现

- 页面头部使用 `FaPageHeader`，展示“地区管理”、用途说明、刷新和具备权限时的新增
  国家/地区入口。
- 主内容只使用一个 `FaPageMain`。
- 桌面左侧层级导航只承载国家/地区和省/州，避免未来全球城市全部进入深度监听树。
- 右侧 `QsGenericTable` 展示当前作用域的直属下级：
  - 根作用域展示国家/地区；
  - 国家/地区作用域展示省/州；
  - 省/州作用域展示城市；
  - 城市节点不再提供新增下级。
- 表格字段至少包括名称、英文名、编码、层级类型、行政类型、自身状态、有效状态、
  排序、更新时间和操作。
- 新增和编辑使用领域表单 `RegionFormModal → QsGenericModal`。
- 启用、禁用使用独立领域确认 Modal，不复用新增/编辑表单表达危险操作。
- 小于 `768px` 时，层级导航进入底部 `QsGenericDrawer`，表格自动切换为地区卡片。
- 页面不得使用渐变、装饰性统计卡、Emoji 图标或另一套视觉系统。

### 5.2 选择器呈现

- 默认占满调用方可用宽度，不使用底层组件固定的 `200px` 作为公共宽度契约。
- 以“国家/地区”“省/州”“城市”三个并列 `FaSelect` 呈现；桌面保持三列，窄屏按顺序
  堆叠，不使用单个级联弹层。
- 每个下拉只展示当前层级的直属 options；完整三级路径另以单个 ASCII 空格连接，
  例如 `中国台湾 台湾 高雄市`。
- 三个下拉分别支持键盘、鼠标和触控操作；未选择上级时，下级保持禁用并显示可理解的
  引导文案。
- 加载、失败、无数据、禁用、只读和清空状态必须可辨识。
- `readonly` 使用可聚焦、可复制的原生只读 `input` 展示完整路径，而不是保留三个可
  操作下拉。
- 在 `390px` 视口中不得发生页面水平溢出，各下拉弹层不得超出可用视口。

## 6. 功能需求

### Requirement 1 - 严格的三级地区数据

**User Story：** 作为系统维护者，我希望数据库强制地区层级完整性，以便任何接口或脚本
都不能写入错层、孤儿或循环数据。

#### Acceptance Criteria

1. 当新的地区 migration 应用于空库或现有数据库时，系统应创建支持
   `COUNTRY_REGION`、`PROVINCE_STATE`、`CITY` 的地区持久化结构。
2. 当写入 `COUNTRY_REGION` 时，数据库应只接受没有上级的 Level 1 节点。
3. 当写入 `PROVINCE_STATE` 时，数据库应只接受直属一个
   `COUNTRY_REGION` 的 Level 2 节点。
4. 当写入 `CITY` 时，数据库应只接受直属一个 `PROVINCE_STATE` 的 Level 3
   节点。
5. 当任意写入尝试形成错层父子、孤儿节点、自引用或循环时，数据库约束或数据库
   trigger 应拒绝该写入，且不得留下部分数据；Service 还应在写入前执行同一规则的
   预校验，以返回可理解的业务错误。
6. 当创建地区时，系统应生成稳定 UUID，并要求全局唯一的技术编码。
7. 当地区来自外部数据时，系统应保留可空的 `sourceName`、`sourceCode` 和真实
   `administrativeType`；这些字段不得替代 UUID 或技术编码作为公共 value。
8. 当同一上级下出现规范化后重复的默认显示名称时，系统应拒绝创建或修改。
9. 当写入负数排序值或未定义层级时，数据库应拒绝该写入。
10. 当地区已经创建后，系统不得通过公共 API 修改其 UUID、技术编码、层级或上级。
11. 当上级地区被禁用时，系统应保留后代自身状态，但把后代
    `effectiveEnabled` 计算为 `false`。
12. 当地区存在下级或未来业务引用时，数据库外键应阻止物理删除；本期系统不得提供
    删除 API。

### Requirement 2 - 可审计的首期种子数据

**User Story：** 作为系统维护者，我希望三地种子数据随 migration 可靠部署并具备来源
证据，以便空库和升级数据库得到同一份可验证数据。

#### Acceptance Criteria

1. 当完整 migration 历史应用于空库时，系统应写入中国大陆、中国台湾和马来西亚的
   全部已确认首期节点。
2. 当 migration 再次执行 deploy 或检查状态时，系统应报告没有待应用 migration，
   且不得重复地区数据。
3. 当检查中国台湾关键路径时，系统应精确得到
   `中国台湾 台湾 高雄市`。
4. 当检查中国大陆直辖市时，系统应得到固定三级路径，例如
   `中国 北京市 北京市`。
5. 当检查马来西亚二级节点时，系统应覆盖 13 个州和 3 个联邦直辖区。
6. 当验证数据完整性时，自动测试应核对本需求 3.4 节记录的逐级数量、唯一编码和关键
   路径，而不是只检查总行数大于零。
7. 当构建、启动或运行 migration 时，系统不得依赖外部网络、运行时下载或未提交的
   本地数据文件。
8. 当正式数据由外部来源转换而来时，仓库应保留允许审计的来源说明、许可证、摘要和
   转换脚本或确定性转换规则。
9. 当未来更新种子数据时，系统应通过新的向前 migration 处理，不得改写已经提交的
   migration，也不得无提示覆盖管理员维护过的地区。

### Requirement 3 - 业务选择只读接口

**User Story：** 作为正常登录的业务用户，我希望读取有效地区并恢复已有 city ID 的
完整路径，以便新建和编辑业务表单都能使用选择器。

#### Acceptance Criteria

1. 在用户具有正常 authenticated Session 且不处于强制改密状态时，当其请求地区
   选择数据时，系统应允许访问，而不要求 `regions:read` 管理权限。
2. 当客户端请求根节点或指定上级的下一级 options 时，系统应只返回有效节点，并按
   `sortOrder`、规范化名称和 UUID 稳定排序。
3. 当客户端请求一个存在的 city ID 路径时，系统应返回且仅返回对应的完整三级路径，
   即使该节点或其祖先已经停用，也应同时返回自身状态和有效状态供历史数据回显。
4. 当客户端请求不存在或非 CITY 的选择值时，系统应返回稳定、可区分的失败契约，
   不得返回不完整路径。
5. 当客户端搜索名称、英文名或地区编码时，系统应返回命中的可选城市及其完整三级
   路径，不得把同名城市脱离上级单独展示。
6. 当上级或城市自身被禁用时，系统不得在业务 options、搜索结果或新选择中返回该
   城市，但 path 查询仍应支持已有业务记录的只读回显。
7. 当公共选择接口成功或失败时，响应应符合现有 OpenAPI、`X-Request-Id` 和
   `ApiError` 规范。
8. 当用户退出登录、身份 epoch 改变或请求被取消时，客户端不得复用上一身份的地区
   请求结果。

### Requirement 4 - QsRegionSelector 公共组件

**User Story：** 作为业务开发者，我希望通过一个稳定组件完成地区选择，以便调用页面
双向维护国家/地区、省/州和城市三个 UUID，不重复处理逐级加载和路径状态。

#### Acceptance Criteria

1. 当调用方使用 `QsRegionSelector` 时，公共 `v-model` 应为
   `RegionSelectorValue`，固定包含 `countryRegionId`、`provinceStateId` 和
   `cityId`；每个未选择字段统一为 `null`。
2. 当用户选择国家/地区、省/州或城市时，组件应立即双向更新完整对象，并发出稳定的
   typed `change`；事件应明确操作来源、当前只读 path 及是否完成三级选择。
3. 当用户切换国家/地区时，组件应清空 `provinceStateId` 和 `cityId`；切换省/州时
   应清空 `cityId`，不得保留已不属于当前上级的下级 UUID。
4. 当调用方传入完整三级 value 时，组件应以 `cityId` 调用 path API，严格核对返回
   path 的三个 UUID 后回显；任一 UUID 不一致均应保留原 value 并显示安全错误。
5. 当传入合法部分 value 时，组件应按现有上级逐级加载直属 options；跳级 value 不得
   被静默修正或当作完整选择。
6. 当组件挂载时，应加载国家/地区 roots；选择或回显上级后只通过
   `listChildren(parentId)` 加载直属下一级，不得下载整棵全球地区树。
7. 三个 `FaSelect` 不提供组件内名称搜索，也不得使用 `ACascader` 或 `FaCascader`；
   Server search API 与地区管理页搜索仍保留，不能因本组件取舍而删除。
8. 完整路径显示必须以单个 ASCII 空格连接，例如 `中国台湾 台湾 高雄市`，不得使用
   `/` 或在分隔符两侧增加其他字符。
9. 当组件加载根节点、任一父级直属 options 或回显路径时，应展示明确状态；请求失败
   时应展示安全中文错误与对应局部重试入口。
10. 当快速切换上级、重试、缓存失效或卸载产生并发请求时，组件应取消无用请求并用
    request version 忽略过期结果，避免旧响应覆盖新状态。
11. 当多个选择器同时请求同一批 options/path 时，数据提供层应合并进行中的相同
    请求；失败、取消或畸形响应不得进入缓存。
12. 当地区管理写操作成功、用户登出或身份 epoch 改变时，地区 options/path cache
    应失效，且已失效请求不得再次写回缓存。
13. 当组件处于 `disabled` 时应阻止修改；`readonly` 应使用可聚焦原生只读
    `input` 展示完整路径，非空历史值仍应可读。
14. 当调用方提供 `name` 时，私有原生表单代理只提交 `cityId`；`required` 对空值和
    部分值都应显示“请选择完整地区”的可见反馈，并将焦点移到首个未完成层级。
15. 三个可见下拉应各自具备可访问名称、键盘焦点和错误语义；组件文档或 Showcase 的
    隔离数据不得替代正式业务 API 或数据库真相源。

### Requirement 5 - 地区管理查询

**User Story：** 作为地区管理员，我希望按当前层级查询地区，以便在大数据量下仍能快速
定位并维护目标节点。

#### Acceptance Criteria

1. 在用户拥有 `regions:read` 时，当其进入地区管理页时，系统应加载可管理的国家/地区
   和省/州导航，以及当前作用域的直属下级列表。
2. 当用户缺少 `regions:read` 时，路由和页面应隐藏或拒绝业务内容，Server 仍应返回
   `403 FORBIDDEN`。
3. 当用户选择根、国家/地区或省/州作用域时，右侧列表应分别显示国家/地区、省/州或
   城市，不得混入其他层级。
4. 当用户搜索当前层级时，系统应按默认显示名称、英文名或编码查询，并明确搜索只作用于
   当前层级和当前上级。
5. 当用户筛选状态时，系统应支持自身启用、自身禁用和因祖先禁用而失效的可辨识结果。
6. 当结果超过一页时，系统应使用现有 `QsGenericTable` 的受控分页契约。
7. 当管理查询失败时，页面应展示安全错误、`requestId` 和重试入口，并保留已选导航
   上下文。

### Requirement 6 - 新增、编辑、排序与启停

**User Story：** 作为地区管理员，我希望在严格权限和层级约束下维护节点，以便主数据
变更安全、明确且可审计。

#### Acceptance Criteria

1. 当用户拥有 `regions:create` 时，其应能在根作用域新增国家/地区、在国家/地区下新增
   省/州、在省/州下新增城市。
2. 当用户在 CITY 节点上请求新增下级时，系统应拒绝该操作。
3. 当用户创建地区时，表单应要求默认显示名称、技术编码、排序和自身状态，并允许填写
   英文名。
4. 当用户拥有 `regions:update` 时，其应能修改默认显示名称、英文名和排序，但不得修改
   UUID、层级或上级。
5. 当创建发生编码冲突，或创建、编辑发生同级名称或层级冲突时，系统应返回稳定业务
   错误，表单应保留用户输入并定位相关字段；编辑请求不得接受技术编码字段。
6. 当用户拥有 `regions:disable` 并确认禁用时，系统应禁用目标节点，同时提示其后代会
   从业务选择器中失效。
7. 当用户拥有 `regions:enable` 并确认启用时，系统应启用目标节点，并重新计算其有效
   状态。
8. 当用户只拥有部分写权限时，页面应只显示允许的操作，Server 应独立执行最终授权。
9. 当写请求提交中时，表单或确认框应阻止重复提交和意外关闭。
10. 当写请求成功时，页面应刷新受影响作用域、更新导航状态、失效选择器缓存，并通过
    `QsToast` 提供反馈。
11. 当写请求结果未知时，页面应通过重新查询确认最终状态，不得直接假设失败后重复写入。
12. 当本期完成时，页面和 API 均不得出现物理删除入口。

### Requirement 7 - 权限、路由与审计

**User Story：** 作为系统管理员，我希望地区管理能力遵循现有 RBAC 与 Audit 体系，
以便操作边界和变更历史可检查。

#### Acceptance Criteria

1. 当 migration 部署完成时，权限目录应新增并授予 `system_admin`：
   `regions:read`、`regions:create`、`regions:update`、`regions:enable`、
   `regions:disable`。
2. 当地区管理路由注册时，叶子路由应要求 `regions:read`，并进入系统管理可访问权限
   判定。
3. 当用户只拥有其他基础数据权限而没有 `regions:read` 时，基础数据父路由不得强制
   重定向到无权访问的地区页。
4. 当地区被创建、更新、启用或禁用时，系统应在同一数据库事务写入对应 Audit event。
5. 当 Audit event 写入时，actor 应来自可信 Session，target 应为地区 UUID；
   metadata 只使用现有可序列化标量，`changedFields` 为排序后逗号分隔字符串、
   `level` 为字符串、`affectedCount` 为数字，不记录完整请求体。
6. 当地区写入或 Audit 写入任一失败时，整个事务应回滚。
7. 当普通业务用户只调用地区选择接口时，系统不得要求或隐式授予任何 `regions:*`
   管理权限。

### Requirement 8 - API 校验、错误与安全

**User Story：** 作为系统维护者，我希望地区接口遵循现有安全错误边界，以便客户端可
稳定处理失败且日志不会泄露内部信息。

#### Acceptance Criteria

1. 当请求 DTO 包含额外字段、非法 UUID、非法层级、负排序或超长文本时，系统应返回
   现有 `422 VALIDATION_FAILED` 契约和中文字段错误。
2. 当目标地区不存在时，系统应返回 `404 REGION_NOT_FOUND`。
3. 当指定上级不存在时，系统应返回 `404 REGION_PARENT_NOT_FOUND`。
4. 当技术编码冲突时，系统应返回 `409 REGION_CODE_ALREADY_EXISTS`。
5. 当父子层级不合法时，系统应返回 `422 REGION_HIERARCHY_INVALID`。
6. 当数据库唯一约束或并发写入引发预期冲突时，系统应映射为稳定业务错误，不得透传
   Prisma、SQL、constraint 名称或驱动堆栈。
7. 当执行地区写操作时，系统应要求有效 Session、正常认证状态、对应权限和现有 CSRF
   保护。
8. 当记录日志、OpenAPI example 或 Audit metadata 时，系统不得记录 token、Cookie、
   密码、连接字符串或完整敏感请求体。

### Requirement 9 - 性能、一致性与全球扩展

**User Story：** 作为业务开发者，我希望首期数据加载顺畅且未来全球扩展不需要一次
下载全部城市，以便组件在数据增长后仍可使用。

#### Acceptance Criteria

1. 当选择器挂载时，客户端应只加载国家/地区 roots；后续按当前父级加载直属下一层，
   不得把未来全球全部城市作为首屏必要负载。
2. 当客户端已有完整三级 value 需要回显时，系统应使用 `cityId` 的 path 能力直接
   恢复并核对三个 UUID，不得为了找一个城市下载全量树。
3. 当管理员浏览地区树时，左侧导航应只承载国家/地区和省/州，城市由右侧分页列表
   承载。
4. 当 options/path 查询使用内存缓存时，缓存 key 应包含身份 epoch、请求类型和规范化
   参数；成功结果的 TTL 最长为 5 分钟，并实现 in-flight dedupe、失败不缓存和过期
   请求不回写。
5. 当管理端修改名称、状态或排序后，当前 tab 应立即失效地区缓存，并通过
   `BroadcastChannel` 通知同源其他 tab；无法接收通知的客户端最多在 5 分钟 TTL 后
   读取数据库最新结果。
6. 当增加新的国家/地区、其省/州和城市时，系统应复用既有 schema、API 和组件契约，
   不得要求增加新层级或改变 `RegionSelectorValue` 三字段契约。

### Requirement 10 - 测试、文档与交付

**User Story：** 作为维护者，我希望地区能力具备可重复的分层验证，以便数据库、接口、
组件和页面都能被独立证明。

#### Acceptance Criteria

1. 当开始 schema 或服务实现前，系统应先增加会失败的地区 schema、DTO、Service、
   Controller 和 E2E 测试。
2. 当开始组件实现或后续重构前，系统应先增加会失败的三级 value/path、逐级清理、
   并发失效、表单代理和结构契约测试。
3. 当开始地区页面实现前，系统应先把现有“地区为空页面、无权限”的基线断言改为新
   需求对应的失败测试，同时保持其余四个基础数据页面仍为空。
4. 当 migration 验证时，系统应在隔离 PostgreSQL 16 中从空库两次 deploy 并执行
   migrate status、约束检查、种子数量和关键路径断言。
5. 当 OpenAPI 变化完成时，系统应通过根级 `contract:sync` 和 `contract:check`，不得
   手工编辑两端 snapshot 或 generated types。
6. 当组件完成时，系统应提供中文 README，说明 public API、数据来源、缓存边界、错误
   状态和表单使用示例。
7. 当页面完成时，系统应在桌面、`390px`、亮色、暗色和 reduced motion 状态下进行
   真实浏览器验证。
8. 当浏览器验证选择器时，系统应覆盖三个下拉的键盘导航、逐级加载与清理、完整 value
   回显、清空、失败重试、required 可见反馈、readonly input 和中国台湾关键路径。
9. 当浏览器验证管理页时，系统应覆盖权限拒绝、层级导航、分页、创建、编辑、启停、
   缓存失效和无水平溢出。
10. 当全部实施完成时，Server check/build/E2E、Web test/typecheck/lint/build、
    OpenAPI contract、根级 check 和 `git diff --check` 均应通过。
11. 当提交 Git 变更时，系统应按需求文档、技术设计、任务计划、数据库/API、组件、
    页面和最终验证小步提交，不得包含 `.env`、generated client、构建产物或无关文件。

## 7. 明确不做

- 不在首期导入中国大陆、中国台湾和马来西亚以外的全球城市数据。
- 不实现第四级区/县/街道选择。
- 不实现地图、经纬度、时区、邮编、运费分区或地理围栏。
- 不实现 Excel/CSV 批量导入、导出或在线数据源自动同步。
- 不实现地区合并、拆分、历史版本、生效日期或别名管理。
- 不允许通过公共 API 修改地区层级或上级。
- 不提供地区物理删除。
- 不修改其他四个基础数据空页面的业务内容。
- 不以组件库示例页代替 `/system/basic-data/regions` 真实业务页面。
- 不在 `QsRegionSelector` 内提供搜索，不使用 `ACascader`、`FaCascader` 或一次性完整
  地区树；此项不删除 Server search API 或地区管理页搜索。
- 不新增前端状态管理或查询库；如需缓存，使用技术设计中限定的轻量数据提供层。

## 8. 需求确认重点

本需求确认时同时确认以下业务口径：

1. 中国大陆根节点显示为“中国”，范围为大陆省级及地级等效单位，不含香港、澳门。
2. 中国大陆固定为 31 个省级、369 个城市层；其中包括 32 个省直管县级地域。直辖市
   使用同名三级路径，例如 `中国 北京市 北京市`。
3. 中国台湾固定使用“中国台湾 台湾 城市/县市级地域”三级路径，并以
   `中国台湾 台湾 高雄市` 为强制验收路径，共 22 个城市层。
4. 马来西亚二级固定覆盖 13 个州和 3 个联邦直辖区；三级采用 DOSM 官方 160 个
   `administrative district` 作为统一业务叶子，而不是采用 223 条非官方
   `cities/towns/districts` 混合集。
5. `QsRegionSelector` value 固定为 `RegionSelectorValue` 三字段对象，各级空值为
   `null`；原生 `name` 表单代理只提交 CITY UUID。完整路径使用单个 ASCII 空格，
   例如 `中国台湾 台湾 高雄市`，不保存展示名称代替 UUID。
6. 本期允许新增、编辑、排序、启用和禁用，但不允许修改上级、层级或物理删除。
7. 首期固定 3 个国家/地区、48 个省/州、551 个城市层，共 602 个节点；后续更新只能
   使用新的向前 migration。
