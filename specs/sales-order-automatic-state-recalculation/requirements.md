# 销售订单自动状态重算需求文档

## 1. 引言

本需求统一处理销售订单在签收、收款、付款约定变更及关联采购订单取消后的派生状态，避免业务人员完成事实操作后仍需手工推进订单，或销售订单继续保留已经失真的采购覆盖状态。

本期不新增“修改付款约定”前端入口，不实现工厂发货、货物入仓、装柜出货业务，只保留现有建设中轻提示。

## 2. 状态边界

- 订单状态自动流转只允许 `CONFIRMED -> PENDING_RECONCILIATION`。
- 自动进入待对账必须同时满足 `fulfillmentStatus = SIGNED` 与 `paymentStatus = PAID`。
- 本期不自动进入 `COMPLETED`，也不自动把 `PENDING_RECONCILIATION` 回退为 `CONFIRMED`。
- 采购覆盖重算只影响关联销售订单的 `fulfillmentStatus`，不改变其 `orderStatus` 或 `paymentStatus`。
- 海运及之后阶段，即 `SEA_TRANSIT`、`SIGNED`，不得因采购取消而倒退。

## 3. 需求与验收标准

### 需求 1：签收且付清后自动进入待对账

**用户故事：** 作为业务人员，我希望在订单已经签收且已经付清时由系统自动进入待对账，避免重复执行订单状态操作。

#### 验收标准

1. 当一笔 `CONFIRMED` 销售订单在业务事务结束时同时满足 `SIGNED + PAID` 时，系统应在同一数据库事务中把 `orderStatus` 更新为 `PENDING_RECONCILIATION`。
2. 当上传签收单使订单由 `SEA_TRANSIT` 进入 `SIGNED`，且订单已经 `PAID` 时，系统应自动进入待对账。
3. 当新增实际收款使订单进入 `PAID`，且订单已经 `SIGNED` 时，系统应自动进入待对账。
4. 当通过既有履约状态接口使订单进入 `SIGNED`，且订单已经 `PAID` 时，系统应自动进入待对账。
5. 当修改付款约定使订单重新计算为 `PAID`，且订单已经 `SIGNED` 时，系统应自动进入待对账。
6. 当订单不同时满足 `SIGNED + PAID`，或 `orderStatus` 不是 `CONFIRMED` 时，系统不得自动改变订单状态。
7. 当系统自动进入待对账时，系统应写入 `ORDER` 状态历史与 `SALES_ORDER_ORDER_STATUS_CHANGED` 审计事件，并标记自动流转原因。
8. 当系统自动进入待对账时，系统不得自动进入 `COMPLETED`。

### 需求 2：取消采购订单后重新计算销售采购覆盖

**用户故事：** 作为业务人员，我希望取消销售关联采购订单后，系统立即重算销售订单的有效采购覆盖，避免销售订单继续显示错误的履约进度。

#### 验收标准

1. 当一笔 `SALES_LINKED` 采购订单成功取消时，系统应在同一数据库事务中，基于所有未取消采购订单重新汇总每条销售明细的有效采购数量。
2. 当重算后仍有销售产品未被完全采购，且销售订单为 `CONFIRMED` 并处于海运前阶段时，系统应把其履约状态更新为 `PENDING`。
3. 当重算后销售产品仍被完全覆盖时，系统应保持当前履约状态；若当前状态为 `PENDING`，系统应推进为 `PREPARING`。
4. 当销售订单已处于 `SEA_TRANSIT`、`SIGNED`、`PENDING_RECONCILIATION`、`COMPLETED` 或 `CANCELLED` 时，系统不得因采购取消而倒退履约状态。
5. 当采购订单为 `STOCK` 或没有关联销售订单时，系统不得执行销售订单覆盖重算。
6. 当重算导致履约状态变化时，系统应写入 `FULFILLMENT` 状态历史及 `SALES_ORDER_FULFILLMENT_STATUS_CHANGED` 审计事件，并记录触发采购订单。
7. 当采购取消事务任一部分失败时，采购取消和销售状态重算都不得部分提交。

### 需求 3：修改付款约定后重算付款及订单状态

**用户故事：** 作为业务人员，我希望付款约定改变后系统按新的约定总价重新判断付款状态，避免付款状态与金额事实不一致。

#### 验收标准

1. 当 `CONFIRMED` 销售订单通过既有付款约定接口成功修改时，系统应根据新的 `agreedTotalAmount` 与未作废实际收款总额重新计算 `paymentStatus`。
2. 当重算后的付款状态发生变化时，系统应写入 `PAYMENT` 状态历史。
3. 当新的约定总价低于有效实际收款时，系统应拒绝修改且不得写入任何状态或金额变更。
4. 当重算后订单同时满足 `SIGNED + PAID` 时，系统应继续执行需求 1 的自动待对账规则。
5. 本期系统不得新增付款约定前端入口；既有 API 应返回重算后的最终状态，为后续入口提供可信结果。

### 需求 4：轻提示反馈

**用户故事：** 作为业务人员，我希望操作完成后立即知道订单是否被自动推进，避免再次查找状态确认结果。

#### 验收标准

1. 当上传签收单或新增实际收款触发自动待对账时，Web 端应显示成功轻提示：“订单已签收且已付清，已自动进入待对账”。
2. 当上述操作成功但没有触发自动待对账时，Web 端应保留与当前操作一致的普通成功轻提示。
3. 当销售关联采购订单取消成功时，Web 端应显示成功轻提示：“采购订单已取消，关联销售订单采购覆盖状态已重新计算”。
4. 当备货采购取消成功时，Web 端应继续显示普通采购取消成功提示。
5. 由于本期不新增付款约定入口，Web 端本期不产生付款约定修改轻提示；未来入口必须依据 API 返回的最终状态提供相同反馈。
6. 轻提示不得替代错误提示、确认弹窗或服务端状态历史。

### 需求 5：保持未落地物流操作

**用户故事：** 作为产品负责人，我希望尚未实现的物流动作继续明确显示建设状态，避免本次需求意外扩大业务范围。

#### 验收标准

1. 当用户点击“工厂发货”时，Web 端应继续只显示“功能正在建设中”轻提示，不得请求履约状态接口。
2. 当用户点击“货物入仓”时，Web 端应继续只显示“功能正在建设中”轻提示，不得请求履约状态接口。
3. 当用户点击“装柜出货”时，Web 端应继续只显示“功能正在建设中”轻提示，不得请求履约状态接口。

## 4. UI 设计规范

### DESIGN SPECIFICATION

1. **Purpose Statement：** 本期只增强既有业务操作完成后的状态反馈，不新增页面、弹窗、按钮或布局。轻提示需要清楚区分普通成功与系统自动推进，但不能打断用户工作流。
2. **Aesthetic Direction：** Industrial/utilitarian，延续千树运营工作台高密度、操作优先的业务界面语言。
3. **Color Palette：** 成功强调绿色 `#15803D`、成功前景 `#F7FFF9`、正文黑色 `#171717`、辅助灰色 `#6B7280`、错误红色 `#DC2626`；实现继续使用项目现有主题语义变量，不新增硬编码颜色。
4. **Typography：** 延续项目现有 `Noto Sans SC` 与 `Noto Sans Mono`，不新增字体依赖。
5. **Layout Strategy：** 不改变现有页面布局；继续使用根层单例 `QsToast` 的右上角浮层反馈，保持非阻塞、短时可读及移动端安全边距。

## 5. 权限与接口边界

- 不新增或修改权限编码。
- 不新增数据库字段、枚举或 migration。
- 不改变既有公开请求 DTO 与响应 DTO 结构。
- 自动状态变更沿用触发原操作的可信用户、请求 ID 与事务权限。
- 本需求会改变既有接口的业务副作用，但不改变接口路径和字段契约。

## 6. 验证要求

- 状态派生规则必须使用单元测试覆盖成功、无操作、终态保护及事务失败。
- 服务测试必须证明状态历史和审计记录与业务更新处于同一事务。
- Web 测试必须证明轻提示依据接口最终状态选择，并证明三个建设中按钮不调用履约接口。
- 最终执行聚焦测试、OpenAPI 契约检查和根级 `node --run check`。
