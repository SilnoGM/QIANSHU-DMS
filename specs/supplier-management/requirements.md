# 供应商管理需求规格

## 1. 文档状态

- 状态：已确认
- 确认日期：2026-08-05
- 正式入口：`/system/service-provider/suppliers`
- 菜单层级：系统管理 → 合作供方 → 供应商管理
- 适用范围：全局供应商主数据，不引入租户或组织隔离

## 2. 目标

为采购及后续业务建立稳定的供应商主数据来源，维护供应商主体、登记、主要联系人、主要地址、状态和备注，并通过现有 `SUPPLIER` 编号规则生成不可编辑的 Supplier Code。

## 3. 需求

### R1 - 入口、菜单与权限

**用户故事：** 作为具备供应商权限的用户，我希望从“系统管理 → 合作供方”进入供应商管理，并且只能执行已授权的操作。

#### 验收标准

1. 当用户拥有 `suppliers:read` 时，系统应展示“合作供方 → 供应商管理”并允许访问 `/system/service-provider/suppliers`。
2. 当用户不拥有 `suppliers:read` 时，系统应隐藏空的“合作供方”菜单并拒绝直接访问。
3. 当用户执行创建、编辑、启用或停用时，系统应分别校验 `suppliers:create/update/enable/disable`。
4. 服务端权限校验应作为最终安全边界，Web 路由权限只用于体验收敛。

### R2 - 供应商身份与自动编号

**用户故事：** 作为供应商管理员，我希望系统自动生成稳定的 Supplier Code，避免人工维护编号导致重复或漂移。

#### 验收标准

1. 当用户创建供应商时，系统应通过内部 `NumberingGeneratorService` 和 `SUPPLIER` 规则生成编号。
2. 创建成功后，系统应保持 Supplier Code、Supplier ID 和对应 Numbering Issuance 不可修改。
3. 新建供应商应固定为停用状态，客户端不得提交 `code`、`enabled` 或 `version`。
4. 系统不承诺编号连续、无断号、可回收或可复用。

### R3 - 主体、登记、联系人、地址与备注

**用户故事：** 作为供应商管理员，我希望维护开展合作所需的基础信息，同时允许先保存不完整草稿。

#### 验收标准

1. 主体类型应只允许 `ORGANIZATION` 和 `INDIVIDUAL`。
2. 法定名称和主体类型应为创建必填项；简称可空。
3. 登记国家/地区和登记号应同时有值或同时为空，同一国家/地区下规范化登记号应唯一。
4. 主要联系人应只保留姓名、电话和微信号；停用草稿允许三者部分或全部为空。
5. 主要地址应只保留国家/地区、省/州、城市、详细地址和邮编；地区只允许合法前缀，邮编可空。
6. 其他信息应只保留备注，不提供网站、邮箱、职位、银行、账期或资质字段。

### R4 - 生命周期、版本与删除边界

**用户故事：** 作为并发使用系统的管理员，我希望编辑和启停不会覆盖他人的新版本，也不会产生不可追溯的删除。

#### 验收标准

1. 当用户更新、启用或停用时，系统应要求 `expectedVersion` 并在版本不一致时返回 `SUPPLIER_STATE_CHANGED`。
2. 当规范化后的结果没有变化时，系统不应增加版本或写入 Audit。
3. 当启用供应商时，系统应只要求联系人姓名非空，且电话或微信号至少一项非空。
4. 登记信息、地址和邮编为空时，只要联系人条件满足，系统仍应允许启用。
5. 已启用供应商不得通过编辑变成不满足启用联系人条件的状态。
6. 系统不应提供 DELETE，并应在数据库层阻止物理删除。

### R5 - 创建幂等与故障恢复

**用户故事：** 作为在不稳定网络中操作的用户，我希望创建请求可以安全确认结果，不会重复创建供应商或重复占用编号。

#### 验收标准

1. 当客户端创建供应商时，应提交 canonical lowercase UUID v4 `Idempotency-Key`。
2. 当同一用户使用同一 key 和同一规范化 payload 重放时，系统应返回原供应商且不得重复写 Audit。
3. 当同一用户使用同一 key 和不同规范化 payload 时，系统应在发号前返回 `SUPPLIER_IDEMPOTENCY_CONFLICT`。
4. 当创建在意图提交后、发号后或业务提交后中断时，相同请求重放应继续或返回原结果。
5. 发号成功但 Supplier 事务失败时，已发编号可以成为合法断号，系统不得回收或复用。

### R6 - Region 引用与历史值

**用户故事：** 作为供应商管理员，我希望新地区引用有效且层级正确，同时历史地区停用后仍能解释原始资料。

#### 验收标准

1. 新建或改变登记地区时，系统应要求它是有效的根级 `COUNTRY_REGION`。
2. 新建或改变主要地址地区时，系统应校验国家/地区 → 省/州 → 城市的合法前缀和父子关系。
3. Region 校验应在调用方事务内按稳定 UUID 顺序获取共享锁，不通过 HTTP 自调用。
4. Region 以后被停用时，系统应保留历史引用，不自动清空，也不阻止无关字段更新。
5. Supplier 启用不应把 Region 或地址重新变成必填项。

### R7 - API、查询与数据最小化

**用户故事：** 作为前端调用方，我希望获得稳定且最小化的管理 API，不在列表响应中传播完整敏感详情。

#### 验收标准

1. 系统应只提供 list、create、detail、update、enable、disable 六个 Supplier operation。
2. 列表应支持服务端搜索、状态/主体类型筛选、分页和稳定排序。
3. 列表响应不应包含完整登记号、电话、微信号、详细地址、邮编、备注或幂等内部字段。
4. 详情响应应返回完整业务字段、版本、时间和 Server 计算的 `enableReadiness`。
5. 系统不应提供 Supplier Catalog、DELETE 或公共发号 API。

### R8 - Audit、安全与错误边界

**用户故事：** 作为审计和运维人员，我希望关键变化可追溯，但日志和错误不会泄露供应商敏感数据。

#### 验收标准

1. 创建、编辑、启用和停用应分别写入 `SUPPLIER_CREATED/UPDATED/ENABLED/DISABLED`。
2. Audit metadata 应只包含 `supplierCode`、`changedFields`、`previousVersion` 和 `version` 中适用的字段。
3. Audit、日志、Toast 和公共错误不得包含登记号、联系人、电话、微信号、地址、备注、原始幂等键或 Hash。
4. Audit 写入失败时，Supplier 业务事务应整体回滚。
5. 已知冲突和校验失败应映射为稳定领域错误，未知底层错误应收敛为安全 `INTERNAL_ERROR`。

### R9 - Web 体验、响应式与无障碍

**用户故事：** 作为桌面或移动端用户，我希望在现有管理后台视觉语言中完成供应商维护，并能使用键盘和辅助技术。

#### 验收标准

1. 页面应使用 `FaPageHeader + FaPageMain + QsGenericTable`，API 和权限副作用由页面持有。
2. 表单、详情和状态确认应分别使用领域 Drawer/Modal，不把供应商能力写入公共组件。
3. 390px 视口应使用移动卡片和底部操作 Drawer，页面不得产生水平溢出。
4. 状态不得只依赖颜色；交互应支持键盘、真实 label、首错聚焦、焦点恢复和 reduced motion。
5. 动态撤权或身份切换时，页面应中止请求、清空受保护数据并关闭维护上下文。
6. 创建结果未知时，页面应冻结原 payload/key，只允许用户主动使用同一请求重新确认结果。

### R10 - Migration、契约、测试与 CI

**用户故事：** 作为维护者，我希望功能通过可重放迁移、自动契约、真实数据库和浏览器测试获得可复核证据。

#### 验收标准

1. Supplier migration 应为新的 forward migration，并在隔离 PostgreSQL 中可从空库重放。
2. OpenAPI 和 Web generated types 应只通过根 `contract:sync` 生成，不手工编辑。
3. Server E2E 应覆盖权限、CSRF、生命周期、并发、幂等、Region、Audit 和数据库约束。
4. Browser E2E 应使用真实 Chrome、真实 Server、隔离 PostgreSQL 和真实 Cookie/CSRF。
5. Supplier Browser Job 加入后，CI gate 应精确汇总八个 validation jobs。
6. 对真实环境只允许只读核验已有 `SUPPLIER` 规则，不自动创建、修改或消耗编号。

## 4. 明确不做

- 多联系人、多地址、联系人职位或邮箱。
- 网站、银行账户、结算账期、资质、附件或审批。
- Supplier Catalog 或公共选择器。
- 删除、归档、导入、导出或批量操作。
- 租户、组织隔离或外部供应商门户。
- 创建或维护 `SUPPLIER` 编号规则。
