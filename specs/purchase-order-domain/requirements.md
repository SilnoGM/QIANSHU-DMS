# 采购订单域需求规格

## 1. 文档状态

- 状态：已确认
- 确认日期：2026-08-27
- 目标模块：采购订单域首版
- 目标页面：`/qs-operations/purchase/pending-purchase-orders`、`/qs-operations/purchase/purchase-orders`

## 2. 目标

采购订单域用于记录面向供应商的正式采购约定、销售来源、产品采购明细、采购金额、实际付款、采购唛头及履约进度。首版同时覆盖销售关联采购和管理员发起的备货采购，并为后续自动生成采购唛头保留稳定的数据边界。

## 3. 业务边界

- 一张采购订单最多关联一张销售订单；一张销售订单允许拆分成多张采购订单。
- `SALES_LINKED` 表示销售关联采购，`STOCK` 表示不关联销售订单的备货采购。
- 只有 `system_admin` 可创建 `STOCK` 采购；普通采购人员只能创建 `SALES_LINKED` 采购。
- 一张采购订单只有一个订单级供应商，保存 `service_provider.supplier` 字典稳定值。
- 采购币种固定为 `CNY`，不得在表单或接口中切换币种。
- 数据库产品继续由产品域管理；`CUSTOM` 临时产品只存在于销售或采购订单明细快照中。
- 关联采购不得加入销售订单之外的产品；额外采购统一通过备货采购处理。
- 首版不包含质检、退货、补货及自动生成唛头。
- 编号仅在确认有效采购订单时由编号域派发；页面打开和客户端草稿编辑均不发号。

## 4. 需求与验收标准

### R1 - 菜单与页面入口

**User Story：** 作为采购人员，我希望从采购订单菜单分别进入待办采购和全部采购。

#### Acceptance Criteria

1. 当用户进入千树运营工作台的采购订单菜单时，采购订单系统应提供“待办采购”和“全部采购”两个入口。
2. 当用户点击“待办采购”时，采购订单系统应进入 `/qs-operations/purchase/pending-purchase-orders`。
3. 当用户点击“全部采购”时，采购订单系统应进入 `/qs-operations/purchase/purchase-orders`。
4. 在采购订单业务能力尚未进入实施阶段时，两个页面应只展示对应页头，不得提前增加推测性表格、筛选器、按钮或接口请求。

### R2 - 采购类型与销售订单关系

**User Story：** 作为采购人员，我希望既能根据销售订单拆分采购，也能由管理员建立独立备货采购。

#### Acceptance Criteria

1. 当创建 `SALES_LINKED` 采购时，采购订单系统应要求且只允许关联一个有效销售订单。
2. 当创建 `STOCK` 采购时，采购订单系统应禁止携带 `salesOrderId`。
3. 当同一销售订单需要向多个供应商采购时，采购订单系统应允许建立多张采购订单，不得对 `salesOrderId` 设置唯一约束。
4. 当非 `system_admin` 用户尝试创建 `STOCK` 采购时，采购订单系统应在服务端拒绝请求。
5. 当用户查看关联采购时，采购订单系统应通过关联销售订单读取客户名，不在采购订单中重复保存客户名。

### R3 - 供应商与固定币种

**User Story：** 作为采购人员，我希望从系统字典选择供应商，并保证所有采购金额都使用人民币。

#### Acceptance Criteria

1. 当用户创建采购订单时，采购订单系统应要求从 `service_provider.supplier` 选择一个有效稳定值。
2. 当确认采购订单时，采购订单系统应在最终事务中重新校验供应商字典项仍然有效。
3. 当保存采购订单时，采购订单系统应固定保存 `currencyCode = CNY`，不接受客户端选择其他币种。
4. 当 `CNY` 币种记录不存在、被停用或最小单位不符合系统约束时，采购订单系统应拒绝确认订单。

### R4 - 正式产品采购明细

**User Story：** 作为采购人员，我希望选择产品档案中的正式产品，并查看采购定价后填写本单采购价。

#### Acceptance Criteria

1. 当用户选择 `CATALOG` 产品时，采购订单系统应只允许状态为 `ACTIVE` 的产品。
2. 当确认 `CATALOG` 行时，采购订单系统应从产品档案读取当前 `purchaseCostAmount` 作为“采购定价”快照。
3. 当产品采购成本为空或 `purchaseCostCurrency != CNY` 时，采购订单系统应拒绝确认该产品行。
4. 当产品 `supplierValue` 与采购订单 `supplierValue` 不一致时，采购订单系统应拒绝确认该产品行。
5. 当用户填写“本单采购价”时，采购订单系统应接受最多两位小数的非负十进制金额，不得自动复制采购定价。
6. 当保存正式产品行时，采购订单系统应保存产品 UUID、编号、名称、属性、采购定价和本单采购价快照。

### R5 - 临时产品采购明细

**User Story：** 作为采购人员，我希望同步或手工增加临时产品，并明确填写两个采购价格。

#### Acceptance Criteria

1. 当销售订单包含 `CUSTOM` 行时，采购订单系统应允许将该临时产品同步到采购订单。
2. 当管理员创建备货采购时，采购订单系统应允许手工新增 `CUSTOM` 临时产品。
3. 当编辑任意 `CUSTOM` 采购行时，采购订单系统应要求用户分别填写“采购定价”和“本单采购价”。
4. 当两个价格任一为空或两者不相等时，采购订单系统应硬拦截确认。
5. 当确认 `CUSTOM` 行时，采购订单系统不应要求 `productId`、产品档案采购成本或产品级供应商。
6. 当保存 `CUSTOM` 行时，采购订单系统不得创建或修改产品主数据。

### R6 - 销售明细同步与累计采购量

**User Story：** 作为采购人员，我希望从销售订单同步产品，并防止同一销售需求被重复超量采购。

#### Acceptance Criteria

1. 当用户选择销售订单后，采购订单系统应返回订单号、客户名、销售产品明细和每行剩余可采购数量。
2. 当同步 `CATALOG` 行时，采购订单系统应保存 `sourceSalesOrderLineId`，并校验源销售行产品与采购行产品一致。
3. 当同步 `CUSTOM` 行时，采购订单系统应保存 `sourceSalesOrderLineId`，并使用销售行名称和说明快照。
4. 当确认关联采购时，采购订单系统应保证每条采购行的来源销售行属于当前 `salesOrderId`。
5. 当同一销售行被多张未取消采购订单引用时，采购订单系统应保证累计有效采购数量不超过销售行数量。
6. 当并发确认可能导致超量采购时，采购订单系统应只允许满足数量约束的事务成功。
7. 当采购订单取消时，采购订单系统应从累计有效采购数量中释放该订单数量。

### R7 - 采购金额与付款约定

**User Story：** 作为采购人员，我希望记录采购总价、定金和尾款，并保证金额严格一致。

#### Acceptance Criteria

1. 当采购明细变化时，采购订单系统应在服务端计算每行金额和 `lineSubtotalAmount`，不信任客户端汇总。
2. 当 `purchaseTotalAmount != lineSubtotalAmount` 时，采购订单系统应硬拦截确认。
3. 当 `purchaseTotalAmount != depositDueAmount + balanceDueAmount` 时，采购订单系统应硬拦截确认。
4. 当金额输入包含浮点数、负数、科学计数法或超过两位用户小数时，采购订单系统应拒绝请求。
5. 当金额持久化时，采购订单系统应使用 `Decimal(30,4)`，并通过规范十进制字符串传输。

### R8 - 确认发号与幂等创建

**User Story：** 作为采购人员，我希望只在确认订单时获得唯一采购订单号，并安全重试未知结果。

#### Acceptance Criteria

1. 当用户打开页面、选择销售订单或编辑客户端草稿时，采购订单系统不得派发采购订单号。
2. 当首次确认有效采购订单时，采购订单系统应使用 `NumberingGeneratorService` 的 `PURCHASE_ORDER` 规则派发编号。
3. 当相同 `Idempotency-Key` 和相同规范化请求被重放时，采购订单系统应返回同一订单，不得重复发号或重复创建。
4. 当不同请求复用同一 `Idempotency-Key` 时，采购订单系统应返回幂等冲突。
5. 当常见业务预校验失败时，采购订单系统应在发号前拒绝请求。
6. 当发号后最终事务因依赖状态或并发数量变化失败时，采购订单系统允许留下可审计断号，不得复用已派发编号。

### R9 - 订单、履约和付款状态

**User Story：** 作为运营人员，我希望分别查看采购订单约定、履约进度和付款进度。

#### Acceptance Criteria

1. 采购订单系统应独立保存 `orderStatus`、`fulfillmentStatus` 和 `paymentStatus`。
2. 当采购订单创建成功时，订单状态应为 `CONFIRMED`，不得持久化业务草稿。
3. 当履约状态变化时，采购订单系统应只允许 `ORDERED -> PREPARING -> SHIPPED -> SIGNED` 顺序流转；采购订单创建成功后直接进入 `ORDERED`。
4. 当付款事实变化时，采购订单系统应自动派生付款状态，不允许客户端直接指定付款状态。
5. 当订单存在有效付款时，采购订单系统应要求先作废付款再取消订单。
6. 当订单取消后，采购订单系统应禁止继续推进履约或新增付款。
7. 采购订单系统不应提供质检、退货或补货状态。

### R10 - 实际付款与可选凭证

**User Story：** 作为财务或采购人员，我希望分次记录实际付款，并保留错误付款的作废轨迹。

#### Acceptance Criteria

1. 当用户新增付款时，采购订单系统应记录付款类型、金额、付款时间、`payment.method` 稳定字典值、备注和操作人。
2. 当付款金额不大于零或累计有效付款超过采购总价时，采购订单系统应拒绝请求。
3. 当累计有效付款为零且采购总价大于零时，付款状态应为 `UNPAID`。
4. 当累计有效付款大于零且小于采购总价时，付款状态应为 `PARTIALLY_PAID`。
5. 当累计有效付款等于采购总价时，付款状态应为 `PAID`；零元采购订单直接视为 `PAID`。
6. 当付款记录录入错误时，采购订单系统应通过作废字段保留原记录，不得物理删除。
7. 当用户需要提供付款凭证时，采购订单系统应允许可选关联私有图片或文档；没有凭证不得阻止付款。

### R11 - 采购唛头

**User Story：** 作为采购人员，我希望首期以文本记录采购唛头，并为后续自动生成保留扩展空间。

#### Acceptance Criteria

1. 当用户填写采购唛头时，采购订单系统应接受最多 2000 个 Unicode code points 的多行文本。
2. 当采购唛头为空白文本时，采购订单系统应规范化为空值。
3. 当保存首期采购订单时，采购订单系统应只保存文本，不生成图片、模板或产品媒体。
4. 当后续增加自动生成能力时，系统应能在不改变首期文本语义的前提下扩展独立生成记录。

### R12 - 查询、权限与审计

**User Story：** 作为运营和管理员，我希望查询全部或待办采购，并保证敏感操作可授权、可追溯。

#### Acceptance Criteria

1. 当用户查询采购订单时，采购订单系统应支持按订单号、销售订单号、客户名、供应商、采购类型、三套状态和采购日期区间筛选。
2. 当查询“待办采购”时，采购订单系统应只返回未取消且“未签收或未付清”的订单。
3. 当返回列表或详情时，采购订单系统应返回采购总价、有效已付金额、未付金额和三套状态。
4. 当用户读取、创建、创建备货采购、更新状态、管理付款或管理凭证时，采购订单系统应分别校验对应权限。
5. 当采购域读取销售来源时，系统应使用采购域受限接口返回最小必要字段，不要求采购人员拥有完整 `sales-orders:read`。
6. 当发生创建、取消、履约变化、付款新增/作废或凭证关联时，采购订单系统应记录审计事件或不可变领域历史。
7. 当记录日志或审计元数据时，采购订单系统不得写入幂等键原文、完整请求体、凭证内容或其他敏感数据。

## 5. UI 设计规格

- Platform：Web，现有 Vue/Arco 千树 DMS 工作台。
- Purpose：让采购人员在高密度运营工作台中快速区分待办与全部采购，并在后续创建流程中明确销售来源、供应商、产品和金额约束。
- Aesthetic Direction：`Industrial/utilitarian`，沿用现有业务工作台而不创建独立视觉主题。
- Color Palette：`#F6F7F8`、`#FFFFFF`、`#1D2129`、`#165DFF`、`#00B42A`、`#F53F3F`；实现必须使用现有主题 Token，并支持亮色和暗色模式。
- Typography：沿用项目的 `Noto Sans SC`、`Noto Sans TC`。
- Layout Strategy：当前两个入口只使用现有 `FaPageHeader`；后续采购表单采用与销售订单一致的高密度 8/4 非对称工作台和窄屏单列，不引入居中营销卡片布局。
- Icons：继续使用现有 Lucide 图标，不使用 Emoji 图标。

## 6. 非功能要求

- 所有最终金额校验不得使用 JavaScript 浮点数。
- Server 请求方向保持 `Controller -> Service -> PrismaService -> PostgreSQL`。
- Controller、DTO 和 OpenAPI decorators 是公共接口真相源。
- 新功能采用 TDD，并使用隔离 PostgreSQL 验证数据库约束、幂等和并发采购量。
- 数据库使用 append-only migration，不修改或重写既有迁移。
- Web 与 Server 继续通过 HTTP/OpenAPI 协作，不增加跨目录源码依赖。
