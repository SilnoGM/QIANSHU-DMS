## 2. 背景与目标

系统需要为每个业务用户维护唯一的人民币资金账户，并维护一个全局公司资金账户。账户余额是实时快照，允许因提款、成本、亏损结算或人工调账变为负数；所有余额变化必须通过统一动账服务产生不可变批次和流水。

订单、提款、采购等业务域与资金账户模块处于同一个 NestJS Server 内。业务域只选择已经存在且允许调用的业务类型并提交业务身份、金额和基本信息；资金账户模块负责解析账户、分成比例、收支方向、分账金额、并发锁、幂等、余额更新、流水和审计。首期不提供远程 HTTP 动账接口。

管理员工作台保留两个路由：“资金账户列表”和“资金账户流水”。超级管理员可以显式开户、修改未来分成比例、执行手动调账、管理业务类型和来源、查看流水详情并对错误批次执行部分或全部冲账。

## 3. 用户故事

### 3.1 业务域开发者

作为订单、提款、采购或费用业务域开发者，我希望通过同一个 Server 内部服务提交业务类型、用户、金额和业务信息，以便在不知道资金账户 ID、分成比例和具体分录的情况下安全完成动账。

### 3.2 超级管理员

作为超级管理员，我希望创建用户资金账户、维护用户分成比例、执行有审计记录的手动调账、查看完整流水并冲销错误批次，以便在不直接修改余额或历史流水的前提下管理资金。

### 3.3 财务分析人员

作为未来的财务分析人员，我希望每笔动账都保存稳定业务分类、类型、来源和比例快照，以便后续按照收益、成本、非收益成本和调账分类计算经营数据。

### 3.4 系统维护者

作为系统维护者，我希望账户余额、批次和流水在并发、重试、审计失败和部分冲账场景下保持一致，以便任意余额都能通过不可变流水追溯和核对。

## 4. 已确认业务决策

1. 资金账户只有人民币，币种固定为 `CNY`。
2. 用户账户主体是系统现有 `User`；一个用户最多一个资金账户。
3. 系统只有一个全局公司资金账户，公司账户不绑定特殊用户。
4. 用户账户在管理员工作台显式创建，创建时必须设置 `0–100%` 的用户分成比例；不得根据历史用户自动创建或推测比例。
5. 用户分成比例可以修改，但只影响修改后的新批次；历史批次使用动账时快照。
6. 账户余额允许为负数，不执行余额不足阻断。
7. 业务域通过同一 Server 内部统一服务动账；首期不开放远程 HTTP 动账接口。
8. 业务域不能提交账户 ID、收支方向、分成比例或拆分金额。
9. 成功批次和流水不可编辑、不可删除；错误动账只能通过批次级冲账纠正。
10. 支持部分冲账；多账户批次使用原比例和原分录快照同步冲账。
11. 管理员手动调账支持正数和负数，并支持 `USER_ONLY` 与 `USER_AND_COMPANY_BY_SHARE` 两种模式。
12. 管理员调账不包含对系统全部用户账户的批量调账。
13. 所有资金管理路由和人工操作只允许 `system_admin`。
14. 本期保存未来统计所需分类和快照，但不实现收益率公式或经营统计看板。

## 5. 术语与数据口径

### 5.1 资金账户

- 用户账户：绑定一个 `User`，保存实时余额和当前用户分成比例。
- 公司账户：全局唯一，不绑定 `User`，不保存固定分成比例。
- 公司在某一批次中的比例始终为 `100% - 用户比例快照`。

### 5.2 业务类型与业务分类

业务类型决定金额符号规则、目标账户、收支方向和分账策略。业务分类用于未来统计：

- `REVENUE`：收益；负数订单结算作为负收益冲减收入。
- `COST`：成本。
- `NEUTRAL`：资金流动，但不计入收益或成本。
- `ADJUSTMENT`：人工调账，默认不计入经营收益或成本。

业务类型和业务分类必须写入动账批次快照。已经产生流水的类型编码不得修改，历史分类不得随当前配置变化。

### 5.3 业务来源

业务来源标识实际发起业务域或管理入口。来源由可信调用上下文绑定，不允许普通业务请求通过输入字段冒充其他来源。业务来源可以限制允许调用的业务类型。

### 5.4 动账批次与账户流水

- 动账批次：一次业务请求的不可变聚合，包含业务金额、类型、分类、来源、规则、比例、业务标识、幂等和审计上下文。
- 账户流水：批次对单一账户造成的一次实际余额变化，包含正数金额、收支方向和动账前后余额。
- 一个按比例批次通常包含用户与公司两条流水。

### 5.5 金额

- 数据库使用 `DECIMAL/NUMERIC`，公共 TypeScript/HTTP 边界使用十进制字符串。
- 业务金额可以按类型允许正负；账户流水金额始终为正数，实际符号由 `CREDIT/DEBIT` 表达。
- 首期金额精度为四位小数，分账采用 `ROUND_HALF_UP`，公司金额承接尾差以保证总额守恒。

### 5.6 冲账

冲账是针对原动账批次生成方向相反的新批次和新流水。原批次和原流水不被更新；`NONE/PARTIAL/FULL` 状态由冲账批次汇总计算。

## 6. 初始化业务类型

| 类型编码 | 名称 | 分类 | 金额要求 | 记账规则 |
| --- | --- | --- | --- | --- |
| `ORDER_SETTLEMENT` | 订单结算 | `REVENUE` | 非零，可正可负 | 正数按比例入账；负数按比例扣款 |
| `USER_WITHDRAWAL` | 用户提款 | `NEUTRAL` | 必须大于 `0` | 全额从用户账户扣除 |
| `PURCHASE_PAYMENT` | 采购付款 | `COST` | 必须大于 `0` | 按比例从用户和公司账户扣除 |
| `RENT_UTILITIES` | 房租水电 | `COST` | 必须大于 `0` | 全额从公司账户扣除 |
| `BUSINESS_ACCOUNT_FEE` | 业务账号费用 | `COST` | 必须大于 `0` | 按比例从用户和公司账户扣除 |
| `ADVERTISING_FEE` | 广告投放费用 | `COST` | 必须大于 `0` | 按比例从用户和公司账户扣除 |
| `NETWORK_IP_VPN_FEE` | 网络 IP/VPN 费用 | `COST` | 必须大于 `0` | 按比例从用户和公司账户扣除 |
| `INVOICE_FEE` | 开发票费用 | `COST` | 必须大于 `0` | 按比例从用户和公司账户扣除 |
| `ADMIN_MANUAL_ADJUSTMENT` | 管理员手动调账 | `ADJUSTMENT` | 非零，可正可负 | 按调账模式全额调整用户或按比例调整用户与公司 |

冲账不是可选业务类型，而是针对原批次的系统操作。

## 7. 功能需求

### Requirement 1 - 账户身份与人民币边界

#### Acceptance Criteria

1. 当用户资金账户创建时，系统应要求目标 `User` 存在，并保证该用户此前没有资金账户。
2. 当公司资金账户初始化时，系统应保证全库只有一个公司账户且不绑定 `User`。
3. 当任意资金账户存在时，系统应将其币种固定为 `CNY`，不得创建或转换其他币种账户。
4. 当资金账户余额更新后小于零时，系统应保存负余额，不得以余额不足拒绝已合法的业务规则。
5. 当用户被禁用时，系统应保留其资金账户、余额和历史流水，不得级联删除或自动清零。
6. 当账户已经产生流水时，系统不得删除账户或改变账户主体。

### Requirement 2 - 开户与分成比例

#### Acceptance Criteria

1. 当超级管理员创建用户资金账户时，系统应要求输入 `0–100%` 的用户分成比例。
2. 当目标用户已经有账户时，系统应拒绝重复开户并保持原账户不变。
3. 当系统中存在没有资金账户的历史用户时，系统不得自动开户或推测其分成比例。
4. 当超级管理员修改用户分成比例时，系统应要求并发版本和修改原因，并只影响后续新批次。
5. 当历史批次被查询或冲账时，系统应使用批次保存的比例快照，不得读取用户当前比例替换历史值。
6. 当公司分成金额计算时，系统应使用 `100% - 用户比例快照`，不得在公司账户保存固定比例。

### Requirement 3 - 业务类型、分类和规则配置

#### Acceptance Criteria

1. 当业务类型创建时，系统应要求稳定编码、名称、业务分类、金额符号策略和合法记账规则。
2. 当规则发布后，系统应冻结已发布版本；任何配置变化应通过新版本生效。
3. 当业务类型已经产生批次时，系统不得修改其稳定编码或静默重写历史分类。
4. 当业务类型停用时，系统应拒绝新动账，但仍允许查询其历史批次和流水。
5. 当配置规则时，系统应只允许受控账户目标、方向策略和金额策略，不得执行任意脚本或公式文本。
6. 当初始化 migration 执行时，系统应建立本规格列出的九个类型及其首个生效规则，不得插入演示流水或用户账户。

### Requirement 4 - 业务来源与调用授权

#### Acceptance Criteria

1. 当业务来源创建时，系统应保存稳定编码、名称、启用状态和允许调用的业务类型范围。
2. 当业务域调用动账服务时，系统应从可信调用上下文解析来源，不得信任普通输入对象中的任意来源编码。
3. 当来源被停用或未被授权调用目标业务类型时，系统应拒绝动账且不得更新余额或生成资金流水。
4. 当历史批次被查询时，系统应返回当时的来源编码和名称快照。
5. 当首期系统实施完成时，系统应只提供同一 Server 内部业务调用，不得开放无服务身份认证的远程 HTTP 动账入口。

### Requirement 5 - 统一内部动账接口

#### Acceptance Criteria

1. 当同一 Server 内任一业务域需要出账或入账时，业务域应通过统一 `FundPostingService.postBusinessEvent()` 调用资金模块。
2. 当业务域调用统一服务时，输入应包含业务类型、条件性用户、业务金额、业务标识、业务单号、摘要、受限扩展信息、发生时间和幂等键。
3. 当业务域提交请求时，系统不得接受调用方指定账户 ID、流水方向、用户比例、公司比例或分账金额。
4. 当动账成功时，系统应返回批次标识、业务金额、分类、比例快照、账户分录、入账时间和幂等重放标识。
5. 当相同调用方和幂等键以相同请求重试时，系统应返回原批次，不得重复更新余额。
6. 当相同调用方和幂等键携带不同请求内容时，系统应返回幂等冲突并保持原批次不变。

### Requirement 6 - 收益、成本和提款规则

#### Acceptance Criteria

1. 当 `ORDER_SETTLEMENT` 金额大于零时，系统应按用户比例向用户账户入账，并将剩余金额向公司账户入账。
2. 当 `ORDER_SETTLEMENT` 金额小于零时，系统应按相同比例从用户和公司账户扣款，并将其统计为负收益。
3. 当 `ORDER_SETTLEMENT` 金额等于零时，系统应拒绝请求且不生成空批次或空流水。
4. 当 `USER_WITHDRAWAL` 执行时，系统应要求正数金额并全额从用户账户扣除。
5. 当按比例成本类型执行时，系统应要求正数金额并按用户比例和公司尾差从两个账户扣除。
6. 当 `RENT_UTILITIES` 执行时，系统应要求正数金额并全额从公司账户扣除。
7. 当比例为 `0%` 或 `100%` 时，系统应允许省略金额为零的账户分录，同时保证有效分录合计等于业务金额绝对值。

### Requirement 7 - 管理员手动调账

#### Acceptance Criteria

1. 当超级管理员发起手动调账时，系统应要求选定用户账户、非零有符号金额、调账模式、原因和幂等键。
2. 当模式为 `USER_ONLY` 时，系统应将全部金额只作用于选定用户账户，公司账户保持不变。
3. 当模式为 `USER_AND_COMPANY_BY_SHARE` 时，系统应按选定用户当前比例同步调整用户和公司账户。
4. 当调账金额为正数时，系统应生成入账流水；当金额为负数时，系统应生成扣款流水。
5. 当手动调账完成时，系统应把批次归类为 `ADJUSTMENT`，默认不计入经营收益或成本。
6. 当管理员选择手动调账时，系统不得把该操作扩展为对系统全部用户账户的批量调账。
7. 当错误来自已有业务批次时，管理员应使用冲账纠正，不得通过手动调账修改或替代原流水。

### Requirement 8 - 原子性、并发和余额一致性

#### Acceptance Criteria

1. 当一个批次影响多个账户时，系统应在同一数据库事务内完成所有账户更新、批次、流水和成功审计写入。
2. 当事务开始时，系统应在第一条业务 SQL 前设置现有事务锁超时和语句超时。
3. 当多个账户需要锁定时，系统应按稳定账户标识顺序加锁，避免业务类型之间形成反向锁顺序。
4. 当同一账户发生并发动账时，系统应保证余额不丢失，并为该账户生成连续且唯一的流水序号。
5. 当任意一条账户更新、流水或审计写入失败时，系统应回滚该批次的全部业务变化。
6. 当幂等唯一约束发生竞争时，系统应重新读取赢家批次并校验请求指纹，而不是使用新幂等键重试。

### Requirement 9 - 不可变批次、流水和失败记录

#### Acceptance Criteria

1. 当动账成功时，系统应创建一个不可变批次和至少一条不可变账户流水。
2. 当批次或流水已经创建时，数据库应拒绝对账务事实执行 `UPDATE` 或 `DELETE`。
3. 当流水创建时，系统应保存正数金额、方向、动账前余额、动账后余额和账户流水序号。
4. 当批次创建时，系统应保存业务类型、分类、来源、规则版本、比例、业务身份和请求追踪快照。
5. 当请求在生成成功账务事实前失败时，系统不得写入伪造的失败资金流水；失败信息应进入通用审计或可观测性边界。
6. 当需要核对余额时，系统应能够使用账户流水重建和校验余额，但不得自动覆盖差异。

### Requirement 10 - 部分与全部冲账

#### Acceptance Criteria

1. 当管理员冲账时，系统应要求原批次、正数冲账额度、原因和幂等键。
2. 当原批次已部分冲账时，系统应把本次冲账额度与历史累计额度合并校验，不得超过原业务金额绝对值。
3. 当原批次包含用户和公司流水时，系统应使用原比例和原分录快照同步生成相反方向流水。
4. 当原批次是负数订单结算时，系统应通过入账流水冲销原扣款。
5. 当发生多次部分冲账时，系统应按累计目标计算各账户本次差额，避免逐次舍入累积造成超额或缺额。
6. 当最后一次冲账使累计额度等于原额度时，系统应与原各账户流水精确闭合。
7. 当同一原批次发生并发冲账时，系统应保证最多只有合法额度提交成功。
8. 当原目标本身是冲账批次时，系统应拒绝把它作为普通原批次再次冲账。

### Requirement 11 - 资金账户列表页面

#### Acceptance Criteria

1. 当账户列表页面渲染时，Web 应组合 `FaPageHeader + FaPageMain + QsGenericTable`，不得建立第二套表格内核。
2. 当页面加载时，系统应展示账户主体、实时余额、用户比例、推导公司比例、比例更新时间和账户更新时间。
3. 当公司账户显示时，页面应提供明确公司标识，并隐藏用户比例修改和用户手动调账操作。
4. 当具有相应权限的超级管理员操作用户账户时，页面应提供创建账户、修改比例、手动调账和查看流水入口。
5. 当手动调账模式或金额变化时，页面应实时预览用户金额、公司金额及调账后的预计余额。
6. 当页面处于桌面或窄屏时，系统应分别使用表格和结构化移动卡片，并保持相同业务操作与权限。
7. 当数据加载、刷新、失败、重试、空结果或身份变化时，页面应复用现有组件状态并清除不再可信的数据。

### Requirement 12 - 资金账户流水页面

#### Acceptance Criteria

1. 当流水列表页面渲染时，一行应代表一条真实账户流水，而不是把多账户批次折叠为一行。
2. 当流水显示时，页面应展示批次、账户、类型、分类、来源、方向、金额、动账前后余额、比例快照、业务单号和时间。
3. 当用户筛选流水时，系统应支持账户、用户、类型、分类、来源、方向、业务单号、时间和冲账状态的服务端过滤。
4. 当管理员打开批次详情时，页面应展示同批次全部账户分录、业务基本信息、规则和比例快照以及完整冲账链。
5. 当批次仍有可冲额度且管理员具有冲账权限时，详情应提供部分冲账入口；列表行不得提供编辑或删除入口。
6. 当金额为负向业务结果时，页面应同时用符号、收支文字和余额前后值表达，不得只依赖颜色。

### Requirement 13 - 权限和安全

#### Acceptance Criteria

1. 当资金权限写入目录时，系统应将读取、开户、比例修改、手动调账、冲账、类型管理和来源管理权限全部标记为 `systemOnly`。
2. 当 migration 授权这些权限时，系统应只授予稳定 `system_admin` 角色，并自校验不存在其他角色授权。
3. 当 Web 控制按钮可见性时，页面应使用相应权限；当请求到达 Server 时，Controller 应再次使用 `PermissionGuard` 强制授权。
4. 当同一 Server 业务域调用内部动账服务时，系统应使用独立来源和类型授权，不得把人工超级管理员权限视为业务调用凭据。
5. 当日志、错误或审计元数据生成时，系统不得记录原始幂等键、敏感请求体或数据库连接信息。

### Requirement 14 - 查询、统计基础和历史准确性

#### Acceptance Criteria

1. 当账户或流水分页查询时，系统应使用稳定排序和 UUID tie-breaker，并返回确定的总数与空列表形态。
2. 当金额通过公共管理 API 返回时，系统应返回十进制字符串，不得返回 JavaScript 浮点数。
3. 当未来统计收益时，系统应把 `REVENUE` 有符号金额用于收入合计，把 `COST` 正向费用用于成本合计。
4. 当未来统计经营结果时，`NEUTRAL` 和 `ADJUSTMENT` 默认应从经营收益和成本中排除。
5. 当冲账发生时，系统应继承原分类并以相反金额抵销原统计结果。
6. 当类型分类、名称、来源名称、规则或用户比例后续变化时，历史查询应继续返回原批次快照。
7. 当本期交付完成时，系统不应新增收益率公式、经营看板或自动财务报表。

### Requirement 15 - 工程质量与范围边界

#### Acceptance Criteria

1. 当开始正式实施时，新功能应采用 TDD，先证明目标能力缺失，再提交测试与最小实现共同恢复绿色。
2. 当数据库变化实施时，系统应只新增 forward migration，不得修改既有 migration。
3. 当 OpenAPI 变化实施时，开发者应通过根 `contract:sync` 生成快照和 Web types，不得手工修改生成资产。
4. 当 Server 与 Web 协作时，双方应通过 HTTP/OpenAPI 管理接口协作，不得建立跨依赖域源码引用；内部业务域调用仅发生在 Server 模块之间。
5. 当共享组件能力足够时，资金页面应复用现有组件；若必须修改公共组件契约，应暂停并取得单独确认。
6. 当验收完成时，系统应通过 Server unit/E2E、迁移、OpenAPI、Web、真实浏览器和根级门禁。
7. 当本期实施时，系统不得新增外币账户、全部用户批量调账、直接余额编辑、任意公式引擎、完整会计总账、账户冻结或远程 HTTP 动账接口。

## 8. UI 需求基线

### 8.1 用途

两个页面面向少量高权限操作人员，重点是快速核对余额、比例、业务归属、前后余额和冲账链，同时在高风险写操作前提供明确预览与确认。

### 8.2 审美方向

采用 `Brutally minimal` 的金融运营工具风格：信息密度高、层级克制、金额和身份优先，不使用装饰性渐变、图片或营销式卡片。

### 8.3 配色

实现必须使用项目现有语义 Token；参考基准为：

- 主文字：`#09090B`
- 次要文字：`#71717B`
- 弱背景：`#F4F4F5`
- 内容背景：`#FFFFFF`
- 危险操作：`#DC2626`

深色模式通过既有 Token 自动映射，不在业务页面硬编码另一套颜色。正负金额不能只依靠红绿颜色区分。

### 8.4 字体与图标

- 中文和普通内容：`Noto Sans SC`
- 金额、比例、编号和时间数据：`Noto Sans Mono`
- 图标：复用项目现有 Lucide 图标，不使用 Emoji 图标

### 8.5 布局

桌面以左侧数据主轴和右侧固定操作轴形成非中心化布局；批次详情使用侧边抽屉承载上下文，创建、比例修改、调账和冲账使用领域模态框。窄屏转换为纵向数据卡片与底部操作区，不产生页面级横向滚动。

## 9. 验收场景摘要

1. 用户比例 `30%`，订单结算 `100.00`：用户入账 `30.00`、公司入账 `70.00`。
2. 用户比例 `30%`，订单结算 `-100.00`：用户扣款 `30.00`、公司扣款 `70.00`，余额可为负。
3. 用户比例 `30%`，采购付款 `100.00`：用户扣款 `30.00`、公司扣款 `70.00`。
4. 房租水电 `100.00`：公司扣款 `100.00`，用户不产生流水。
5. 手动调账 `USER_ONLY/-100.00`：选定用户扣款 `100.00`，公司不变。
6. 手动调账 `USER_AND_COMPANY_BY_SHARE/-100.00`：用户扣款 `30.00`、公司扣款 `70.00`。
7. 对原 `-100.00` 订单亏损部分冲账 `40.00`：用户入账 `12.00`、公司入账 `28.00`。
8. 相同幂等键相同请求只生成一个批次；相同键不同请求返回冲突。
9. 审计写入失败时，批次、流水和余额更新全部回滚。
10. 非 `system_admin` 既看不到两个路由，也无法通过直接请求访问管理接口。
