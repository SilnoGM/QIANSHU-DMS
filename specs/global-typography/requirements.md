- 关联现行规范：

## 2. 背景

千树 DMS 已完成正式应用字体家族统一：

- 普通文本使用 `Noto Sans SC`。
- 结构化数据使用 `Noto Sans Mono`，中文缺字由 `Noto Sans SC` 承接。
- 原生 Emoji 是普通文本字体之外唯一允许的设备字体例外。

目前只有字体家族和主题颜色具备全局真相源。字号、行高、字重、字距仍主要由 UnoCSS utility、Fantastic-admin 基础组件、Arco Design Vue 默认样式和页面局部样式分别决定，产生以下问题：

1. 根字号 `14px` 由第三方 Arco CSS 隐式提供，项目没有显式接管根字号和行高。
2. 页面标题、登录标题、组件目录标题、区块标题、卡片标题没有稳定层级。
3. Fa 与 Arco 的按钮、表单标签、标签和弹窗标题存在不同字体指标。
4. FaTable 与 `QsGenericTable` 的表头规则不一致。
5. 单号、数量、百分比、金额和日期时间的字体家族及字重不一致。
6. 移动端卡片字段标签存在 `12/400`、`12/500`、`14/400` 三种实现。
7. 页面大量直接组合 `text-*`、`leading-*`、`font-*`，缺少可审计的语义角色。

本需求建立一套只服务于正式产品排版的全局 Token 和消费规则，并分阶段迁移已经审计的共享组件与正式页面。

## 3. 用户故事

### 3.1 业务用户

作为需要长时间扫描订单、结算、用户、权限和审计数据的业务用户，我希望页面标题、正文、标签、数据和操作具有稳定且可预测的层级，以便快速定位信息并降低视觉疲劳。

### 3.2 移动端用户

作为在窄屏设备上查看和处理数据的用户，我希望表格自动转为可读卡片，字段标签、业务编码、数字和日期仍保持清晰，不需要横向滚动或缩小关键数据字号。

### 3.3 前端开发者

作为维护正式应用的前端开发者，我希望通过语义 Token 选择排版角色，而不是在每个页面重复组合字号、行高和字重，以便统一修改、静态审计和防止回归。

## 4. 设计规格

### 4.1 Purpose Statement

全局排版规范服务于千树 DMS 的高频数据扫描、状态判断和业务操作。它必须强化信息层级与结构化数据的可比性，同时保持现有后台系统的操作效率，不把排版改造扩大为页面重设计。

### 4.2 Aesthetic Direction

采用 **Industrial/utilitarian**：

- 以信息密度、可扫读性和稳定节奏为优先。
- 使用克制的 Zinc 中性色和单一品牌绿。
- 通过字号、字重、行高和字体家族表达层级，不依赖装饰性阴影、渐变或动画。
- 设计变量：`DESIGN_VARIANCE=3`、`MOTION_INTENSITY=2`、`VISUAL_DENSITY=8`。

### 4.3 Color Palette

亮色模式基线：

| 角色 | 基线值 | 实现要求 |
| --- | --- | --- |
| 背景 | `#FFFFFF` | 使用 `--background` |
| 主文字 | `#09090B` | 使用 `--foreground` |
| 次级文字 | `#71717B` | 使用 `--muted-foreground` |
| 边框 | `#E4E4E7` | 使用 `--border` |
| 品牌强调 | `#15803D` | 使用 `--primary`，不得兼任 success |

代码不得因本规范硬编码上述亮色值。暗色模式继续由现有主题 Token 提供对应值。

### 4.4 Typography

- Sans：`Noto Sans SC`
- Mono：`Noto Sans Mono, Noto Sans SC`
- Emoji：复用现有原生 Emoji 例外栈
- 禁止新增 `Inter`、`Roboto`、`Arial`、`Helvetica`、`system-ui`、`-apple-system` 等正文回退
- 禁止浏览器伪造未提供的粗体或斜体

### 4.5 Layout Strategy

- 桌面端保留当前页面骨架、工具栏、表格和数据轨道。
- 移动端保留现有单列卡片和操作 Drawer。
- 本需求不调整组件高度、内外边距、栅格、导航结构或弹窗尺寸。
- 只在排版层修正层级与节奏，不增加动效、装饰卡片或新 UI 依赖。

## 5. 术语

| 术语 | 定义 |
| --- | --- |
| 基础 Token | 字号、行高、字重、字距等不可直接表达业务含义的尺度 |
| 语义 Token | `page-title`、`body`、`action`、`data` 等表达阅读角色的排版组合 |
| 组件 Token | `table-header` 等只适用于特定组件族的角色 |
| Sans | 普通中文、普通拉丁文字和操作文案使用的字体家族 |
| Mono | 单号、编码、数字、金额和日期时间使用的结构化数据字体家族 |
| 正式应用 | `web/apps/qsmds-arco` |
| 参考应用 | `web/examples/**`，本需求只允许回归验证，不允许直接修改 |

## 6. 功能需求

### Requirement 1 - 全局排版基础

**User Story：** 作为前端开发者，我希望正式应用显式拥有排版基础 Token，以便不再依赖第三方 CSS 默认值。

#### Acceptance Criteria

1. 当正式应用加载全局样式时，系统应显式声明 `12px`、`14px`、`16px`、`18px`、`20px`、`24px`、`30px`、`36px` 的字号基础 Token。
2. 当正式应用加载全局样式时，系统应显式声明 `16px`、`20px`、`24px`、`28px`、`32px`、`38px`、`40px` 的行高基础 Token。
3. 当正式应用加载全局样式时，系统应显式声明 `400`、`500`、`600`、`700` 的字重基础 Token。
4. 当正式应用渲染 `body` 时，系统应显式应用 Sans `14/20/400`，不得依赖 Arco 的根字号和行高。
5. 当正式应用渲染原生表单控件时，系统应继续使用现有全局 Sans 字体家族。
6. 当代码语义或结构化数据显式选择 Mono 时，系统应继续使用现有全局 Mono 字体 Token，不得建立第二套字体家族别名。

### Requirement 2 - 页面标题与正文层级

**User Story：** 作为业务用户，我希望页面标题、区块标题和正文具有稳定层级，以便快速理解页面结构。

#### Acceptance Criteria

1. 当桌面端渲染普通页面标题时，系统应应用 Sans `24/32/600`。
2. 当小于 `768px` 的视口渲染普通页面标题时，系统应应用 Sans `20/28/600`。
3. 当组件目录等展示型页面渲染 Hero 标题时，系统应在桌面端应用 Sans `30/38/600`，在移动端应用 Sans `24/32/600`。
4. 当登录页渲染登录标题时，系统应使用页面专用的 Sans `36/40/700`，不得把该角色复用于普通页面标题。
5. 当页面渲染区块标题时，系统应应用 Sans `18/28/600`。
6. 当页面渲染组件标题时，系统应应用 Sans `16/24/600`。
7. 当页面渲染紧凑卡片标题时，系统应应用 Sans `14/20/600`。
8. 当页面渲染普通正文时，系统应应用 Sans `14/20/400`。
9. 当页面渲染需要更宽松阅读节奏的说明正文时，系统应应用 Sans `14/24/400`。
10. 当页面渲染说明或辅助正文时，系统应使用 `--muted-foreground`，不得继续使用 `secondary-foreground/50` 表达普通说明。

### Requirement 3 - 表单与操作

**User Story：** 作为填写表单和执行操作的用户，我希望标签、输入内容、帮助信息和按钮保持一致，以便准确理解控件状态。

#### Acceptance Criteria

1. 当 Fa 或受支持的 Arco 表单渲染字段标签时，系统应应用 Sans `14/20/500`。
2. 当表单渲染帮助信息时，系统应应用 Sans `12/16/400` 和 `--muted-foreground`。
3. 当表单渲染错误信息时，系统应应用 Sans `12/16/400` 和 `--destructive`。
4. 当不小于 `768px` 的视口渲染输入框或文本域时，系统应应用 Sans `14/20/400`。
5. 当小于 `768px` 的视口渲染输入框或文本域时，系统应应用 Sans `16/24/400`，以避免移动浏览器聚焦缩放。
6. 当 Fa 或受支持的 Arco 按钮渲染普通操作文案时，系统应应用 Sans `14/20/500`。
7. 当操作按钮处于禁用状态时，系统应保持统一的 `opacity: 0.5`。
8. 当 Arco mini 按钮表达紧凑尺寸时，系统应保留其 `12px` 尺寸语义，不得被普通 action 规则覆盖。

### Requirement 4 - 标签与辅助信息

**User Story：** 作为扫描状态和字段信息的用户，我希望普通标签、状态标签和辅助信息具有清晰但不过度抢眼的层级。

#### Acceptance Criteria

1. 当页面渲染普通 meta 信息时，系统应应用 Sans `12/16/400` 和 `--muted-foreground`。
2. 当移动卡片渲染字段名称时，系统应应用 Sans `12/16/500` 和 `--muted-foreground`。
3. 当页面渲染普通 Tag 或 Badge 时，系统应应用 Sans `12/16/500`。
4. 当页面渲染状态 Tag 时，系统应应用 Sans `12/16/600`。
5. 当状态标签表达 success、warning 或 destructive 时，系统应使用现有或后续独立的状态颜色语义，不得用排版 Token 改写业务颜色。

### Requirement 5 - 表格与结构化数据

**User Story：** 作为高频查看业务数据的用户，我希望表头、普通值、单号、数字、金额和日期时间有稳定且可比较的排版。

#### Acceptance Criteria

1. 当正式应用渲染 FaTable 或 `QsGenericTable` 表头时，系统应自动应用 Sans `13/18/600` 和 `--muted-foreground`。
2. 当表格渲染普通正文值时，系统应应用 Sans `14/20/400` 和 `--foreground`。
3. 当表格或移动卡片渲染行号、来源或辅助说明时，系统应应用 meta 角色。
4. 当表格或移动卡片渲染单号或业务编码时，系统应应用 Mono `14/20/500` 和 `tabular-nums`。
5. 当表格或移动卡片渲染数量或百分比时，系统应应用 Mono `14/20/400` 和 `tabular-nums`。
6. 当表格或移动卡片渲染金额或汇总结果时，系统应应用 Sans 或 Mono `14/20/500`；数字内容应启用 `tabular-nums`。
7. 当表格或移动卡片渲染日期时间时，系统应应用 Mono `14/20/400` 和 `tabular-nums`。
8. 当表格渲染操作按钮时，系统应复用 action 角色。
9. 当表格列右对齐时，系统不得仅根据右对齐推断该列是 numeric 或 emphasis。
10. 当 `QsGenericTable` 消费全局表格 Token 时，系统应移除重复的局部字号 Token。
11. 当迁移表格列排版时，系统应使用现有 slot、`cellClass`、`DateTimeDisplay` 和 `AmountDisplay`，不得新增公共 column 数据结构。

### Requirement 6 - 弹窗与 Drawer

**User Story：** 作为在弹窗和移动 Drawer 中完成任务的用户，我希望标题、说明、表单和操作与主页面保持相同层级。

#### Acceptance Criteria

1. 当 FaModal 渲染标题时，系统应应用 Sans `18/24/600`。
2. 当受支持的 Arco Modal 渲染标题时，系统应与 FaModal 标题角色对齐。
3. 当弹窗渲染说明正文时，系统应复用 description 角色。
4. 当弹窗渲染表单和按钮时，系统应复用 form 与 action 角色。
5. 当移动 Drawer 渲染标题和说明时，系统应与 dialog title 和 description 对齐。
6. 当应用排版规则时，系统不得修改弹窗宽度、高度、遮罩、焦点管理或提交行为。

### Requirement 7 - 移动端数据卡片

**User Story：** 作为移动端用户，我希望数据卡片在窄屏下保持可读和可操作。

#### Acceptance Criteria

1. 当视口宽度为 `390px` 时，用户、角色、权限、审计和 `QsGenericTable` 的移动布局应保持无水平溢出。
2. 当移动卡片渲染字段名时，系统应使用 compact-label。
3. 当移动卡片渲染普通值时，系统应使用 body。
4. 当移动卡片渲染编码、数字或日期时，系统应使用对应 data 角色。
5. 当移动卡片渲染重点值时，系统应使用 data-emphasis 或 Sans body-medium。
6. 当移动端切换为卡片布局时，系统不得为了容纳内容把业务数据缩小到 `14px` 以下。

### Requirement 8 - 主题与颜色

**User Story：** 作为使用亮色或暗色主题的用户，我希望文字层级在两种主题下保持一致且具有足够对比度。

#### Acceptance Criteria

1. 当应用处于亮色主题时，排版角色应通过现有语义颜色 Token 获取颜色。
2. 当应用处于暗色主题时，排版角色应自动消费暗色语义颜色 Token，不得存在亮色硬编码。
3. 当本需求完成时，系统不得新增另一套主题颜色源。
4. 当当前产品未开放暗色切换入口时，本需求不得擅自启用该入口；暗色排版通过现有主题状态和受控验收路径验证。
5. 当排版改造涉及状态文字时，系统不得把 `--primary` 重新定义为 success。

### Requirement 9 - 工程边界与兼容性

**User Story：** 作为维护者，我希望排版规范只改变已经确认的正式范围，并能安全地与共享组件和参考应用共存。

#### Acceptance Criteria

1. 当实施全局排版规范时，系统应只修改正式应用、必要的共享组件、相关测试和文档。
2. 当共享组件需要消费正式应用语义时，系统应使用带静态 fallback 的共享 shortcut，或由正式应用通过稳定 `data-slot` 桥接；不得让参考应用因缺少正式应用 CSS 变量而失去排版。
3. 当共享组件发生修改时，系统应执行相关参考应用检查与构建，但不得直接修改 `web/examples/**`。
4. 当实施 Arco bridge 时，系统应只覆盖已经审计的字体指标，不得修改 Arco 组件布局、交互、颜色或第三方源码。
5. 当实施本需求时，系统不得修改 Server、公共 API、数据结构、数据库 schema 或根依赖域。
6. 当需要识别 numeric、identifier 或 datetime 时，系统不得通过列名、文案或对齐方式进行隐式猜测。
7. 当偏离本需求或技术设计时，实施者应先更新规格并重新确认，不得直接扩大范围。

### Requirement 10 - 测试、文档与交付

**User Story：** 作为维护者，我希望全局排版改造具备可重复验证和长期使用文档，以便后续页面继续遵循相同规范。

#### Acceptance Criteria

1. 当开始代码实施前，系统应先修复已发现的测试基线矛盾，并证明基线测试通过。
2. 当新增排版 Token 前，系统应先增加失败的 Token 契约测试。
3. 当迁移数据组件和页面前，系统应先更新或新增对应失败的消费契约测试。
4. 当一个实施阶段完成时，系统应运行与该阶段匹配的定向测试、类型检查和 lint。
5. 当全部阶段完成时，系统应通过 Web `check`、正式构建、测试构建、字体完整性和字体零残留守卫。
6. 当共享组件发生变化时，系统应通过参考应用检查与构建。
7. 当视觉实现完成时，系统应在桌面、`390px` 移动端、亮色和暗色状态下检查代表页面的计算样式与水平溢出。
8. 当本需求完成时，系统应生成 `docs/前端文档/全局排版规范.md`，并更新 `docs/文档索引.md`。
9. 当提交 Git 变更时，系统应按文档、Token、基础组件、数据表格、页面迁移和最终修正小步提交，不得包含无关文件。

## 7. 代表性验收页面

最低浏览器验收覆盖：

1. 登录页：登录标题、说明、表单、按钮和移动输入字号。
2. 业务组件页：页面标题、Hero、区块标题、`QsGenericTable` 桌面表格和移动卡片。
3. 用户管理页：`FaPageHeader`、查询表单、FaTable、用户表单 Modal、移动卡片。
4. 角色管理页：移动卡片标题、编码、数量和字段标签。
5. 权限目录页：分组标题、权限编码和说明。
6. 审计日志页：事件编码、用户、请求标识和日期时间。

## 8. 明确不做

- 不改变现有字体资源、Unicode 分片、Emoji 边界或字体加载流程。
- 不修改 `web/examples/**` 源码。
- 不修改 `web/node_modules/**` 或 pnpm store。
- 不新增 UI、字体、图标或动画依赖。
- 不重新设计页面布局、间距、组件高度、圆角、阴影或动效。
- 不启用当前关闭的暗色主题切换入口。
- 不新增或修改公共 API、组件公共数据结构、数据库 schema 或业务接口。
- 不把所有历史页面一次性替换为新 utility；只迁移技术设计中列出的正式消费方。
- 不在本需求中补建 success、warning 等颜色 Token；只记录其与品牌 `primary` 的边界。

## 9. 已确认决策

1. 全局表头采用 Sans `13/18/600`，由组件自动应用。
2. 普通正文采用 Sans `14/20/400`。
3. meta 采用 Sans `12/16/400`。
4. identifier 采用 Mono `14/20/500`。
5. numeric 与 datetime 采用 Mono `14/20/400` 和 `tabular-nums`。
6. emphasis 采用 Sans 或 Mono `14/20/500`。
7. action 采用 Sans `14/20/500`，禁用透明度为 `0.5`。
8. 移动输入保持 `16/24/400`。
9. 排版颜色使用主题语义 Token，不硬编码亮色值。
10. 本次先确认技术设计，再生成 `tasks.md` 并进入正式实施。
