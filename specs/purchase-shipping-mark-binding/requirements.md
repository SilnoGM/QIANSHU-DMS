# 采购唛头规则绑定与自动派发需求

状态：用户已确认本轮实施绑定配置，并授权对应表和 API；任务见 [实施任务](tasks.md)。下文自动派发部分保留为后续提案，本轮不实施。供应商收款资料不在范围内。

## 1. 目标与边界

在保留供应商字典的前提下，配置产品库供应商与唛头编号规则的绑定。新增采购订单在最终二次确认时自动派发唛头编号，并保存到采购单。配置与采购业务消费分开，编号规则引擎继续统一管理流水。

已确认的业务基线：

- 一个字典供应商最多绑定一条唛头规则，一条规则允许多个供应商使用，共用该规则的流水。
- 所有自定义产品采购统一使用 `CUSTOM_MARK`，不按手填供应商名称查找绑定。
- 一张采购单生成一个唛头编号，不按产品行、件数、采购批次另行派发。
- 新增采购统一使用自动唛头，不允许手改编号；填写期间只展示匹配规则，不占号。
- 最终点击“确认提交订单”后，服务端校验、派发并保存；重复提交或未知结果重试不能重复派发。
- 缺失绑定、规则缺失、用途不符、规则停用或没有生效版本时明确提示并阻止提交。
- 修改绑定不改写已生成唛头；历史手填唛头保持原样。
- 编号管理页新增次要按钮“唛头规则绑定”，进入独立页面；现有用途切换不增加第四个 Tab。

本期不恢复独立 `Supplier` 主数据，不修改通用字典字段，不添加每供应商独立计数器，不扩展编号片段、输出长度、中文变量或双序列，不开放公共任意发号接口。不自动创建、发布、启用 `CUSTOM_MARK`，不生成历史订单唛头，不增加已保存订单的重新生成入口。

## R1：绑定关系

**用户故事：**作为配置管理员，我希望为字典供应商指定一条唛头规则，使业务员无需自行判断使用哪个规则。

1. 当设置或更换绑定时，系统应使用 `service_provider.supplier` 的稳定 Item `value` 标识供应商，不使用显示名或独立 Supplier ID。
2. 当保存绑定时，系统应校验供应商有效，规则用途为 `SHIPPING_MARK`、状态启用且存在生效版本。
3. 当同一供应商已有绑定时，系统应通过版本校验更换原绑定，不增加第二条同时生效的绑定。
4. 当多个供应商选择相同规则时，系统应共用原规则的周期与流水，不派生供应商级序列。
5. 当供应商名称改变时，系统应继续按稳定值解析原绑定；当供应商停用时，系统应保留配置并展示不可用状态。
6. 当管理员保存配置时，系统应记录操作人、时间及前后规则，且保存本身不得消耗编号。

## R2：自定义产品统一规则

**用户故事：**作为采购人员，我希望自定义产品采购直接使用统一规则，而不用为每个手填供应商建立配置。

1. 当采购产品类型为 `CUSTOM` 时，系统应直接解析编码为 `CUSTOM_MARK` 的规则，不按 `customSupplierName` 匹配字典或绑定。
2. 当配置页展示自定义产品规则时，系统应只读展示规则和可用状态，不允许改选其他规则。
3. 当 `CUSTOM_MARK` 不存在、用途错误、未启用或没有生效版本时，系统应明确报告对应原因，不自动创建规则或退回手填唛头。

## R3：配置入口与权限

**用户故事：**作为管理员，我希望在编号管理内集中维护唛头绑定，同时让采购人员只消费配置。

1. 当用户具有配置读取权限时，编号管理页应展示“唛头规则绑定”次要按钮，与“新建编号规则”并列。
2. 当进入配置页时，系统应保持编号管理导航高亮，上方展示固定自定义规则，下方展示供应商绑定表格。
3. 当展示表格时，系统应包含供应商、绑定规则、规则状态和操作；未绑定供应商应可被发现，不只列出已有绑定。
4. 当用户没有配置修改权限时，系统应只允许查询，不展示可用的保存入口；服务端独立执行鉴权。
5. 当采购人员只有合法采购创建权限时，系统应允许其读取当前采购场景所需的规则摘要，但不授予绑定维护或编号管理权限。
6. 当配置或查询失败时，系统应保留可恢复的上下文，不把失败渲染为“未绑定”或默认可用。

## R4：采购填写与正式提交

**用户故事：**作为采购人员，我希望正式保存订单时自动获得可信的唛头编号。

1. 当新增销售关联采购或备货采购时，系统应根据采购产品类型及供应商展示命中的规则，不要求业务员输入编号。
2. 当填写、切换供应商、返回上一步或打开提交确认弹窗时，系统不得创建发号记录、消耗流水或提前冻结提交幂等键。
3. 当点击最终“确认提交订单”时，系统应重新校验完整采购资料、来源数量、供应商及唛头规则，再正式派发并保存。
4. 当填写期间绑定或规则生效版本发生变化时，系统应提示刷新核对，不能静默按另一规则提交。
5. 当正式创建成功时，系统应保存生成编号及可追溯的派发关联；页面应提示成功并按原流程返回采购列表。
6. 当新创建请求试图提交手写唛头或指定任意规则时，服务端应拒绝，不能信任前端隐藏控件代替校验。

## R5：一致性、重试与历史保护

**用户故事：**作为采购人员，我希望网络失败或重复点击不造成多张订单、多个唛头或错误关联。

1. 当相同身份使用相同幂等键和相同请求重试成功创建时，系统应返回原采购订单及原唛头，不重复推进流水。
2. 当相同幂等键对应不同请求或操作人时，系统应返回冲突，不覆盖原订单或已有派发。
3. 当唛头派发与采购保存尚未提交且事务失败时，系统应整体回滚本次唛头变更；回滚的候选编号不作为正式派发结果向用户展示。
4. 当事务已提交但响应丢失时，系统应按原幂等键恢复已保存结果；后续规则停用或绑定变化不应阻碍读取这一既有结果。
5. 当取消采购单或更换供应商绑定时，系统不得回收、重用或修改已正式派发的唛头。
6. 当读取历史手填唛头时，系统应按原文本展示，不补号、不覆盖、不虚构派发记录。
7. 当同一规则被多张采购单并发使用时，系统应沿用规则内唯一、周期计数和并发保护；不承诺跨规则文本唯一或无断号。

## 2. UI 约束

- 目标为现有桌面后台，沿用绿色主题、现有字体 token 和高密度表格；不另创视觉系统。
- 复用 `FaPageHeader`、`FaPageMain`、`QsGenericTable`、现有表单和通知组件。
- 配置页与采购页均覆盖加载、无权限、空数据、停用、失败和恢复状态；状态不能只依赖颜色。
- 桌面与窄屏均可操作，键盘焦点明确，亮暗主题使用现有语义 token。
- 普通本地可纠正失败使用轻提示；服务端失败及结果未知保留恢复提示，不自动更换幂等键重新提交。

## 3. 审批与实施边界
