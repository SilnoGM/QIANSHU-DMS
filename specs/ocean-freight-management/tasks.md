## 3. 关键测试矩阵

| 场景 | 预期结果 |
| --- | --- |
| 同一新建请求重复提交 | 一个业务对象、一次编号派发 |
| `0917柜` 在 2026 年创建，2027 年读取 | 日期仍为 `2026-09-17` |
| `0918柜` 与同仓 `0918-01柜` | 同日同序号冲突明确提示 |
| 月日不存在或历史来源跨年 | 拒绝无效日期或保留冲突，不自动纠正 |
| 一个货件两个包装明细，同一柜 | 允许 |
| 同一货件被并发分配到两个柜 | 仅合法一方成功，另一方返回冲突 |
| `L-010831-01~10`，10 件 | 一条装柜明细、一条正常账单行 |
| 单件约 1.288 材 × 10 件 | 整行约 12.88，计费 13 材 |
| 材积非常接近整数边界 | 根据完整计算结果向上取整，不受展示舍入影响 |
| 整行毛重 180 kg，10 件 | 计重仍为 180 kg |
| 来源材积系数为 28316 | 保存来源值，系统按 28317 计算并显示差异 |
| 单价高低不同 | 按显式计费方式处理，不用价格大小猜测 |
| 补派送 500 TWD，无新增代收，汇率 4.8 | 净影响 `-104.17 CNY`，不重复计算货物或原代收 |
| 补费行同时带历史代收金额 | 保留来源，确认本次有效代收前不能直接确认核对 |
| 同一货件多条包装行 | 不给每行重复分配整件代收金额 |
| 正常行跨账单重复导入，或只改文件名 | 防止重复计费；明确的后续调整允许建立 |
| 缺少尺寸且按重量计费 | 不虚构尺寸，可根据完整重量计费依据核对 |
| 缺少代收或费用的必要判断 | 标记未完善，不静默置零 |
| 原表整单换算与逐条换算差两分 | 两种口径可追溯，不自动摊入任一货件 |
| 未授权用户请求页面或 API | 前后端权限边界都有效 |
| 已核对时直接修改费用或关联 | 拒绝，需有原因地重新打开 |
| 确认核对同时修改账单汇率或装柜资料 | 通过锁和版本阻止过期确认 |
| 任何保存、导入、核对、重新打开 | 账户余额、资金流水、销售收款无变动 |

## 4. 验证方法与提交要求

业务开发默认采用有意义的失败测试，再实现并验证。公式用纯函数测试；关系与竞态用隔离 PostgreSQL 集成测试；鉴权和接口用对应 HTTP 测试；界面用定向组件测试与真实浏览器检查。不要使用源码字符串断言代替金额、事务或权限行为验收。

Schema 和 API 实施后按项目既有入口执行适用验证，包括 Server 定向测试、Web 定向测试、OpenAPI 同步检查及相关依赖域检查。只有实际受影响或仍有未解风险时才扩大检查范围。迁移验证不得隐式读取个人持久数据库连接。

每个通过验证的完整逻辑变更单独提交，提交格式使用英文 type 加中文描述。提交前审查暂存内容，不混入用户已有修改，不提交原始 Excel 中的私人资料、真实环境文件、生成目录或日志。

本次是纯文档整理，以内容一致性、本地链接和 `git diff --check` 验证；不运行与文档无关的业务构建或数据库操作，也不把业务开发任务标记完成。
