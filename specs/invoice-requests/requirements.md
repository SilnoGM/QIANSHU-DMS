# 开票申请与审批 需求规格

## 1. 文档状态

- 状态：已定稿（2026-10-14，经三轮口径确认，无未决项）。
- 目标域：`invoice-requests`（权限前缀 `invoice-requests:*`）。
- 目标页面：千树运营工作台「发票管理」下的开票申请、开票记录；千树财务工作台「发票管理」下的开票审批。
- 依赖规格：[数据库迁移规范](../../docs/后端文档/数据库迁移规范.md)、[fund-account-management](../fund-account-management/requirements.md)（资金入账接入）。
- 技术设计：[design.md](design.md)。

## 2. 背景与目标

台湾统一发票（三联式）的开票信息收集与传递目前发生在系统外：抬头与统编靠人工核对、明细金额靠人工计算、开票进度靠口头催问、发票照片散落在个人设备、开票成本没有系统依据。本功能把「运营填报 → 财务审核与通知 → 回传发票照片 → 结算入账」整条链搬进系统，形成可查询、可留痕、成本公式化并真实入账的单据流。

## 3. 业务边界

本功能**不包含**：

- 不生成、不管理台湾税局的发票字号（字轨号码）——仅归档发票照片。
- 不打印、不导出；三联式发票版式仅作字段参照，系统不复刻票面。
- 不做税务申报。
- 不含站内通知：系统当前没有通知/消息能力，「通知开票」在系统内的含义只是「记录已通知」，通知动作在线下完成。
- 不做 OCR 与图像识别。
- 不含票面零税率 / 免税场景：系统只按应税 5% 计算（票面存在「應稅 / 零稅率 / 免稅」三栏，本域只覆盖應稅）。
- 不关联柜次、销售订单等业务单据：发票备注是纯自由文本。

## 4. 角色、可见范围与权限

| 页面 | 工作台 | 使用者 | 动作 |
| --- | --- | --- | --- |
| 开票申请 | 千树运营工作台 | 运营人员 | 填写、提交；对已退回单重新提交 |
| 开票记录 | 千树运营工作台 | 运营人员 | 查看（只读）、取消本人单 |
| 开票审批 | 千树财务工作台 | 财务人员 | 审核并通知、退回、上传照片、结算入账、取消 |

- 运营**仅可见本人提交的记录**（服务端按提交人过滤）；财务可见全部。
- 权限点（命名规范 `<域>:<动作>`）：

| 权限码 | 覆盖动作 | 授予 | 行级归属 |
| --- | --- | --- | --- |
| `invoice-requests:create` | 提交 / 重新提交 | 运营 | 仅本人单可重提 |
| `invoice-requests:read` | 查看 | 运营 + 财务 | 运营仅本人单 |
| `invoice-requests:read-all` | 跨提交人查看 | 财务 | 不限（与 `:read` 共同构成财务的全量视图） |
| `invoice-requests:review` | 审核并通知 | 财务 | 不限 |
| `invoice-requests:return` | 退回重填 | 财务 | 不限 |
| `invoice-requests:cancel` | 取消开票 | 运营 + 财务 | 运营仅本人单；财务不限 |
| `invoice-requests:document` | 上传发票照片 | 财务 | 不限 |
| `invoice-requests:settle` | 结算入账 | 财务 | 不限 |

权限点管「能不能做这类事」，行级归属管「能不能对这张单做」，两者都要服务端校验。

## 5. 需求与验收标准

### R1 申请单的填写与提交

**User Story：** 作为运营人员，我要把开票信息一次填准，系统自动算好金额，避免手算与抄错。

#### Acceptance Criteria

1. 填写项：抬头名称、统一编号（手填）、1–5 行明细（品名 / 数量 / 单价）、发票备注、申请单备注、寄送信息（姓名 / 电话 / 地址）。
2. 明细行金额 = 数量 × 单价，由系统计算且不可手改；销售额合计 = Σ 明细金额；营业税应税 = 四舍五入(销售额 × 0.05，0.05 固定)；总计 = 销售额 + 营业税（**取整后相加**）。
3. 提交成功后跳转「开票记录」页；提交失败保留表单内容。
4. 每次提交在事务内派发申请单号（编号域），单号不可回收。

### R2 提交时的重复申请二次确认

#### Acceptance Criteria

1. 提交（含重新提交）时，若存在另一张单的「抬头名称 + 统一编号 + 营业税应税 + 总计」四项**字面完全一致**，弹窗二次确认并逐张列出相似单的单号、状态、提交日期。
2. 比对池 = 开票审核中 / 已通知开票 / 已开出邮寄 / 已结算入账；**不含已取消与已退回**。
3. 比对不做归一化（抬头写法差异会漏报，已接受）；弹窗为软提示，确认后仍可提交。

### R3 财务审核并通知

#### Acceptance Criteria

1. 财务在「开票审核中」状态下可执行「审核并通知」，弹窗只读展示申请单全文，并提供「复制开票信息」到剪贴板。
2. 复制文本与弹窗展示同源（同一套标签与分组空行）、缺值留空、资料不齐不触发复制；只含发票备注，不含申请单备注。
3. 动作完成后状态转「已通知开票」，记录审核人与通知时间；**不跳转**（关闭弹窗、刷新列表）。
4. 复制入口在单据详情中长期保留，不限于本动作弹窗。

### R4 退回重填

#### Acceptance Criteria

1. 财务在「开票审核中」状态下可退回，**退回原因必填**。
2. 状态转「已退回」，运营**可编辑全部字段**（回填原值、表单顶部展示退回原因）后「重新提交」，**保留原单号**。
3. 重新提交后回到「开票审核中」，记录首次申请日期与最近一次提交时间。
4. 退回可多次发生，每次留痕。

### R5 取消开票

#### Acceptance Criteria

1. 取消是终态；**取消原因必填**。
2. 运营仅可取消本人且处于「开票审核中」或「已退回」的单。
3. 财务可在「已结算入账」之前的任意状态取消。
4. 在「已通知开票」或「已开出邮寄」状态取消时，提示「实物发票需线下处理」；留痕记录取消时所处状态。

### R6 上传发票照片

#### Acceptance Criteria

1. 「已通知开票」状态下财务上传 1 张发票照片（jpg / png / webp，≤10 MiB），上传即定稿，**不允许补传与替换**；提交前二次确认「清晰完整、上传后不可替换」。
2. HEIC 等不支持格式需明确提示。
3. 状态转「已开出邮寄」，记录发票上传日期（5 天计时起点）；上传弹窗并排展示系统总计，提示财务核对票面总额。

### R7 结算入账

#### Acceptance Criteria

1. 前置条件：已上传发票照片，且距上传时间 ≥ 120 小时（恰好 120 小时允许）。
2. 入账成本 = `向上取整(总计 ÷ 系统当前汇率 × 0.06 + 30)`，单位人民币；计算顺序严格为「先除汇率、再乘 0.06、最后加 30」。
3. 汇率在入账时读取当前值并冻结快照；界面展示值与服务端重算值不一致时拒绝并要求刷新。
4. 弹窗展示算式全貌（总计 / 汇率值与取数时刻 / 0.06 / +30 / 结果）并二次确认。
5. 状态转「已结算入账」（终态），记录结算日期、汇率快照与入账金额。
6. 入账真实产生资金流水、扣减资金账户，接入既有 `INVOICE_FEE`，**归属用户 = 申请人**。

### R8 状态机与可编辑性

#### Acceptance Criteria

1. 六态：开票审核中 / 已退回 / 已通知开票 / 已开出邮寄 / 已结算入账 / 已取消。除「已退回」「开票审核中」外的状态不可编辑；「已结算入账」「已取消」为终态不可逆。
2. 已通知开票之后的「修改」等价于「取消 + 新建」（新单号）；纠错路径见需求表。
3. 已结算入账后的金额错误**不改单据**：以资金域整批冲账 + 管理员手动调账为准。

### R9 留痕

#### Acceptance Criteria

1. 单据状态历史：每次状态变更记录动作、从 → 到、操作人、时间、原因（退回与取消的原因必填）。
2. 关键日期：申请日期、最近一次提交时间、发票上传日期、结算日期。
3. 全局审计事件：提交 / 重新提交 / 退回 / 审核并通知 / 上传照片 / 结算入账 / 取消 各自一个事件，与业务事实同事务写入。

### R10 开票申请页面

#### Acceptance Criteria

1. 页面结构：抬头与统编 → 明细行表格（1–5 行，可增删）→ 汇总区（只读自动计算）→ 发票备注 + 申请单备注 → 寄送信息 → 底部提交。
2. 提交前二次确认，确认文案列出明细行数与总计。
3. **离开页面的二次确认**：仅在有未提交内容时触发；覆盖路由离开、路由参数切换、刷新/关闭标签页（浏览器原生弹窗）、提交进行中（硬阻止）；确认弹窗为「继续编辑 / 确认放弃」。本质是「不做草稿保存、离开即丢弃」，提交成功后立即清除脏标记。
4. 从「已退回」单进入时回填原值、顶部展示退回原因、按钮为「重新提交」。

### R11 开票记录页面

#### Acceptance Criteria

1. 仅本人数据；提供六态筛选（带计数）与关键词搜索。
2. **「已退回」需有显著筛选与计数**（系统无通知能力，运营只能主动查看发现被退回）。
3. 列表列出申请单号、提交时间、品名摘要、总计、状态、最近操作时间与操作人、发票照片入口。
4. 提供只读详情（多行明细、寄送信息、发票照片、状态历史）；已退回行提供「重新填写」入口。

### R12 开票审批页面

#### Acceptance Criteria

1. 一个页面 + 六态筛选 + 按状态显示行内动作；动作弹窗依次为审核并通知、退回重填、上传发票照片、结算入账、取消。
2. 未满 120 小时的「已开出邮寄」单，结算按钮禁用并展示剩余时间。
3. 并发以乐观锁拒绝（版本不一致报错并提示刷新）。

### R13 路由与菜单

#### Acceptance Criteria

1. 运营工作台新增「发票管理」分组，含开票申请（表单）与开票记录两个菜单项；财务工作台新增「发票管理」分组，含开票审批。
2. 分组门槛用工作台准入码，叶子用业务码；表单页与详情等隐藏路由不占菜单。

### R14 资金入账归属

#### Acceptance Criteria

1. 成本归属用户为**申请人**，按申请人当前分成比例从「用户账户 + 公司账户尾差」两条分录扣除。
2. 该成本与既有「全流程金流费率 0.7%」无关；6% 是开票服务费，30 元为人民币侧邮寄费。

## 7. 异常与边界

1. 退回与取消是仅有的两条逆向路径，其余全部单向；终态不可逆。
2. 取消不等于实物消失：通知之后取消只结束系统单据，实物发票需线下作废 / 收回。
3. 「不可修改」的代价：已通知开票之后改动 = 取消 + 新建，需代开票方作废重开、运营重填。
4. 已结算入账后的错误只能人工兜底（资金域冲账 + 管理员调账）。
5. 票面与系统可能不一致（样票单价栏为空白、金额由代开票方填写），成本公式用的是系统内总计，上传环节的人工核对是唯一防线。
6. 时间口径以 UTC 存储、按 UTC+8 展示；5 天等待期以上传时刻起算（票面开立日期不记录）。
7. 汇率缺失或 ≤ 0 时结算入账失败关闭；汇率在展示与提交之间变更时拒绝并要求刷新。
8. 照片上传即定稿：格式与体积不符、上传失败均需明确反馈，且不可补救。
9. 四项比对为软提示，写法差异会漏报。
10. 无通知能力的后果：被退回、被取消只能靠运营主动查看记录页得知。
11. 资金侧成本落在申请人个人账户与公司账户，不属于财务。

## 8. 非验收范围

不做：发票字号 / 字轨号码的记录与 OCR；发票版式打印与导出；税务申报；站内通知；票面零税率 / 免税；与柜次、销售订单等业务单据的结构化关联；行级备注；草稿保存；已取消单的「复制新建」预填（可作为后续优化）。

## 9. 决策留档（2026-10-14）

| 主题 | 结论 |
| --- | --- |
| 逆向路径 | 增加「退回重填」与「取消开票」；通知后不可改，只能「取消 + 新建」 |
| 取消边界 | 财务可在结算入账之前随时取消；运营仅限「开票审核中 / 已退回」；退回原因与取消原因均必填 |
| 成本公式 | `向上取整(总计 ÷ 当前汇率 × 0.06 + 30)`；6% 为开票服务费，与 0.7% 全流程金流费率无关；30 元在人民币侧 |
| 汇率 | 入账时取当前汇率并冻结快照 |
| 资金 | 真实入账、接入 `INVOICE_FEE`、归属用户 = 申请人、人民币 |
| 纠错 | 已结算入账后以「资金域冲账 + 管理员调账」为准 |
| 营业税 | 0.05 固定；非整数四舍五入取整；取整后相加得总计 |
| 明细 | 1–5 行；数量、单价、金额一律整数；金额自动算不可手改；单价必填 |
| 备注 | 发票备注 + 申请单备注两个；行级备注不做；申请单备注不进复制文本 |
| 统编 | 手填，校验 8 位数字 |
| 寄送 | 电话单值单行文本、不复用既有解析规则、不要邮递区号、无长度上限 |
| 照片 | 1 张，jpg/png/webp ≤10MiB，不可补传与替换 |
| 字号 | 不记录；不引入 OCR |
| 去重 | 四项字面一致时软提示；比对池不含已取消与已退回；不做归一化 |
| 编号 | 走编号域新建规则并派发；重新提交保留原单号 |
| 流转 | 提交后跳转开票记录；财务审核后不跳转 |
| 可见范围 | 运营仅本人 |
| 权限 | 财务三动作拆分 |
| 输出 | 不打印、不导出 |
