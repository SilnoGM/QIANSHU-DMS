# 状态切换工具栏计数需求

## 0. 文档状态

- 状态：已确认
- 确认日期：2026-08-31

## 1. 需求简介

`QsStatusSwitchToolbar` 已用于销售订单列表、采购待办列表和组件库，但正式业务页面尚未展示来自服务端的全量状态计数；全部采购页面也尚未接入该组件。本需求为全部采购增加订单状态快捷筛选，并让仓库内所有 `QsStatusSwitchToolbar` 使用场景都展示与当前非状态筛选条件一致的计数。

本需求中的“计数”均指符合当前搜索、日期和其他非工具栏筛选条件的完整结果集数量，不是当前分页已加载的行数。

## 2. 适用范围与术语

### 2.1 正式业务页面

1. 销售订单：
   - 全部销售订单。
   - 待办销售订单。
2. 采购订单：
   - 全部采购订单。
   - 待办采购订单。

### 2.2 组件库

组件库中的 `QsStatusSwitchToolbar` 固定数据示例也属于本需求范围。示例用于展示视觉与交互状态，不请求业务接口，但每一个示例项都必须提供数值计数。

### 2.3 计数基准条件

“计数基准条件”是当前列表除工具栏所代表状态维度之外的全部有效筛选条件，包括但不限于：

- 搜索关键字；
- 订单日期范围；
- 币种、出单人；
- 供应商、采购类型；
- 履约状态、付款状态；
- 页面所属视图（全部或待办）。

当前选中的工具栏状态不属于计数基准条件。各工具栏项目必须基于同一组基准条件独立计数，避免用户切换项目后其他项目的计数随之失真。

## 3. 功能需求

### 3.1 全部采购状态切换

**用户故事：** 作为采购运营人员，我希望在全部采购页面直接按订单状态切换，以便快速查看所有、已确认、已完成或已取消的采购订单。

#### 验收标准

1. 当用户进入全部采购页面时，系统应在现有列表区域展示 `QsStatusSwitchToolbar`。
2. 工具栏应按以下稳定编码和顺序展示：
   - `ALL`：全部订单；
   - `CONFIRMED`：已确认；
   - `COMPLETED`：已完成；
   - `CANCELLED`：已取消。
3. 当 URL 中没有合法状态值时，系统应默认选择 `ALL`。
4. 当用户切换工具栏项目时，系统应重置到第一页并按对应订单状态查询；选择 `ALL` 时不附加订单状态条件。
5. 当用户刷新页面、执行浏览器前进或后退时，系统应从 URL 恢复合法的工具栏选择。
6. 因为工具栏已经承担订单状态筛选职责，全部采购的通用筛选抽屉不应继续展示重复的“订单状态”筛选项；待办采购中由服务端限定为有效待办订单的同一冗余筛选项也应移除。

### 3.2 所有工具栏项目展示计数

**用户故事：** 作为运营人员，我希望在切换状态前看到各分类的订单数量，以便判断任务规模和优先级。

#### 验收标准

1. 当任一正式业务页面成功加载列表时，系统应为该页面工具栏的每一个项目展示服务端返回的数值计数。
2. 当某个分类没有订单时，系统应明确显示 `0`，不得省略计数占位。
3. 当列表存在多页时，计数应覆盖完整查询结果，不得使用当前页行数推算。
4. 当用户修改搜索、日期范围或其他非工具栏筛选条件时，系统应重新获取全部工具栏项目的计数。
5. 当用户只切换工具栏项目时，各项目应继续基于相同计数基准条件展示可比较的计数。
6. 当筛选请求处于刷新状态时，系统应保留上一份成功计数，直至新的同一请求世代成功返回，避免数值闪烁为无意义的空值。
7. 当较早请求晚于较新请求返回时，系统不得使用过期响应覆盖当前列表与计数。
8. 当请求失败时，系统应沿用页面现有错误反馈机制，且不得把旧计数冒充为本次筛选成功结果。

### 3.3 全部订单计数语义

**用户故事：** 作为运营人员，我希望全部订单页面的计数与订单状态互斥关系一致，以便正确理解各状态规模。

#### 验收标准

1. 全部销售订单应展示：
   - `ALL`：符合计数基准条件的全部销售订单；
   - `CONFIRMED`：已确认；
   - `PENDING_RECONCILIATION`：待对账；
   - `CANCELLED`：已取消；
   - `COMPLETED`：已完成。
2. 全部采购订单应展示：
   - `ALL`：符合计数基准条件的全部采购订单；
   - `CONFIRMED`：已确认；
   - `COMPLETED`：已完成；
   - `CANCELLED`：已取消。
3. 当订单状态互斥时，各具体状态计数之和应等于同一基准条件下的 `ALL` 计数。
4. 当前页表格的 `total` 应与当前选中项目的计数一致。

### 3.4 待办订单计数语义

**用户故事：** 作为运营人员，我希望待办工具栏准确显示每类任务数量，同时保留一张订单可属于多类待办的业务语义。

#### 验收标准

1. 待办销售订单应展示：
   - `ALL`：至少命中一个销售待办条件的去重订单数；
   - `PENDING`、`PREPARING`、`LAND_TRANSIT`、`WAREHOUSE_ARRIVED`、`SEA_TRANSIT`：分别命中对应履约状态的订单数；
   - `WAITING_PAYMENT`：付款状态为未收齐范围的订单数。
2. 待办采购订单应展示：
   - `AWAITING_SHIPMENT`：已下单或备货中的有效待办订单数；
   - `AWAITING_WAREHOUSE`：已发货的有效待办订单数；
   - `AWAITING_PAYMENT`：未付款或部分付款的有效待办订单数。
3. 当同一订单同时命中履约待办与付款待办时，系统应在每个命中分类中分别计数。
4. 待办分类计数允许重叠，因此各分类计数之和可以大于去重后的待办订单总数。
5. 当前页表格的 `total` 应与当前选中待办分类的计数一致；销售 `ALL` 待办的 `total` 应使用去重后的联合计数。

### 3.5 只读计数契约

**用户故事：** 作为前端开发人员，我希望列表服务提供可校验的权威计数摘要，以便避免前端遍历全部分页或根据当前页猜测数量。

#### 验收标准

1. 当销售或采购列表查询成功时，服务端应通过类型明确的只读公共契约提供当前视图全部工具栏项目的计数。
2. 计数摘要应包含当前视图声明的每一个稳定编码，且值为大于或等于 `0` 的整数。
3. 服务端应使用与列表相同的权限范围、搜索规范化、日期边界和非状态筛选条件计算计数。
4. 服务端不得为了计数修改订单、状态历史、审计记录或其他业务数据。
5. 前端不得通过下载全部分页数据来生成工具栏计数。
6. 本需求允许新增只读计数响应字段或只读查询端点；具体契约形式在技术设计阶段确定。

### 3.6 组件库状态展示

**用户故事：** 作为组件使用者，我希望组件库完整展示带计数的各种状态，以便确认组件在正常、选中、禁用和窄屏场景下均符合规范。

#### 验收标准

1. 当用户打开组件库的状态切换工具栏页面时，所有示例项目都应显示数值计数。
2. 原“无计数状态”示例应改为带计数的普通状态，不再把缺少计数作为正式展示场景。
3. 禁用状态仍应保留，并同时显示计数。
4. 窄屏容器仍应使用组件现有横向滚动能力，不应因计数增加而压缩或折行项目文字。
5. `QsStatusSwitchToolbar` 的通用 `count?: number` 类型可以保持可选；本需求只要求仓库内实际使用数据完整传入计数，不扩大公共组件 API 变更范围。

## 4. UI 设计规格

```text
DESIGN SPECIFICATION
====================
1. Purpose Statement: 在订单状态切换入口直接呈现各分类规模，并为全部采购补齐与销售订单一致的状态导航；不改变既有列表的信息架构和操作路径。
2. Aesthetic Direction: Industrial/utilitarian（工业化运营工具风格，强调密度、可扫描性和稳定布局）
3. Color Palette: 继续使用项目现有 primary、foreground、muted-foreground、background、border Token；选中态沿用主色绿，不新增页面专用颜色。
4. Typography: 状态标签沿用 Noto Sans SC；计数沿用 Noto Sans Mono、tabular-nums。继续使用 --qs-font-sans 与 --qs-font-mono。
5. Layout Strategy: 保持 QsStatusSwitchToolbar 现有 56px 外层高度、40px 项目高度、单行布局和横向溢出浏览；计数位于标签右侧。全部采购工具栏放在与待办采购、销售订单相同的列表头位置，不改搜索、日期、表格和分页布局。
```

## 5. 非目标

- 不修改销售或采购订单状态集合与状态流转规则。
- 不修改数据库 schema，也不新增 migration。
- 不改变现有分页参数、默认页大小和排序规则。
- 不新增第三方依赖。
- 不重设计 `QsStatusSwitchToolbar` 的尺寸、色彩、动效或公共交互。
- 不实现状态批量操作或新的订单业务动作。

## 6. 验证要求

1. 单元测试应覆盖全部采购状态选择的规范化、URL 查询构造和计数映射。
2. 服务端测试应覆盖销售与采购全部视图、待办视图、零计数、筛选联动、分页独立性和待办重叠计数。
3. 前端页面测试应覆盖销售与采购所有工具栏项目均传入计数，以及全部采购工具栏的渲染和切换。
4. 组件库测试应覆盖所有示例项均包含计数、禁用项带计数和窄屏横向浏览未回归。
5. OpenAPI 生成与契约快照应通过，Web 与 Server 类型检查、测试和构建应通过。
6. 真实页面验收应覆盖：全部销售、待办销售、全部采购、待办采购和组件库状态切换工具栏页面。
