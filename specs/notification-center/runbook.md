## 1. 角色与权限

| 角色 | 能做什么 | 权限码 |
| --- | --- | --- |
| 系统管理员 | 渠道配置、节点导入与更新、绑定、群目标、模板、策略、发送记录 | `assistant-*`、`notification-*` |
| 值班运维 | 查看概览、账号在线状态、发送失败；不能改模板与策略 | `assistant-channel:read`、`assistant-account:read`、`notification-record:read` |
| 财务/运营群管理员 | 维护群成员；不登录系统 | 无系统权限 |

节点导入、停发、解绑属于高权操作，必须使用个人账号并留审计；不要共用账号。

## 2. 上线前检查

1. 公司号已实名，且已稳定在线 3~5 天；新号前 24 小时可能掉线。
2. 公司号微信昵称与头像已设置为「千树小助理」；员工看到的发送者名称取这里。
3. 公司号已加入财务群、运营群；两个群都已保存到通讯录，否则 `fetchContactsList` 同步不到。
4. 财务群、运营群标记为 `internalOnly = true`，成员均为有权查看金额与客户名称的内部员工。
5. 审核人、测试员工已添加公司号为好友；非好友不可发送。
6. 环境变量已配置：`ASSISTANT_GEWE_BASE_URL`、`ASSISTANT_GEWE_TOKEN`、`ASSISTANT_WORKER_ENABLED`。Token 只放环境变量或密钥服务，不写文档、日志、示例。
7. 管理端可以打开「通知中心 > 千树小助理」，账号状态显示 `ONLINE`。

## 3. 日常检查

每天至少一次，或由监控告警触发：

| 检查项 | 正常值 | 异常处理 |
| --- | --- | --- |
| 公司号状态 | `ONLINE` | 见第 4 节 |
| 最后在线时间 | 5 分钟内 | 超过 10 分钟告警 |
| 队列最老 `PENDING` | < 1 分钟 | 超过 10 分钟告警，见第 7 节 |
| 15 分钟失败率 | < 20% | 超过 20% 告警，见第 7 节 |
| 未验证绑定数 | 0 | 通知管理员补验证 |
| 失效绑定数 | 0 | 通知管理员重绑 |
| 群目标 `internalOnly` | true | 立即停用该群并复核成员 |

## 4. 节点管理与掉线恢复

> 账号登录、掉线重连与退出全部在 GeWe 控制台完成。系统只导入 `appId`/`wxid`、调用 `checkOnline` 刷新状态，并提供公司号个人二维码；不要在系统里寻找扫码入口。

### 4.1 首次导入或换号

1. 在 GeWe 控制台打开公司号节点详情，确认状态为「在线」。
2. 复制节点的 `appId` 与 `wxid`。
3. 进入「千树小助理 > 公司号」，点「导入公司号」，填写备注名、`appId`、`wxid`；系统会调用 `checkOnline`，离线节点拒绝导入。
4. 导入成功后状态应为 `ONLINE`，并确认「启用派发」开关为开启；执行「测试发送」做连通性自检。
5. 换号：先在控制台完成新号登录并确认在线，再在系统导入新 `appId`；停用旧账号，避免派发选错号。

### 4.2 掉线

1. 管理端显示 `OFFLINE`，或点「检查状态」返回离线；派发按离线退避，TTL 到期转 `EXPIRED`。
2. 到 GeWe 控制台重连或重新扫码；不要调用系统的登录、重连或退出接口。
3. 控制台确认节点在线后，回到系统点「检查状态」，状态恢复 `ONLINE`。
4. 反复掉线：检查控制台登录地区、代理与多设备互挤；不要同时在手机、iPad、电脑登录同一账号。

### 4.3 待导入（`REQUIRES_LOGIN`）

- 仅历史占位账号或尚未导入 `appId` 的账号会处于 `REQUIRES_LOGIN`；系统不会为它发起扫码。
- 在「公司号」卡片点「更新节点」，填入控制台中的 `appId`/`wxid`；系统校验在线后转为 `ONLINE`。
- 未导入前不参与发送，个人二维码也不可用。

### 4.4 疑似封号

1. 立即在管理端停用渠道（`notification_channel_settings.enabled = false`），停止所有派发。
2. 检查手机端提示：限制登录、限制聊天、封号。
3. 优先按微信官方流程申诉；不要用新的非实名号直接顶替。
4. 需要换号时：准备新实名号 → 养号 3~5 天 → 在控制台登录并确认在线 → 系统导入新 `appId`/`wxid` → 加入内部群 → 重新绑定受影响员工 → 自检 → 恢复渠道。
5. 封号期间通知只走业务主通道；管理端记录事件与影响范围。

## 5. Token 与配置

- `ASSISTANT_GEWE_TOKEN` 只从环境变量或密钥服务读取；不要写入源码、示例、测试、文档或聊天记录。
- 轮换 Token：在 GeWe 控制台生成新 Token → 更新部署环境 → 重启 API（worker 在 API 进程内）→ 用自检消息验证 → 确认旧 Token 失效。
- 不要在日志、错误响应、审计元数据中出现 Token；发现泄露立即轮换并排查日志。
- `ASSISTANT_GEWE_BASE_URL` 必须是 `https://`；生产只允许 `https://api.geweapi.com`。
- 阶段 1 不配置 `ASSISTANT_CALLBACK_SECRET`，也不开放回调地址。

## 6. 群目标管理

1. 在微信里把群保存到通讯录；未保存的群不会出现在 `fetchContactsList`。
2. 管理端点「同步群」；同步会按群详情刷新名称、头像和成员数。新群的 key 默认是 `chatroomId`；通过卡片「更多 → 编辑信息」改为语义 key（如 `finance`、`operations`），并填写用途。
3. 修改 key 后，事件策略里引用旧 key 的 `targetKeys` 必须同步更新。
4. 勾选 `internalOnly` 前，逐个核对群成员：必须是内部员工，且有权查看金额与客户名称。
5. 群成员变化时重新核对；出现外部人员立即取消 `internalOnly` 或停用群目标，并通知管理员。
6. 禁止把含外部方（例如承运商、客户）的群设为敏感通知目标。
7. 群消息可能被降权，部分成员看不到；关键广播仍要配合站内消息或人工确认。

## 7. 管理员绑定 SOP

### 7.1 新员工绑定

1. 管理员当面展示公司号个人二维码（「账号 > 个人二维码」）。
2. 员工扫码添加好友；管理员在手机端同意。
3. 管理端「员工绑定」选择系统用户 → 「从通讯录选择」。
4. 核对昵称、备注、头像，选中对应微信；不要只凭昵称模糊匹配。
5. 创建绑定，记录 `boundByUserId`。
6. 点「发送测试」，弹窗默认填入随机内容，可手动编辑（≤500 字）或点「随机内容」重新生成；确认发送。
7. 发送成功即写入 `verifiedAt` 与 `verifiedByUserId`；随后让员工确认收到，未收到则排查好友关系后重发（同一绑定 30 秒冷却）。
8. 只有已验证绑定才允许接收 1:1 消息，尤其是金额与客户名称。

### 7.2 换号与改绑

- **微信不变、只换员工归属**：在「员工绑定」点「改绑」，选择新员工。改绑会清空原验证状态，必须重新发送测试消息。
- **员工换微信**：新微信先添加公司号为好友，解绑旧绑定（写审计），再按 7.1 重新绑定并验证。
- 不要用「停用」来释放微信：`(account_id, wxid)` 唯一键仍然占用，后续绑定会冲突。
- 改绑要求目标员工启用，且不能已经绑定同一公司号；冲突返回 `ASSISTANT_BINDING_USER_CONFLICT`。

### 7.3 离职

1. 在用户管理停用账号；绑定自动失效。
2. 管理员解绑，必要时从内部群移除。
3. 检查是否有未发送的交付；停用用户的个人交付应落 `SKIPPED`。

### 7.4 好友被删

1. 好友巡检发现非好友，绑定置 `INVALID`。
2. 通知员工重新添加公司号。
3. 管理员重新绑定并验证；未验证前不发送敏感内容。

### 7.5 绑错人

1. 立即解绑，停止向该微信发送。
2. 查询发送记录：如果已经发过金额或客户名称，按第 9 节处理。
3. 重新绑定正确的人并验证。
4. 记录事件、操作者、影响范围。

## 8. 发送与停发

- 全量停发：管理端「千树小助理 > 渠道」关闭 `enabled`；已入队未发送的交付不再派发，按 TTL 过期。
- 单事件停用：事件 × 渠道策略关闭 `enabled`；其他事件不受影响。
- 恢复：先确认账号在线、模板与群目标正常，再开启；先向测试群发自检消息。
- 不要用生产员工做限速或模板测试；测试只发测试群和管理员本人。

## 9. 故障处置

### 9.1 账号离线

1. 查看最后在线时间与最近错误码。
2. 到 GeWe 控制台重连或重新扫码；系统侧只点「检查状态」，不调用登录/重连接口。
3. 离线期间不重试轰炸；交付按 TTL 过期，业务主通道兜底。
4. 记录中断起止时间与影响事件。

### 9.2 Token 无效

1. 管理端概览显示 `CONFIG_INVALID` 或发送全部 403。
2. 检查环境变量是否被覆盖或轮换未生效。
3. 更新 Token、重启 API、自检；不要在前端或日志里粘贴 Token。

### 9.3 队列积压

1. 查看最老 `PENDING` 与 worker 租约状态。
2. 检查账号是否离线、GeWe 是否持续 5xx、数据库是否慢查询。
3. 租约空窗超过 1 分钟：确认 `ASSISTANT_WORKER_ENABLED` 与进程存活。
4. 积压过多时先停发，避免恢复后集中轰炸；按事件优先级恢复。

### 9.4 大面积失败

1. 按失败码分组：离线、超时、403、限流。
2. 离线/超时按第 9.1 处理；403 检查 Token 与账号状态；限流降低发送速率。
3. 不要盲目手动重试全部；先抽一条测试群消息验证链路。

### 9.5 误发或敏感信息外泄

1. 立即停用渠道或对应事件策略。
2. 记录消息内容、接收人、时间、操作者；不要删除记录。
3. 通知直属负责人与安全负责人，按公司流程处理。
4. 若是绑定错误：解绑、重绑、验证；若是群成员越界：停用群目标并复核成员。
5. 评估是否需要撤回（GeWe 有撤回接口，但撤回不保证对方未看到）；不要依赖撤回消除影响。

## 10. 变更与审计

- 模板、策略、渠道配置、绑定、解绑、停发、重试都写审计；不要绕过管理端直接改数据库。
- 变更前记录原因，变更后验证一条测试消息。
- 大促、月末对账等高峰前，提前检查账号在线、队列、群成员。
- 交接班时确认：账号在线、队列为空、失败率正常、无未验证绑定。

## 11. 站内通知支持

- 员工看不到站内消息：确认事件策略的 `IN_APP` 渠道已启用、员工在 `target` 解析结果内、消息未被归档或清理。
- 未读数不更新：确认页面可见、30 秒轮询在运行、浏览器标签没有被节流；点开铃铛或刷新页面会立即拉取。
- 桌面通知不弹：确认是桌面端、浏览器权限已授予、页面处于隐藏/失焦状态、系统未开启勿扰；页面关闭后不会提醒，这是预期行为，没有 Web Push。
- 归档/取消归档：归档未读消息会同时标记已读；取消归档后保持已读，不会让未读数回跳。
- 员工反馈“消息还在但红点没了”：属于已读/归档口径，不是丢失；在「已归档」筛选里可以找到。
- 管理员不能查看他人的站内消息；需要排查时只核对聚合数量与事件策略。
- 保留期清理：每日低峰执行 `pnpm -C server notifications:cleanup`。未归档 180 天、已归档 1 年、交付 90 天；通知只有在没有剩余收件箱条目和交付时才删除。命令输出 `kind=notification_cleanup` 与四类删除计数。
- 桌面通知：仅桌面端显示开关；由 Web Locks 主标签轮询 `inbox/new`，其他标签通过 BroadcastChannel 同步未读数；页面关闭后不推送。
