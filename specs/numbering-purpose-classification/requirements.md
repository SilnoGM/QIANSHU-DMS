# 编号用途分类与新增页面需求

状态：用户已确认本需求基线；`design.md` 为待确认技术设计，尚未进入实施。

## 目标与边界

编号管理区分“业务编码 / 唛头编码”，共用现有编号规则引擎与派发机制。列表增加用途视图和用途列；新增规则先选择用途，再进入独立新增页面。仅迁移新增入口，编辑、复制和详情继续使用抽屉。

现有规则统一归为业务编码。本期不接入采购自动唛头，不扩展双序列、中文输出、业务变量、编号长度或派发接口；不重置、回收或改写任何已派发编号。

## R1：规则用途

**用户故事：**作为编号管理员，我希望区分规则用途，同时继续使用同一套配置和派发能力。

1. 当展示编号规则时，系统应将其用途显示为“业务编码”或“唛头编码”。
2. 当对现有规则实施经批准的迁移时，系统应将全部现有规则归为业务编码，并保留原规则 ID、规则编码、版本、计数状态与派发记录。
3. 当两类规则进行预览、发布、启停和派发时，系统应保持现有引擎、权限和编号行为，不按用途另建引擎或共用同一个计数器。

## R2：用途切换与计数

**用户故事：**作为编号管理员，我希望按用途查看规则，并看到各类规则数量。

1. 当进入编号列表时，系统应在页面头与表格之间展示 `QsStatusSwitchToolbar`，依次为“全部编码 / 业务编码 / 唛头编码”，默认选择全部编码。
2. 当切换用途时，系统应从服务端查询对应规则并返回第一页，保留当前搜索词、规则状态、排序及每页数量。
3. 当搜索词或规则状态变化时，系统应重新统计三项数量；计数应覆盖全部匹配记录，不受当前用途、分页或排序影响。
4. 当响应成功时，系统应满足“全部编码数量 = 业务编码数量 + 唛头编码数量”；列表 `total` 应等于当前用途项的数量。
5. 当请求失败或过期时，系统不得把错误当成零条记录，也不得用旧请求覆盖新视图。

## R3：用途分类列

**用户故事：**作为编号管理员，我希望直接从表格识别每条规则的用途。

1. 当列表展示任一用途视图时，系统应保留“用途分类”列，位于“编号规则”之后、“编号结构”之前。
2. 当展示用途列与执行用途筛选时，系统应使用同一个服务端用途字段，不根据规则名、规则编码或前端状态推断。

## R4：新增前选择用途

**用户故事：**作为编号管理员，我希望在填写规则前明确其用途。

1. 当具有现有新增入口权限的用户点击“新增规则”时，系统应打开基于 `QsGenericModal` 的双卡片用途选择弹窗。
2. 当弹窗打开时，系统应展示“业务编码 / 唛头编码”两张单选卡片，交互和视觉参考现有销售币种与采购产品类型选择弹窗。
3. 当尚未选择用途时，系统应禁用“进入新增规则”；当选定用途并点击该按钮时，系统应携带用途进入独立新增页面。
4. 当用户取消或关闭弹窗时，系统不得创建规则、生成草稿记录或派发编号。
5. 当使用键盘或减少动态效果设置时，系统应提供可见焦点、明确选中状态及相应的低动态交互。

## R5：独立新增页面

**用户故事：**作为编号管理员，我希望在完整页面内配置和预览规则，而不受抽屉宽度限制。

1. 当进入新增页面时，系统应展示并锁定所选用途，迁移现有规则身份、重置周期、说明、片段编辑及服务端预览能力。
2. 当访问新增页且用途缺失或非法时，系统应要求重新选择用途，不得默认为业务编码并允许直接保存。
3. 当规则保存成功时，系统应提示成功并返回编号管理列表，刷新列表与计数；保存仍只创建草稿，不自动发布、启用或派发。
4. 当有未保存输入且用户离开时，系统应提供放弃确认；校验失败或请求失败时应保留输入，避免重复提交。
5. 当使用编辑、复制和详情功能时，系统应保留原有抽屉，不因新增页面迁移而丢失版本控制、冻结约束或关闭保护。

## 交付限制

- 本轮仅整理需求和设计，不修改运行代码、schema、公共 API 或数据库。
- 技术设计列明 schema/API 变化，需单独确认后才能实施。
- 实施可生成新的 migration 文件，但当前未授权应用业务数据库；隔离测试数据库不包含业务数据。
- 后续实施采用 TDD，包含前后端与隔离数据库、浏览器验证；仅本地标准提交，不推送。
