## 2. 需求简介

销售关联采购需要区分从未采购、部分采购和已完成采购后三种业务场景。前两种场景继续同步销售订单中可采购的明细；第三种场景允许尚未进入海运的已完成采购订单追加新的销售产品，并在销售金额原子更新后把新增产品同步到采购表单。

订单进入 `SEA_TRANSIT` 或后续阶段后，原销售订单不得再追加产品，新增客户需求必须创建新的销售订单。本需求不允许采购表单绕过销售明细直接增加客户加购产品。

## 3. 当前事实与约束

1. 销售关联采购明细通过 `sourceSalesOrderLineId` 唯一关联销售明细，采购数量按销售明细逐行累计。
2. 有效采购数量不得超过对应销售明细数量；被取消的采购订单不参与有效采购数量。
3. 销售订单全部销售明细被有效采购覆盖后，系统自动把履约状态从 `PENDING` 推进为 `PREPARING`。
4. `PREPARING`、`LAND_TRANSIT` 和 `WAREHOUSE_ARRIVED` 不得为了加购回退到 `PENDING`。
5. 当前销售订单产品只在创建时写入，尚无面向已确认订单的追加产品公共接口。
6. 当前采购来源选择器已使用 `QsStatusSwitchToolbar`、服务端可信计数和采购权限域图片接口。
7. 当前销售订单金额保留 `SalesOrderAmountRevision`，能够记录金额变更前后快照和变更原因。
8. 当前 `FaMultiStepLoader` 支持顺序异步动作、完成状态和分步错误事件，可承载加购后的连续处理过程。

## 4. 术语与计算口径

### 4.1 海运前

“海运前”是以下销售履约状态集合：

```text
PENDING
PREPARING
LAND_TRANSIT
WAREHOUSE_ARRIVED
```

`SEA_TRANSIT` 和 `SIGNED` 不属于海运前。

### 4.2 有效采购记录

有效采购记录是满足以下全部条件的销售关联采购记录：

```text
purchaseType = SALES_LINKED
salesOrderId = 当前销售订单 ID
orderStatus != CANCELLED
```

### 4.3 已采购数量与剩余数量

每条销售明细独立计算：

```text
purchasedQuantity(line)
  = SUM(有效采购明细.quantity)
    WHERE sourceSalesOrderLineId = line.id

remainingQuantity(line)
  = MAX(line.quantity - purchasedQuantity(line), 0)

remainingQuantity(order)
  = SUM(remainingQuantity(line))
```

相同数据库产品的不同销售明细不得合并；`CUSTOM` 明细同样按销售明细 ID 独立计算。

### 4.4 三个采购视图

三个视图按以下优先级和事实互斥分类：

| 视图 | `orderStatus` | 履约状态 | 有效采购 | 订单剩余数量 |
| --- | --- | --- | --- | ---: |
| 未采购订单-采购 | `CONFIRMED` | `PENDING` | 不存在 | 大于 0 |
| 部分采购订单-采购 | `CONFIRMED` | 海运前 | 存在且已采购数量大于 0 | 大于 0 |
| 已完成采购-加购产品 | `CONFIRMED` | 海运前 | 存在 | 等于 0 |

不满足任一规则的订单不得出现在选择器中。

## 5. UI 设计规格

### 5.1 Purpose Statement

采购操作员需要在一个选择器中快速判断销售订单处于首次采购、继续采购还是客户加购阶段，并在客户加购时完成销售产品追加、金额变更和采购同步。界面必须清楚区分三个场景，同时保持采购创建页现有的表单密度和业务上下文。

### 5.2 Aesthetic Direction

- `Industrial/utilitarian`
- 复用千树运营工作台现有业务组件，不引入新的装饰性视觉语言。

### 5.3 Color Palette

- `#FFFFFF`：主内容背景。
- `#F3F4F6`：只读明细、历史采购和次级区域背景。
- `#D1D5DB`：分隔线和不可编辑边界。
- `#00923F`：主操作、完成状态和可信选择反馈。
- `#6B7280`：辅助说明、已采购只读信息。

### 5.4 Typography

- `Noto Sans SC`：中文标题、正文、表单和状态文案。
- `Noto Sans Mono`：销售订单号、金额、数量和稳定业务编号。

### 5.5 Layout Strategy

1. 销售订单选择弹窗顶部固定 `QsStatusSwitchToolbar`，搜索固定在其下方，分页固定在底部，仅候选列表滚动。
2. “销售订单加购产品”使用独立业务弹窗；桌面端采用左侧订单与金额摘要、右侧新增产品编辑区的不对称双栏布局，移动端按订单摘要、产品编辑、金额变化顺序纵向排列。
3. 原销售产品只作为紧凑只读摘要，不与新增产品输入混排；新增产品区域复用订单产品编辑器的图片、产品提示、售价、数量和小计语义。
4. `FaMultiStepLoader` 使用全屏覆盖层承载保存后的三个异步步骤，禁止处理期间关闭，不使用额外颜色或自定义图标体系。

## 6. 需求与验收标准

### R1 - 三个可信采购视图

**User Story：** 作为采购操作员，我希望按采购事实切换三个互斥视图，以便选择正确的后续动作。

#### Acceptance Criteria

1. 当用户打开销售订单选择弹窗时，系统应通过 `QsStatusSwitchToolbar` 展示“未采购订单-采购”“部分采购订单-采购”“已完成采购-加购产品”三个视图。
2. 当用户切换视图时，系统应保留搜索关键词、重置页码和弹窗内草稿选择，并重新查询目标视图。
3. 当系统查询任一视图时，服务端应按第 4.4 节规则计算候选订单，不应接受客户端自定义状态组合或采购数量条件。
4. 当系统返回工具栏计数时，计数应使用与当前关键词相同的基础条件，并分别执行三个可信视图规则。
5. 当有效采购被取消或新增销售明细改变剩余数量时，系统应以最新数据库事实重新分类订单。
6. 当订单已经进入 `SEA_TRANSIT`、`SIGNED`、待对账、已完成或已取消状态时，系统不应把该订单返回到三个采购视图。

### R2 - 未采购订单同步全部产品

**User Story：** 作为首次处理销售来源的采购操作员，我希望一次同步全部销售产品，以便建立第一张销售关联采购单。

#### Acceptance Criteria

1. 当订单属于“未采购订单-采购”且用户确认选择时，系统应读取该销售订单全部销售明细。
2. 当数据库产品属于当前采购供应商时，系统应把完整销售数量同步为可编辑采购明细。
3. 当销售明细为 `CUSTOM` 时，系统应继续允许同步，并沿用采购定价与本单采购价手工填写且必须相等的规则。
4. 当数据库产品不属于当前采购供应商时，系统应保留既有不兼容统计，不得把该产品写入本次采购明细。
5. 当用户提交采购订单时，服务端应继续逐行校验销售来源和剩余采购数量。

### R3 - 部分采购订单同步剩余产品

**User Story：** 作为处理拆分采购或加购恢复的采购操作员，我希望只编辑剩余未采购产品，同时查看历史采购事实。

#### Acceptance Criteria

1. 当订单属于“部分采购订单-采购”且用户确认选择时，系统应按销售明细返回已采购数量、剩余数量和历史有效采购明细。
2. 当销售明细剩余数量大于 0 时，系统应按剩余数量生成可编辑采购行，并把该剩余数量作为本次最大采购数量。
3. 当销售明细已经存在有效采购时，系统应把每条历史采购明细显示为灰色只读行，并展示采购定价、本单采购价、数量、小计和备注。
4. 当用户悬停“已采购”信息时，系统应说明该销售明细已存在有效采购单及对应已采购数量。
5. 当用户中断“已完成采购-加购产品”流程后重新进入选择器时，只要新增销售明细仍有剩余数量，系统应在“部分采购订单-采购”视图提供恢复入口。

### R4 - 已完成采购订单进入加购流程

**User Story：** 作为采购操作员，我希望在海运前为已经采购完成的销售订单追加客户产品，以便继续使用原销售订单处理临时加购。

#### Acceptance Criteria

1. 当订单属于“已完成采购-加购产品”时，候选行主操作应使用“加购产品”语义，而不是普通“确认选择”。
2. 当采购表单尚未选择供应商时，系统应阻止启动加购，并使用轻提示要求先选择供应商。
3. 当用户确认目标订单且具备所需权限时，系统应关闭选择器并打开独立的“销售订单加购产品”弹窗。
4. 当加购弹窗打开时，系统应展示销售订单号、客户、当前履约状态、币种、原销售产品摘要和金额变化摘要。
5. 当订单状态在弹窗打开后发生变化时，正式保存前服务端应重新校验，不得依赖选择器缓存状态。

### R5 - 只追加销售明细

**User Story：** 作为销售订单负责人，我希望加购保留原销售与采购快照，以便后续审计能够区分历史订单内容和客户新增内容。

#### Acceptance Criteria

1. 当用户编辑加购产品时，系统应只允许创建新的销售明细，不允许修改或删除任何原销售明细。
2. 当客户追加与历史相同的数据库产品时，系统应允许创建新的独立销售明细，不得增加已采购明细的原数量。
3. 当用户新增数据库产品时，系统应保存当前产品编号、名称、属性和标准售价快照，并要求填写本单售价和数量。
4. 当用户新增 `CUSTOM` 产品时，系统应要求填写产品名称、本单售价和数量，并允许填写描述。
5. 当用户选择数据库产品时，加购弹窗应只提供符合当前采购供应商的产品；`CUSTOM` 产品不受产品供应商限制。
6. 当追加后的销售明细总数超过订单既有上限时，系统应拒绝保存并指出产品明细数量超限。
7. 当用户提交加购时，系统应要求填写加购原因；默认值可为“客户加购产品”，用户可以修改。

### R6 - 海运前资格与硬拦截

**User Story：** 作为订单运营负责人，我希望海运成为原销售订单加购的明确截止点，以避免已经装运的订单被事后改变。

#### Acceptance Criteria

1. 当销售订单为 `CONFIRMED` 且履约状态属于海运前集合时，服务端应允许执行追加产品资格校验。
2. 当销售订单履约状态为 `SEA_TRANSIT` 或 `SIGNED` 时，服务端应拒绝追加产品，并提示必须新建销售订单。
3. 当销售订单状态为待对账、已完成或已取消时，服务端应拒绝追加产品。
4. 当销售订单在加购期间从海运前推进到 `SEA_TRANSIT` 时，服务端应以行锁后的最新状态拒绝本次保存，且不得写入部分结果。
5. 当加购成功时，系统应保持原履约状态，不得回退到 `PENDING` 或自动推进到其他状态。

### R7 - 销售金额原子变更

**User Story：** 作为财务和销售人员，我希望加购产品与销售金额保持一致，以便订单总价、尾款和付款状态可信。

#### Acceptance Criteria

1. 当用户提交加购产品时，系统应按新增明细的本单售价和数量计算新增小计。
2. 当加购成功时，新的 `lineSubtotalAmount` 应等于旧销售产品小计加新增产品小计。
3. 当加购成功时，新的 `agreedTotalAmount` 应等于旧约定总价加新增产品小计。
4. 当加购成功时，`depositDueAmount` 应保持不变，`balanceDueAmount` 应增加新增产品小计。
5. 当加购成功时，系统应保留全部有效实际收款，并依据新的约定总价重新计算付款状态和待收金额。
6. 当新增销售明细、金额更新、金额修订记录或审计写入任一步骤失败时，系统应回滚整个销售加购事务。
7. 当金额变更成功时，系统应记录金额变更前后快照、加购原因和操作人。

### R8 - 多步骤加载与采购同步

**User Story：** 作为采购操作员，我希望系统明确反馈加购处理进度，并在完成后自动把新增产品带入采购单。

#### Acceptance Criteria

1. 当用户在加购弹窗二次确认后，系统应关闭加购弹窗并显示不可关闭的 `FaMultiStepLoader`。
2. 当系统保存销售新增明细时，加载器应显示“正在新增销售产品”；完成后应显示新增成功反馈。
3. 当服务端完成销售金额原子更新时，加载器应显示“完成销售订单金额变更”。
4. 当系统重新读取销售来源并生成采购表单明细时，加载器应显示“同步产品到采购单”。
5. 当同步完成时，系统应把新增销售明细作为可编辑采购行，把历史采购明细作为灰色只读行，并关闭加载器。
6. 当流程成功时，采购表单应继续关联原销售订单和当前采购供应商，用户可以填写采购价格、付款约定并正常提交。
7. 当销售加购保存失败时，系统应停止流程、关闭加载器并显示可恢复错误；销售订单不得产生部分变更。
8. 当销售加购已经成功但采购同步失败时，系统应保留销售变更，允许用户从“部分采购订单-采购”重新选择并同步，不得再次创建相同销售明细。

### R9 - 并发、重复提交与状态恢复

**User Story：** 作为系统维护人员，我希望加购操作在网络未知结果和并发处理下不会产生重复产品或错误金额。

#### Acceptance Criteria

1. 当用户提交加购时，客户端应携带当前销售订单版本，服务端应在行锁事务中校验最新版本和状态。
2. 当两个用户并发追加同一销售订单时，最多一个请求应基于同一订单版本成功；其他请求应收到可恢复的状态冲突。
3. 当用户重复点击确认时，客户端应只启动一次加购流程。
4. 当请求结果未知且用户重试相同操作时，系统不得静默创建重复销售明细；应通过可信版本或幂等机制返回既有结果或明确要求刷新确认。
5. 当加购成功后采购尚未提交时，订单应按最新剩余数量进入“部分采购订单-采购”，以支持跨页面恢复。
6. 当后续采购补齐新增销售明细时，订单应退出“部分采购订单-采购”；原履约状态保持不变。

### R10 - 权限、审计与数据边界

**User Story：** 作为系统管理员和审计人员，我希望跨销售与采购域的加购动作受到明确授权并可追溯。

#### Acceptance Criteria

1. 当用户查询三个采购视图和采购域产品图片时，系统应继续要求 `purchase-orders:create` 权限，不应额外要求销售订单读取权限。
2. 当用户执行销售产品加购时，系统应要求 `sales-orders:update` 权限；采购页面只有同时具备采购创建和销售更新权限时才应启用“加购产品”。
3. 当用户缺少销售更新权限时，第三视图订单可以保持可见，但加购操作应禁用并说明所需权限。
4. 当加购成功时，系统应记录销售产品追加事实、操作人、销售订单 ID、新增销售明细 ID、金额增量和加购原因。
5. 当系统记录审计元数据时，不应写入客户电话、地址、凭证内容或其他非必要敏感字段。
6. 当采购表单同步销售产品时，采购域应继续通过自身权限接口读取销售来源，不应绕过现有 HTTP 和 OpenAPI 边界。

## 7. 非目标

- 不修改或删除既有销售明细。
- 不允许在采购表单中直接新增没有 `sourceSalesOrderLineId` 的客户加购产品。
- 不回退销售履约状态，也不重算历史履约状态。
- 不允许 `SEA_TRANSIT`、`SIGNED`、待对账、已完成或已取消订单加购。
- 不修改既有采购单的产品、价格、数量或付款信息。
- 不自动提交采购订单，不提前派发新的采购订单号。
- 不把客户加购需求转化为备货采购。
- 不在本阶段决定数据库 Schema、migration、接口路径或具体类名；这些属于 Phase 2 技术设计。

## 8. 验收场景

| 场景 | 当前履约 | 有效采购 | 剩余数量 | 预期视图或行为 |
| --- | --- | --- | ---: | --- |
| 新销售订单 | `PENDING` | 无 | 3 | 未采购订单-采购，同步全部产品 |
| 首张采购只覆盖部分 | `PENDING` | 有 | 2 | 部分采购订单-采购，历史行置灰 |
| 部分采购后取消一张采购单 | 海运前 | 有 | 1 | 部分采购订单-采购，可恢复补采 |
| 全部采购完成 | `PREPARING` | 有 | 0 | 已完成采购-加购产品 |
| 陆运中全部采购 | `LAND_TRANSIT` | 有 | 0 | 已完成采购-加购产品 |
| 已到仓全部采购 | `WAREHOUSE_ARRIVED` | 有 | 0 | 已完成采购-加购产品 |
| 全部采购后新增销售产品 | 海运前 | 有 | 从 0 变为新增数量 | 自动进入部分采购订单-采购并同步新增产品 |
| 加购保存成功但同步失败 | 海运前 | 有 | 大于 0 | 保留销售变更，可从部分采购视图恢复 |
| 加购期间进入海运 | `SEA_TRANSIT` | 有 | 0 | 保存失败且无部分写入，要求新建销售订单 |
| 已海运订单 | `SEA_TRANSIT` | 有 | 任意 | 不进入三个视图，必须新建销售订单 |
| 已签收或已完成 | `SIGNED` 或后续订单状态 | 有 | 任意 | 不进入三个视图，禁止加购 |
| 同产品再次加购 | 海运前 | 有 | 0 | 创建新的独立销售明细，不改历史明细 |
| `CUSTOM` 加购 | 海运前 | 有 | 0 | 保存销售快照，采购同步后手填且校验采购价格 |
| 并发加购 | 海运前 | 有 | 0 | 一个版本成功，其他请求冲突并要求刷新 |
