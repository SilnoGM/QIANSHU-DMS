## 2. 需求简介

销售订单产品必须由销售域统一维护。采购人员在新增采购订单时只能选择销售订单并同步服务端计算出的待采购产品，不得在采购表单内新增或修改销售产品。

“全部销售订单”页面新增“修改产品”操作。符合资格的销售订单可以新增产品、增加既有产品数量；只有不存在有效采购单的销售明细才可以减少数量或移除。修改完成后，系统原子更新销售产品、销售金额、付款状态、采购覆盖与履约状态，并保留完整审计。

## 3. 已确认业务基线

1. 选择销售订单弹窗只保留“未采购订单-采购”和“部分采购订单-采购”两个可信视图。
2. “已完成采购-加购产品”视图及采购创建页内的销售加购流程全部取消。
3. 用户需要新增待采购产品时，必须先从“全部销售订单”的操作列进入“修改产品”。
4. 销售订单产品修改入口仅面向 `CONFIRMED` 且履约状态未到 `SEA_TRANSIT` 的订单。
5. 增加新产品或增加既有销售明细数量不受有效采购单限制。
6. 减少既有销售明细数量或移除销售明细时，该销售明细必须不存在有效采购单。
7. 若修改后存在待采购数量，订单履约状态应回到 `PENDING`，使其重新进入待采购流程。
8. 若修改后的约定总价小于实际有效收款总额，系统不得保存。

## 4. 术语与可信计算

### 4.1 海运前

```text
PENDING
PREPARING
LAND_TRANSIT
WAREHOUSE_ARRIVED
```

`SEA_TRANSIT`、`SIGNED` 不属于海运前。

### 4.2 有效采购单与有效采购数量

有效采购事实必须同时满足：

```text
purchaseType = SALES_LINKED
salesOrderId = 当前销售订单 ID
orderStatus != CANCELLED
purchaseOrderLine.sourceSalesOrderLineId = 当前销售明细 ID
```

```text
purchasedQuantity(line)
  = SUM(有效采购明细.quantity)

remainingQuantity(line)
  = MAX(line.quantity - purchasedQuantity(line), 0)

remainingQuantity(order)
  = SUM(remainingQuantity(line))
```

被取消采购单中的明细不构成“有效采购单”，但历史事实不得被物理删除或改写。

### 4.3 产品修改金额差额

```text
amountDelta
  = 修改后有效销售明细小计 - 修改前有效销售明细小计

newLineSubtotalAmount
  = oldLineSubtotalAmount + amountDelta

newAgreedTotalAmount
  = oldAgreedTotalAmount + amountDelta
```

系统不接受客户端提交汇总金额，所有金额与采购覆盖均由服务端重新计算。

## 5. UI 设计规格

### 5.1 Purpose Statement

销售人员需要在销售域内安全维护海运前订单的产品变化，采购人员只消费正式销售明细。界面应同时展示订单金额、既有产品、采购锁定原因和本次变化，避免用户误以为已采购产品可以减少。

### 5.2 Aesthetic Direction

- `Industrial/utilitarian`
- 延续千树运营工作台现有高密度业务界面，不新增独立装饰体系。

### 5.3 Color Palette

- `#FFFFFF`：主内容背景。
- `#F3F4F6`：只读行、采购锁定行和次级信息区。
- `#D1D5DB`：边界与分隔线。
- `#00923F`：主操作、可提交状态和可信成功反馈。
- `#B45309`：减少限制、金额风险和需关注提示。

### 5.4 Typography

- `Noto Sans SC`：标题、正文、表单和状态说明。
- 项目现有 mono 数据字体：销售订单号、金额、数量和版本。

### 5.5 Layout Strategy

1. “全部销售订单”操作列显示“查看”；符合资格且具备权限时追加“修改产品”。
2. 新组件 `QsSalesOrderProductsEditorModal` 沿用当前 `90rem` 最大宽度，改为“订单信息面板 → 统一产品行编辑器 → 价格变化面板”的纵向结构。
3. 既有销售明细与新增草稿统一交给 `QsOrderProductLineEditor` 展示和编辑，并使用稳定行 ID 区分；存在有效采购单的行明确展示删除、数量与产品身份锁定原因。
4. 正式提交前展示修改摘要和二次确认；服务端处理期间禁止重复提交。
5. 移动端改为纵向结构，触控目标不小于项目现有 `44px` 规范。

## 6. 需求与验收标准

### R1 - 采购入口收敛为两个视图

**User Story：** 作为采购人员，我希望采购页面只处理已存在的销售产品，以避免采购域越权修改销售数据。

#### Acceptance Criteria

1. 当用户打开“选择销售订单”弹窗时，系统应仅展示“未采购订单-采购”和“部分采购订单-采购”两个 `QsStatusSwitchToolbar` 视图。
2. 当销售订单不存在有效采购单、处于 `CONFIRMED + PENDING` 且剩余数量大于 `0` 时，系统应将其归类为“未采购订单-采购”。
3. 当销售订单存在有效采购数量、处于 `CONFIRMED + 海运前` 且剩余数量大于 `0` 时，系统应将其归类为“部分采购订单-采购”。
4. 当销售订单剩余数量等于 `0` 时，系统不应把它返回给任一采购来源视图。
5. 当采购创建页加载时，系统不应加载、渲染或触发销售产品修改弹窗、销售产品修改 API 或销售加购多步骤加载器。
6. 当用户同步销售来源时，系统应继续只同步服务端返回的剩余销售明细，并以灰色只读行展示已采购事实。

### R2 - 全部销售订单提供唯一修改入口

**User Story：** 作为销售人员，我希望从全部销售订单直接修改产品，以保证销售数据先于采购数据变更。

#### Acceptance Criteria

1. 当用户查看“全部销售订单”页面时，操作列应继续显示“查看”。
2. 当订单为 `CONFIRMED`、履约状态属于海运前且用户具备 `sales-orders:update` 权限时，系统应额外显示“修改产品”。
3. 当订单为 `SEA_TRANSIT`、`SIGNED`、待对账、已完成或已取消时，系统不应显示“修改产品”。
4. 当用户缺少 `sales-orders:update` 权限时，系统不应提供产品修改入口。
5. 当用户点击“修改产品”时，系统应加载服务端最新修改上下文，不应依赖列表行中的金额、版本或采购事实执行保存。

### R3 - 产品修改上下文可信展示

**User Story：** 作为销售人员，我希望在修改前看到每条产品的采购约束和金额，以便作出正确调整。

#### Acceptance Criteria

1. 当产品修改弹窗打开时，系统应展示订单号、客户、履约状态、付款状态、币种、版本和当前金额。
2. 当系统返回既有销售明细时，每一行应包含稳定销售明细 ID、行类型、产品快照、本单售价、当前数量、小计、有效采购数量以及是否允许减少。
3. 当销售明细存在有效采购单时，系统应禁止删除该行，禁止改变其产品身份、来源和类型，并禁止把数量调整为小于有效已采购数量；名称、描述、备注和本单售价等销售快照仍可修改。
4. 当销售明细不存在有效采购单时，系统应允许减少数量，并允许将数量降至 `0` 以表达移除。
5. 当产品修改期间订单版本、状态或采购事实变化时，服务端应在正式保存前重新校验并拒绝过期意图。

### R4 - 新增产品与增加数量

**User Story：** 作为销售人员，我希望增加客户新需求，以便后续采购同步新增的剩余数量。

#### Acceptance Criteria

1. 当用户增加既有销售明细数量时，系统应允许增加，不论该行是否存在有效采购单。
2. 当用户新增目录产品时，系统应允许选择任意有效产品，不应要求先选择采购供应商，并应保存当前产品编号、名称、属性和标准售价快照。
3. 当用户新增 `CUSTOM` 产品时，系统应要求填写名称、本单售价和正整数数量，并允许填写描述。
4. 当用户新增与既有目录产品相同的产品时，系统应允许其作为新的独立销售明细存在，不得隐式合并不同销售明细 ID。
5. 当修改后的有效销售明细数超过订单上限时，系统应拒绝保存。
6. 当用户删除尚未提交的新草稿行时，系统应立即从本地草稿移除，不产生服务端写入。

### R5 - 减少数量与移除产品

**User Story：** 作为销售人员，我希望减少尚未进入有效采购的客户需求，同时保护已经采购的历史事实。

#### Acceptance Criteria

1. 当既有销售明细不存在有效采购单时，系统应允许把数量修改为小于当前数量的正整数。
2. 当既有销售明细不存在有效采购单且用户把数量调整为 `0` 时，系统应在业务上移除该销售明细，使其不再参与订单展示、金额和采购覆盖计算。
3. 当既有销售明细存在任一有效采购单时，系统应拒绝移除；允许把数量减少至有效已采购数量，但不得低于该数量。
4. 当销售明细只关联已取消采购单时，系统应把该明细视为不存在有效采购单，并允许减少或移除；已取消采购历史仍应保留。
5. 当修改会导致订单没有任何有效销售明细时，系统应拒绝保存。
6. 当客户端伪造可减少标记或绕过界面提交时，服务端仍应按最新有效采购事实拒绝非法减少。

### R6 - 销售金额与付款状态原子更新

**User Story：** 作为财务人员，我希望产品变化与订单金额保持一致，以保证应收和付款状态可信。

#### Acceptance Criteria

1. 当产品修改保存时，系统应根据服务端规范化后的销售明细计算 `amountDelta`。
2. 当金额增加时，系统应保持原定金，增加尾款。
3. 当金额减少但新约定总价仍不低于原定金时，系统应保持原定金并减少尾款。
4. 当金额减少使新约定总价低于原定金时，系统应先展示加强版二次确认；用户明确确认后，系统才可把定金下调到新约定总价并把尾款调整为 `0`。
5. 当客户端未携带定金下调确认、但服务端重新计算后确认需要下调定金时，系统应拒绝保存，不得自动下调。
6. 当新约定总价小于全部未作废实际收款总额时，系统应拒绝保存，且不得产生部分变更。
7. 当修改成功时，系统应保留全部未作废实际收款，并依据新约定总价重新计算付款状态和待收金额。
8. 当销售明细、金额、付款状态、金额修订、履约状态或审计写入任一步骤失败时，系统应回滚整个事务。

### R7 - 采购覆盖与履约状态联动

**User Story：** 作为订单运营人员，我希望产品修改后订单重新进入正确采购阶段，以便采购人员看到真实待采购数量。

#### Acceptance Criteria

1. 当产品修改后订单剩余采购数量大于 `0` 时，系统应把履约状态设置为 `PENDING`，并记录履约状态历史。
2. 当原订单不存在有效采购单且修改后仍有销售明细时，系统应保持 `PENDING`，并进入“未采购订单-采购”。
3. 当原订单存在有效采购单且修改后剩余数量大于 `0` 时，系统应进入“部分采购订单-采购”。
4. 当订单原为 `PENDING`、存在有效采购单且通过减少或移除未采购产品使剩余数量变为 `0` 时，系统应推进为 `PREPARING`。
5. 当订单原履约状态为 `PREPARING`、`LAND_TRANSIT` 或 `WAREHOUSE_ARRIVED` 且修改后剩余数量仍为 `0` 时，系统应保持原履约状态。
6. 当修改后重新采购补齐全部销售明细时，系统应继续使用采购提交后的可信覆盖规则推进订单，不应由客户端直接指定履约状态。

### R8 - 并发、权限与审计

**User Story：** 作为系统管理员，我希望产品修改受到销售权限控制并具备可追溯性。

#### Acceptance Criteria

1. 当用户读取或提交产品修改时，系统应要求 `sales-orders:update` 权限，不应再要求 `purchase-orders:create` 权限。
2. 当用户提交产品修改时，客户端应携带打开弹窗时的销售订单版本，服务端应在事务行锁后校验最新版本。
3. 当两个用户基于同一版本并发修改时，最多一个请求应成功，其他请求应收到可恢复的版本冲突。
4. 当用户重复点击确认时，客户端应只提交一次；未知网络结果不得自动重放修改请求。
5. 当修改成功时，系统应记录操作人、销售订单 ID、前后版本、增加行、数量变化、业务移除行、金额差额和原因。
6. 当系统记录审计元数据时，不应写入客户电话、地址、附件内容或其他非必要敏感信息。
7. 当已有“销售产品追加”审计枚举无法准确描述减少和移除时，系统应以增量 migration 扩展审计语义；migration 通过隔离验证后应直接应用当前开发数据库，并验证数据库状态。

### R9 - 修改弹窗交互与反馈

**User Story：** 作为销售人员，我希望在提交前看清变化和限制，以降低误改订单的风险。

#### Acceptance Criteria

1. 当 `QsSalesOrderProductsEditorModal` 打开时，桌面端应使用 `90rem` 最大宽度，并从上到下展示订单信息面板、统一产品编辑器和价格变化面板；移动端保持纵向布局。
2. 当既有行不存在有效采购时，用户可通过删除操作移除；当既有行存在有效采购时，删除操作与产品身份变更应锁定，数量输入最小值应为有效已采购数量。
3. 既有产品和新增产品应统一复用 `QsOrderProductLineEditor` 的产品图片、名称、备注、本单售价、数量和小计交互。
4. 当用户点击提交且存在本地校验错误时，系统应使用轻提示并定位字段，不应展示页面顶部持久错误。
5. 当本地校验通过且不涉及定金下调时，系统应展示普通二次确认，列出增加、减少、移除、金额变化和履约状态影响。
6. 当本地预览判断需要下调定金时，系统应使用一层加强版二次确认，突出原总价、新总价、原定金、新定金和减少金额，并使用“确认调整定金并保存”按钮；不应再连续弹出第三层确认。
7. 当服务端返回版本冲突、采购锁定、缺少定金下调确认或金额低于已收款时，系统应保留用户草稿并展示可恢复错误。
8. 当修改成功时，系统应关闭弹窗、使用成功轻提示并刷新销售订单列表；用户随后需要进入采购页面完成采购。
9. 当产品修改成功时，系统不应自动跳转采购页面、自动创建采购单或自动派发采购订单号。

## 7. 非目标

- 不在新增采购页面直接创建或修改销售产品。
- 不保留“已完成采购-加购产品”第三视图。
- 不修改既有采购单的产品、数量、价格、付款或物流信息。
- 不修改产品档案；既有行的名称、描述、备注和售价变更只写销售订单快照。
- 不回写或重算既有采购订单的产品快照、价格与数量。
- 不自动合并相同目录产品的不同销售明细。
- 不允许 `SEA_TRANSIT` 及后续阶段修改原销售订单产品。
- 不自动创建新销售订单。
- 不应用到生产数据库；当前开发数据库按已确认要求直接应用 migration。

## 8. 核心验收场景

| 场景 | 有效采购事实 | 修改 | 预期结果 |
| --- | --- | --- | --- |
| 未采购订单新增目录产品 | 无 | 新增 1 行 | 保存成功，仍为 `PENDING`，进入未采购视图 |
| 已采购完成订单新增产品 | 有 | 新增 1 行 | 保存成功，回到 `PENDING`，进入部分采购视图 |
| 已采购行增加数量 | 有 | `2 → 3` | 保存成功，新增的 1 件成为待采购数量 |
| 已采购行减少数量 | 有 | `2 → 1` | 服务端拒绝，不写入任何变化 |
| 未采购行减少数量 | 无 | `3 → 2` | 保存成功，金额和剩余数量同步减少 |
| 未采购行移除 | 无 | `2 → 0` | 业务移除成功，历史审计保留 |
| 只关联已取消采购单 | 无有效采购 | 减少或移除 | 允许修改，取消采购历史保留 |
| 减少后总价低于已收款 | 任意 | 金额下降 | 服务端拒绝，事务零写入 |
| 减少后刚好完成采购覆盖 | 有 | 移除剩余未采购行 | 从 `PENDING` 推进为 `PREPARING` |
| 海运中订单 | 任意 | 点击修改 | 页面不提供入口，服务端同样拒绝 |
| 并发修改 | 任意 | 同版本提交两次 | 最多一次成功，另一次版本冲突 |
| 修改后需要采购 | 有 | 新增或增加 | 用户从采购页“部分采购订单-采购”同步剩余产品 |

## 9. Phase 1 确认门

本需求文档已确认，进入 Phase 2 技术设计，重点明确：

3. 金额、付款状态、采购覆盖和履约状态的单事务写入顺序。
4. 新组件与采购页面旧流程的删除范围。
5. 审计枚举与 migration 内容，以及隔离验证后应用当前开发数据库的步骤。
