# 销售订单域需求规格

## 1. 文档状态

- 状态：已确认并进入实施
- 确认日期：2026-08-20
- 目标模块：销售订单域首版
- 目标页面：`/operations/sales-orders`、`/operations/sales-orders/create`

## 2. 目标

销售订单域用于记录一次正式销售约定、客户快照、产品成交明细、约定收款、实际收款、履约凭证及独立状态。首版必须为后续按地区、币种、产品和收款情况分析销售数据建立稳定、可追溯的结构化基础。

## 3. 业务边界

- 一张订单只允许一个币种；首版仅允许 `TWD` 或 `MYR`。
- 首版只保存客户快照，不创建或更新客户主数据。
- 数据库产品仍由产品域管理；订单临时产品只存在于当前订单明细快照中。
- 约定金额与实际收款分开记录。
- 订单状态、履约状态和付款状态分别管理。
- 首版不建设退款模型；已有有效收款的订单不能取消。
- 编号由编号域内部服务派发；页面打开、选择币种和上传临时凭证均不发号。

## 4. 需求与验收标准

### R1 - 币种前置选择

**User Story：** 作为销售人员，我希望在进入新增订单页之前固定订单币种，以免产品价格和订单金额混用币种。

#### Acceptance Criteria

1. 当用户点击“新增销售订单”时，销售订单系统应先显示币种选择弹窗，而不是直接进入表单。
2. 当用户选择 `TWD` 或 `MYR` 并确认时，销售订单系统应把币种作为路由参数带入新增页。
3. 当新增页缺少币种参数或参数不属于 `TWD | MYR` 时，销售订单系统应阻止编辑并返回销售订单列表重新选择。
4. 当用户已进入新增页时，销售订单系统应固定该币种，不允许在表单中修改。

### R2 - 订单基础信息与正式发号

**User Story：** 作为销售人员，我希望系统自动带出日期和出单人，并只在正式保存时分配订单编号。

#### Acceptance Criteria

1. 当新增页加载时，销售订单系统应默认使用当前业务日期，并允许用户选择今天或历史日期。
2. 当用户选择未来日期时，销售订单系统应硬拦截保存。
3. 当新增页加载时，销售订单系统应显示当前登录用户为出单人且不允许选择其他用户。
4. 当用户打开表单、编辑草稿或上传临时文件时，销售订单系统不得调用编号域发号。
5. 当用户首次正式保存有效订单时，销售订单系统应通过 `NumberingGeneratorService` 的 `SALES_ORDER` 规则派发订单编号。
6. 当同一 `Idempotency-Key` 和同一请求内容被重放时，销售订单系统应返回同一订单；不同请求内容复用同一 Key 时应返回幂等冲突。
7. 当发号成功而订单事务随后失败时，销售订单系统允许产生断号；同一 Key 重试仍应复用已派发编号。

### R3 - 客户与三级地区快照

**User Story：** 作为销售人员，我希望保存客户姓名、电话和结构化地址，以便履约及后续地区销售分析。

#### Acceptance Criteria

1. 当用户填写订单时，销售订单系统应要求客户姓名、电话、国家/地区、省/州、城市和详细地址完整存在。
2. 当用户选择地区时，销售订单系统应复用 `QsRegionSelector` 的三级稳定 UUID。
3. 当正式保存订单时，销售订单系统应重新校验三级地区的层级、父子关系和有效状态，不信任客户端提交的名称或编码。
4. 当保存地区时，销售订单系统应同时保存三级地区 UUID、编码快照和名称快照。
5. 当保存详细地址时，销售订单系统应移除全部 Unicode 空白字符，包括半角/全角空格、换行、Tab 和不换行空格。
6. 当规范化后的详细地址以已选完整地区、`省/州 + 城市` 或城市名称开头时，销售订单系统应返回 `ADDRESS_DETAIL_CONTAINS_SELECTED_REGION` 并硬拦截保存。
7. 当生成完整地址时，销售订单系统应按“国家/地区名称 + 省/州名称 + 城市名称 + 详细地址”无分隔符拼接，并保证结果不含空白字符。
8. 当地区以后改名或停用时，销售订单系统应继续使用订单快照回显历史地址。

### R4 - 正式产品与订单临时产品

**User Story：** 作为销售人员，我希望选择现有产品或为本单增加临时产品，并按真实成交价出单。

#### Acceptance Criteria

1. 当订单币种为 `TWD` 时，产品选择器应只返回状态为 `ACTIVE` 且存在 TWD 标准售价的产品，并只展示 TWD 标准价。
2. 当订单币种为 `MYR` 时，产品选择器应只返回状态为 `ACTIVE` 且存在 MYR 标准售价的产品，并只展示 MYR 标准价。
3. 当用户选择数据库产品时，销售订单系统应保存产品 UUID、编号、名称、属性和选定币种标准价快照。
4. 当用户新增临时产品时，销售订单系统应只保存本订单的名称、说明和成交信息，不得向 `products` 写入数据。
5. 当产品在选择后、保存前被停用或失去对应币种标准价时，销售订单系统应硬拦截并要求重新选择。
6. 当用户填写数量时，销售订单系统应只接受正整数。
7. 当用户填写真实售价时，销售订单系统应接受最多两位小数的非负金额，并使用真实售价乘数量计算行金额；新增明细默认 `0.00`，不得自动复制标准价。

### R5 - 约定金额与汇总硬校验

**User Story：** 作为销售人员，我希望同时记录明细汇总、约定总价、定金和尾款，并保证它们严格一致。

#### Acceptance Criteria

1. 当订单明细变化时，销售订单系统应在服务端重新计算 `lineSubtotalAmount`，不信任客户端计算结果。
2. 当 `agreedTotalAmount != lineSubtotalAmount` 时，销售订单系统应硬拦截保存。
3. 当 `agreedTotalAmount != depositDueAmount + balanceDueAmount` 时，销售订单系统应硬拦截保存。
4. 当任一约定金额为负数或币种与订单币种不一致时，销售订单系统应硬拦截保存。
5. 当已确认订单调整定金或尾款约定时，销售订单系统应要求修改原因，并保存修改前后金额快照。

### R6 - 实际收款记录

**User Story：** 作为财务或销售人员，我希望分次记录实际收款，以便区分约定和实际到账。

#### Acceptance Criteria

1. 当用户新增实际收款时，销售订单系统应记录收款类型、金额、收款时间、方式、参考号、备注和操作人。
2. 当有效实际收款总额为零时，付款状态应为 `UNPAID`。
3. 当有效实际收款总额大于零且小于约定总价时，付款状态应为 `PARTIALLY_PAID`。
4. 当有效实际收款总额等于约定总价时，付款状态应为 `PAID`。
5. 当新增收款将导致累计有效收款超过约定总价时，销售订单系统应硬拦截。
6. 当收款记录录入错误时，销售订单系统应通过作废记录保留审计轨迹，不得物理删除。

### R7 - 凭证与临时媒体

**User Story：** 作为销售人员，我希望在订单保存前上传出单凭证、收款凭证与签收单图片；新上传的订单凭证全部仅支持图片。

#### Acceptance Criteria

1. 当用户尚未保存订单时，销售订单系统应允许上传临时媒体资产且不得发放订单编号。
2. 当用户正式保存订单时，销售订单系统应在同一订单事务中激活并关联所选临时资产。
3. 当临时资产过期、类型不允许、状态异常或不属于当前用户时，销售订单系统应硬拦截关联。
4. 当用户放弃表单时，未关联临时资产应继续由媒体域既有过期回收机制处理。
5. 当凭证已关联订单时，销售订单系统应通过受权限保护的内容接口回显图片或文档。
6. 当履约状态切换到 `SIGNED` 时，销售订单系统应要求至少存在一份有效 `DELIVERY_RECEIPT`。

### R8 - 三套状态与流转

**User Story：** 作为运营人员，我希望分别观察订单约定、履约进度和付款进度。

#### Acceptance Criteria

1. 销售订单系统应分别保存 `orderStatus`、`fulfillmentStatus` 和 `paymentStatus`。
2. 当订单从 `DRAFT` 变更为 `CONFIRMED` 或 `CANCELLED` 时，销售订单系统应校验允许的订单状态流转并记录历史。
3. 当履约从 `PENDING` 依次进入 `PREPARING`、`LAND_TRANSIT`、`WAREHOUSE_ARRIVED`、`SEA_TRANSIT`、`SIGNED` 时，销售订单系统应校验顺序并记录历史。
4. 当付款记录变化时，销售订单系统应派生并持久化最新付款状态，不允许客户端直接指定付款状态。
5. 当订单已有有效实际收款时，销售订单系统应拒绝取消订单。
6. 当订单履约状态为 `SIGNED` 时，销售订单系统应拒绝取消订单。
7. 当订单下存在未取消的销售关联采购单时，销售订单系统应拒绝取消订单。
8. 当订单已 `CONFIRMED` 时，客户快照和地址应冻结；金额约定只能通过受控修改接口变更。

### R9 - 查询与地区分析基础

**User Story：** 作为管理人员，我希望查询订单并按地区、币种和日期形成可信销售统计基础。

#### Acceptance Criteria

1. 当用户查询销售订单时，销售订单系统应支持按订单号、客户关键字、币种、订单状态、履约状态、付款状态和出单日期区间筛选。
2. 当返回列表时，销售订单系统应返回订单总价、已收金额、未收金额及三套状态。
3. 当后续分析地区销售时，系统应使用订单保存的三级地区 UUID 分组，不解析完整地址字符串。
4. 当汇总销售金额时，系统应按 `orderDate` 和 `currencyCode` 分组，不得直接合计 `TWD` 与 `MYR`。
5. 当默认统计正式销售时，系统应排除 `CANCELLED` 订单。

### R10 - 权限、安全与审计

**User Story：** 作为管理员，我希望订单敏感操作受权限控制且可以追溯。

#### Acceptance Criteria

1. 当用户读取、创建、更新状态、管理收款或管理凭证时，销售订单系统应分别校验对应权限。
2. 当服务端处理出单人时，销售订单系统应只使用可信 Session 用户，不接受 Body 指定操作人。
3. 当发生创建、状态变化、金额调整、收款新增/作废或凭证关联/解除时，销售订单系统应记录审计事件或不可变领域历史。
4. 当记录日志、错误或审计元数据时，销售订单系统不得写入完整客户地址、电话、媒体内容、幂等键或其他敏感请求体。

## 5. 非功能要求

- 所有金额使用十进制定点数，不使用 JavaScript 浮点数进行最终校验。
- Server 请求方向保持 `Controller -> Service -> PrismaService -> PostgreSQL`。
- Controller、DTO 和 OpenAPI decorators 是公共接口真相源。
- 新功能采用 TDD，并使用隔离 PostgreSQL 验证数据库约束和并发行为。
- Web 必须支持亮色/暗色主题、键盘操作、明确错误文本和窄屏布局。
