# 采购审核派发基础唛头与货件唛头

## 已确认范围（2026-09-08）

- 新采购单提交时保存采购订单号、产品及完整货件配置，进入 `PENDING_REVIEW + ORDERED`；此时不派发唛头、不消耗唛头流水。
- 审核通过时每张采购单只申请一个基础唛头。单货件的货件唛头直接等于基础唛头；多个货件分别保存 `基础唛头/货件-01`、`基础唛头/货件-02`。序号至少两位，100、1000 不截断。
- `PurchaseOrder.shippingMarkText` 保存采购基础唛头，`shippingMarkIssuanceId` 保存唯一的编号派发关联。
- `PurchaseOrderPart.shippingMarkText` 独立保存货件唛头。`partNumber` 仅是本采购单内部序号，不是正式货件编号。后续货件域的主数据、正式编号字段及编号规则派发不在本次范围。
- 唯一性沿用编号引擎的规则内唯一语义，不扩展为跨规则全局唯一。
- 历史 v3 订单级唛头及 v4 逐货件唛头全部保留，不回填、不改号、不重复派发。
- 本次修改代码、契约和新增 migration；不应用业务库、不重启、不推送、不发布。

## 创建与审核边界

1. 新创建使用 `purchase-order.create.v5` 指纹。创建请求结构及规则预检保持不变，预检不预留容量，货件分配仍须完整覆盖采购产品数量。
2. v3、v4 已存在的请求分别按原版指纹严格恢复；未知结果必须保留原 key 和原始快照，不能自动换 key 绕过冲突。
3. 审核以当时有效的供应商字典绑定或 `CUSTOM_MARK`、当前 ACTIVE 规则版本为准。日期段采用实际审核派发时间，不冻结创建时的规则或采购日期。
4. 审核沿用来源销售行、采购单、销售单的锁序与 `expectedVersion` 校验；`PURCHASE_ORDER.REVIEW_SHIPPING_MARK` 使用采购单 UUID 作稳定派发键、已存创建指纹作编号请求指纹。
5. 基础号派发、基础号保存、全部货件派生码、审核状态、状态历史、审计和销售覆盖推进在同一个数据库事务中完成。
6. 规则不可用、容量不足、任一保存或后续状态更新失败时整体回滚，保持待审核。重复审核仍返回 `409 PURCHASE_ORDER_STATE_CHANGED`，前端重查详情后提示真实状态，不虚构重试成功。
7. 未审核取消不派号；已审核取消保留真实派发记录，不回收或重用已派编号。

## 数据约束与迁移

- 新增 `20260908013900_purchase_order_review_shipping_marks`，不修改已应用迁移，也不带入编号索引或销售外键名称等无关 schema 差异。
- 新 v5 采购单及货件创建时唛头均为 null；货件分配在创建事务最终数量校验后封存。
- 基础唛头只允许在已封存采购单从待审核转为已确认时写入一次；数据库核验编号用途、consumer、订单稳定键和创建指纹。
- 货件仅允许同一审核事务将 null 唛头补写成正确派生值；内部序号、产品分配、历史派发关联以及已写唛头保持不可变。
- 订单级延迟约束最终核对全部货件，防止仅保存基础号或遗漏部分货件；不为每条货件全单重扫。
- 货件唛头最长 72 字符，覆盖 64 字符基础号加 `/货件-1000`；基础号字段保留原宽度，避免影响历史人工长唛头。
- 历史货件独立派发关联及键摘要保留为可空字段，新 v5 不再填写。

## 前端与公共契约

- 创建、配置器、确认弹窗统一提示“审核通过后生成并派发”，不在客户端预生成码。
- 采购单基础唛头与货件唛头分开展示。审核前显示待生成状态，不提供空码复制。
- 列表优先展示真实采购基础唛头；单件与基础号相同时不重复展示，多件保留各货件查看与复制，历史 v4 不反推基础号。
- 详情 `parts[].shippingMarkText` 允许 null；`shippingMarks` 始终只返回真实已生成的货件码，待审核为 `[]`。
- 审核请求结构不变；同步响应空值语义、审核可能返回的唛头规则错误以及 Server/Web OpenAPI 快照。
