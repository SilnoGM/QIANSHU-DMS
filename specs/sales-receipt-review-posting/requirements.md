# 销售收款审核与资金入账需求基线

## 状态与范围

- 日期：2026-09-08。
- 状态：已完成需求、设计与实施；2026-09-09 用户另行明确授权执行迁移，本机业务库已应用，详见 [验证记录](verification.md)。
- 本规格覆盖此前“新增实际收款直接生效”的提交行为；既有正式收款及历史凭证仍保留真实含义。
- 入口：销售订单新增实际收款弹窗，以及 `/qs-finance/sales-receipts` 财务工作台。
- 本期不新增财务主管、采购主管角色，不实施采购付款入账、采购审核改造、实际退款或提现业务。

## 已确认业务规则

1. 弹窗提交产生待审核收款申请，财务工作台按申请展示；待审核与驳回金额不计入销售已收金额。
2. 每笔申请保存收款类型、原币金额、实际收款时间、方式、备注、提交人及恰好一份凭证。
3. 申请提交后业务内容冻结；驳回需填写原因，重提创建新申请并保留原记录及关联。
4. 申请审核通过时创建正式收款及凭证关联，并更新订单付款状态。
5. 资金归属销售订单开单人，不是收款提交人或财务审核人。
6. 使用 `ORDER_SETTLEMENT` 规则向用户与公司账户分账，不采用用户全额入账的替代规则。
7. 在审核入账时读取系统货币汇率配置，将 TWD/MYR 转为 CNY；保存实际采用的汇率、规则、比例及金额快照。
8. 审核与入账成功后，用户份额立即成为账户可用余额；本期不新增冻结余额层，也不建设提现/消费入口。
9. 正式收款作废时按原入账分录全额反向记账，保留原流水；不使用当前汇率或当前分账比例重新计算。
10. 冲正允许账户余额为负数；财务纠错使用独立权限，作废原因必填。
11. 审核、正式收款、分账、余额、订单状态及审计必须在同一个数据库事务内提交；作废与冲正亦然。
12. 重复点击、超时重试和并发处理不能重复生成申请、正式收款、入账或冲正。
13. 不另建通用审批引擎；单次最终审核字段留在申请表，操作追溯复用审计表。

## 金额与状态口径

- 已确认收款：正式收款中 `voidedAt IS NULL` 的原币金额之和。
- 待审核收款：`PENDING_REVIEW` 申请的原币金额之和。
- 剩余应收：订单应收总额减已确认收款。
- 可申请金额：订单应收总额减已确认收款、再减待审核收款。
- 不同币种分别汇总，CNY 入账合计另列；金额和汇率不得使用 JavaScript 浮点数计算。
- 审核后的申请保持 `APPROVED`；正式收款作废状态从关联收款读取，不将原审核结论改成驳回。
- 资金出账表示系统记账冲正，不表示向客户实际退款。

## 核心验收

- 提交后财务能看到待审核申请及凭证，销售已收和资金余额均不变化。
- 审核通过后只生成一笔正式收款和一个入账批次，用户/公司分录合计等于换算后的 CNY 金额。
- 任一保存、记账或审计失败时全链路回滚；申请仍待审核且无余额变化。
- 汇率、规则、账户等依赖不可用时明确阻止通过，不写入半笔业务。
- 正式收款作废与原入账全额冲正同步成功，余额不足不阻止负余额结果。
- 后续修改汇率、规则或分成比例不改变历史入账和冲正金额。
- 待审核、驳回及已通过申请的凭证均不会因新增引用域未接入而被清理。
- 无审核或纠错权限的用户不能通过旧接口、直接 URL 或直接 HTTP 请求绕过控制。
