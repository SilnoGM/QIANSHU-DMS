# 采购产品类型前置选择与销售来源过滤需求规格

## 1. 文档状态

- 状态：已确认
- 确认日期：2026-09-04
- 目标模块：采购订单创建入口、采购订单创建页、采购域销售来源选择
- 关联规格：
  - [`../purchase-order-domain/requirements.md`](../purchase-order-domain/requirements.md)
  - [`../purchase-sales-order-selector-integration/requirements.md`](../purchase-sales-order-selector-integration/requirements.md)
  - [`../sales-order-purchase-shortcut/requirements.md`](../sales-order-purchase-shortcut/requirements.md)

## 2. 背景与目标

当前采购创建流程在进入页面后才选择供应商，销售订单候选列表也不按供应商或销售明细类型过滤，用户可能先绑定一张订单，随后才发现没有属于当前供应商的可采购产品。

本需求在所有采购新增入口前增加“采购类型选择”弹窗，先确定本次采购使用产品库产品还是自定义产品，并收集对应供应商资料。进入采购页面后，销售订单选择、产品同步和最终提交均使用同一组初始化条件，从入口处阻止无效组合。

## 3. 术语与独立维度

### 3.1 采购来源类型 `purchaseType`

- `SALES_LINKED`：销售关联采购，必须关联一张销售订单。
- `STOCK`：备货采购，不得关联销售订单，继续要求 `purchase-orders:create-stock` 权限。

### 3.2 产品采购类型 `productMode`

- `CATALOG`：产品库产品采购，只允许产品库正式产品。
- `CUSTOM`：自定义产品采购，只允许 `CUSTOM` 临时产品。
- `MIXED`：只用于无损标识历史混合明细采购单，不允许新建。

`purchaseType` 与 `productMode` 是两个独立维度，不得复用同一个字段或枚举。页面标题可继续使用“采购类型选择”，代码、接口和数据结构必须使用明确的 `productMode` 命名。

## 4. 已确认业务边界

1. 一张新采购单只能包含一种 `productMode`，不得同时保存 `CATALOG` 和 `CUSTOM` 明细。
2. `CUSTOM` 采购的供应商是自由文本快照，不自动创建或修改 `service_provider.supplier` 字典项。
3. `CUSTOM` 销售来源过滤只判断剩余 `CUSTOM` 明细，不使用采购侧填写的供应商名称。
4. 进入创建页后 `productMode` 只读；供应商允许修改，但修改后必须清除绑定订单及全部下游数据。
5. 全部采购页、待办采购页和销售订单“新增采购”操作统一经过前置选择流程。
6. 备货采购保留管理员权限且不展示销售订单关联能力。
7. 采购币种继续固定为 `CNY`，编号仍只在最终确认时幂等派发。
8. 已取消采购单不占用销售明细已采购数量。

## 5. 功能需求与验收标准

### R1 - 所有采购新增入口先选择产品采购类型

**用户故事：** 作为采购人员，我希望在进入采购表单前先明确产品采购类型和供应商，以避免进入表单后才发现没有可采购产品。

#### Acceptance Criteria

1. 当用户点击“新增采购”时，系统应先打开“采购类型选择”弹窗，不得立即进入采购创建页。
2. 当有权限的用户点击“新增备货采购”时，系统应先打开相同弹窗，并保留 `STOCK` 采购来源类型。
3. 当用户从销售订单待采购操作点击“新增采购”时，系统应先打开相同弹窗，并保留目标销售订单作为预选上下文。
4. 当用户取消或关闭弹窗时，系统应停留在当前页面且不得创建草稿、幂等键或采购订单号。
5. 当用户缺少对应创建权限时，系统不得通过弹窗或直接路由绕过权限限制。

### R2 - 双面板产品采购类型选择

**用户故事：** 作为采购人员，我希望清楚地区分产品库产品采购和自定义产品采购，以便后续只处理当前类型的产品。

#### Acceptance Criteria

1. 当弹窗打开时，系统应横向展示“产品库产品采购”和“自定义产品采购”两个互斥面板，并在窄屏下转换为纵向排列。
2. 当用户选择一个面板时，系统应使用明确的边框、背景和单选语义展示选中状态。
3. 当用户切换面板时，系统应清除上一类型填写的供应商资料和校验错误，不得保留不可见的旧值。
4. 当用户尚未选择产品采购类型时，系统不应展示第二步供应商控件，也不得启用“开始采购”。
5. 当新采购订单正式提交时，系统应保证所有明细 `lineType` 与选定 `productMode` 一致。

### R3 - 按产品采购类型收集供应商

**用户故事：** 作为采购人员，我希望产品库采购使用受控供应商，而自定义采购可以记录没有进入字典的实际供方名称。

#### Acceptance Criteria

1. 当用户选择 `CATALOG` 时，系统应在第二步使用 `QsDictionarySelect` 从 `service_provider.supplier` 选择当前有效供应商。
2. 当用户选择 `CUSTOM` 时，系统应在第二步展示“供应商名称”文本输入，不创建或修改字典项。
3. 当用户提交 `CUSTOM` 供应商名称时，系统应执行 Unicode NFKC、首尾空白清理、非空和最多 128 个 Unicode code points 校验。
4. 当供应商资料无效或尚未完成时，系统应禁用“开始采购”并显示就地错误。
5. 当正式提交采购订单时，系统应在服务端重新校验 `CATALOG` 字典供应商仍然有效，并重新校验 `CUSTOM` 供应商名称。

### R4 - 初始化采购创建页

**用户故事：** 作为采购人员，我希望弹窗选择结果自动进入采购表单，避免重复填写。

#### Acceptance Criteria

1. 当用户点击“开始采购”且初始化资料有效时，系统应进入与入口对应的 `SALES_LINKED` 或 `STOCK` 创建页。
2. 当创建页加载时，系统应回填只读 `productMode` 和对应供应商资料。
3. 当用户刷新合法的创建页 URL 时，系统应恢复相同初始化资料，不得静默改变采购类型或供应商。
4. 当创建页缺少、包含多个、超长或非法初始化参数时，系统应拒绝进入可编辑表单并返回安全入口。
5. 当用户切换供应商时，系统应清除已绑定销售订单、来源明细、本次产品明细、已采购只读明细、定金、尾款和由上述数据产生的错误。

### R5 - 按供应商和产品采购类型过滤销售订单

**用户故事：** 作为销售关联采购人员，我希望只看到能够为当前供应商和产品类型产生采购明细的销售订单。

#### Acceptance Criteria

1. 当 `productMode = CATALOG` 时，系统应只返回至少存在一条当前产品供应商等于所选 `supplierValue` 且剩余可采购数量大于零的 `CATALOG` 销售明细的订单。
2. 当 `productMode = CUSTOM` 时，系统应只返回至少存在一条剩余可采购数量大于零的 `CUSTOM` 销售明细的订单。
3. 当过滤 `CUSTOM` 销售订单时，系统不应使用采购侧填写的自由文本供应商名称作为条件。
4. 当销售订单不再是 `CONFIRMED`、履约状态已到海运中或之后、或者没有目标剩余明细时，系统不应返回该订单。
5. 当采购来源视图为“未采购订单”或“部分采购订单”时，系统应继续使用现有有效采购记录和剩余数量规则分类，同时把当前 `productMode` 和供应商条件应用于候选资格。
6. 当弹窗返回计数、分页总数、列表产品摘要和搜索结果时，系统应对它们应用完全相同的过滤条件。
7. 当展示候选订单产品摘要时，系统应只展示符合当前过滤条件且仍有剩余数量的目标明细，避免展示无法同步的产品。

### R6 - 按初始化条件同步销售产品

**用户故事：** 作为采购人员，我希望同步动作只带入当前采购真正能够处理的销售产品。

#### Acceptance Criteria

1. 当 `productMode = CATALOG` 时，系统应只同步当前供应商下仍有剩余采购数量的 `CATALOG` 来源明细。
2. 当 `productMode = CUSTOM` 时，系统应只同步仍有剩余采购数量的 `CUSTOM` 来源明细。
3. 当来源明细已有有效采购记录时，系统应只展示与当前目标来源明细相关的灰色只读行，并继续置于待采购行之后。
4. 当没有任何符合条件的剩余明细时，系统应禁止继续并使用轻提示说明原因。
5. 当同步完成后，系统应继续保留来源销售行 ID、剩余数量上限、`CUSTOM` 双价格相等和 `CATALOG` 当前采购成本规则。

### R7 - 备货采购按产品采购类型限制编辑器

**用户故事：** 作为管理员，我希望备货采购也遵守前置选择的产品采购类型，以免一张采购单混入不同来源产品。

#### Acceptance Criteria

1. 当创建 `STOCK + CATALOG` 采购时，系统应只允许从所选字典供应商的产品库添加 `CATALOG` 产品。
2. 当创建 `STOCK + CUSTOM` 采购时，系统应只允许手工添加 `CUSTOM` 产品。
3. 当创建备货采购时，系统不应展示销售订单选择器、销售来源同步或来源销售行字段。
4. 当非管理员尝试通过路由或 API 创建 `STOCK` 采购时，服务端应继续拒绝请求。

### R8 - 服务端可信校验与并发一致性

**用户故事：** 作为业务负责人，我希望候选列表变化或并发采购不会产生错误关联、跨供应商采购或超量采购。

#### Acceptance Criteria

1. 当创建请求到达服务端时，系统应在事务内重新校验 `purchaseType`、`productMode`、供应商来源和全部明细类型的组合。
2. 当 `CATALOG` 产品当前供应商与采购单供应商不一致时，系统应拒绝请求。
3. 当销售来源行不属于目标销售订单、类型不匹配或已无足够剩余数量时，系统应拒绝请求。
4. 当并发请求竞争同一销售明细剩余数量时，系统应继续使用来源行锁和累计有效采购量保证只有合法事务成功。
5. 当客户端伪造 `MIXED`、同时提交两种供应商字段或绕过入口参数时，系统应拒绝请求。
6. 当请求因依赖状态变化失败时，系统应返回稳定业务错误，不泄露完整请求体、供应商内部配置或数据库信息。

### R9 - 历史采购订单无损兼容

**用户故事：** 作为运营和审计人员，我希望新流程上线后仍能真实查看历史混合采购单和历史字典供应商。

#### Acceptance Criteria

1. 当迁移现有仅包含 `CATALOG` 的采购单时，系统应回填 `productMode = CATALOG`。
2. 当迁移现有仅包含 `CUSTOM` 的采购单时，系统应回填 `productMode = CUSTOM`，并保留原字典供应商事实。
3. 当迁移现有同时包含两种明细的采购单时，系统应回填只读 `productMode = MIXED`，不得拆单、改号或重算金额。
4. 当读取历史 `MIXED` 采购单时，系统应继续支持列表、详情、付款、履约、取消和审计，不允许以 `MIXED` 创建新订单。
5. 当读取历史字典供应商时，系统应继续使用现有 `resolveStoredValue()` 解释有效、停用或未知值。

### R10 - 采购列表、详情与下游供应商展示

**用户故事：** 作为采购和运营人员，我希望产品库供应商和自定义供应商在采购列表、详情及后续履约中都能被正确识别。

#### Acceptance Criteria

1. 当采购单使用字典供应商时，系统应继续展示字典解析后的标签和历史状态。
2. 当采购单使用自由文本供应商时，系统应展示创建时保存的供应商名称，不得将其标记为未知字典值。
3. 当采购列表执行关键字搜索时，系统应支持匹配自由文本供应商名称。
4. 当详情、工厂发货、付款或其他下游能力读取供应商时，系统应使用统一的供应商展示结构，不得假定 `supplierValue` 永远非空。
5. 当本需求首期上线时，系统不要求新增独立供应商主数据、联系人、地址或供应商生命周期能力。

## 6. UI Design Specification

```text
Purpose Statement:
  在用户进入四步采购表单前收敛产品来源和供应商范围，减少先选订单、后发现无法同步的返工。
  弹窗同时服务销售关联采购、备货采购和销售订单快捷新增采购入口。

Aesthetic Direction:
  Industrial/utilitarian，沿用千树运营工作台现有高密度业务界面。

Color Palette:
  #009A44（主操作与选中态）、#FFFFFF（弹窗与面板）、#F6F7F8（次级背景）、
  #E5E7EB（边框与分隔）、#DC2626（校验错误）；运行时使用现有语义 Token。

Typography:
  正文使用 Noto Sans SC；订单号和技术编码使用 Noto Sans Mono。

Layout Strategy:
  弹窗上部使用左右双面板形成第一步选择，下部按选择结果展开第二步供应商控件，
  底部固定取消与“开始采购”；窄屏转换为纵向面板并保持 44px 最小点击目标。

Icons:
  使用现有 Lucide 图标，不使用 Emoji 或新增图标体系。
```

## 7. 非功能要求

- 新功能、公共 API、数据库迁移和复杂联动必须采用 TDD。
- Web 与 Server 继续通过 HTTP/OpenAPI 契约协作，不增加跨依赖域源码引用。
- 销售来源过滤、计数和分页在服务端完成，不得依赖前端加载全部订单后过滤。
- 数据库使用 append-only migration，不修改既有 migration。
- 自由文本供应商名称不得写入 `service_provider.supplier`，不得恢复独立 Supplier 域。
- 最终提交前不得创建幂等键、写采购单或派发 `PURCHASE_ORDER` 编号。
- 所有新路由参数、查询参数和文本字段必须限制单值、长度并进行规范化。

## 8. 明确不做

- 不允许新建混合 `CATALOG + CUSTOM` 采购单。
- 不允许通过自定义采购自动创建供应商字典项。
- 不给销售订单 `CUSTOM` 明细增加供应商字段。
- 不恢复独立供应商 API、Store、页面、权限或数据库表。
- 不改变采购固定 `CNY`、付款约定、履约状态、取消重算和编号幂等规则。
- 不在本需求中增加采购订单编辑或历史订单拆分能力。
