# 销售订单履约状态扩展需求规格

## 1. 文档状态

- 状态：已确认
- 确认日期：2026-08-26
- 依赖规格：[销售订单域需求规格](../sales-order-domain/requirements.md)
- 目标页面：`/operations/sales-orders`

## 2. 目标

把销售订单履约状态从四级粗粒度进度扩展为六级物流进度，使采购、陆运、到仓、海运和签收阶段可以分别查询、展示和审计，同时保持订单状态、履约状态和付款状态相互独立。

## 3. 状态定义

| 顺序 | 状态编码 | 显示文案 |
| ---: | --- | --- |
| 1 | `PENDING` | 待采购 |
| 2 | `PREPARING` | 备货中 |
| 3 | `LAND_TRANSIT` | 陆运中 |
| 4 | `WAREHOUSE_ARRIVED` | 已到仓 |
| 5 | `SEA_TRANSIT` | 海运中 |
| 6 | `SIGNED` | 已签收 |

`PENDING` 继续作为新订单的默认履约状态。旧状态 `SHIPPED` 不再属于有效枚举，其历史语义统一映射为 `LAND_TRANSIT`。

## 4. 需求与验收标准

### R1 - 六级履约状态

**User Story：** 作为订单运营人员，我希望按采购和物流阶段查看订单进度，以便准确判断当前待办事项。

#### Acceptance Criteria

1. 当新订单创建成功时，销售订单系统应把 `fulfillmentStatus` 初始化为 `PENDING`，并显示为“待采购”。
2. 当用户查看、筛选或读取销售订单时，销售订单系统应只使用本规格定义的六个履约状态。
3. 当服务端生成 OpenAPI 契约时，销售订单系统应公开六个有效履约状态，且不得继续公开 `SHIPPED`。
4. 当桌面端或窄屏端展示订单进度时，销售订单系统应显示完整中文状态文字，并仅把颜色作为辅助识别信息。

### R2 - 严格顺序流转

**User Story：** 作为管理员，我希望订单进度按真实物流顺序推进，避免跳级或倒退导致数据失真。

#### Acceptance Criteria

1. 当履约状态从 `PENDING` 变更时，销售订单系统应只允许进入 `PREPARING`。
2. 当履约状态从 `PREPARING` 变更时，销售订单系统应只允许进入 `LAND_TRANSIT`。
3. 当履约状态从 `LAND_TRANSIT` 变更时，销售订单系统应只允许进入 `WAREHOUSE_ARRIVED`。
4. 当履约状态从 `WAREHOUSE_ARRIVED` 变更时，销售订单系统应只允许进入 `SEA_TRANSIT`。
5. 当履约状态从 `SEA_TRANSIT` 变更时，销售订单系统应只允许进入 `SIGNED`。
6. 当用户尝试跳级、倒退、原状态重复提交或从 `SIGNED` 继续流转时，销售订单系统应硬拦截并返回既有的履约状态流转错误。
7. 当履约状态成功变更时，销售订单系统应继续写入状态变更历史和审计事件。

### R3 - 签收凭证约束

**User Story：** 作为管理员，我希望只有具备有效签收单的订单才能确认已签收，以便状态与履约材料一致。

#### Acceptance Criteria

1. 当用户尝试把履约状态从 `SEA_TRANSIT` 变更为 `SIGNED` 时，销售订单系统应要求订单至少存在一份有效签收单。
2. 当订单不存在有效签收单时，销售订单系统应阻止进入 `SIGNED` 并返回既有的签收单缺失错误。
3. 当用户仅通过“货物签收”上传签收单时，销售订单系统不得自动修改履约状态。
4. 当签收单已上传但尚未执行管理员状态流转时，销售订单系统应保持原履约状态不变。

### R4 - 历史状态迁移

**User Story：** 作为系统维护人员，我希望旧订单和历史记录在状态扩展后仍然可读、可筛选和可审计。

#### Acceptance Criteria

1. 当数据库迁移发现订单履约状态为 `SHIPPED` 时，销售订单系统应把该值迁移为 `LAND_TRANSIT`。
2. 当状态变更历史的 `fromStatus` 或 `toStatus` 为 `SHIPPED` 且维度为履约状态时，销售订单系统应把该值迁移为 `LAND_TRANSIT`。
3. 当履约状态审计事件元数据中的 `fromStatus` 或 `toStatus` 为 `SHIPPED` 时，销售订单系统应把该值迁移为 `LAND_TRANSIT`。
4. 当执行上述历史编码迁移时，销售订单系统不得新增状态变更历史、不得增加订单版本、不得修改订单业务更新时间。
5. 当迁移完成时，订单表、履约状态历史和对应审计元数据中不得残留 `SHIPPED`。

### R5 - 查询与变更记录展示

**User Story：** 作为订单查看人员，我希望列表筛选和变更记录使用相同状态口径，避免同一编码出现不同文案。

#### Acceptance Criteria

1. 当用户打开履约状态筛选时，Web 应按业务顺序展示六个状态选项。
2. 当用户选择任一履约状态时，Web 应把对应稳定编码作为 `fulfillmentStatus` 查询参数提交。
3. 当订单列表展示订单进度时，桌面端和窄屏端应使用同一状态文案和语义颜色。
4. 当状态变更记录展示履约状态时，Web 应把六个编码解析为对应中文文案，不得显示原始技术编码。

## 5. 设计规格

- Purpose：在高密度订单表格和状态变更记录中准确表达采购与跨境物流阶段。
- Aesthetic：`Industrial/utilitarian`，延续现有销售订单列表视觉体系。
- Palette：灰色 `#6B7280`、琥珀色 `#D97706`、天蓝色 `#0284C7`、青绿色 `#0F766E`、蓝色 `#2563EB`、绿色 `#16A34A`；实现使用现有主题 Token 和明暗主题类。
- Typography：沿用项目 Noto Sans 与 Noto Sans Mono。
- Layout：不新增页面结构；继续使用订单状态列的双行复合单元格、筛选面板和变更记录弹窗。
- Icons：本次状态标签不新增图标；如后续增加进度可视化，只使用项目现有 Lucide 图标。

## 6. 非功能要求

- Controller、DTO 和 OpenAPI decorators 继续作为公共契约真相源。
- Prisma schema 与追加 migration 必须保持一致，不修改既有 migration。
- 状态校验以服务端状态机为最终真相源，Web 不得成为流转规则真相源。
- 新功能采用 TDD，并使用聚焦测试覆盖枚举、迁移、状态机、API 契约和 Web 映射。
- 状态文字必须在亮色、暗色、桌面和窄屏场景保持可读，不能只依赖颜色传达含义。

## 7. 本期不包含

- 自动采购、物流接口或仓库系统集成。
- 根据签收单上传自动进入 `SIGNED`。
- 跳级、撤回、回退或管理员强制覆盖进度。
- 新增履约审批表、审批人或审批意见字段。
- 修改订单状态、付款状态或收款计算规则。
