# 顺联航账单对账批次需求

## 0. 文档状态

- 状态：已确认
- 确认日期：2026-09-29

## 1. 需求简介

顺联航账单已具备对账状态：明细行二态（未对账 / 已对账，由 `slh_bill_lines.reconciled_at` 决定），账单三态（未对账 / 部分对账 / 对账完成，由明细行汇总派生）。目前缺少承载「一次对账作业」的实体——财务打开账单管理页只能看到状态，点「开始对账」只能得到一句「对账功能暂未开放」。

本需求实现对账批次：**一个批次 = 一张账单的一轮核对**，批次在创建时通过「唛头 → 柜次行」匹配冻结本轮可核对的明细行集合，详情页只承载这些行。同一张账单会分多轮核对，因为一个账单内的明细行需要匹配到顺联航柜次中符合条件的行（该柜次行必须有货件匹配、有销售来源和采购来源），而对账当时并非所有明细行都能匹配到。

## 2. 适用范围与术语

### 2.1 术语

1. **对账批次**：一次对账作业，对应一张账单；同一账单可有多轮批次。
2. **匹配**：读取账单明细行的唛头（配合柜号与装柜日期）在顺联航柜次中定位柜次行，并校验该柜次行的合格条件。
3. **合格三条件**：柜次行有货件匹配（`shipmentId` 非空）、货件所属采购订单有销售来源（`salesOrderId` 非空）、有采购来源（采购订单存在）。
4. **占用**：一张账单同时只能有一个进行中的对账批次。
5. **进行中 / 已完成**：批次自身的作业生命周期；由 `completedAt` 是否为空派生。

### 2.2 匹配作用域

匹配只针对该账单中**未对账**的明细行（`reconciled_at IS NULL`）。已对账的行不再参与匹配、不再进入任何批次。

## 3. 功能需求

### 3.1 对账批次列表

**用户故事：** 作为财务人员，我希望看到所有对账批次及其进度，以便继续未完成的对账作业。

#### 验收标准

1. 当用户进入 `/qs-finance/bill-reconciliation/slh-bill-reconciliation` 时，系统应展示对账批次表格，含批次编号、状态、账单编号、账单名称、账单期间、本批次已核对行数 / 成员行数、创建人、创建时间，以及操作列的「查看详情」。
2. 当用户点击「查看详情」时，系统应进入该批次的对账详情页。
3. 页面应提供「新建对账」入口。
4. 列表默认筛选「进行中」，并可切换到「已完成」与「全部」。
5. 当用户无 `slh-bills:reconcile` 权限时，系统应展示无权限提示，且不请求批次接口。

### 3.2 新建对账（两步弹窗）

**用户故事：** 作为财务人员，我希望先选账单、再看到本轮能核对哪些明细行，以便判断这次对账的工作量。

#### 验收标准

1. 当用户点击「新建对账」时，系统应打开两步弹窗：第一步「选择要核对的账单」，第二步「核对范围预览」。
2. 第一步的候选账单应满足：生效中（未被取代）、至少一行未对账（对账状态为未对账或部分对账）、**没有进行中的对账批次**。
3. 第一步为单选，未选择账单时「下一步」禁用。
4. 当用户进入第二步时，系统应读取该账单未对账明细行的唛头并与顺联航柜次中的行匹配，展示**已匹配合格的行**与**不合格的行及其原因**。
5. 当匹配结果为 0 条时，系统应禁用「开始对账」并说明该账单当前没有可核对的行。
6. 当用户点击「开始对账」时，系统应在服务端事务内重跑匹配、派发批次编号并创建批次与其成员行，随后跳转该批次详情页。
7. 系统不得允许用户在已匹配的行中取消勾选；批次成员即创建时命中的全部行。
8. 当预览时看到的命中集合与创建时重跑的命中集合不一致（并发或数据变化）时，系统应拒绝创建并提示用户重新查看预览，不得静默变更范围。
9. 用户应能在第二步返回第一步重新选择账单。

### 3.3 匹配规则

**用户故事：** 作为财务人员，我希望匹配结果可解释，以便理解某一行为什么不能核对。

#### 验收标准

1. 匹配应按以下顺序定位柜次：
   1. 规范化账单行的柜号文本（柜次名称形如 `MMDD柜` 或 `MMDD-NN柜`）；
   2. 以柜号中的 `MMDD` 与序号（缺省 1）加**该明细行装柜日期的年份**定位 `ContainerBatch`；
   3. 当名称路径定位不到时，从唛头中取 4 位 `MMDD` 作为辅助推断，年份仍取该明细行装柜日期的年份，柜次序号取 1。
2. 当年份按明细行装柜日期取得时，系统不得使用当前年份或账单期间年份替代（同一张账单可能跨年）。
3. 当柜次定位命中多于一条时，系统应判定为不合格，不得自行猜测。
4. 定位到柜次后，系统应使用账单行唛头在该柜次的行中匹配，并要求命中行满足合格三条件。
5. 不合格原因应分层给出，至少覆盖：柜次定位失败（缺柜号且唛头无法推断、柜号格式非法、无对应柜次、柜次命中多条）、柜次内无同唛头行（含账单行缺唛头）、命中柜次行但不满足货件或来源条件。
6. 系统应记录每条命中行的匹配来源（柜号名称命中 / 唛头推断命中）与所依据的柜次行。

### 3.4 对账详情页

**用户故事：** 作为财务人员，我希望在详情页只看到本轮能核对的行并完成核对，以便收工。

#### 验收标准

1. 当用户进入 `/qs-finance/bill-reconciliation/:id` 时，面包屑末级应显示「顺联航账单对账详情」，页面标题应包含批次编号。
2. 页面应展示批次信息与两个数字：**本批次已核对行数 / 成员行数**、**本账单还剩多少行未核对**（未对账明细行总数）。
3. 页面主体只展示该批次的成员行（含行级对账状态、匹配来源）；不属于本批次的行不得出现在该批次的明细表中。
4. 当批次为进行中时，用户应能勾选未核对的成员行并提交「确认核对」。
5. 当批次已完成时，页面应只读，不提供核对入口。
6. 当核对成功后，被核对行的行级状态应变为已对账，账单对账状态随之按既有派生规则变化。

### 3.5 核对与结束

**用户故事：** 作为财务人员，我希望能分批核对并在本轮结束时收工，剩余的行留到下一轮。

#### 验收标准

1. 核对提交时，服务端应校验批次处于进行中、行属于该批次且当前未对账。
2. 核对提交时，服务端应使用成员行冻结的柜次行依据重新校验合格三条件；**任一行不再合格时整批拒绝**，返回行号与原因，且不写入任何一行。
3. 核对成功时应同时写入明细行的对账时刻与成员行的核对时刻、核对人，二者在同一事务内完成。
4. 用户应能对进行中的批次执行「结束本次对账」，即使本轮尚未核对任何行或账单仍有未对账行。
5. 当批次结束后，系统应记录结束时刻与结束人，该批次转为已完成、账单占用解除、不可再追加核对。
6. 当账单仍有未对账行时，用户应能对该账单再次发起新建对账；新批次重新匹配未对账的行。
7. 系统不得因为批次创建、核对或结束而删除或改写账单与明细行之外的既有凭证数据。

### 3.6 批次编号

**用户故事：** 作为财务人员，我希望批次编号符合既有编号域的规则并可用于检索。

#### 验收标准

1. 批次编号必须通过既有编号域机制派发：编号域编码 `SLH_RECON_BATCH_NO`，消费方标识 `SLH_RECON_BATCH.CREATE`。
2. 系统不得自行实现第二套编号生成逻辑；规则不存在或未启用时，创建应失败并给出可操作的错误信息（提示检查编号规则）。
3. 编号应在创建事务内派发并与批次、审计同事务提交或回滚；重试不得跳号。
4. 编号由服务端在提交时生成，前端不得预取或自行拼接。

### 3.7 占用与并发

**用户故事：** 作为财务人员，我希望同一张账单不会被两个对账作业同时处理。

#### 验收标准

1. 当账单已有进行中批次时，系统应拒绝为它创建新批次，并提示该账单正在对账中。
2. 系统应在创建事务内对目标账单行加锁并复检准入条件，避免并发创建绕过占用规则。
3. 创建接口应支持幂等键：同一操作者以同一键重试应返回同一批次，不得重复消耗编号。

### 3.8 审计

**用户故事：** 作为内控与审计人员，我希望对账作业留痕，以便回溯谁在什么时候核对了哪些行。

#### 验收标准

1. 创建批次与结束批次应写入审计事件，事件类型在既有 `audit_event_type` 枚举中追加。
2. 核对动作应按批次记录一条审计（含批次编号、账单编号与本次核对的行号集合）。
3. 审计事件的中文标签应在前端审计页面可用。

## 4. UI 设计规格

```text
DESIGN SPECIFICATION
====================
1. Purpose Statement: 让财务在一处完成「选账单 → 看本轮可核对范围 → 记录核对结论 → 收工」的闭环，不改变账单管理与账单详情页既有信息架构。
2. Aesthetic Direction: Industrial/utilitarian（沿用工作台既有的密集、可扫描运营工具风格）
3. Color Palette: 继续使用项目 primary、foreground、muted-foreground、background、border Token；状态标签沿用对账状态既有语义色（未对账红 / 部分对账黄 / 完成绿），不新增页面专用颜色。
4. Typography: 编号与数字沿用等宽 + tabular-nums；标题层级沿用 qs-type-* 语义类。
5. Layout Strategy: 列表页沿用 FaPageHeader + QsStatusSwitchToolbar + QsGenericTable；新建弹窗沿用 QsGenericModal（xl）+ FaSteps 的步骤式骨架（参照海运柜次变更弹窗），第二步正文为可滚动的行表；详情页沿用 FaPageHeader + FaPageMain 分区块，头部展示批次信息与两个数字，主体为成员行表格。移动端沿用 QsGenericTable 的卡片形态与操作插槽。
```

## 5. 非目标

- 不修改账单导入、解析、收货人回填与账单三态派生规则。
- 不修改 `slh_bills`、`slh_bill_lines` 表结构与两个既有触发器的白名单。
- 不实现撤销对账、移出批次、作废批次。
- 不新增权限码，复用 `slh-bills:reconcile`。
- 不实现明细行与柜次行的金额、材积逐项比对判定（本轮只做匹配与核对留痕；比对 UI 由后续规格定义）。
- 不修改柜次、装柜明细与货件的既有编辑能力。

## 6. 验证要求

1. 匹配纯函数单测覆盖每条不合格原因，以及跨年、唛头尾两位不参与柜次序号、缺唛头、跨仓歧义四类反例。
2. 服务端 e2e 覆盖：创建成功与编号派发、占用冲突、零命中拒绝、预览与创建范围不一致拒绝、核对复检整批拒绝、核对成功后的行级与账单级状态变化、结束批次解除占用后再次创建成功。
3. 契约快照与前端类型生成一致；Web 与 Server 类型检查、lint、单测通过。
4. 前端测试覆盖：路由清单、两步弹窗步骤切换与禁用条件、详情页只展示成员行的数据边界。
5. 三语文案齐全（zh-cn / zh-tw / en）。
