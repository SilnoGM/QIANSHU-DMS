# 销售订单快捷新增采购需求

## 文档状态

- 状态：已确认
- 确认日期：2026-09-01

## 简介

销售订单“待采购”列表当前将 `SUBMIT_PURCHASE` 展示为“提交采购”，点击后仅显示建设中轻提示。本需求将该入口改为“新增采购”，并跳转到销售关联采购创建页，在第一步自动绑定用户点击的销售订单。

本需求只缩短销售订单到采购订单的操作路径，不改变采购创建、产品同步、付款约定、最终提交、编号派发或销售采购覆盖判断等既有业务规则。

## 范围

### 本期包含

- 调整销售订单“待采购”操作文字与点击行为。
- 在采购创建路由中携带销售关联采购类型和来源销售订单 ID。
- 采购创建页只在首次进入时校验并自动绑定有效来源订单。
- 保留用户在第一步重新选择其他销售订单的能力。
- 对缺失、非法、不可见或已不符合来源条件的销售订单进行安全降级。
- 补充前端逻辑测试、页面测试和真实浏览器回归。

### 本期不包含

- 不自动同步销售产品明细；用户仍在第二步主动点击“同步销售产品明细”。
- 不自动提交采购订单，不提前创建幂等键，不提前派发采购订单号。
- 不调整销售订单或采购订单的公共 API、OpenAPI、数据结构、数据库 schema 或 migration。
- 不改变备货采购入口、管理员权限或备货采购特有规则。
- 不改变采购提交后的销售订单采购覆盖与进度联动规则。

## 需求

### 需求 1：待采购操作改为“新增采购”

**用户故事：** 作为销售订单处理人员，我希望从待采购订单直接发起采购，以减少重复查找销售订单的操作。

#### 验收标准

1. 当待办销售订单处于“待采购”操作场景时，系统应将原“提交采购”按钮显示为“新增采购”。
2. 当用户不具备 `purchase-orders:create` 权限时，系统不应向该用户展示“新增采购”操作。
3. 当页面不是销售待办页面，或订单不满足既有“待采购”动作解析规则时，系统不应新增该操作。
4. 系统应保留现有操作图标、按钮层级、间距、悬停态和表格布局，不引入新的视觉层级。

### 需求 2：点击后进入销售关联采购

**用户故事：** 作为采购创建人员，我希望点击“新增采购”后直接进入对应订单的销售关联采购表单，以便马上补充采购信息。

#### 验收标准

1. 当用户点击“新增采购”时，系统应导航到命名路由 `operationsPurchaseOrderCreate`。
2. 系统应通过路由查询参数传递 `type=SALES_LINKED`、被点击销售订单的 `salesOrderId` 和用于现有来源接口定位的 `salesOrderNo`；其中只有查询结果中的 ID 完全匹配才可确认身份。
3. 当导航成功时，采购创建页应继续使用现有四步销售关联采购结构，并保持“全部采购”菜单高亮。
4. 当用户通过备货采购入口进入页面时，系统应忽略任何销售订单快捷绑定参数，并继续执行备货采购规则。

### 需求 3：首次进入时可信地自动绑定销售订单

**用户故事：** 作为采购创建人员，我希望目标销售订单在第一步自动选中，同时仍由系统确认它是当前可用的采购来源。

#### 验收标准

1. 当 `type=SALES_LINKED`，且 `salesOrderId`、`salesOrderNo` 都是单个非空字符串时，系统应使用 `salesOrderNo` 通过现有采购域来源订单接口查询候选订单，不应直接把 URL 参数构造成已选订单。
2. 当查询结果中存在 ID 完全匹配且仍满足来源规则的销售订单时，系统应调用现有 `selectSourceSalesOrder()` 流程完成绑定和剩余可采购明细加载。
3. 当自动绑定完成时，第一步“销售订单关联”区域应显示现有绿色内边框选中态，并展示该订单的订单号、客户和日期。
4. 当自动绑定完成后，用户应仍可点击“选择销售订单”并改选其他订单。
5. 当用户改选或清除后，系统不应因响应式更新、步骤切换或返回第一步而再次自动覆盖用户选择。
6. 当自动绑定成功时，系统不应自动进入第二步，也不应自动同步销售产品明细。

### 需求 4：无效快捷来源安全降级

**用户故事：** 作为采购创建人员，我希望订单状态变化或链接异常时页面仍可继续使用，而不是卡死或绑定错误订单。

#### 验收标准

1. 当 `salesOrderId` 或 `salesOrderNo` 缺失、为空、为数组或不是受支持的单值字符串时，系统应忽略自动绑定并保留手工选择入口。
2. 当来源订单不存在、用户不可见、已不满足 `orderStatus = CONFIRMED` 或未出现在采购域来源查询结果中时，系统不应绑定任何订单。
3. 当自动绑定查询失败时，系统应使用非阻塞轻提示告知用户自动关联失败，并允许用户手工选择销售订单。
4. 当自动绑定或剩余明细加载请求被取消、身份上下文变化或页面卸载时，系统不应写入过期结果。
5. 系统不应因为快捷绑定失败而自动提交、修改销售订单状态或创建任何采购数据。

### 需求 5：保持既有采购规则

**用户故事：** 作为业务负责人，我希望快捷入口只预选销售订单，不绕过采购表单已有校验和业务约束。

#### 验收标准

1. 当销售订单自动绑定成功时，系统应继续要求用户选择供应商并按既有规则同步采购产品。
2. 当用户重新选择销售订单时，系统应继续清空依赖旧来源的产品、付款约定和销售明细映射。
3. 当销售订单包含 `CUSTOM` 产品时，系统应继续执行现有手填采购定价、本单采购价相等和剩余数量限制。
4. 当用户最终提交采购订单时，系统应继续在原提交链路中执行校验、幂等派发、采购覆盖计算和销售订单进度联动。

## DESIGN SPECIFICATION

1. **Purpose**：缩短销售“待采购”到采购创建第一步的业务路径，让用户明确自己正在为哪一张销售订单新增采购。
2. **Aesthetic Direction**：Industrial / utilitarian；完全沿用千树运营工作台现有业务表格、四步表单和选中态，不新增装饰性组件。
3. **Color Palette**：主色 `#009A44`，页面背景 `#FFFFFF`，弱背景 `#F5F7F6`，边框 `#D7DED9`，主要文字 `#111827`；实际实现继续使用现有语义主题变量。
4. **Typography**：中文与界面文字使用 `Noto Sans SC`，订单号等数据使用 `Noto Sans Mono`；不新增字体或局部字号体系。
5. **Layout Strategy**：销售表格仅替换操作文案与交互；采购页保持左侧分步表单、右侧实时详情的既有布局。第一步自动绑定后复用现有销售订单关联卡片和绿色内边框，不新增横幅、弹窗或额外占位区。
6. **Interaction Feedback**：正常自动绑定不额外打扰用户；只有自动绑定失败时使用现有轻提示，页面仍停留在第一步并允许手工选择。

## 验证范围

1. 逻辑测试覆盖动作文案、采购权限、路由参数规范化、单次自动绑定和非法参数降级。
2. 页面测试覆盖销售待采购操作跳转，以及采购第一步自动展示目标销售订单。
3. 浏览器回归覆盖从“待采购”点击“新增采购”到采购创建第一步的真实导航与可重新选择行为。
4. 执行 Web 相关测试、类型检查和 Lint，最后执行根目录 `node --run check`。
